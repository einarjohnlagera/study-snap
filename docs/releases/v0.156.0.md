# Release Notes: v0.156.0 — Say What You Meant to Show

## Release Theme

Makes an existing announcement field finally visible where learners actually see it, and gives
NoteLib its first structured feedback channel — a bounded, single-question campaign distinct from
the always-open Send Feedback modal.

## Key Features

**📣 Actionable notification CTAs**
- The notification inbox has rendered an announcement's `ctaLabel` field nowhere, ever — it was
  authored in Admin, stored, and sent to every client, but never displayed. It now renders as a
  visible call-to-action inside the existing notification card, without turning the card into a
  nested link (a WCAG and HTML-validity trap this release had to specifically avoid).
- Long announcement bodies now clamp to 3 lines instead of stretching the inbox indefinitely, the
  dismiss button meets the 44px touch-target minimum, and the full card is tappable instead of just
  its interior padding.
- Admins get a live character counter with a soft target while writing an announcement body, plus
  helper text clarifying that the "Link label" field is the visible action text learners will tap.

**💬 Campaign Feedback — a bounded research instrument**
- A new `/feedback` page asks every learner one structured question — "What gets in the way when you
  study with NoteLib?" — with nine primary options, four conditional follow-ups, and an always-visible
  optional free-text field.
- This is deliberately **one fixed instrument, not a campaign framework**: there's no campaign table,
  no registry, no admin lifecycle controls to build or maintain. One response per learner is
  guaranteed by a database constraint, and a learner who already responded always sees their own
  submission confirmed — even after the window closes.
- The response window closes automatically on a configured date, overridable without a deploy if the
  timing needs to move.
- The campaign has no entry point of its own by design — it's reached only through a linked
  announcement, keeping it clearly separate from the permanent, always-available Send Feedback
  channel.

## Polish & Fixes

- Caught during pre-commit review: pairing Tailwind's line-clamp utility with a `block` class would
  have silently disabled the clamp in production, since the two utilities conflict in this project's
  compiled stylesheet and `block` wins. Fixed before it ever shipped, and independently re-confirmed
  during the pre-signoff pressure test.
- Added a real-database test proving a duplicate campaign submission is actually rejected by the
  database itself, not just handled correctly by application code against a simulated failure.
- The campaign's close date is configurable via an environment variable rather than requiring a code
  deploy to adjust.
- A pre-signoff falsification pass (one cold-context agent, no inherited assumptions) checked twelve
  specific implementation claims against the real code — precedence ordering, concurrency safety,
  cross-user access scoping, account-deletion cleanup, and more. All twelve held. Three small
  documentation precision fixes came out of it: a corrected description of how one fix was verified,
  and two small robustness improvements to the tracking checkpoint for this release's own results.
- This release originally shipped as two separate versions before both were folded into one; the
  in-app notification improvements and the feedback campaign ship together here.

## Known Limitations

- The feedback campaign has no in-app entry point until an announcement linking to it is published
  in Admin — this is a deliberate, manual, owner-run step (exact copy recorded in `RELEASES.md`), not
  an oversight. The close-date clock starts at deploy regardless of when that announcement goes out.
- This campaign was approved for shipping on a measured 1.8% click-through floor with no impression
  denominator behind it — there's no way yet to distinguish "few people saw it" from "many saw it and
  passed." A dated checkpoint is tracking the actual results in `ROADMAP.md`'s Backlog Index.
