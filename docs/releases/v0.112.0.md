# Release Notes: v0.112.0 — Connection Pool Integrity

## Release Theme
The production connection pool is configured for the first time, and the question that decides whether the structural fix would work at all is settled with measurements rather than argument.

## Key Features

**🔌 The connection pool is configured**
- Before this release there was no HikariCP configuration anywhere: production ran on a framework-default pool of 10 and a 30-second acquisition timeout that nobody chose
- `maximum-pool-size: 20`, verified safe against the live database — `max_connections = 103` with 3 reserved gives a deploy-overlap ceiling of 50, because Render runs two instances during a deploy
- `connection-timeout: 5000` so a waiter fails fast instead of queueing 30 seconds; that queueing is what let the health check blow past Render's probe threshold and get the instance restarted
- `leak-detection-threshold: 60000` logs a full stack trace naming whatever holds a connection past 60 seconds — the instrument that will identify the culprit the next time this happens

**🔬 The Open Session In View question is settled**
- The effective `hibernate.connection.handling_mode` is `DELAYED_ACQUISITION_AND_HOLD`, set unconditionally by Spring rather than inherited from Hibernate
- Measured directly against the pool: with the EntityManager still open, the connection is still held after the transaction commits, and it is the EntityManager close — the end of the HTTP request — that returns it
- This means relocating LLM calls off the transaction would release the transaction while the connection stayed bound, so the structural fix could have shipped, looked correct, and not fixed the exhaustion

**🛡️ Guards that make the configuration a decision rather than a default**
- The three pool settings, the deploy-overlap ceiling and the fast-fail direction are pinned against the production profile, read as text because the test profile shadows it
- A guard asserts the production overlay cannot silently shadow those settings
- The LLM read timeout is pinned behaviourally, after a mutation showed that hardcoding it back still compiled and left the configuration key in place — the property would have become dead config with every test still green

## Polish & Fixes
- The LLM read timeout is now configurable, with its default deliberately unchanged at 180 seconds — made tunable, not shortened, since one HTTP client serves every LLM call including the largest generation
- Background generation is held to two concurrent tasks so it cannot claim a large share of the pool; work is delayed, never dropped
- The production database is read-only for Claude, recorded as a standing rule with a hand-over protocol for statements that need to be run
- Six overstatements in the outage diagnosis corrected against the log: the instance was restarted rather than replaced, with no deploy; the health-check attribution is an inference rather than a mechanism; the log is not severity-filtered; and "nothing recovered on its own" is not established
- The falsification queries gained the read-burst and baseline cases they were missing, and a column error that would have made one of them fail outright was fixed
