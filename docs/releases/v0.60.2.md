# Release Notes: v0.60.2 — Challenge Quiz Known-Limitations Cleanup

## Release Theme

Close three narrow, ungated concurrency and entry-point gaps that v0.60.1 deliberately deferred as Known Limitations, none of which depended on a product decision or data pull.

## Key Features

**🔁 Claim-Release Rollback Fix**
- A failed "+5 Questions" batch could roll back the very cleanup step meant to free the learner's claimed bank rows, leaving them stuck claimed until they naturally expired.
- `releaseClaims` now runs in its own independent transaction, so it commits regardless of the outer generation call's rollback.

**🔒 Expiry-vs-Completion Lock Race Fix**
- An unlocked session lookup could race a concurrent completion: if a learner finished a Challenge Quiz right as an expiry-driven cleanup ran for the same session, the cleanup could win the write and silently overwrite the real `COMPLETED` result back to `FORFEITED`.
- Session resolution now locks the candidate row and re-verifies its status is unchanged before applying any forfeit — for both Challenge Quiz and Board Exam Mode.

**↩️ Resume/Start Fresh at the Collection Entry Point**
- Launching Challenge Quiz from a collection/Review Set's premium-exam CTA found a live session and resumed it silently, without the Resume/Start Fresh choice the note detail page's Challenge Quiz card already offered.
- That navigation now carries the same entry marker, so a live session gets the same choice regardless of entry point. Long Exam and Interview Practice launches are unaffected.

## Polish & Fixes

- Routed to Codex as a deliberate one-off token-conservation choice rather than this project's usual "isolated bug fix, Claude Code direct" lane; audited before commit per the standard Codex-delivery process.

## Known Limitations

- **Item 1's new test verifies declaration, not behavior.** The `releaseClaims` fix is confirmed correct by direct code review (a call to a distinct Spring bean, not a self-invocation, so the new transaction propagation applies as expected), but its accompanying test checks the `@Transactional` annotation is present via reflection rather than proving behaviorally that a release survives an outer rollback — no existing integration test touches `challenge_quiz_question_bank`, and building one correctly was judged higher-risk to rush than the gap it would close. A dedicated `@SpringBootTest` covering this is a reasonable fast-follow if this area sees more concurrency work.
