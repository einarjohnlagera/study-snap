# Release Notes: v0.179.0 — Lighter Listings

## Release Theme
Make the public library cheaper and safer for the small production database to serve, in two stages (a much lighter listing query on the backend, then bounded, privacy-safe caching on the frontend); Stage A deployed on 2026-11-03 and Stage B on 2026-11-06, both stayed up through their first day, and whether Stage B lowers database load is still being measured.

## Key Features

**⚡ A Much Lighter Public Library Listing (Stage A, backend)**
- The two sorts that can be ordered in SQL now pick the page of notes first and read card details only for that page, and each page looks up program names for its own notes instead of aggregating the whole public catalog. The listing returns the same cards in the same order with the same program lists, with no migration and no API change.
- Measured on production after 72 hours (paired against the old statement shape): the unfiltered listing page fell from about 14.5 s to about 0.34 s of database time per call, and a `courseProgram` page from about 3.0 s to about 1.2 s.
- A temporary, allowlisted request header lets the diagnostics recorder count catalog walks by type (sitemap, subject page, exam hub). It is client-asserted and never used for any decision.
- Stage A passed its 72-hour read: no database kill, no server error after a burst, and nine busy minutes (41 to 68 listing requests) all answered normally.

**🔒 Public Pages That Never Show Withdrawn Content for Long (Stage B, frontend)**
- Subject pages, exam hubs and the "More from…" rails on public note pages now render on request over a small in-process cache with a hard 120-second limit; the sitemap uses a one-hour limit. A note that is made private or edited disappears from those pages within two minutes (the sitemap within an hour), and an expired entry is never served, even when the backend is slow or failing.
- A load that fails, times out or comes back incomplete shows the existing "busy" page (the sitemap returns a server error) instead of a partial list. Walks finish only when the catalog says there is no more, and a note repeated across a page boundary is shown once.
- After a failed load the same page is not retried for 15 seconds, so one slow database episode cannot stack new work on top of an abandoned request.

**🧭 Pages That Respond Right Away (Stage B, frontend)**
- Subject pages and exam hubs show a calm loading skeleton in about a tenth of a second while their data loads; it shows that the page is responding and does not shorten the wait. The first real whole-catalog sitemap walk in production took 23.5 seconds for 44 pages and 2,186 notes.
- Links to subject pages no longer prefetch them in the background: a real browser's prefetch was found to start a full catalog walk for pages nobody opened. A static test guards the known links, and new subject links must follow the same rule.
- Canonical addresses, structured data and the sitemap now use the `www` host, which the apex already redirected to.

**🔎 Evidence for the Next Step**
- A bounded, privacy-safe per-minute cache statistics line (hits, misses, shared loads, backoffs, wait buckets, errors; no keys, slugs or paths) and the walk-type counter show what the walkers actually do. Stage B's first day: three 52-page exam-hub walks and three 44-page sitemap walks, all attributed and answered normally.

## Polish & Fixes
- Two cold reviews and mutation tests found and fixed, before deploy: a walk that could cache a partial list, a slow load that could serve data older than its limit, an unbounded failure retry, and a prefetch that started catalog walks for links nobody clicked.
- Verified before deploy: 237 frontend suites and 2,884 tests, and on a Vercel Preview with a stand-in catalog 13 of 13 real-browser scenarios and 25 of 25 privacy, failure and strict-walk checks. The Preview never touched the real API, so these show behavior, not production-scale latency or database capacity.
- **Honest status of the goal:** Stage B has been stable (no database kill, connections steady at 20) but has **not been shown to reduce database load**: hub and sitemap walks are at least as frequent as under Stage A, and the per-instance cache can repeat a 52-page walk on each instance. `courseProgram` listing calls ran about 24% and unfiltered calls about 20% above Stage A's average over the comparison window; the counts are small and the data cannot support a cause. A separate investigation of the repeated hub traversal is recorded; no optimization is selected and the 120-second limit is unchanged.
- Two database memory samples of 265.5 and 266.0 MB (99% of the limit) were seen without any kill; one during a walk, one not. Three server errors (HTTP 503) occurred over about two minutes on 2026-11-07 with no connection to Stage B's walkers; their cause is unknown.
- Known limits, recorded and not hidden: a failed page still renders with HTTP 200 and unknown subject addresses still return the empty page; a made-up subject address costs one backend walk per request; a note unpublished in the middle of a walk can be skipped until the next refresh; caches are per instance, not shared; Vercel's free plan keeps runtime logs for one hour.
- Found by the pre-signoff cold review and left for a follow-up (no change to the deployed frontend was authorized): an exam hub now shows its busy page when the official review sets request fails, where `v0.178.0` showed the notes without them; the back link on a public note page, shown to signed-in readers, can still prefetch a subject listing and start a catalog walk because it is not covered by the prefetch guard test; and caches being per instance means repeated cold loads are possible on a busy hour.
- **Not covered by this release:** creator and profile pages still use a 300-second data cache and can show a withdrawn note's title and previews, an edited bio or a profile switched to private for longer than the two-minute bound. That is a confirmed privacy defect with a decided fix (the same hard-limit cache at 120 seconds) scheduled for a following release. Do not read this release as meaning every public page meets the two-minute bound.
- The Stage B +72-hour read passed on 2026-11-10 (read-only; no kill, no restart, no server error after the 2026-11-07 episode); stabilization closure is now pending the merge of this sign-off and the tag. The 2026-11-07 episode of three HTTP 503 responses was traced to the earlier v0.178.0 ranking-snapshot protection (a deliberate calm 503 when the snapshot is rebuilding), not to Stage B; the exact requests refused were not identified. Stage B's effect on database load is still not established (held and stable, not shown to have fallen; the cache hit rate cannot be read beyond Vercel's one-hour log retention), and the rise in backend requests from Saturday night is unexplained (volumes fell back by 2026-11-09, after an overnight lull of about six and a half hours).
- Checkpoints: Stage A +24 h passed (2026-11-04) and +72 h passed (2026-11-06). Stage B +1 h clean (walk health extended), +24 h passed as written (2026-11-07, with the 503 reading and a 266 MB memory sample reported to Product UX), +72 h passed (2026-11-10: no database kill or restart in about 86 hours, no server error after the 2026-11-07 episode, connections 20 to 21, highest 30-minute memory sample 256.0 MB; report `docs/claude-plans/2026-11-10-v0179-stage-b-72h-read-report.md`). The database upgrade stays ruled out by the owner; the lighter list read for the catalog walkers is not built.
- No pricing, quota, entitlement, prompt or learner-facing copy changed beyond the loading skeleton; no migration; no infrastructure change; no crawler blocking, rate limit or `noindex` rule.
