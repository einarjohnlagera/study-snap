# Release Notes: v0.180.0 — Public Page Reliability and Privacy

## Release Theme
Creator and profile pages stop showing a withdrawn note, an edited bio or a profile switched to private for longer than two minutes and fail closed with a calm message instead of showing old data, and the exam hub keeps its study notes when only its review sets fail to load.

## Key Features

**🔒 Fresher, Safer Creator and Profile Pages**
- Creator and profile pages no longer sit behind a five-minute cache: their data is kept for at most 120 seconds in a separate, bounded part of the website's in-memory cache, shared by concurrent visitors so a busy moment does not multiply backend reads.
- A private, withdrawn or edited item can no longer be served from the cache after those 120 seconds, and a failed refresh never falls back to the old data.
- A missing profile is never cached, so a profile that appears later is found straight away.
- Both pages are rendered on request, and a username of `.` or `..` is treated as not found without asking the backend.

**🙂 A Calm Message When a Profile Can't Load**
- When the profile cannot be loaded, the visitor sees "We couldn't load this profile" with a **Try again** button, in place of a broken page. The message never shows an error text or says the profile is private, deleted or missing.
- The page head for that state carries the title "Profile temporarily unavailable | NoteLib" and is marked `noindex`, so search engines are asked not to keep it.
- This is a browser-side message: the page's HTTP status stays 200, and nothing here claims server-side error status or crawler-visible error handling.

**📚 Exam Hubs Keep Their Notes**
- When only the official review sets fail to load, the hub still shows its study notes and a short, honest section ("Official review sets are temporarily unavailable"), instead of failing the whole page. There is no Retry button.

## Polish & Fixes
- This is a **code sign-off only**: the release is built, verified and approved as a release candidate, and as of the 2026-11-10 sign-off commit it is not deployed. Production behaviour changes only with the separately approved deployment, whose outcome is recorded in the GitHub Release, and nothing here claims the 120-second bound holds in production.
- Verified locally, on a local production build with a real headless browser, on an isolated Vercel Preview (13 of 13 checks on the second run) and by two independent cold reviews; the Preview used controlled fake data, so it shows the serving path, not real production traffic or a production deployment's own settings.
- The failure signals were demonstrated on a Preview of the release code: the error state appeared, every failing page view wrote an error-level log entry, and the cache statistics line showed the failures under a new `profile` group.
- The cache statistics line gains a `profile` group; counts for the existing groups are unchanged.
- A stale comment about subject-link prefetching on the subject page was corrected.
- Known limitations, all recorded: a crafted username containing `/`, `\`, a null byte, `%` or `;` reaches the error state instead of "not found"; the page head and body can briefly disagree on a confirmed missing profile (it can cost a second request); the per-instance cache may send more profile reads to the backend than the old shared cache (unmeasured, with a post-deployment checkpoint); the profile read code writes no log line of its own when a read fails; "Try again" gives no visible sign that a retry ran.
- Product UX returned a conditional go on the deployment plan on 2026-11-10; production deployment was not yet authorized as of the 2026-11-10 sign-off commit. The merge is a normal one: the version bump in `backend/pom.xml` makes the backend restart with unchanged code, and the deployment plan watches that restart as a deploy.
- No backend code, migration, prompt, pricing, quota or entitlement changed; the only `backend/` change is the version number in `pom.xml`.
