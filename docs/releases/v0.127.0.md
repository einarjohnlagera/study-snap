# Release Notes: v0.127.0 — Failure Attribution and Learner Dates

## Release Theme
A date you set for yourself stops disappearing, and a generation that fails stops leaving no explanation behind.

## Key Features

**📅 Your exam date survives being reorganised**
- If you set a target completion date on a study plan and later nested that plan under a bigger Goal, the date was silently thrown away — and nothing else recorded it, so it was gone for good.
- It now moves up to the Goal instead. If the Goal already has a nearer date, that one stays: a completion target is a deadline, so the closest one wins.
- The adoption path already worked this way. The two paths disagreed, and that was the whole bug.

**🔍 A failed generation now records why it failed**
- A regeneration that failed because the monthly limit ran out mid-burst was recorded only as "failed". The reason existed nowhere in the database — it survived by luck, in server logs that had not yet rotated.
- Notes now carry the reason, a code, and the moment it happened.
- Crucially, **retrying does not erase it**. Retrying is exactly what destroyed the evidence last time.
- The same fix covers first-time generation and both bulk paths, because they share the same failure handler.

## Polish & Fixes
- The public library's default "Recommended" ordering does less work per request: the view count it ranks on now reads straight from an index instead of scanning matching rows. Sized against the real table first, and confirmed the database would actually use it.
- A comment claiming that table had no such index was corrected.
- Failure reasons never include raw internal error text — an unexpected failure records a safe, generic reason.
