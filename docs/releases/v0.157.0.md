# Release Notes: v0.157.0 — Watching More Closely

## Release Theme

NoteLib can now see what its background work is doing to the database and whether its retention emails
actually bring learners back, instead of only knowing they were sent.

## Key Features

**🔭 Pool diagnostics now see background work**
- When the database connection pool saturates, the diagnostic log used to say "requests in flight = []", which
  could mean nothing was holding a connection or that the holder was invisible. Executor tasks and every
  scheduled job (all route through six guarded scheduling methods) are now registered by name (`ClassName.methodName`), so the next incident's log is readable.
- A second scheduler thread means one slow database-bound job can no longer delay the saturation detector that
  is supposed to report on it. Two such jobs firing at the same instant still can.
- The design deviated from the plan on purpose: Spring hands a scheduler's task decorator an internal wrapper
  rather than the job, which would have silently discarded every job's name, so the scheduler is subclassed.

**📬 Retention email click and open tracking**
- Every retention email's call-to-action now carries an unguessable per-send marker, so a click can be tied to
  that send's record. Opens are counted in aggregate only, across all mail on the account.
- The marker grants no access. Someone holding another learner's marker could flag that one send as clicked, an
  analytics-only effect; a mismatched, unknown or malformed one is logged and skipped, and a database outage
  makes Resend retry rather than losing the event.
- This is the evidence needed before deciding whether these emails should stay email at all.

**⚖️ One daily email budget that actually governs**
- The 100/day budget used to be checked by only one of five retention email types, and counted every email
  the system sent, including password resets. It now counts the five retention types and every one of them
  consults it.
- Send order is now deliberate priority: the due-concepts digest, then weak-concept reminders, then
  inactivity nudges. Found by reading production before signoff: inactivity was already pinned at 60/day, so
  without this the digest would have dropped to roughly zero.

**📈 Traffic analytics**
- Vercel Web Analytics is on the root layout, on the free plan.

## Polish & Fixes

- A click webhook with a non-ISO timestamp is now skipped instead of returning a 500 that Resend would retry.
- A failure in the digest no longer cancels that day's inactivity and weak-concept emails.
- All four database-touching executors are now test-guarded as decorated, and the LLM executor as not.
- A second click keeps the first recorded click time.
- The orphaned public `sendInactiveUserEmails()` entry point no longer bypasses the budget.
- The admin re-engagement campaign no longer eats the automated retention budget; note it is also no longer
  counted against Resend's 100/day.
- Stage 2 evidence bound recorded: only inactivity and the digest have a measurable audience today.
- Known limitations: weekly summary and the monthly creator digest cannot currently send while inactivity
  saturates the budget (immaterial with 1 and 0 opted-in learners); tracking is unverified until deploy and
  needs Resend click/open tracking and webhook events enabled.
