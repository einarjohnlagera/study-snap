# Release Notes: v0.152.0 — The Missing Half of v0.150.0

## Release Theme

Gives the many-to-many Program Family architecture (`v0.150.0`) the curator UX it needed to actually
get finished — family-first Admin management, one canonical catalog-create modal, and an additive
backfill of the approved initial membership matrix.

## Key Features

**🗂️ Family-first Admin catalog management**
- `/admin/course-programs` now opens on a URL-reflected **Program Families** tab by default — a table
  of every family (including empty ones, never filtered by `is_active`) with member counts and one
  modal covering both rename and a full family-side membership replacement.
- The **Course / Programs** tab keeps the inverse, per-program workflow for curators who think in terms
  of "which families does this one program belong to" instead.
- Both tabs read the same unfiltered catalog, so a program a curator later deactivates stays reachable
  from either management surface.

**🔍 One shared catalog picker, one program-creation flow**
- New `CatalogMultiSelect` — a searchable, real-checkbox multi-select — replaces both remaining raw
  `<select multiple>` instances in the codebase, in both a compact "count" density and a chip density.
- New `CourseProgramCreateModal` collapses two previously-divergent create forms (Admin's single-family
  form and note-authoring's already-multi-family one) into one shared component: one validation path,
  one near-match/duplicate-conflict experience, one place that keeps Exam Goal behavior correct.

**🌱 Additive initial membership backfill**
- `POST /course-program-catalog/families` can now create a family with initial members in one call, and
  a new `PATCH /course-program-catalog/families/{id}` renames a family and/or replaces its membership
  set — atomically, ADMIN-only, and distinguishing an *omitted* membership set (leave it alone) from an
  *explicit empty* one (clear it).
- `V147__program_family_initial_membership.sql` additively lands the approved 50-pair
  family↔program matrix by exact name, `ON CONFLICT DO NOTHING`, no hard failure on a missing catalog
  row — safe against a fresh database and against however far ordinary curator work has already gotten.

## Polish & Fixes

- Family duplicate-name matching now collapses internal whitespace the same way the program-side check
  already did, and a rename correctly excludes its own row from the conflict check.
- Corrected two `docs/features/notes.md` claims that had described the pre-`v0.150.0` single-FK family
  mechanism and single-family catalog creation — both stale since the many-to-many migration, caught by
  this release's own feature-doc sweep rather than a diff that happened to touch that file.
- `docs/features/program-families.md` and `docs/features/admin-dashboard.md` rewritten to describe the
  family-first flow, the omitted-vs-explicit-empty membership distinction, and the two-tab Admin IA.

## Known Limitations

- **The post-deploy production-acceptance anti-join has not run yet.** This release's migration,
  `V147`, has not merged to `main` as of signoff, so it has not executed against production. The
  anti-join (checking the full 50-pair matrix against `course_program_family` with 0 missing pairs
  expected) is the follow-up once it deploys — tracked in `ROADMAP.md`'s Backlog Index, not a signoff
  blocker, since the migration is additive and idempotent regardless of exactly how many rows are
  missing when it finally runs.
- **A pre-signoff cold-agent falsification pass found one adjacent defect, fixed the same day it was
  found:** the Admin rename modal always re-sent a family's full membership set even on a name-only
  edit, which could silently overwrite a concurrent admin's membership change on the same family
  (never crossed family boundaries, never touched note applicability, never corrupted data). Fixed
  before this ever reached production.
- **The membership-edit case (not the rename-only case) still computes its full replacement set from an
  in-modal snapshot.** A concurrent edit to the same family during that window is still last-write-wins.
  Inherent to full-set replace; a real fix would be optimistic concurrency, a different feature.
- **`course_programs.is_active` still has no write path anywhere in the codebase.** Unchanged here,
  deliberately — this release's Admin editors already use the unfiltered catalog so an eventual inactive
  row stays manageable, but nothing can set the flag false today. Tracked as its own Backlog Index row.
