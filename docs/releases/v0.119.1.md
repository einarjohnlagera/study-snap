# Release Notes: v0.119.1 — Public Catalog Bounds

## Release Theme
The public library stops doing work proportional to the entire catalog on every read, and a server that is merely busy stops being mistaken for one that has died.

## Key Features

**⚡ Public pages stop loading the whole library to show a few notes**
- Browsing, searching and sorting public notes now ask the database for exactly the page being shown, instead of loading every public note and narrowing it afterwards.
- The homepage's note count, the related notes on each public note page, and the Explore discovery sections were each loading the entire catalog. All of them now cost what they look like they should cost.
- This is the third time this shape of problem has surfaced as the library has grown. The code path that made it possible has been removed rather than worked around.

**🧭 Explore's ordering is unchanged**
- Featured, Popular and Recent are ranked by the same rules as before — the same freshness decay, the same weighting of copies, likes and views, the same tie-breaking. The ranking moved to the database; what you see did not move with it.

**🩺 A busy server is no longer treated as a dead one**
- The health check no longer depends on the same database connections the application is using to serve readers, so a burst of traffic can no longer make a perfectly healthy instance look unresponsive and get it restarted mid-request.

## Polish & Fixes
- Related notes on a public note page are now ordered most-recent-first rather than by recommendation rank. This was a deliberate trade to make the page cheap; the ranked order needs work that is not built yet.
- An unpaginated request for public notes now returns at most 50 rather than everything. Every caller in the product already asked for fewer than that.
- Public note pages reached by their subject-and-title URL now resolve with a single lookup instead of scanning the catalogue, including for notes with no title or no subject, which resolve exactly as they did before.
- Corrected two comments in the codebase that claimed this class of problem had already been addressed — one describing pagination as having bounded the work, and one presenting a larger connection pool as the fix. Neither was true, and both would have misled the next person to look.
