# Release Notes: v0.47.1 — V82 Migration Collision Hotfix

## Release Theme

Unblock production deploys, which have failed since `v0.46.0` merged, by resolving a duplicate Flyway migration version.

## Key Features

**🔧 Migration Collision Fix**
- Two backend migrations both claimed version 82: `V82__email_budget_and_suppression.sql` (already applied everywhere, including prod) and `V82__user_due_concepts_digest_reminder_preference.sql` (introduced with the due-concepts-digest feature). Flyway refuses to start when it finds two migrations at the same version, so every deploy attempt since `v0.46.0` merged has failed at startup.
- Root cause: a rebase artifact — `releases/v0.46.0` was cut from `main` before `v0.45.2` existed and later rebased onto latest `main`, but the digest migration kept its version number from the older base instead of picking up the number the newer `main` had already taken.
- Fixed by renumbering the never-applied digest migration to `V92`, the next free version after the existing highest (`V91`). Verified directly against the local dev DB's `flyway_schema_history` — the ground truth of what's actually been applied — that `V82__email_budget_and_suppression.sql` is the one already recorded there and the digest migration has never run anywhere, so the rename carries zero schema risk in either direction. Confirmed clean with a full backend test suite run and a real Spring Boot application-context startup against a persistent local database.

## Polish & Fixes

- No visible behavior change — this renumbers a migration file only; its contents are unchanged.
- Deploy note: if a prior failed deploy left a stale build artifact behind, run a clean build (`./mvnw clean install`) before deploying — a non-clean build can still surface the old collision even after this fix.
