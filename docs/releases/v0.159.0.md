# Release Notes: v0.159.0 — Nothing Lost in the Batch

## Release Theme

A bulk operation no longer loses its result: learners are told in the bell when topics failed to generate, and when a bulk regeneration finishes.

## Key Features

**🔔 Bulk generation tells you what failed**
- When a bulk generation fails topics or runs out of monthly capacity, the bell now carries the list of topics that did not make it, in the notification itself.
- Until now that list lived only in a one-time receipt that was deleted on read and swept after 24 hours, and a topic that failed never became a note, so nothing else could show it.
- A fully successful run stays silent, and the message never promises a retry or claims Study Packs are ready.

**✅ Bulk regeneration tells you it finished**
- A regeneration that reaches its normal end sends one notification with the number of Study Packs updated, and says plainly that existing Study Packs are unchanged and still work when some were not.
- A run that was interrupted sends nothing, because saying it finished would be false.

**🏷️ Notifications can badge and still expire**
- Badge eligibility and unread expiry are now two independent settings, so a result notification lights the bell and still ages out after 90 days if it is never opened.
- Review Set updates are unchanged and are still never expired while unread.

**🔍 The 5-second connection timeout, read properly**
- Only the last week of logs exists, and in that week the timeout produced 500 errors in one saturation incident. Most other 500s were database connection drops in the first seconds after a deploy goes live.
- Whether to keep the timeout is still an owner decision, and the deploy-time drops are recorded as a separate finding to verify.

## Polish & Fixes
- `CLAUDE.md` named an async generation entry point that does not exist; it now points at `StudyPackService.startAsyncGenerationFromNote`.
- `notifications.md` no longer says every unread actionable notification is retained forever, which stopped being true for result notifications.
- A test gap was closed: nothing pinned the idempotency key of either new notification, so a re-run could have notified twice unnoticed.
- A pre-signoff pressure test found that an interrupted bulk generation would have listed already-created notes as failed in its notification, that the "and N more" count could point at the wrong list, and that the regeneration message over-claimed; all three are fixed.
- The new notifications were checked with 21 deliberately planted defects, each caught by a named test.
