# Release Notes: v0.37.4 — Idle GC & Metaspace Ceiling Hotfix

## Release Theme

Continue the production memory-restart investigation with the first fix guided by real, live JVM metrics instead of inference alone.

## Key Features

**🧠 Idle Heap Reclaim**
- Live actuator sampling on Render caught the backend's container RSS plateauing near 95-97% within minutes of boot — before the bulk of request traffic even arrived — while heap committed (~207MB) sat well above heap used (~99MB). G1 wasn't handing that idle-committed slack back to the OS.
- Added `G1PeriodicGCInterval=30000` and `G1PeriodicGCInvokesConcurrent` to the Dockerfile's `JAVA_OPTS`, giving G1 a recurring, concurrent (non-pausing) opportunity to uncommit unused heap — the primary fix candidate for this round.

**🛡️ Metaspace Ceiling & Native Memory Visibility**
- Found `MaxMetaspaceSize` was unset entirely (`jvm.memory.max` reported `-1`) — nothing was capping Metaspace growth, and any future runaway would stay invisible to JVM-level OOM logging, indistinguishable from every other silent SIGKILL in this investigation.
- Added `MaxMetaspaceSize=200m` as a tripwire: a future Metaspace runaway now surfaces as a logged `OutOfMemoryError` instead of another unexplained restart.
- Added `NativeMemoryTracking=summary` so `jcmd <pid> VM.native_memory summary` is available on demand, without a redeploy, if the next round needs to break down memory the JVM's standard metrics can't categorize.

## Polish & Fixes

- No code change — this release is a Dockerfile `JAVA_OPTS` env var change only, fully reversible, same risk profile as the v0.37.1 hotfix.
- Deployed as an instrumented experiment, not a declared fix: the RSS plateau either drops post-deploy (confirming the gap was reclaimable heap slack) or stays pinned (pointing at native memory — thread stacks, GC bookkeeping, or `GoogleVisionOcrService`'s per-call `ImageAnnotatorClient` creation — as the next thread to pull).
