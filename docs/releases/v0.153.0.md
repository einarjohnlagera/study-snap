# Release Notes: v0.153.0 — The Missing Telemetry

## Release Theme

Stops re-investigating the same unidentified production outage a fifth time and ships the diagnostic
instrumentation that would actually answer it, plus an unrelated, mid-cycle-folded fix for a growing
Authored Depth metadata backlog.

## Key Features

**📡 Hikari saturation request-path diagnostics**
- A servlet filter now keeps a cleanup-safe, thread-keyed snapshot of every request path currently in
  flight. When the Hikari connection pool is saturated (`activeConnections >= maximumPoolSize` with
  waiters present) for two consecutive samples, a fixed-delay detector logs the pool counts and every
  request in flight at that moment — the one thing that would have named the culprit on the spot across
  all four production outages this year (2026-09-04, -05, -10, -17).
- It emits once per saturation episode, rearms once the pool recovers, and disables itself safely if the
  configured `DataSource` is ever not Hikari. Verified against a genuinely exhausted real Hikari pool,
  not a mock.

**⚙️ Tomcat/Hikari thread-pool alignment**
- `server.tomcat.threads.max` lowered from 25 to 18 (an intermediate value of 20 was tried first and
  found insufficient — see Known Limitations). Reserves headroom below the 20-connection Hikari pool so
  the health check and this app's own DB-bound scheduled jobs are never competing with ordinary request
  traffic for the last connection.
- **Not yet effective in production**: Render's `SERVER_TOMCAT_THREADS_MAX=25` environment variable
  overrides this default until the owner changes or removes it.

**⚠️ Publication-time Authored Depth warning**
- A non-blocking amber warning now appears on every real path that publishes an individual note or
  batch as Public — the "Make this note public?" confirmation, the private-share modal's own "Publish &
  Share Link" button, and the Bulk Generate form's Public toggle — when no Authored Depth is set.
  Publication always proceeds either way; the warning only tells the curator the note won't surface
  under any Authored Depth filter in the Public Library until one is set.

**🔎 Admin missing-Authored-Depth signal**
- The existing curator-scoped Admin Applicable Programs table now shows each owned note's Authored
  Depth and can filter to notes where it's missing — the first way a curator has had to see which of
  their own notes need this metadata repaired.

## Polish & Fixes

- A pre-signoff Opus falsification pass (a fresh cold agent, owner-requested, escalated past the
  per-item verification tiers declared at kickoff) checked all 19 pre-declared claims across all four
  items above against real code execution — a genuinely exhausted pool, a mutated config value, a full
  Spring context boot, real HTTP requests. No code defect found; it did catch written claims that
  outran what the tests actually proved, all fixed in the same release (see Known Limitations).
- `InFlightRequestTrackingFilter` now runs ahead of Spring Security (`@Order(HIGHEST_PRECEDENCE + 1)`),
  so a connection held during authentication's own database lookup is visible to the saturation
  snapshot rather than silently excluded.
- Two new tests close gaps the falsification pass found: the detector re-arming after a saturation
  episode recovers, and the detector staying silent under genuinely concurrent (not just sequential)
  ordinary load.
- `docs/features/note-detail.md` and `docs/features/bulk-generation.md` updated to document the new
  publication-time warning, which had shipped without a feature-doc update.
- All 18 Codex prompt files for already-shipped or just-shipped releases removed (gitignored scratch
  files, not tracked in git) — an established repo convention last done for several older releases at
  once, overdue for a repeat.
- 21 stale git branches deleted (18 already merged into `main`, 3 remote-only branches whose work had
  either shipped as part of an old release merge or been re-landed elsewhere), plus 4 stale worktrees.

## Known Limitations

- **Leg B's shipped value (18) meaningfully reduces, but does not absolutely guarantee, the starvation
  mechanism behind all four outages.** Two background LLM/generation executors and 16 `@Scheduled` jobs
  still draw on the same connection pool without being bounded by `threads.max`. A new
  `[CHECKPOINT]` in `ROADMAP.md`'s Backlog Index (due 30 days after the owner confirms the Render env
  var is actually changed) asks whether a fifth occurrence recurs once this is genuinely live.
- **The saturation registry has no coverage of non-request threads** — the same executors and scheduled
  jobs above never pass through the servlet filter that populates it. A connection held by a generation
  task across a slow OpenAI call would render as an empty in-flight list, which is ambiguous between
  "nothing was in flight" and "the holder was never eligible to be tracked." Not fixed this release —
  closing it is a larger design question (should non-request threads register themselves too) than this
  release's scope.
- **A1 (owner action: confirm/enable Render per-request logging) is still open.** Checked directly via a
  read-only Render logs query at signoff — no `request`-type log entries exist for the production
  service, only `app` and `build` — contradicting an assumption that it was already on by default.
  Enabling it (a Render plan/add-on feature, not a code change) remains the owner's action.
- **The 282-note Authored Depth backlog's manual cleanup and B2 backfill (`docs/claude-plans/authored-depth-b2-board-taker-backfill-DRAFT.sql`, owner-executed) both start now that F1 has shipped**, tracked by the new `[CHECKPOINT — due 2026-10-02]` in the Backlog Index (kill criterion: still >10 unclassified at that read escalates to tooling, not a third extension).
- **`PoolSaturationDetector.poll()` shares Spring's default single-threaded scheduler with all 16 other
  `@Scheduled` jobs**, several DB-bound. During saturation, any of those blocking on a connection stalls
  the 2-second poll for the duration — a latent detection-latency risk, not fixed here to keep this leg's
  diff minimal.
- **`sanitize()` on the logged request path strips only `\n`/`\r`**, with no length bound or other
  control-character stripping. Low severity — fires only during genuine saturation, on a codebase with
  no existing log-injection-hardening convention to hold it against.
