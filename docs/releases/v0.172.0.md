# Release Notes: v0.172.0 — Headroom

## Release Theme

Takes load off a production database that was being pushed past its memory ceiling and restarted,
and stops a Challenge Quiz edge case from failing a request outright.

## Key Features

**🗄️ Lighter Explore discovery sections**
- The Featured and Popular sections are now ranked in one database query instead of two.
  Copies, likes and views are each counted once per request, where before they were counted once
  per section.
- The query keeps note content out of its sorts and joins. On the production query plan it is
  narrower and cheaper than before: estimated cost ~25,300 → ~18,600. These are planner estimates,
  not measured memory.
- Rankings are unchanged. The scoring formula is still defined in one place and shared with the
  paginated Public Library listing. That listing's SQL is pinned byte-for-byte by tests, which were
  checked against the code from before this release.
- Returning to the Explore overview reuses the sections already loaded instead of requesting them
  again. Retry, and coming back after an error, still fetch fresh.

**🧩 No more failed Challenge requests from a repeated question**
- If `+5 Questions`, a quiz start, or an Official template copy produced a question already in the
  learner's question bank, the whole request could fail with an error. No learner is known to have
  hit it, so this was fixed before it caused harm.
- The duplicate is now skipped as it is saved, including when two requests race. The learner still
  gets the question in their quiz; it just isn't banked a second time.

## Polish & Fixes
- Copy counts on the Explore overview now update right after you copy a note, so the reused sections never show a stale count; re-copies and copying your own note correctly leave the count unchanged.
- The owner applied a database setting that turns off parallel query workers on the production database, one of the memory-pressure levers from the investigation. It is confirmed in effect for every app connection.
- A follow-up check is set for 2026-10-22: if the database still has 5 or more memory kills in the week after deploy (it had 9), the plan upgrade becomes the next step.
- An independent pre-signoff review tried to disprove 13 specific claims about this release's two changes and found no code defects; its one product-visible finding, the stale copy count, was fixed before release.
- Corrected two out-of-date monitoring notes and two imprecise sentences in the Challenge Quiz documentation that this release made inaccurate.
