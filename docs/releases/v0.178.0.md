# Release Notes: v0.178.0 — Production Stabilization

## Release Theme
Cut the work that lets the public catalog starve the production database, and add the evidence needed for the next step; the release is code-complete but not yet deployed, and whether it stops the database kills is not yet known.

## Key Features

**⚡ A Faster, Bounded Public Library Listing**
- The ranked public-library listing reads a bounded in-process snapshot of engagement counts and tag membership instead of recomputing them on every call; on a production-shaped database limited to 0.1 CPU, a tag-filtered request went from about 900 ms to about 95 ms and throughput under eight concurrent callers rose about eight times.
- Visibility and every other filter stay live, so a note made private disappears at once; tag membership and engagement ordering may lag a new or retagged note by about five minutes under traffic, and up to about fifteen after a quiet period.
- If the snapshot is unavailable and the database is saturated, the listing answers with a calm "this page is a little busy, please try again" message instead of piling more work onto the database.

**🏗️ Deploys Stop Walking the Catalog**
- A production build no longer fetches the whole public catalog from the production API (393 requests down to 1); subject pages, exam hubs and the sitemap render on first request and are cached.

**🔎 Evidence for the Next Step**
- A temporary, bounded diagnostic records who calls the public API and which header carries the real client address, without logging search text, tokens or full addresses, so the follow-up work can rest on facts.

## Polish & Fixes
- Choosing a subject and a tag together no longer fails; the tag filter's SQL had a missing space that made the combination throw.
- A header value is never handed to a name resolver, and caller-controlled text is quoted in the diagnostic log; both were found by an independent review before release.
- A latent test flake caused by the new startup build was fixed at its root.
- Not covered by this release: the rest of the database load (listing projections, facets, creator-impact), any limit on direct API callers, and the connection overlap during a deploy, so a deploy may still be followed by a kill; the database upgrade stays deferred with explicit triggers.
- No pricing, quota, entitlement, prompt or learner-facing copy changed beyond the busy message, and the release is not merged to `main`.
