# Release Notes: v0.87.0 — Failure Attribution

## Release Theme
When a bulk-generated topic fails, the curator is now told which check rejected it.

## Key Features

**🔍 Per-topic failure reasons**
- Bulk Generate records why each topic failed, not just that it failed
- The reason appears as secondary text under the topic in the existing failure banner
- Validation rejections now name the field they came from — an invalid overview reads differently from an invalid key idea
- Quota-blocked topics keep their own group and carry no reason, since the banner already explains them

**🛡️ Safe by construction**
- A failure that is not a known application error contributes a generic reason and the error's type — never its raw message, and never a stack trace
- The existing failed-topic list keeps its exact shape, so `Retry these` and every receipt already in the system work unchanged
- Receipts created before this release render exactly as they did, with no placeholder and no layout shift

## Polish & Fixes
- A batch that fails before reaching its topic loop now attributes that failure to every topic, rather than leaving them blank
- Documented that generation receipts are consumed on read and expire after 24 hours, so recorded reasons are for the curator in the moment and the server log remains the durable record
- Recorded that this release changed no validation whatsoever — the same inputs succeed and fail as before, they are simply legible now

## Scope note
This release opened as **Published Bounds**, targeting three note-length bounds the model was never told about. Its first scope item was to reproduce the failure before fixing it, and a live probe across fourteen topics and every domain found the bounds never fire. That scope was retired on its own pre-committed gate, and the release became the work both prior investigations had actually needed: making failures explain themselves.
