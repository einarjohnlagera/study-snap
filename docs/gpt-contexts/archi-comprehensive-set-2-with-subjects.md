Yes — and this is an important distinction before we continue.

**Section ≠ Subject.**

In NoteLib today:

* **Subject Plan / child Review Set** = a major curriculum area inside the ALE journey.
* **Section** = an organizational label *inside that plan*. It only controls how notes are grouped and displayed in that particular Review Set.
* **Subject** = permanent metadata on the canonical Note. It answers **“what academic subject does this note belong to?”** and follows the note wherever it is reused.
* A Section can contain notes from **more than one Subject**, although keeping them reasonably aligned makes curation easier.

That separation matters because a canonical note can sit in several Review Sets without changing its Subject. It also means we should **not rename Subjects merely to match our ALE sections**. This matches NoteLib's current metadata architecture, where Subject is the knowledge shelf while Review Sets communicate the learning journey. 

And yes — let's make the Architecture master list explicit now so **nothing gets lost later**.

Below is the revised **ALE Comprehensive Review master curriculum** in:

> **Subject Plan → Section → Note Title → Subject**

I’m also marking each item:

* **✅ Existing** = already in the current Architecture set or existing Architecture-tagged pool
* **♻️ Reuse** = existing canonical note elsewhere that should be reused
* **🆕 New** = needs authoring

Claude's audit is especially useful here because it confirms the current Architecture set has no sections, two whole ALE areas already have written notes outside the set, and the external Architecture-tagged pool is intentionally over-inclusive and must be curated rather than blindly imported.

### One thing I would change from our older Architecture organization

I **would not create Subjects called**:

* `History and Theory of Architecture`
* `Planning and Site Development`
* `Structural Concepts for Architecture`
* `Building Materials and Construction`
* `Building Laws and Regulations`

**just because those are our new Subject Plan names.**

Some of those happen to be valid Subjects in specific cases, but the Review Set hierarchy shouldn't leak into note metadata. A note about Greek architecture should remain:

> **Title:** Greek Architecture
> **Subject:** History of Architecture

—not Subject = `History and Theory of Architecture` merely because that's the ALE plan containing it.

That gives us exactly the architecture NoteLib was designed for:

> **ALE Comprehensive Review**
> → **History and Theory of Architecture** *(Subject Plan)*
> → **Ancient Architecture** *(Section)*
> → **Greek Architecture** *(Note)*
> → **History of Architecture** *(Subject metadata)*

And somewhere else, the exact same Greek Architecture note could participate in another Study Plan without needing to be renamed or reclassified.

So **this version is the master list I would preserve going forward**. When we start actually creating the missing notes, I recommend we work **Subject by Subject**, not Section by Section, because it maps directly to NoteLib's Bulk Generate constraints and will greatly reduce metadata mistakes.
