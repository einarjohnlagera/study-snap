## Method

1. **SQL pre-screen.** It reads each explanation's explicit per-statement verdicts ("Statement 1 is correct…",
   "Statement 2 is false…") and compares them with the keyed choice's text, not its index, because choice
   order varies between rows.
2. **Every flagged item** went to one of two cold Opus checkers. Each judged both statements from subject
   knowledge (Philippine board-exam context, PFRS = IFRS) and derived the correct choice.
3. **A third cold checker** took a fixed random sample (`ORDER BY md5(id)`) of 50 unflagged items whose
   explanation had a verdict the screen could parse (V), and 50 whose explanation had none (N). That
   measures what the screen misses.

## What it means for R1 (the v0.175.0 guard)

**A check that only reads the explanation is not enough.** This screen is precise (166 of 170 flags are real,
about 98%) but catches only about 40% of wrong keys. About half the explanations state no per-statement
verdict at all, and that is where most of the misses are. The guard needs per-statement verdicts the
validator can read: for example, a schema field carrying each statement's true/false, from which the key is
derived or checked. **That is a schema and prompt change, so it needs the owner's sign-off on the exact
change** (R1 as approved).
