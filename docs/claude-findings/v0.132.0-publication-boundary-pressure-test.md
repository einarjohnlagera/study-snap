## F1 — `adoptGoal` silently produces an EMPTY adopted Goal (highest severity)

`NoteCollectionService:1023` gates on `countByParentCollectionId(sourceGoalId) == 0` — **unfiltered**.
`:1037` then filters `sourceChildren` to published only. Nothing reconciles the two.

A Goal whose children are ALL unpublished passes the gate (count > 0) and yields `sourceChildren = []`.
The copy loop runs zero times, and `adoptGoal` never copies the root's own items — only
`adopt(sourceChild, …)` inside the loop copies anything.

Learner result: a collection with zero Subject Plans and zero notes. `adoptedSubjectCount = 0` AND
`skippedSubjectCount = 0`, so the skipped-notice renders nothing. `persistAdoptedGoal` →
`assignAdoptedCollectionAsPrimaryWhenMissing` makes this empty shell a new learner's PRIMARY collection.
`findByOwnerUserIdAndSourcePlanId` now hits, so re-adopting returns `alreadyAdopted` — **retry cannot
fix it**; the learner must delete it. The set's public adoption count increments for the empty adoption.

**This commit converted a loud failure into a silent one:** the same shape previously raised
`CollectionNotFoundException` from `adopt()` on the private child.

No test covers `adoptGoal` against an all-unpublished child set.

## F2 — `listPublic` is unfiltered while `getPublic` is filtered (found independently by BOTH agents)

`NoteCollectionService:237` — `findByParentCollectionIdIn`, `loadItemCounts`, `loadReadyCounts`,
`rollUpCounts`, `loadChildCounts` all carry no `published_at` predicate. `getPublic` now does.

Anonymous Explore / Exam Hub / dashboard cards render `childCount`, `itemCount` and `readyCount`
(`public-study-plan-card.tsx:55-60`) plus `Preview this plan · N notes`. A curator's unpublished
Subject Plan is COUNTED on the card and ABSENT from the page it links to.

Attribution, stated precisely: those count queries were unfiltered before this commit too. **What this
commit introduced is the divergence.** `docs/features/collections.md`, added by this same commit,
states the opposite principle in its own words — that counting a plan the page will not show would
"advertise its existence and leave the public view contradicting itself."

`childCount > 0` is also what sets `isGoal` and routes the Adopt button to `adoptGoal` — so F2 is the
router into F1.

Not covered by the recorded Known limitation, which names removals, reorders and renames only.

## F3 — first publication of any PRE-EXISTING collection stamps nothing

V141's first `UPDATE` has **no visibility predicate**, so every row alive at deploy — PRIVATE drafts
included — gets a non-null `published_at`. `updateVisibility:977` guards
`previousVisibility != PUBLIC && saved.getPublishedAt() == null`, which is therefore **false for every
pre-existing collection**.

A pre-existing PRIVATE draft, given new Subject Plans and topics after deploy and then published, runs
`publishInitialCurriculum` **never**. The post-deploy content stays unpublished, `getPublic` and both
adopt paths see only pre-deploy rows, and `last_update_published_at` stays NULL.

**Proposed fix — guard on `last_update_published_at`, not `published_at`.** V141's third UPDATE stamps
that field for pre-existing PUBLIC source roots ONLY, making it the exact "has this set ever been
published" discriminator the guard needs:
- pre-existing PRIVATE draft, first publish → NULL → runs (fixes F3)
- collection created after deploy → NULL → runs (unchanged)
- pre-existing PUBLIC set → non-null → skipped (unchanged)
- PUBLIC → PRIVATE → PUBLIC → non-null → skipped, so edits made while private still require an explicit
  `Publish update` (boundary preserved — a plain "always stamp" fix would break this)

The negative branch has no test; the only existing test sets `publishedAt = null`, exercising solely the
branch that fires.

## F4 — a publish failure is invisible to the curator

The `catch` sets `mutationError` and the Card is in the DOM — but `setPublishUpdateOpen(false)` sits
inside `try`, so on failure the modal stays open, and `AppModal` portals a `fixed inset-0 z-50
bg-black/55` backdrop over the page body where that Card lives
(`collection-detail-page-client.tsx:3561` goal / `:3742` leaf).

Proved empirically by the reviewing agent: `ERR_INSIDE_DIALOG: false`, `MODAL_STILL_OPEN: true`,
`CONFIRM_ENABLED: true`. The curator sees a click that did nothing and will click again.

**This defeats the obvious test for it** — `expect(screen.getByText(msg)).toBeInTheDocument()` passes.
It is the `v0.131.0` disabled-control lesson one layer up: the control is enabled, the FEEDBACK is
occluded.

Success path is fine: `setPublicationStatus(result)` refreshes, so no stale badge.

## F5 — no publication surface on the page where curators actually edit

`isOfficialReviewSetCuratorView` requires `parentCollectionId === null`, but `addItems` throws
`GOAL_CANNOT_ACCEPT_NOTES_MESSAGE` when a collection has children — so a Goal-shaped Review Set root
**cannot hold a topic**. Every topic addition happens on a child Subject Plan via the Builder
(`study-plan-builder-page-client.tsx`). Grep for `Unpublished changes` / `publishReviewSetUpdate` across
`app/` and `components/` returns `collection-detail-page-client.tsx` only.

A curator adds a Subject Plan and ten topics in the Builder and leaves. Nothing there says the work is
invisible to learners; there is no way to publish from it. `touch()` bumps only the child's `updatedAt`,
so a root page open in another tab never refires its status effect (deps
`[collection?.updatedAt, collectionId, isOfficialReviewSetCuratorView]`).

  Not a live defect — one agent executed the real client and the request shape is correct — but the
  guard the repo requires is absent.

## Corrections to the implementing session's own claims

- **"The backfill is asserted against REAL migrated rows, not a hand-built fixture" is FALSE as worded.**
  `NativeQueryPostgresIntegrationTest:2743` seeds its own rows after Flyway, then replays the backfill
  by reading the shipped SQL text. DDL is real and a mutation to V141 IS caught — but the rows are the
  test's, not the migration's. **Pre-declared guard #4 is structurally unsatisfiable** in a
  Flyway-on-empty-schema harness; reading the real SQL is the best available approximation. The guard
  needs rewording; the test does not need changing.
- **Claims CONFIRMED and now better-evidenced than before:** the six `published_at` filters are all
  source-side and unreachable by adopted rows (`NoteService:386` forces adopted notes PRIVATE, so an
  admin cannot publish an adopted copy); `countAdoptionsByCollectionIds` is unfiltered; publish is
  atomic, row-locked and idempotent; and the controller's MockMvc `Content-Type` guard is load-bearing
  — deleting it reproduces the `v0.119.0` 415 exactly.
