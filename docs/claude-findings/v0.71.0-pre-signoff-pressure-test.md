This is the **full pre-signoff pressure test** required by `CLAUDE.md` ("Before closing a release, decide the

## Method

Six parallel read-only agents inventoried every backend and frontend file touched by the release, plus a seventh
covering the onboarding flow (which the release did **not** touch but whose invariants it changed). Findings were
synthesised and pressure-tested via `advisor`.

Three things were done deliberately to avoid the failure mode of a review that just agrees with itself:

- **Agents were told not to trust the handoff brief.** Four of its claims turned out to be wrong (see
  "Brief claims disproven").
- **Blocker-grade claims were re-verified by the synthesising session against the real code**, not accepted from
  an agent report. Two claims were downgraded or corrected this way; one was upgraded.
- **The single highest-stakes claim (B1) was verified empirically**, not by reasoning, because its mechanism ran
  through JPA flush ordering — a bug class `CLAUDE.md` names as one that must not be reasoned about serially.

## B1 — `copyNote` throws a foreign-key violation. Empirically proven. **FIXED 2026-08-06.**

**FIXED**, together with B2 and after it, so the flush never propagated a derived row. `noteRepository.flush()`
now sits between the `save()` and the raw-JDBC join write, matching create and update. The regression test
asserts the **ordering** via Mockito `InOrder` rather than merely that `flush()` was called — verified to fail
when the flush is removed.

`backend/.../service/NoteService.java:352-353` — **line numbers corrected 2026-08-06.** They were `:339-340`
when this was written; the C1 fix added lines to `update()`, which sits above `copyNote`, and shifted every
citation in this section. Verify before editing rather than trusting any number here.

```java
352: NoteEntity saved = noteRepository.save(copy);
353: noteCourseProgramRepository.replace(saved.getId(), noteCourseProgramRepository.findIdsByNoteId(source.getId()));
```

No `noteRepository.flush()` between them. Both sibling call sites have one — `:191-194` (create) and `:231-234`
(update). `NoteEntity` has a plain assigned `@Id UUID` (no `@GeneratedValue`, no `@Version`, not `Persistable`),
so Spring Data resolves `isNew() == false` and calls `em.merge()`, deferring the INSERT to flush.
`NoteCourseProgramRepository` is raw `JdbcTemplate`, which does not trigger a Hibernate autoflush. `NoteService`
is class-level `@Transactional` (`:102`) and `copyNote` (`:270`/`:274`) adds no override. V107 declares
`fk_note_course_program_note ... REFERENCES notes(id)`, not deferrable.

**Empirical proof.** A throwaway probe reproducing the exact sequence (since deleted):

```
PROBE_A rows visible to raw JDBC after save(), before flush = 0
PROBE_B child INSERT FAILED: DataIntegrityViolationException :: Referential integrity constraint violation:
        "NOTE_COURSE_PROGRAM FOREIGN KEY(NOTE_ID) REFERENCES NOTES(ID)"
PROBE_C rows visible to raw JDBC after save()+flush() = 1
PROBE_D child INSERT SUCCEEDED after flush
```

**Blast radius — measured, not assumed.** Local dev DB with V107 applied (`flyway_schema_history` confirms
version 107, success):

- **18 of 40 public notes (45%) have join rows** → `POST /notes/{id}/copy` fails on 45% of the public corpus.
- 38 of 119 notes overall; of the 92 notes that have a program string at all, 37 (40%) got a join row.

Caveat: local corpus, not production. Production's recorded vocabulary
(`docs/claude-prompt/canonical-knowledge-architecture-out/15-vocabulary-and-impact-results.md`) is far more
concentrated in catalog-matching values — Civil Engineering 197, Accountancy 154, Education 146, Nursing 130,
Architecture 90, IT 74, against only ~19 notes on excluded values — so the production share is likely
substantially higher than 45%, but that figure is **unmeasured**.

**Entry points.** `POST /notes/{id}/copy` (`NoteController.java:239-245`), copy-on-signup (`:250`), and
study-plan adoption (`NoteCollectionService.java:1268`).

**Failure scenarios.**
- A learner clicks "Copy to my library" on any backfilled public note → **500**.
- A learner adopts a 12-note curated study plan → `copySourceItems` catches `RuntimeException` per item and
  increments `skippedCount`, so they get an adopted plan with **zero notes and no error shown**.

The empty case is silent (`replace` with an empty set does no insert), which is why learner-to-learner copies of
non-backfilled notes still work and why this was never noticed.

**Fix:** add `noteRepository.flush()` after `:352`, matching create (`:193-194`) and update (`:244-245`) —
**but see the ordering trap below.** (Line numbers corrected 2026-08-06; previously cited as `:339`, `:192`,
`:232`.)

> ### ~~Fix-order dependency — do not fix B1 alone~~ — CLEARED 2026-08-06, B2 shipped first
> **B1 is now unblocked.** B2 was fixed by `V108`, which removes the mechanically derived learner rows, so what
> `copyNote` propagates after the `flush()` is curator-authored and inherited rows only — which is the intended
> behaviour, not an amplifier. The original dependency, retained for the reasoning:
>
> The `flush()` makes copy *succeed*, which then starts propagating stale join rows (B2's amplifier at `:353`)

## B2 — V107's backfill froze the Course / Program of every learner note it touched

**FIXED 2026-08-06 by `V108__remove_derived_learner_note_programs.sql`.** Option 7 (prevent the mechanical
derivation), per the doctrine ratified in `ADR-001` → *Representation authority*. The additive migration deletes
join rows whose note is both learner-owned and not a copy; curator-authored rows and rows inherited by copying a
curated note survive, so the fix is the narrow provenance rule rather than the wrong broader "learner notes carry
no join rows". `V107` is unmodified — its checksum has already been applied outside production.
`DerivedLearnerNoteProgramRemovalMigrationTest` covers it, with the `DELETE` deliberately outside the PL/pgSQL
block so the B4 stripping trap below cannot hide it; the inheritance guard was verified to fail when the
not-a-copy condition is dropped. The finding is retained below as the record of what was found and why.

`backend/src/main/resources/db/migration/V107__note_course_program.sql:27-34`. Found independently by **three**
agents.

The backfill has **no owner filter**, so learner-owned notes got join rows. Every read path then gates the legacy
string behind "no join row exists", and no code path can ever clear a learner's join row —
`NoteService.java:233` reconciles only `if (curator)`, and `PUT /notes/{id}/applicable-programs` is curator-gated
(`NoteApplicableProgramsService.java:110-124`).

The in-code comment at `NoteService.java:236-239` justifies leaving join rows alone because "a learner never
authors them". **V107 falsifies that premise.**

**Failure scenario.** A student's note has `course_program = 'Nursing'`; V107 backfills a `Nursing` join row. The
student edits Course / Program to `Pharmacy` and saves. `notes.course_program` becomes `Pharmacy`; the join row
stays `Nursing`. Thereafter:

- **Generation** — `StudyPackGenerationContextResolver.java:131` returns `Nursing` (join row wins), so every
  future Study Pack, quiz and exam is authored against Nursing. Pre-v0.71.0 the same note produced `Pharmacy`.
  Blast radius is every generation path: Challenge Quiz, Quick Review, Adaptive Practice, Long Exam, Board Exam
  pool, Interview Practice, Post-Session Next Step.
- **Discovery** — the note files under `Nursing` in the library filter and facets, never under `Pharmacy`.
- **Display** — private `NoteResponse` shows `Pharmacy` (`:1483`) while public detail shows `Nursing`
  (`:1602-1610`). Same note, two answers, same release.

The edit is silently inert, permanently, with no user-reachable remedy. **Amplifier:** `NoteService.java:340`
propagates the stale row into every copy.

> ### B2 and C1 are two halves of ONE design decision, not two independent bugs
> Both hang off `NoteService.java:233`'s `if (curator)` guard. That guard is deliberate — it preserves inherited
> rows — and is simultaneously the mechanism that makes learner edits inert (B2) and the reason the invariant is
> never re-checked against stored rows (C1). Two agents proposed **opposite** fixes: validate against
> `findIdsByNoteId(noteId).size()`, versus clear join rows on a learner update. Those are different answers to
> one question: **should a learner-owned note be allowed to carry join rows at all?**
> Answer it once. Fixing B2 and C1 separately will produce an incoherent rule.

## C1 — The multi-program ⇒ Domain Context invariant is validated against the request, never stored rows

> **FIXED 2026-08-06 — but NOT by the one-liner this document and the owner-decisions table prescribe.**
> "Change `assertMultiProgramHasDomainContext` to read `findIdsByNoteId(noteId).size()`" is correct for the
> learner branch and **a bug for curators**, because a curator's `courseProgramIds` is the set being *written*
> moments later by `replace(saved.getId(), courseProgramIds)`. Applied to both branches it validates the
> **pre**-update set against the **post**-update domain:
>
> - curator reduces 3 programs → 1 while clearing Domain Context — post-state legal, stored = 3 → **throws,
>   blocking a legal edit**. Reproduced: mutating the fix to the naive form fails
>   `update_byCuratorOwner_validatesTheRequestedProgramsRatherThanTheStoredRows` with exactly this exception.
> - curator expands 1 → 6 with Domain Context still null — post-state illegal, stored = 1 → **passes, writing
>   the state slice 4 forbids**.
>
> **Shipped rule:** validate the set in effect *after* the update — the request for curators, the stored rows
> for learners. This is the ruling ("validation reads the stored rows, not the request") applied to the branch
> the ruling was about, not a re-litigation of it. `create` is unchanged: the note does not exist yet, so the
> request set is the whole post-create truth, and a learner create writes no join rows.
>
> **GATE CLOSED BY CONSTRUCTION, 2026-08-06 — no owner query is owed.** Production has not received
> `note_course_program` at all; slices 1–4 deploy as one unit when the release merges. V107 creates **at most one

claims are wrong:

1. **"A null-dependency compatibility constructor on `StudyPackGenerationContextResolver` was removed."** It never
