## 1. BLOCKING — learner note-creates silently write an invisible, unclearable `notes.learner_level`

**Found independently by all three agents.**

The pre-fill is gated on `!isEditMode` but **not on profile type**:

- `note-editor-page-client.tsx:372` — `learnerLevel: previous.learnerLevel || me.learnerLevel || ""`, applied for every profile.
- `note-editor-form.tsx:500` — the Authored Depth select renders only inside `showAuthoringMetadataFields` (`isTeacherSelectableNoteTarget`). A `STUDENT` never sees it.
- `note-editor-page-client.tsx:741` / `:1017` — `learnerLevel: draft.learnerLevel || null` is sent **unconditionally**, unlike `courseProgramText` / `courseProgramIds` on the adjacent lines, which *are* gated on `showTargetProfileTypeField`.
- `NoteService.java:174,182` persists it with no role gate.
- `private-note-detail-page-client.tsx:1381` sends `note.learnerLevel` back untouched for non-teachers — **so no surface in the product can ever clear it.**

Every account has a non-null `learnerLevel` after onboarding, so this fires on essentially every learner create.

**Why it is not cosmetic.** `StudyPackGenerationContextResolver.java:177-184` returns the *note* level whenever non-null, ahead of the reader level, and `AGENTS.md:1634-1635` locks the note's authored level as a curriculum **floor** a lower reader level cannot lower. A learner who authors at `SENIOR_HIGH` and later moves their profile to `COLLEGE` is permanently pinned to `SENIOR_HIGH` for those notes, with no control anywhere to fix it. Previously `NULL` let resolution follow the profile. It also changes shared/public notes: a copy now carries the original author's level as the floor instead of falling back to the reader's.

**It converts a resolve-time fallback into a frozen stored value**, which is the opposite of what `ADR-001` constraint 2 protects.

**Docs it falsifies — including this release's own anti-drift block:**
- `RELEASES.md:43` — *"This release is **entirely curator-side** and touches no learner result screen…"* Textually false: the primary note-creation path for every learner changed.
- `RELEASES.md:21` — *"The value is persisted only because a human saved the form, so a stored value continues to mean 'a person decided this.'"* False for learners; no human saw the field.
- `note-editor-page-client.tsx:371` (the code's own comment) — *"it lands in a visible control the author can change."* False for learners.

**A test edited in this release ratifies the bug.** `note-editor-page-client.test.tsx:620-631` asserts `learnerLevel: "COLLEGE"` on a `targetProfileType: "STUDENT"` create — the learner path — with a comment framing it as intended. Its `getAuthUser` mock has no `profileType`, so there is no control and no pre-fill on that fixture, only an invisible write. Both *new* pre-fill tests use `profileType: "TEACHER"`; the learner case is covered only by that wrong assertion. **Same failure mode as `v0.74.0`.**

**Fix:** gate `learnerLevel` in the create payload on `showTargetProfileTypeField`, matching the already-gated program fields, and flip the test. Owner call if instead the learner write is wanted — but then `RELEASES.md:21` and `:43` must change, not stay.

## 2. Profile pre-fill overwrites an *explicitly empty* depth — including one restored from the retry stash

**Found by two agents.** `bulk-generation-page-client.tsx:160-167`, `:127`, `:239`.

Both guards test **truthiness, not provenance**:
- the getMe updater bails on `if (current)`, so an explicit blank is indistinguishable from untouched;
- the stash effect only records provenance when the stashed value is non-empty (`:127`);
- `handleCollectionChange` bails on `current && learnerLevelSource === "user"`, so a deliberately-blank explicit choice is not protected either.

**Deterministic repro (no timing needed):** curator submits a bulk batch with Authored Depth left blank → some topics fail → Library → **Retry**. The stash restores blank with source `"none"`, `getMe` resolves and injects the profile level, and **the retried notes are authored at a different depth than the batch they replace.**

Falsifies `bulk-generation.md:41`, `:49`, `:51` — including the sentence this release added claiming *"a level restored from a retry stash counts as explicit"* — and `notes.md:73` ("blank remains a real, selectable null state").

**Fix:** bail on `learnerLevelSource !== "none"` rather than on `current`; set `"user"` from the stash unconditionally.

## 3. Switching or clearing the Review Set leaves the previous set's depth displayed and submitted

`bulk-generation-page-client.tsx:233-245`. `handleCollectionChange` only touches depth when the newly selected set *has* a resolved level; nothing resets it otherwise.

Repro: pick Review Set A (`BOARD_EXAM_REVIEW`) → depth shows Board Exam Review → switch to Review Set B (no resolved level) → **depth stays Board Exam Review**, source still `"collection"`, and it submits under B. Selecting "No Collection" likewise leaves it.

**The shipped test that appears to cover this passes vacuously.** `bulk-generation-page-client.test.tsx:216` — *"leaves authored depth empty when the Review Set has no resolved level"* — starts from an empty control and never exercises a **switch**, so it asserts strictly less than its name claims.

## 4. Review Set membership is all-or-nothing — one deleted note drops the entire set

`NoteCollectionService.java:944` (`loadOwnedNotesByIdOrThrow`, body `:1677-1690`), reached from `NoteBulkGenerationService.java:373`.

It throws `NoteNotFoundException` on the **first** unresolvable id, before writing anything. Repro: a 50-topic batch runs for many minutes (500 ms throttle + LLM latency); notes appear in the Library as they are created; the user deletes one. At completion all 49 survivors plus the deleted id are passed, the call throws, `:377` catches and logs — and **zero** notes are added. The user sees 49 generated notes and an empty Review Set, with the only signal in a server log.

`bulk-generation.md` describes a *per-write* failure; the code has a **batch-wide** one. Fix (filter to still-owned ids, or catch per id) or record as a Known limitation.

## 7. `resolvedLearnerLevel` can cross a visibility boundary on the unauthenticated public endpoint

`NoteCollectionService.java:1918` (`toPublicDetailResponse`), reached from `getPublic` via `GET /collections/public/{id}` (no `@PreAuthorize`).

The discriminating fact: **a PUBLIC collection can have a non-null `parentCollectionId`** — `validatePublishable:1253` does not require top-level. So an admin publishing a single child leaf under a PRIVATE parent causes the walk to read that private row and emit its level to anonymous callers. Impact is small (admin-only publish path, the datum is an enum value), but it is the only field on that response derived from a row the caller cannot see, and `resolvedLearnerLevel` is consumed solely by the owner-scoped bulk-authoring selector — it has no business on the public mapper.

## Verified CORRECT — do not re-check

- **Migration V112** additive, nullable, no backfill, no version collision; `varchar(50)` matches the `@Enumerated(STRING)` mapping.
- **Wire binding**, proven empirically with a throwaway Jackson test: `collectionId` binds; `learnerLevel` binds `"COLLEGE"` / `""` / omitted **distinctly** — the extra record constructors do not displace the canonical one. No existing test covered this, and the repo has prior art of being bitten by it.
- **Clear-to-NULL works end-to-end** — `parseLearnerLevelOrThrow("")` → null, update guards on `!= null` so `""` clears while omitted preserves; the frontend sends `""` only on change.
- **Ancestor walk** is cycle-safe, depth-bounded, owner-scoped, returns on first hit, and never defaults to `COLLEGE`. No reachable data shape yields a *wrong* level.
- **No N+1.** All 15 mapper call sites are inside `@Transactional`; `list()` and `listPublic()` return only `parentCollectionId IS NULL` rows so the walk terminates at hop 1 as an L1-cache hit with zero SQL, and `listNoteAccepting` loads all owned collections so every ancestor is already in the session. The non-transactional `adopt`/`adoptGoal`/`generateCompanion` reach no mapper. **One agent claimed an N+1 on `/collections`; it assumed `list()` returned the whole hierarchy and did not check the repository method. Verified wrong — `NoteCollectionService.java:151`.**
- **No bean cycle** — `contextLoads` passes; `@Autowired` is on the 15-arg constructor so multi-constructor ambiguity does not arise.
- **Idempotency is real** — `addItems:942-948` filters against existing ids, and the added test asserts it correctly.
- **Nothing escapes the `finally`** in `processBatch`.
- **Authorization** on the new paths is owner-scoped; the `noteAccepting` param does not bypass `@PreAuthorize`.
- **Goal-exclusion predicate is consistent** across `listNoteAccepting`, `validateNoteAcceptingCollection`, and the pre-existing `addItems` guard — no childless-Goal hole.
- **ADR-001 constraints 1–4 all hold** in code: Domain Context is never inferred on either surface, `LearnerLevel` is unchanged, the rename is copy-only, and the resolved level is never written server-side onto a note.
- **The rename is complete and correctly scoped** — no user-visible "Note Learner Level" remains in code, and the reader axis (`onboarding`, `profile`, the dashboard completion prompt) still reads "Learner Level".
- **The pre-fill genuinely cannot reach an edit surface** — `isEditMode` is prop-derived and constant for the component's life, so ordering cannot defeat the guard; the inline metadata panel is seeded solely from the note.
- **Collections-load failure** leaves the form usable and submittable, with `role="alert"` and a retry action.
- **`ADR-001`'s amended Sequencing section is accurate** — `AGENTS.md:1081` and `handleEdit` confirm editability shipped in `v0.70.0`; heading hierarchy intact; `collections.md`'s new H3 sits cleanly after the restored hierarchy list.

**Finding 1's fix is NOT the one the audit proposed, and the difference matters.** Two agents suggested gating the *request payload* on `showTargetProfileTypeField`. That would have introduced a new bug: `PUT /notes/{id}` is a full replace, so a learner editing a note that already carries a depth would have had it **nulled on save** — the exact failure `docs/features/notes.md` warns about (*"hiding a field must never null it"*). Gating the **pre-fill** instead is correct in all four cases (create/edit × learner/curator), because in edit mode the draft is seeded from the note and round-trips intact. A regression test now pins the round-trip case specifically so the payload-gating "fix" cannot be reintroduced.

**Gating the pre-fill also makes `RELEASES.md`'s "entirely curator-side" claim true again** — the doc was right and the code had drifted, so this is not a case of choosing which to edit.

**Two shipped tests asserted less than their names claimed and have been replaced with ones that fail against the old code:** the vacuous "leaves authored depth empty when the Review Set has no resolved level" (never exercised a switch) and the ratifying `learnerLevel: "COLLEGE"` learner-path assertion. The original `learnerLevel: null` was correct only *by accident* — it predated profile-type awareness — so it was replaced with named learner/curator tests rather than reverted.

**One fix uncovered a second latent defect.** Adding `collectionId` to the retry stash type was not sufficient: `consumeBulkGenerationRetryStash` **whitelists fields on read**, so the new field was silently dropped and the restore test failed. A comment now records that adding a stash field requires touching the reader too.

**Not changed, deliberately:** the 13-arg test-only constructor still passes `null` for `noteCollectionService`. It is documented as test-only, Spring binds the `@Autowired` 15-arg constructor, and a test that supplies a `collectionId` through it fails loudly rather than silently. The genuinely dead 14-arg constructor was removed.

**Still open — an owner decision, not a defect:** whether this release owes a `[CHECKPOINT]` row. The value claim ("curators keep the inferred depth rather than overriding it") has no metric without new instrumentation, and this repo's own gate forbids a dated checkpoint whose metric does not fire. So it is either ship an event now, or record at signoff that no checkpoint is owed because this implements a ratified ADR direction rather than a bet. Must not be left silent.
