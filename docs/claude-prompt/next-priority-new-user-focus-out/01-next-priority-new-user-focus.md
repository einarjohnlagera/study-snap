# NoteLib Release Sequencing — Track A vs. Track B vs. Track C

## 1. Which tracks actually fit "new users to retain"

**Track A's CPALE hub fits.** A new exam hub is a top-of-funnel acquisition play by construction — it exists to get found by people searching for CPALE-related content who have never touched the product. There is no retention mechanic in it at all; its entire value is "get a person who doesn't know NoteLib exists into the funnel." That is squarely inside the new mandate.

**Track B (H1+H5) fits, and it fits more precisely than Track A does.** Despite living in a document called "retention diagnosis," what H1 and H5 actually do is operate on users in their first one-to-two weeks after signup: H1 asks a freshly-signed-up (or freshly exam-date-confirmed) user to make a concrete commitment while motivation is highest; H5 makes sure that whatever moment is supposed to honor that commitment lands them on one coherent next action instead of a blank dashboard. Both mechanisms are only meaningful for someone who *just* arrived — there is no version of this that reaches back to someone who signed up eight months ago and vanished. The label "retention" in the internal doc title is describing the *mechanism* (a commitment-and-return loop), not the *population* — and the brief is explicit that the population here is new users, not lapsed ones. So Track B is not merely tolerated by the new posture, it's a direct, purpose-built implementation of it: it's the "get newly-arrived people to come back for session two and three" half of the mandate that Track A's pure top-of-funnel work doesn't touch at all.

**Track C does not fit, and this needs to be said plainly rather than softened.** Track C's subject population is explicitly people who already used the product and already left. There is no reading of "outbound interviews to already-churned users" that lands on "new user." The fact that it shares a document with Track B's "retention diagnosis" label is a filing accident, not a signal that they're the same initiative — Track B is about preventing a *future* first-two-weeks churn event on a user who hasn't left yet; Track C is about understanding a *past* churn event on a user who already has. Different populations, different time direction, different purpose. Under the stated posture, Track C is explicitly out of scope as a priority, full stop — its only path to relevance in this session is the "costs nothing so run it anyway" argument addressed in item 3, not a repositioning as retention work.

## 2. CPALE hub vs. H1+H5 — sequencing recommendation

The anti-pattern check the brief asks for applies to *both* candidates, and it resolves the same way for both: **neither is ready to be scoped as a release yet, because both sit on top of an unconfirmed gate, and confirming the gate is cheap while building on top of an unconfirmed gate is not.**

For the CPALE hub, the gate is a depth-count check — does the ~100+ notes signal actually clear the same 25-30-notes-in-one-clean-bucket bar the other three hubs cleared before being built. That's a single query against the note taxonomy. It is not engineering work in the "build a feature" sense; it's a five-minute verification that either turns into a real, scoped, small release (proven shape — this is the fourth instance of a pattern already shipped three times) or turns into "not yet, keep growing the CPALE note base first."

For H1+H5, the gate is bigger and already has more riding on it: the earlier release explicitly pre-committed to a decision rule — re-check the cohort's return-rate data in roughly late July, and if the signal is positive *or ambiguous* (not clearly negative), ship H1+H5. That window has arrived, and the re-check has not been run this cycle. This is not a new verification step invented for this session — it's an *overdue* commitment the team already made to itself. Until that number is pulled, there is no honest basis to scope H1+H5 as a release, because the team's own stated rule requires seeing that data first — and the pre-acknowledged small-sample risk means even pulling the number might not resolve cleanly.

Given that, the sequencing verdict is: **do not scope a release for either track right now.** The correct next action for both is a verification step, not a build, and that verification step is cheap for both. But if the question is which track's *build* should be scoped first once its gate clears — it's the CPALE hub. It's the smaller bet, it reuses an already-proven mechanism (three prior hubs, same shape), its prerequisite check is faster and lower-stakes to run, and unlike H1+H5 it isn't gated on a data signal that was pre-acknowledged as possibly too noisy to read cleanly. H1+H5 is the bigger, more structurally important bet for the new acquisition-and-early-retain strategy, but "bigger and more important" is exactly why it should not be scoped on faith while its own decision gate sits unpulled — that's building on top of an unconfirmed gate, which is the precise anti-pattern this session was told to watch for.

## 3. Verdict on Track C (churned-user interviews)

**Run it anyway.** Track C fails the "does this fit new-user-to-retain" test cleanly — say that part plainly, it does not, and it should not be prioritized, resourced, or reframed to pretend otherwise. But the decision in front of us isn't "should we prioritize learning from churned users" — it's "does sending five already-written emails and reading the replies cost anything that Track A or Track B need." It doesn't. It requires no engineering time, no branch, no release slot, and no attention from whoever is going to run the CPALE depth check or pull the H1/H5 cohort data. Holding it accomplishes nothing except delaying free information; running it costs nothing and might surface something useful for whenever the org does eventually revisit lapsed users. The only discipline required here is not letting Track C's findings quietly get treated as justification for a new track later — its output is background context, not a green light to reprioritize back toward churned users. Send it, read the replies, and shelve the findings until they're relevant to a track that's actually about that population.

## 4. P1 (Search Console) and P3 (exam-content guides)

Both should be **explicitly handed back to the product owner right now**, not left to keep waiting silently.

**P1 (Search Console setup)** is not an ambiguous case — it requires domain/DNS-level access that only the product owner has. There is no version of an engineering session that can execute this regardless of priority. Leaving it in the backlog unflagged reads as "still being triaged" when the actual status is "blocked on one specific person taking one specific administrative action." It should be surfaced as a standing action item with the access requirement stated plainly, not re-listed every cycle as if it might get engineered eventually.

**P3 (exam-named content guides)** is similar but for a different reason — it's not blocked on access, it's blocked on subject-matter truth. Content claiming to be accurate PNLE/ALE/LET (or CPALE) study material cannot be fabricated by an AI coding session without a real curator standing behind the claims; doing so anyway would be a credibility risk directly inside the SEO surface the team just invested in improving. This should also go back to the product owner as "needs a curator sourced by you, not an engineering task," with the added note that it's explicitly the kind of top-of-funnel content P1's Search Console data would eventually help evaluate — so there's a soft sequencing dependency worth naming (P3 is more valuable to build *after* P1 is live and generating query data on what people are actually searching for), but that dependency is not a reason to keep either one sitting unflagged.

Neither should "keep waiting with no action" — both get an explicit, named handback in this session's output, because both have sat in Track A's list looking like backlog items an engineering cycle might eventually pick up, when neither one actually is that.

## 5. The one thing to do next

**Re-pull the cohort return-rate data for the H1+H5 decision gate. That is the single concrete first step, and it should happen before anything else in this session's output gets acted on.**

Reasoning for why this wins over the CPALE depth check as *the* headline action, even though both are cheap verification steps and both are legitimate to do: the H1/H5 gate is time-boxed and already pre-committed — the team told itself "check in late July," and nobody has run the check yet. That's not a nice-to-have verification, it's an overdue commitment against the team's own stated rule, and it determines whether the single largest available release (a two-part commitment-and-resolver system aimed exactly at the new stated priority) is buildable at all this cycle. The CPALE depth check is real and should also get run — it's a five-minute query and there's no reason to sequence it behind anything — but it is not time-pressured the way the H1/H5 window is, and its outcome only unlocks a smaller, lower-stakes release either way. Pull the cohort numbers first; if they read positive or ambiguous per the pre-committed rule, scope H1+H5 next. Run the CPALE note-count query in parallel since it costs nothing to do alongside — but don't let a same-day, low-stakes count check displace the actual overdue decision-gate query as this session's real next action.
