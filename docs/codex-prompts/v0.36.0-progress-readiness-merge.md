## TASK

Merge the standalone `/progress` (cross-plan) and `/collections/{id}/readiness` (plan-scoped) pages into one canonical `/progress` route with an in-page switcher, and unify the readiness vocabulary that currently differs between them.

## GOAL

Today the product has two pages expressing the same ConceptHealth-derived readiness signal with different vocabularies and entry points — a full `/progress` cross-plan dashboard and a separate `/collections/{id}/readiness` plan-scoped page. This confuses users about which page is canonical. Merging them into one surface, with one label set (`ready / mastered / due / not started`) used everywhere, makes "how ready am I" a single coherent answer regardless of entry point.

## CONTEXT

Decisions already made (do not re-litigate):
- **Canonical URL stays `/progress`.** It already has 5 inbound links (nav, dashboard focus card, dashboard goal card, progress-focus-guide, goal-nudge-card) vs. 1 inbound link to `/collections/{id}/readiness` (the "Check readiness" button on the plan detail hero). Changing 1 link is cheaper than changing 5.
- **View model: in-page switcher.** `/progress` defaults to "All subjects" (cross-plan, today's `getProgressReport()` behavior). A plan picker lets the user switch to a single plan's readiness (`getPlanReadiness(id)`), deep-linkable via `?collectionId={id}`. Do NOT build a deep-link-only model with no on-page switcher — the picker is required.
- **Nav label and page title are unchanged.** Nav stays "Progress", page header stays "My Progress" / eyebrow "MY PROGRESS". Do not rename to "Readiness" or "Progress & Readiness" — this was explicitly decided against because it would put two vocabulary words in permanent nav real estate, undercutting the unified-vocabulary goal, and because "Progress" nav already has 5 items and is mobile-width-constrained.
- **No backend changes.** Both `GET /me/progress` and `GET /collections/{id}/readiness` already exist and already share `ProgressReportService` ConceptHealth classification. Reuse both endpoints as-is from the frontend; do not add a new endpoint, aggregation field, or AI call.
- **The plan picker lists leaf/Subject plans only**, not Goal collections. Use `NoteCollectionSummary.childCount === 0` to filter `listCollections()` results for the picker (Goal collections have their own separate embedded readiness rollup on collection detail — see explicit out-of-scope note below). Note: `childCount === 0` is a proxy, not an exact "is-leaf" flag — there is no `type`/`isGoal` field on `NoteCollectionSummary`. Verified backend behavior: `NoteCollectionService.getReadiness` does not distinguish Goal vs. Subject collections; it reads `note_collection_items` for the given id, so a Goal collection id returns a zeroed `PlanReadinessResponse` (0 notes, 0 concepts), not a 404. This means the proxy's only failure mode is a freshly-created empty Goal (0 children) appearing in the picker and showing an empty/zero readiness state if selected — harmless, not a crash or wrong-data leak. Do not treat this as needing a backend fix; just use the `childCount === 0` filter as specified.

Anti-drift rules from AGENTS.md that this task must update, not just obey:
- `AGENTS.md` "Study Plan Readiness Rule" (~line 136-143) currently states: *"Plan readiness is allowed only on the dedicated owner-scoped route `/collections/[id]/readiness` backed by `GET /collections/{id}/readiness`."* This sentence is now stale by design — plan readiness moves to `/progress?collectionId={id}`, still backed by the same `GET /collections/{id}/readiness` endpoint (the backend route/behavior is unchanged; only the frontend page that renders it moves). Update this rule to describe the new frontend location while preserving every other constraint in that section verbatim: the 404/ownership resolution rule, "reuse `ProgressReportService` classification, do not invent thresholds/persist fields/call AI", the no-mastery rule for collection list/execution rows, the shared `ReadinessSummary` vocabulary rule, and the `PLAN_READINESS_VIEWED` analytics-on-load rule.
- Do not touch the separate "Study Plan Hierarchy Rule" (Goal readiness) section — that's explicitly out of scope (see below).

What is explicitly OUT of scope:
- The Goal-collection embedded readiness widget in `frontend/app/collections/[id]/collection-detail-page-client.tsx` (`GoalDetailView`, the `ReadinessSummary variant="compact"` block and the child-plan readiness cards). That is a different aggregation (Goal readiness derived from child readiness counts, per AGENTS.md "Study Plan Hierarchy Rule") rendered inline on collection detail, not the `/collections/{id}/readiness` sub-route. Do not modify it, do not fold it into `/progress`.
- No billing/quota/price/checkout changes. No new chart library or dependency — reuse the existing CSS progress-bar pattern and inline SVG ring already in `ReadinessSummary`.
- No changes to the Free/PLUS-PRO gate: the readiness signal (`% ready`, mastered/due/not-started counts) stays Free in both views; per-concept review timing (`daysSinceReview`, `lastCorrectAt`/`lastIncorrectAt`-derived timestamps) stays PLUS/PRO-gated in both views. Do not widen or narrow this gate while merging.

Prior implementation pattern to reuse:
- `frontend/components/readiness/readiness-summary.tsx` already exports `ReadinessSummary`, `ReadinessBar`, and the vocabulary helpers (`getReadinessStatusLabel`, `getReadinessBarTone`, `getReadinessAccentBorder`, `getReadinessTextColor`, `isReadinessNotStarted`). This is the single shared component/vocabulary source — it is already used correctly by `frontend/app/collections/[id]/readiness/readiness-page-client.tsx` and by the note-detail readiness card in `frontend/components/notes/private-note-detail-page-client.tsx`.

Replace `SubjectProgressCard` with `ReadinessBar`/`ReadinessSummary` reuse rather than hand-patching its strings.

## ERROR STATES

- Network/API error loading `getProgressReport()` in "All subjects" mode → existing inline error state (`Could not load your progress report. Try refreshing.`) — unchanged.
- Network/API error loading `getPlanReadiness(collectionId)` in plan-scoped mode → reuse the old readiness page's error card copy/retry button, not the cross-plan error copy.
- 404 from `getPlanReadiness` (deleted, not-owned, or malformed collection id) → "not found" state with a link to `/collections`, matching the deleted page's prior behavior exactly.
- Switching the picker while a request is in flight must not race: a stale response for a previously-selected collection must not overwrite state after the user has switched again (guard with a request-id ref or cancellation flag, same pattern already used in `getProgressReport`'s `cancelled` flag).
- No `@Transactional` or idempotency concerns — this is a read-only frontend consolidation with no backend writes.
