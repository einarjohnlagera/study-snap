## TASK

Fix the Study Plan Builder so a brand-new, empty collection can become a Goal (nested Subject plans), and give every plan detail page (Goal or leaf) one consistent "Build" entry point into the builder.

## GOAL

Today there is no way to create a Goal-shaped Study Plan (e.g. "CPALE Mastery" with child Subject plans) from scratch. Creating a new plan always yields a flat collection, and the Builder's "Add subject plan" control only renders once a collection already has children — a state nothing in the shipped UI can produce for a fresh collection. This blocks curators (and any user) from building the nested Goal structure the product already supports and displays elsewhere (readiness rollups, Goal detail, Goal adopt). This task removes that dead end and makes the builder entry point consistent everywhere.

## CONTEXT

Investigation already done, do not re-derive:

- `frontend/app/collections/[id]/builder/study-plan-builder-page-client.tsx` branches purely on `collection.childCount`: `refreshBuilder()` (~line 1100-1118) returns the leaf state immediately when `collectionResult.childCount === 0`, without ever calling `getCollectionGoal`. The render function (~line 1656) has the same gate: `if (collection.childCount === 0) { return <leaf JSX> }`.
- `setCollectionParent` (the call that nests a collection under another, turning the parent into a Goal) is invoked from exactly one place in the whole frontend: inside `handleAddSubject` (~line 1282-1309), which is only reachable via the `AddSubjectModal` rendered in the Goal-view JSX branch (~line 1898-1904). A collection with `childCount === 0` can never reach that button today.
- **This is confirmed to be a frontend-only gap, not a backend restriction.** `NoteCollectionService.validateParentCanAcceptChild` (backend, `NoteCollectionService.java` ~line 614-621) only requires the prospective parent to (a) be top-level (`parentCollectionId == null`) and (b) have zero items (`PARENT_WITH_NOTES_MESSAGE` if not). A freshly created collection satisfies both — there is no `isGoal` flag and no requirement that the parent already have children. Do not add a backend migration, flag, or new endpoint; the existing `PATCH /collections/{id}/parent` (`setCollectionParent` in `lib/api.ts`) already supports this.
- `handleAddSubject(title: string)` is already generic: it creates a child collection (`createCollection`) and nests it under `collectionId` (`setCollectionParent`), then calls `refreshBuilder()`. It does not depend on `goal` or `subjects` state being non-empty, and needs no changes — it can be called as-is from the leaf branch.
- The per-note "Add notes" flow (`handleAddLeafNotes`) already exists and is unchanged.
- Detail-page entry points today, confirmed by reading `frontend/app/collections/[id]/collection-detail-page-client.tsx`:
  - Goal hero actions (~line 1837-1845): one prominent `ResponsiveActionLink` labeled `"Build"` → `/collections/{id}/builder`, `action="edit"`, next to the "…" menu (Edit metadata / Delete).
  - Leaf hero actions (`PlanHeroCard`, ~line 1955-1963): only `"Check readiness"` → `/progress?collectionId=`, plus the same "…" menu. **No builder link at all** in the leaf hero.
  - Leaf detail's "Notes" card header (~line 2062-2076) has a separate, smaller `ResponsiveActionLink` labeled `"Edit"` → the same `/collections/{id}/builder` route. This is the only current way to reach the builder from a leaf plan's detail page.
- **Decision already made with the user**: consolidate to one consistent top-level "Build" button on every plan detail page (Goal and leaf alike). Remove the now-redundant Notes-card "Edit" link entirely. Leave the "…" menu's metadata-only "Edit" (opens `EditCollectionModal`) untouched on both Goal and leaf — that edits title/description, not structure, and is a separate concern.

What is explicitly OUT of scope:
- No new `isGoal` flag, no backend migration, no new endpoint.
- No change to the existing Goal-view "empty goal with zero children" state (`"No subject plans yet"` + `Add subject` button, shown when a collection already has `childCount > 0` at the top level but `goal.children` is empty — see `page.test.tsx` "shows an empty-goal state with add subject"). That is a different, already-working scenario (a Goal that lost its children) and must keep working unchanged.
- No change to `AddSubjectModal`, `AddNotesModal`, or any subject/leaf mutation handler logic — reuse them as-is.
- No change to the two-level nesting constraint (Goal → Subject only) or any other rule in AGENTS.md's "Study Plan Hierarchy Rule".

## REQUIRED CHANGES

Frontend only:

1. **`frontend/app/collections/[id]/builder/study-plan-builder-page-client.tsx` — tri-state empty builder.**
   In the leaf-view render branch (`collection.childCount === 0`, ~line 1656 onward), the current "No notes yet" empty state (~line 1702-1710) renders only when `leafItems.length === 0`, with a single "Add notes" CTA. Change this so that when `leafItems.length === 0` (i.e. the collection is genuinely undecided — no items and no children), the empty state offers **both** actions side by side: the existing "Add notes" button and a new "Add subject plan" button (reuse `labels.subjectSingular` for the label, matching the Goal branch's existing wording pattern, e.g. `Add ${labels.subjectSingular.toLowerCase()}`). The "Add subject plan" button opens the existing `AddSubjectModal` (`setAddSubjectOpen(true)`), which must now also be rendered inside this leaf-branch return (it currently is only rendered in the Goal branch, ~line 1898-1904) — reuse the same `addSubjectOpen` state and `handleAddSubject` handler already defined at the top of the component; do not duplicate them.
   Once `handleAddSubject` succeeds, its existing `refreshBuilder()` call refetches `getCollection`, which will now return `childCount > 0`, flipping the component to the Goal-view branch once `getCollectionGoal` resolves.
   **This transition has a real timing defect you must fix, not just wire through.** In `refreshBuilder` (~line 1100-1118), `setCollection(collectionResult)` fires immediately after the initial `Promise.all`, then `await getCollectionGoal(...)` and `await Promise.all(childDetails...)` run before `setGoal(goalResult)` fires — two separate `await` gaps, so React commits an intermediate render where `collection.childCount > 0` (already updated) but `goal` is still `null` (not yet set). The top-level guard at ~line 1643, `if (loadState === "error" || !collection || (collection.childCount > 0 && !goal))`, treats exactly that combination as a load failure and renders the "Could not load builder / Retry" error card — on the one action this feature exists to enable. This is specific to the leaf→Goal transition (an existing Goal's `goal` state is never null mid-refresh, since it retains its last-good value; only the from-`childCount:0` case starts from `goal === null`). Fix by treating this transient state as loading, not error — e.g. track that a refresh is in flight (or gate the guard so `collection.childCount > 0 && !goal` only counts as an error once `loadState !== "loading"`/no refresh is pending) so the transition shows a loading state, never the error card, until `goal` lands.
   Once the user has added at least one note instead (`leafItems.length > 0`), the "Add subject plan" option must no longer render — the collection is committed as a leaf per the backend's `PARENT_WITH_NOTES_MESSAGE` rule, and attempting to nest it would now fail server-side. Gate the dual-choice UI strictly on `leafItems.length === 0`, matching the existing empty-state condition already in the code.

2. **`frontend/app/collections/[id]/collection-detail-page-client.tsx` — consolidated Build entry point.**
   - Leaf hero actions (`PlanHeroCard` usage, ~line 1955-1963): add a `ResponsiveActionLink` to `/collections/{id}/builder`, `action="edit"`, `label="Build"`, `variant="outline"`, `size="sm"` — same shape as the Goal hero's existing Build link — placed before the existing "Check readiness" link in the actions row.

   - Do not touch the Goal hero's existing "Build" link, or either hero's "…" menu (Edit metadata / Delete) — those are unchanged.
