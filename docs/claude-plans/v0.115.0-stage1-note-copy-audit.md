## 0. Executive summary

The hazard in the brief is **real by mechanism and entirely unrealised in production**. It is also **already named in `ADR-001`** as a deliberately-deferred open item, which the brief did not state and which materially changes what this audit owes: this is not a discovery, it is a decision that was parked with a Backlog row.

Three findings change the recommendation away from both pre-recorded options:

1. **The learner has no lever at all.** On a copy carrying exactly one join row — which is **100% of the affected production population** — the personal `course_program` string is skipped by `update` (`NoteService.java:246-256`), and the Applicable Programs editor is curator-only (`NoteApplicableProgramsService.java:118`). Both representations are frozen. The brief's "never confirms or edits them" is too weak: the learner **cannot** confirm or edit them.
2. **Option C has no reachable trigger.** Its premise ("learner edits → learner values replace copied values") requires an edit event that the shadowing predicate makes unreachable on every affected note.
3. **Option D is refuted by the source population.** 608 of 1360 curated public notes carrying join rows have a **NULL** `course_program` string, and 551 carry **2+** rows. D would leave those copies with *no* program representation at all.

**Recommendation:** reject D, reject C as stated, and take a third option the ADR does not name — **clear inherited join rows at the publish transition** (`NoteService.updateVisibility:484`). It is one write path, changes no discovery SQL, is behaviourally inert on all 536 existing notes, and does not prevent anyone from publishing.

**Stated honestly:** this is structurally *D applied at publish rather than at copy*, so it inherits D's costs — but only on copies the learner **deliberately publishes** (0 to date, versus every copy under D), and at the moment classification becomes a public act. It also has a property D lacks: clearing the rows **un-shadows the learner's own Course / Program field**, which the client then renders and requires (`note-editor-form.tsx:427`, `private-note-detail-page-client.tsx:1647`). That is the mechanism that hands the learner the lever finding 1 says they do not have. Full cost analysis in **I.2.4**.

## G. Note copy architecture — full trace

### G.1 Copy entry points

| Entry point | Location | Join rows copied? | `copied_from_*` set? | `source_note_id` set? | Study Pack |
|---|---|---|---|---|---|
| `copyNote(id, owner)` | `NoteService.java:318` | **yes** | yes | yes | yes |
| `copyNote(id, owner, includeStudyPack=false)` | `NoteService.java:322` | **yes** | yes | yes | no |
| Owner **self-copy** (`isOwner` branch) | `NoteService.java:369-374` | **yes** | **no** (all nulled) | **yes** | **no** |
| `copyPublicNoteForSignup` | `NoteService.java:443` | **yes** (delegates to `copyNote:451`) | yes | yes | yes |
| Shared-note copy (live share) | same `copyNote`, gated `:327-331` | **yes** | yes | yes | yes |

**The single most important structural fact:** the join-row copy at `NoteService.java:397` sits **outside** the `if (isOwner) … else …` block that begins at `:369`. Every copy path — public copy, shared copy, signup copy, and owner self-copy alike — replaces the copy's join rows with the source's:

```java
noteCourseProgramRepository.replace(saved.getId(), noteCourseProgramRepository.findIdsByNoteId(source.getId()));
```

The `flush()` immediately above it (`:396`) is required because `replace` is raw JDBC and cannot see JPA's pending persistence context; the comment at `:393-395` records that omitting it makes `copyNote` throw on *"every curated note"* since slice 4.

**Owner self-copy differs only in provenance and generated content**, not in applicability: `copiedFromNoteId/UserId/Title/At` are nulled and `copiedFromPublic=false` (`:370-374`), and `copySourceStudyPack` is skipped (it runs only under `if (!isOwner)` at `:399-400`). Join rows still copy.

> **Doc-vs-code discrepancy (1).** `CLAUDE.md` states *"owner self-copies still copy only user-authored fields and exclude generated content."* Read as a description of Study Pack content this is true; read as a description of the copy it under-describes `:397`, which copies curated catalog applicability on the self-copy path too. Harmless today (a self-copy is same-owner, so a curator's self-copy legitimately keeps curator rows), but the sentence should not be relied on as a statement that self-copy carries no join rows.

### G.2 What is copied verbatim

`NoteService.java:357-367`:

- `title` (`:357`)
- `subject` → `resolveCanonicalSubjectForCopy` (`:358`, impl `:1772`) — normalized + canonicalized against the subject catalog
- `course_program` → `normalizeCourseProgramForCopy` (`:359`, impl `:1492`) — normalized + length-clamped, **value preserved**
- `domain_context` → **verbatim** (`:360`)
- `learner_level` → verbatim (`:361`)
- `tags`, `content`, `target_profile_type` (`:362-366`)
- `status = DRAFT`, `visibility = PRIVATE` (`:364-365`)
- `source_note_id = source.getId()` — **on every copy, including self-copy** (`:367`)

### G.3 The overlapping representations — exactly where they arise

A copied note carries **two** independent representations of "which program does this note belong to":

| # | Representation | Written at | Learner can edit? |
|---|---|---|---|
| **R1** | `notes.course_program` (free text) | `NoteService.java:359` | **No** when shadowed — `:246-256` |
| **R2** | `note_course_program` join rows | `NoteService.java:397` | **No, ever** — `NoteApplicableProgramsService.java:118` |

Both are populated by the same copy operation, from the same source note, with no relationship recorded between them and no way for the owner to reconcile them.

### G.4 Read semantics — which representation wins

`NoteCourseProgramShadowing.isShadowed(joinRowCount, domainContext)` (`util/NoteCourseProgramShadowing.java:8-24`):

```
discoveryIgnoresIt  = joinRowCount >= 1
generationIgnoresIt = domainContext != null || joinRowCount == 1
shadowed            = discoveryIgnoresIt && generationIgnoresIt
```

"Shadowed" means **`notes.course_program` cannot be read on any path** — it is dead data the owner still nominally owns.

**Applied at two places only:**
- `NoteApplicableProgramsService.java:48-51` — to tell the client the string is unreadable (`courseProgramShadowed` in the DTO).
- `NoteService.java:246-256` — to **skip writing** `course_program` on a learner update.

The `:249-255` comment explains the skip: writing `null` would discard a string a pre-slice-4 curated note carried into its copy, and falling through to `resolveRequestedCourseProgram` would stamp the *owner's profile program* onto the note, which `docs/features/notes.md` forbids on an edit.

**Discovery readers — all five enumerated** (the ADR claims five; this is the full set):

| # | Reader | Location | Shape |
|---|---|---|---|
| 1 | Public library course/program filter | `PublicLibraryRepositoryImpl.java:211-221` | `exists(join)` OR (`not exists(join)` AND string) |
| 2 | Public library free-text search | `PublicLibraryRepositoryImpl.java:262-274` | same shape |
| 3 | Private library course/program filter | `NoteLibraryRepositoryImpl.java:328-346` | same shape |
| 4 | Public legacy-value vocabulary | `NoteCourseProgramRepository.java` `FIND_LEGACY_VALUES_BY_VISIBILITY` | `NOT EXISTS` guard |
| 5 | Owner legacy-value vocabulary | `NoteCourseProgramRepository.java` `FIND_LEGACY_VALUES_BY_OWNER` | `NOT EXISTS` guard |

Plus two **name** sources with **no ownership or curator filter**: `FIND_NAMES_BY_VISIBILITY` (public chip vocabulary, consumed at `NoteService.java:1241`) and `FIND_NAMES_BY_OWNER_USER_ID` (`:1226`). And a **display** path: `PublicLibraryRepositoryImpl.java:60-70` aggregates `program_names` for `visibility='PUBLIC'` notes onto the public card — so a learner's public copy would *render* the curator's programs on its own public card.

**Generation reader:** `StudyPackGenerationContextResolver.java:137` returns the joined catalog name at **exactly one** row; `:36` throws `MultiProgramDomainContextRequiredException` at 2+ rows with a null Domain Context.

### G.5 The complete hazard chain, verified end to end

1. Learner copies a curated note → `copyNote:397` writes curator join rows onto a learner-owned note.
2. Copy is `PRIVATE` (`:365`) and status `DRAFT`/`GENERATED`.
3. With exactly one join row, `isShadowed(1, anything) = (1>=1) && (dc!=null || 1==1) = **true** unconditionally`. The string is frozen (`:246-256`); the join rows are unreachable (`NoteApplicableProgramsService:118`).
4. Learner flips to `PUBLIC` — `canManageVisibility = isEmailVerified || isPublic` (`private-note-detail-page-client.tsx:1036`), an ordinary action; backend `NoteService.updateVisibility:484` applies no applicability logic whatsoever.
5. Discovery reader #1 (`PublicLibraryRepositoryImpl:213`) now matches the note under the **curator's** program slug. Reader #2 matches it on the curator's program name in search. The public card displays the curator's program names.

**Curator classification has become learner publishing authority, on a note the curator never published, with the learner unable to alter or even contest it.**

## H. Copy precedence recommendation

### H.1 The proposed semantics

> copied source applicability INITIALIZES the learner Note; explicit learner applicability REPLACES it.

**Confirmed as the correct *principle*, and it is what the code already intends** — `copyNote:397` initializes, and the `update` comment at `:275-278` deliberately preserves rather than clears. The principle also correctly rules out unioning, which nothing in the code does today and which nothing should introduce.

**But as a *change proposal* it is currently unimplementable, because the "explicit learner applicability" event does not exist.**

### H.2 What the code can and cannot distinguish

**Can distinguish (structurally, no new column):**
- That a note is a copy — `copied_from_note_id` (non-owner copies) / `source_note_id` (all copies).
- That a join row on a **learner-owned** note is copy-inherited. This holds *by construction*, on four independent legs:
  - `create` never writes rows for a non-curator — `courseProgramIds = curator ? … : Set.of()` and `replace` is inside `if (curator)` (`NoteService.java:187, 206-208`).
  - `update` never touches rows for a non-curator (`:270-278`).
  - `replace` requires `isOwner && isCurator` (`NoteApplicableProgramsService.java:118`).
  - `V108` deleted the historically-derived rows, and *Curation authority* (ADR-001, ratified 2026-08-11) closed the admin-writes-on-others'-notes mechanism.
  - Production confirms it: 536/536 carry `copied_from_note_id`, 0 have no provenance.

**Cannot distinguish:**
- Whether the learner has ever *seen*, *confirmed* or *consented to* the inherited programs. There is no confirmation flag, and no `updated_at` on the join row that would separate "inherited" from "affirmed".
- Which of two representations the learner *intends*, because they can set neither.

### H.3 Option D — stop inheriting join rows on copy

**Verdict: reject — but on *scope*, not on the cost itself.** The recommended fix (section I) is structurally *D applied at the publish transition rather than at copy*, so it inherits D's costs on the subset of copies that get published. This audit therefore wins the comparison on population and consent, not by pretending the costs vanish. See I.2.4.

D is inert for the existing 536 (string agrees, one row, no DC). **But "inert" must not be generalised past them**, and the source-population query shows what D costs *every future copy*:

- **608 of 1360 (44.7%)** curated public notes carrying rows have a **NULL** `course_program`. `create` sets `entity.setCourseProgram(curator ? null : …)` (`NoteService.java:188`), so *every post-slice-4 curator note has a null string by construction*. Under D, copies of these carry **no program representation at all** — invisible to program-specific discovery in both the private and public library, and the next learner edit hits the residual `resolveRequestedCourseProgram` throw the ADR already names as a defect.
- **551 of 1360 (40.5%)** carry **2+** rows. A single free-text string **cannot represent them**.

D also invites an unstated companion decision — *copy the joined catalog name into the copy's string at copy time*. That is a **row→string** derivation. `V108`/*Representation authority* forbids **string→row** and is silent on the reverse, so it is a genuinely new decision rather than a covered one. Even granted, it cannot express the 551 multi-program notes, so D stays lossy for 40% of the source catalog.

**Why the publish-transition variant is materially better rather than merely later:** D pays these costs on **every copy** (4791 to date, 536 with rows), silently, at a moment the learner is not thinking about classification. The publish variant pays them only on copies the learner **deliberately publishes** (0 to date), at the exact moment classification becomes a public act, and on a surface where the learner is then *asked* for the value (I.2.4). Private copies — the overwhelming majority, and the shape where inherited rows are genuinely useful for the learner's own library filter and for generation — keep working untouched.

> **Doc-vs-code discrepancy (2).** `ADR-001`'s canonical-shapes table row 3 depicts *"Curated note copied by a learner — `notes.course_program`: as copied"*, implying a populated string. For post-slice-4 curated notes the string is **null** (`NoteService.java:188`), so "as copied" copies nothing. The table describes the V107-era shape (which is exactly why all 536 existing copies have a populated agreeing string — V107 backfilled a row *without* clearing the string) and does not describe copies made today.

### H.4 Option C — learner's own value clears the copied rows

**Verdict: reject as stated — its trigger is unreachable.**

The brief argues C's prior rejection reason (*cannot distinguish derived from inherited rows*) does not apply on a copy where every row is inherited by construction. **That argument verifies** — see H.2, and 536/536 carry provenance. The ADR's stated reason is genuinely inapplicable here.

**But C fails for a different and more decisive reason.** C needs a "learner sets their own value" event. On a one-row copy:

```
isShadowed(1, dc) = (1 >= 1) && (dc != null || 1 == 1) = true    // for ANY Domain Context
```

so `NoteService.java:253-255` **skips the write**. The learner's string cannot change. **100% of the affected population is one-row**, so C's trigger fires on **zero** notes.

C's trigger becomes reachable only at 2+ rows with a null Domain Context. Production has **0** such learner notes, and that shape *cannot generate a Study Pack at all* (`StudyPackGenerationContextResolver.java:36`). It is also unreachable from today's catalog: **0** curated public notes have 2+ rows and no Domain Context, so no copy can be born into that shape.

So C is not one amendment but **two**: un-shadow the field (amending the shadowing ruling) *and* clear on write (amending the learner-save-synchronization rejection). It should not be presented as a peer of D.

### H.5 Recommendation

**Take neither D nor C. Keep copy-initialization exactly as it is, and cut curator authority at the publish transition** (section I).

Rationale: the *private* copy carrying inherited rows is a **correct and useful** shape — it is how a copied note stays findable in the learner's own library under the program it actually belongs to (reader #3), and it is what makes generation work (`resolveCourseProgram` at one row). Nothing about the private case is broken. **The defect is exclusively at the publication boundary**, and it should be fixed there rather than by degrading the copy.

If the owner later wants genuine learner control, the honest sequencing is: **first** make the note's programs *visible and confirmable* to the learner, **then** decide precedence. Deciding precedence before the learner has any lever is deciding between two values the learner cannot set.

## I. Public-discovery integrity

### I.1 The hazard, precisely

**Visibility ≠ program-specific discovery**, and today the product conflates them for copies. Publishing is a *visibility* decision the learner takes; being shelved under `Civil Engineering` is a *classification* decision the **curator** took, on a **different note**, that rides along silently and cannot be contested by the person who owns the note or revoked by the person who authored the classification.

Three distinct consequences, all at `visibility='PUBLIC'`:
1. **Shelving** — reader #1 (`PublicLibraryRepositoryImpl:213`) matches the copy under the curator's program slug.
2. **Search** — reader #2 (`:262-274`) matches the curator's program name.
3. **Display** — the public card renders the curator's program names (`:60-70`).

Chip vocabulary is *not* meaningfully harmed: `FIND_NAMES_BY_VISIBILITY` has no ownership filter, but every inherited row is a catalog row the curator's own public note already publishes, so no new chip is minted.

### I.2 Recommended fix — clear inherited rows at the publish transition

**Smallest clean model:** when a learner-owned note transitions to `PUBLIC`, drop its inherited join rows; keep everything else.

**Seam:** `NoteService.updateVisibility:484`. It already computes exactly the predicate needed for analytics at `:494`:

```java
if (previousVisibility != NoteVisibility.PUBLIC && visibility == NoteVisibility.PUBLIC) { … }
```

**Why this is the smallest option:**
- **One write path.** `updateVisibility` is the only place a note becomes public (`setVisibility` appears at `:194` create-PRIVATE, `:365` copy-PRIVATE, `:491` here).
- **Zero discovery SQL changes.** Nothing in any of the five readers moves. Contrast the predicate route (below), which would need a matching `copied_from_note_id is null` clause added to *each* of the five — and the repo records that a previous fix of this class *"only the visibility-scoped half was guarded when C2 was fixed"*, i.e. this codebase has already shipped a partial sweep of exactly this set.
- **Behaviourally inert on the entire existing population.** All 536 are private, so nothing changes retroactively. Were any published, string == joined name would make shelving identical anyway.
- **Does not prevent publishing.** The learner publishes exactly as before; the note remains public and fully discoverable by title, subject, tags, content and search. It falls back to reader #1's string branch, so it is shelved under the *learner's own* string when they have one — which is learner-owned classification, the correct authority.
- **It is the honest product statement:** going public is the learner's act, so that is the moment curator authority ends.

**Guardrails this needs, stated rather than discovered later:**
- Restrict the clear to **learner-owned** notes (`!CuratorAuthoringPredicate.isCurator(owner)`). A curator publishing their own note must keep their authored rows — otherwise this destroys the entire curated catalog on the next publish.
- **Mirror hazard, named because `ADR-001` already warns about it in the *Curation authority* section:** public → private → public. Once cleared, the rows are gone permanently; a later un-publish does not restore them. This is *acceptable and arguably correct* (the learner has affirmatively published under their own classification), but it must be stated, and it is the reason not to implement this as a reversible "suppress" flag — a flag is a second representation, which is the class of problem this audit exists to reduce.
- **The 608-null-string case and the un-shadowing consequence** are the fix's one real cost. Both are analysed in **I.2.4**, which also names the companion server-side fix this owes.

### I.2.4 The un-shadowing consequence — the one real cost, and why it is a feature

**This must be stated because it is the same cost that refutes D.** Clearing the rows takes `joinRowCount` to 0, so the shadowing predicate flips:

```
before publish:  isShadowed(1, null) = (1>=1) && (null!=null || 1==1) = true   → update SKIPS the string (:253-255)
after  clear:    isShadowed(0, dc)   = (0>=1) && …                    = false  → update WRITES the string (:254)
```

So the *next* metadata save after publishing calls `resolveRequestedCourseProgram(request.courseProgramText(), owner)` (`NoteService.java:1444`), whose null branch (`:1450-1453`) either **stamps the owner's profile program** onto a now-public note — which the comment at `:249-255` says `docs/features/notes.md` forbids on an edit — or **throws `CourseProgramSelectionRequiredException`**, blocking an unrelated title edit.

**Verified against the client, and the outcome is benign on the main path.** When `courseProgramShadowed` is `false`:
- the Course / Program field **renders** — `note-editor-form.tsx:427` (`showAuthoringMetadataFields || !courseProgramShadowed`);
- the save is **client-blocked while it is empty** — `private-note-detail-page-client.tsx:1647`, which pushes `"Course / Program(s)"` into `missing` when `courseProgramShadowed === false && !metadataDraft.courseProgram.trim()`.

So on Note Detail the learner is *asked for the value and cannot save without it*. `courseProgramText` arrives non-null, `:1446-1448` returns it, and neither the stamp nor the throw fires.

**This inverts the ADR's own concern in a way worth stating plainly.** *"No learner-facing Applicable Programs UI"* records that **requiring a value nothing can read** is the defect it exists to close. After the clear the string is no longer unreadable — it is the note's **only** representation — so requiring it is now **correct**. The un-shadowing is not collateral damage: it is precisely the mechanism that converts *"the learner has no lever"* (finding 1) into *"the learner states their own classification at the moment they publish."* **That is the authority transfer this fix exists to make.**

**Residual, owed as a companion fix rather than hidden:** the client guard is client-side only. Any PUT path that omits `courseProgramText` on an un-shadowed note still reaches `:1450-1453`. `ADR-001` already names this same residual throw on the AI-suggestion surface as a live defect. It should be closed server-side — on a learner edit where the stored string is non-null and the request omits the field, **retain the stored value** rather than re-resolving from the profile.

**The null-string subset — decision owed, and I recommend the stricter branch.** For a copy of one of the 608 null-string curated notes, clearing leaves *no* representation until the learner next edits. Two options:

- **(i) Clear rows, leave the string as-is (null stays null).** The note is public and fully findable by title, subject, tags, content and search, but appears under **no program chip** until the learner states one. **Recommended.**
- **(ii) Clear rows, backfill the string from the joined catalog name when null.** Discovery is unchanged and the value becomes learner-editable.

**(ii) is rejected.** It re-launders the curator's classification into learner-owned public-discovery authority through a different column, without the learner ever stating anything — which is the hazard this section exists to close, not a fix for it. It is also the row→string derivation `V108` does not cover, and it cannot round-trip the 551 multi-program notes through one string. **(i) is the honest reading of the governing constraint** — *a public note with unconfirmed copied applicability may legitimately remain public without being shelved under those programs.* The gap it leaves is closed by the learner's next edit, and optionally by surfacing the one field at publish time — **one field, not a wizard.**

### I.2.5 Transaction boundary

`NoteService` is class-level `@Transactional` (`:110`), so `updateVisibility` (`:484`) already runs in a transaction and an added row delete would be atomic with the visibility write. Note the seam that bit this repo at `:396`: `NoteCourseProgramRepository` is **raw `JdbcTemplate`** while the visibility change goes through **JPA**. `JdbcTemplate` joins the same transaction-bound connection, so no second connection is involved — but the JDBC delete does **not** see JPA's pending persistence context. Here that is harmless (the delete targets pre-existing child rows and the parent already exists, so there is no FK-ordering hazard of the kind `:396`'s `flush()` guards). **Confirm ordering at implementation time rather than assuming it.**

### I.3 Alternative considered and not recommended

**Predicate route** — add `and n.copied_from_note_id is null` to the `exists(join)` branch. **Corrected count:** only the *public* surface is harmful, so this is **three** changes, not five — readers #1 (`PublicLibraryRepositoryImpl:211-221`), #2 (`:262-274`) and the public card aggregate (`:60-70`). Reader #3 is the private library, where inherited rows are wanted; #4/#5 are vocabulary sources already `NOT EXISTS`-guarded.

Still rejected, on narrower grounds: three SQL readers versus one write path, every future public reader becomes a place to forget the clause, and the C2 precedent recorded in `NoteCourseProgramRepository`'s own Javadoc — *"only the visibility-scoped half was guarded when C2 was fixed"* — is this codebase having already shipped a partial sweep of exactly this reader set. It also leaves the contradictory state in the database permanently rather than resolving it, and would suppress rows on curator-owned copies too.

### I.4 Backward compatibility

**No migration is needed and none should be written.** All 536 affected notes are private, so the publish-transition fix reaches them naturally if and when their owners publish. Mass-cleaning historical notes is explicitly forbidden by the anti-drift list and is unnecessary here: the population that would be cleaned is exactly the population that is not yet harmful.

## 19. Domain Context on copy

**Copied?** Yes, verbatim and unconditionally — `NoteService.java:360`, `copy.setDomainContext(source.getDomainContext())`, outside the owner/non-owner branch.

**Learner-editable?** **Yes** — and this is the sharpest asymmetry in the whole area. In `update`, `entity.setDomainContext(domainContext)` (`NoteService.java:262`) sits **outside** the `if (!curator)` guard that constrains `course_program`. So on a shadowed copy, **Domain Context is the learner's only functioning metadata lever**: the string is frozen (`:246-256`) and the programs editor is curator-only (`NoteApplicableProgramsService:118`).

**How Automatic resolves on a copy.** `StudyPackGenerationContextResolver.effectiveAuthoringDomain` → Domain Context label when set; otherwise `resolveCourseProgram` (`:137`), which returns the joined catalog name at **exactly one** row and falls through to the personal string at 0 or 2+.

**Production:** all 536 copies carry **no** Domain Context and **exactly one** row → all 536 currently resolve their authoring domain through the **joined catalog name**. Under the recommended publish-transition fix, a published copy would fall through to its string — which is **identical** on all 536, so generation output is unchanged. Under option D it would likewise be identical for these, but *null* for the 608-null-string class, which is one more count against D.

**Multi-program learner copies.** None exist (0 learner notes with 2+ rows), and none can currently be created: all 551 multi-row curated notes carry a Domain Context, which copies with them. **The latent path is real though:** a curator authoring a 2+-row note *without* a Domain Context creates a note whose copies cannot generate at all — `StudyPackGenerationContextResolver:36` throws `MultiProgramDomainContextRequiredException`, and the learner's only escape is to set a Domain Context themselves, which is the one lever they do have. Worth a guard on the curator side, but it is **not** this workstream's to fix and touches taxonomy surfaces a sibling agent owns.

**Does source-derived Domain Context provenance matter?** **No, and it should not be introduced.** Domain Context is single-valued, learner-editable, and directly visible on the note surface — so learner-visible metadata and generation behaviour already agree, which is the rule to preserve. It has none of the three properties that make Applicable Programs hazardous: it is not multi-valued, not curator-locked, and **not read by any public-discovery filter** (it appears in none of the five readers). Adding provenance to it would be schema weight against a non-problem, and would risk making it multi-valued in effect — explicitly on the anti-drift list.

## O (note-copy slice). Minimum durable provenance

**Recommendation: add nothing. No `source` column on `note_course_program`, no confirmation flag.**

Three semantics must stay **separate**, and only the first two are this workstream's:

| Semantic | Question | Mechanism | Status |
|---|---|---|---|
| **Note ORIGIN** | Where did this note come from? | `copied_from_note_id` / `copied_from_user_id` / `copied_from_title` / `copied_at` (`NoteService.java:376-380`); `source_note_id` (`:367`, set on **all** copies incl. self-copy) | **Exists, sufficient.** Display-only; asserts no ongoing authority. |
| **COPIED-APPLICABILITY** | Is this join row a copied default or a learner-confirmed value? | **Derivable, no column needed** — on a learner-owned note every join row is copy-inherited by construction (H.2, four legs + 536/536 production confirmation) | **Sufficient.** |
| **PUBLIC-CLASSIFICATION authority** | Who decided this note appears under this program shelf? | Under the recommendation: **the act of publishing**. Rows are cleared at the transition, so a public learner note's classification is always its own string. | **Resolved by the fix, not by provenance.** |

The `source` column `ADR-001` rejected stays rejected, and its rejection is now *better* justified than when it was made: the reason given (*cannot distinguish derived from inherited*) has been superseded by `V108` + *Curation authority*, which **eliminated the derived class** rather than merely detecting it. Provenance is unnecessary because the ambiguity no longer exists.

**One caveat for completeness:** a curator's own **self-copy** inherits rows with `copied_from_note_id` NULL (`:397` sits outside the `isOwner` branch, `:370` nulls the field). That is a curator-owned note, outside this population, and it is correct there — but any future code keying on `copied_from_note_id` to mean "has inherited rows" must not be applied to curator-owned notes.

**Explicitly not proposed:** a universal inheritance framework. Plan-adoption provenance (sibling agent) legitimately needs *stronger, ongoing* source identity than note copy does; note copy needs the opposite — a clean, terminating handoff. Forcing them into one mechanism would import ongoing-sync semantics into a model whose governing principle is that **the copy is independent**.

## Final Questions

**Q4 — Does learner Note copy currently have contradictory applicability representations?**
**Yes, structurally — but they are in *agreement* on 100% of the production population, not in conflict.** Every copy carries `notes.course_program` (`:359`) *and* `note_course_program` rows (`:397`), with join rows winning discovery and generation, and the string frozen. All 536 affected notes have string == joined catalog name and 0 conflicts, so the contradiction is latent rather than active. What *is* actively wrong today is not divergence but **unreachability**: the owner can edit neither representation.

**Q5 — Is "learner explicit value replaces copied applicability" the cleanest semantics?**
**As a principle, yes** — it correctly forbids unioning and correctly refuses permanent inheritance. **As an implementable change today, no**, because the shadowing predicate leaves no reachable "explicit learner value" event on any affected note. It should be adopted as the stated doctrine and revisited only if a learner-facing applicability control is ever built.

**Q6 — How should learner-published copies establish program-specific discovery authority?**
**By publishing, and then by stating their own program.** Clear inherited join rows at the `PRIVATE → PUBLIC` transition for learner-owned notes (`NoteService.updateVisibility:484`), so a public learner note is shelved by its own string or by nothing. Private copies keep inherited rows — that is where they are useful and harmless. Clearing also un-shadows the learner's own field, so the next edit *asks them* for the value (I.2.4) — authority is transferred rather than merely revoked. A null-string copy stays public and unshelved until they answer, which is the intended semantics. This preserves `NoteVisibility` as `PRIVATE | PUBLIC` (no third value; `AccountPurgeService.java:224` deletes only `PRIVATE`, so a third value would survive account deletion — verified), keeps publishing unrestricted, and needs no wizard.
