## The release: 5 items, in this order

1. **LIVE DEFECT — shared quizzes silently mis-grade MULTI_SELECT.** `PublicQuizItem`
   (`dto/PublicQuizItem.java:5-9`) carries only `question, choices, concept` — dropping `questionFormat`
   and `correctIndices` — and `getSharedQuizResults` (`QuizShareLinkService:135-137`) grades
   `answer == correctIndex`, which for MULTI_SELECT resolves to `correctIndices.getFirst()`. On correct
   answers `[0,2]`, **picking 2 scores zero.** The prompt instructs 1–2 MULTI_SELECT per quiz, so this
   is live in every shared quiz. All 10 `QuizShareLinkServiceTest` tests miss it. **Do this first — a
   combined quiz multiplies the exposure.**
2. **LIVE DEFECT — a PLUS/PRO supporter picks 30 questions and silently gets 10.**
   `resolveQuestionCount:351-363` returns the default for any `profileType != TEACHER`, ignoring the
   request, while the modal offers 10/20/30 with a lock badge only for FREE.
3. **LIVE FALSEHOOD — the product advertises this feature to people who can't use it.** A guidance tip
   (`private-note-detail-page-client.tsx:3249-3252`, `tipId="teacher-generate-quiz-multi-note"`, rendered
   **unconditionally**) tells learners to select multiple notes in the library; that CTA is TEACHER-gated.
4. **Combined quiz**, snapshotted into a NEW table.
5. **Supporter-reachable multi-note picker** and a share surface not routed under `/notes/[id]`.

## Decisions taken — do NOT re-derive

- **STORAGE: snapshot into a NEW table** (owner). `generated_quizzes` and its unique index stay
  untouched. **Refs REJECTED**: regenerating a source note would mutate a live shared quiz, and
  `getSharedQuizResults`' exact `answers.size() != questions.size()` check (`:128-130`) then **400s a
  recipient mid-quiz**. **Nullable `note_id` REJECTED**: `NoteService.mapToResponse:1529` is an
  owner-unscoped `findByNoteId` returning `Optional` — a second row throws on **every** note-detail load.
- **The migration is purely additive.** `CREATE TABLE` only. No backfill, no data copied from
  `generated_quizzes`, no downtime. Existing quizzes are untouched and keep working.
- **Do NOT generate fresh questions across N notes.** Assemble from per-note quizzes that already exist.
  Generating would fire `incrementChallengeQuizGeneration` N times against one
  `assertQuizCreditAvailable` check — a quota-semantics change, and it would also make combining slow.
  Combining as designed is a DB read + copy, effectively instant.
- **Item 2 is NOT a licence to raise the question cap.** The defect is the SILENT DISCARD. Honour the cap
  or withdraw the choice; raising it is an untaken pricing decision.
- **Tier: ONE SCOPED COLD AGENT**, framed as falsification. Re-evaluated after the amendment and it holds
  — the table is additive, taking a shared quiz creates no session and writes no `ConceptHealth`
  (verified, grep 0 in both services), and items 1–3 are correctness fixes. **Escalate only if** the
  combined quiz ends up generating fresh across N notes.
- **Routing: CODEX** for items 4–5. Items 1–3 are small enough inline. Re-run the routing test if scope
  grows again.

## Claims that were WRONG and are now corrected — do not resurrect

- **Audit §15 said slice 6 forces the session-anchoring migration. FALSE.** `GeneratedQuizService` and
  `QuizShareLinkService` reference `quick_review_sessions` **zero times**. Corrected in the audit doc
  (PR #1247). **The session-anchoring migration now has NO forcing slice**, so the plan/note session
  collision stays a named Known limitation with no scheduled fix — a decision owed, not an oversight.
- **`collection-exam.ts` and the "Challenge multi-note picker" are NOT reusable.** The first is 54 lines
  of collection-scoped helpers with no UI; the second is inline JSX selecting `studyPackId`, not `noteId`.
  `/library/exam-builder` does the right selection but is TEACHER-gated and DOCX-only — it is the MODEL,
  not the artifact. The library's `selectionMode` multi-select IS ungated and reusable.
- **`note_id NOT NULL` was never THE blocker.** `exportCombinedDocx` (`GeneratedQuizService:265-321`)
  already assembles a combined quiz over N notes from refs, with no schema change.

## Also found, owed a decision rather than a default

- `notes(id) ON DELETE CASCADE` + `quiz_share_links.generated_quiz_id ON DELETE CASCADE` (`V65:3`) mean
  deleting ONE source note today destroys a whole quiz and its live share link, silently. The snapshot
  design removes this for combined quizzes; it stays true for single-note ones.
- A 6-note combined quiz costs SIX Study Pack generations + SIX quiz generations before combining
  (`openGenerateQuizModal:1843-1855` auto-triggers Study Pack generation). Pre-existing, but state it.
- With snapshot, regenerating a source note does NOT refresh a combined quiz. Default: leave it, record
  as a Known limitation. Owner has not ruled.

## Lessons this session paid for, in order of cost

1. **A negative assertion must have a REACHABLE subject.** Four vacuous assertions found, one written
   *while hunting that exact class*. A `never()` whose subject is never stubbed passes regardless.
2. **Write the guard at the LAYER THE DEFECT LIVES AT.** A card-level test cannot catch a page-level bug;
   that mutation survived.
3. **A test can survive its own mutation** if the fixture cannot discriminate. Fixing a defect without
   pinning it lets it regress identically — that happened with the leaf CTA.
4. **Verify "X already does Y" against code BEFORE it reaches a prompt.** Three of four claims in this
   release's kickoff were wrong; §15 had been wrong for four releases.
5. **A wrong correction is worse than the wrong number** — it arrives with the authority of a fix. One
   was written and discarded only because the row was opened first.
6. **The staleness check should extend to the PLAN DOCUMENTS a row cites**, not just the row. §15 was the
   biggest miss yet and was never in the Backlog table.
7. Call `advisor()` **before** writing any Codex prompt, and again on the diff.
