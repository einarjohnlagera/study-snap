## ⚠️ Four collisions with repository reality

Each was verified against code today. Three change the work; one changes copy that would otherwise
ship wrong.

### 1. ⚠️ BLOCKER — Section grouping (B7) is impossible from the current payload, and "Section" is not what the spec assumes

B7 asks for `Subject Plan → Section → Note`, and forbids inferring Sections from titles.

**Subject Plan grouping is fine.** `ReviewSetUpdateChange` carries `sourcePlanId` (a UUID) and
`subjectTitle` — real, durable placement identity.

**Section grouping cannot be done at all**, for two independent reasons:

- **There is no Section field in the update payload.** `ReviewSetUpdateChange` is
  `(type, sourcePlanId, sourceNoteId, subjectTitle, noteTitle, previousValue, currentValue, applied)`.
  No section, and nothing to derive one from.
- **A "Section" is not an entity — it is a string label on the collection item.**
  `NoteCollectionItemEntity.label` (`:31`) holds it, and the builder groups by string equality after
  canonicalisation (`study-plan-builder-page-client.tsx:133-180`, `buildLeafSections`). Sections have
  no id, no row, and no existence apart from matching text on items.

**This is not a title-based grouping trap.** `label` is a genuinely *stored, curator-authored*
field — distinct from the note title — so grouping by it is legitimate provenance, not inference.
The spec's prohibition is on inferring sections from *note titles*, which this would not be.

**Smallest safe extension, and it is genuinely small:** add one nullable `sourceSectionLabel` to
`ReviewSetUpdateChange`, populated from `sourceItem.getLabel()`. **That variable is already in scope
at the `ADDED_NOTE` construction site** (`NoteCollectionService.java:2266-2269`), so this costs **no
extra query, no join, and no N+1** — it is one field passed from an object already loaded.

**This is the one genuine owner decision in the release.** Three options:

| Option | Cost | Consequence |
|---|---|---|
| **A. Ship Subject Plan grouping only** | Frontend-only, tier stays cheap | Meets B7's mandatory half; "Section only when trustworthy provenance exists" is satisfied by *it does not exist yet* |
| **B. Add `sourceSectionLabel`** (recommended if Sections matter) | ~1 DTO field + 1 line in the service + response-shape test | Full B7 hierarchy; **makes this a backend release**, which moves routing and verification tier |
| **C. Defer Sections to a follow-up** | Zero | Clean, and B7 explicitly tolerates unsectioned grouping |

**My recommendation: A now, B as a fast follow** — because B7's own fallback clause (*"group by
Section only when trustworthy Section provenance exists"*, *"unsectioned Notes must remain valid"*)
is already satisfied by option A, and keeping this release frontend-only is worth more than one
level of hierarchy.

### 2. ⚠️ `Add N new topics` will print the wrong N if taken from `additionsAvailable`

B2/B4 specify the count in the primary action. The obvious source is wrong:

```java
// NoteCollectionService.java:3523-3529
private int additionsAvailable() {
    return (int) changes.stream()
            .filter(change -> "ADDED_NOTE".equals(change.type())
                    || "ADDED_SUBJECT_PLAN".equals(change.type()))   // ← counts Subject Plans as topics
            .count();
}
```

A Subject Plan is **not a topic**. On the owner's own example shape — *84 new topics across 6
subjects* — if those 6 subjects are newly added plans, `additionsAvailable` returns **90** while the
learner receives 84 topics. The button would promise six topics that do not exist.

**Fix is frontend-only and must be explicit:** count `ADDED_NOTE` for the topic count, and count
distinct `sourcePlanId` for the *"across N subjects"* phrase. **Do not change
`additionsAvailable`** — it correctly gates *"is there anything to apply"* (`:2676`) and is used as
a boolean threshold; repurposing it as a display count would break that gate.

**Guard this with a named test:** an update carrying both `ADDED_NOTE` and `ADDED_SUBJECT_PLAN`
whose button count equals the `ADDED_NOTE` count alone. Without it the defect is invisible — both
numbers are plausible.

### 3. ✅ A6 timestamps are free — the field is already there

`NotificationResponse` carries `createdAt` as an `OffsetDateTime`, alongside `readAt` and
`dismissedAt`. **A6's conditional resolves to yes, with no backend work.** Timestamps are in scope.

### 4. ⚠️ The `upstream` sweep (B10) reaches further than the panel

Every learner-facing string is in one function, `sourceUpdateChangeText`
(`collection-detail-page-client.tsx:628-648`) — four of its seven branches say *upstream*. But the
word also appears in the section heading *"Changed upstream — no action taken"* (`:790`), and
`docs/features/collections.md:932` describes the flow using *Apply additions* by name.

**This is the repo's own surface-sweep rule** — a file that *describes* a feature is never in the
diff when the feature changes. The sweep must cover the panel, the headings, the feature doc, and
`frontend/app/collections/[id]/page.test.tsx:736,758`, which pin `"Apply additions"` by exact string.

## ⚠️ Production reality: the two workstreams are ONE journey

Read 2026-09-11 via Render MCP (read-only). This is the most consequential thing in this plan and it
was not visible from code.

**All 42 notifications are a single type, `REVIEW_SET_UPDATE`, created in one batch on 2026-09-10.**

| Property | Value |
|---|---|
| Distinct types | **1** — `REVIEW_SET_UPDATE` |
| With a CTA | **42 of 42** |
| Unread | **41 of 42** |
| Ever dismissed | **0** |
| Max title / body length | **32 / 70 characters** |
| Created | all on **2026-09-10**, one day old |

Every row is identical except the collection id:

> **This Review Set has been updated**
> Open your Review Set to review and apply the latest published changes.
> CTA: **View Review Set** → `/collections/{id}`

### What this changes

**1. ⚠️ The A5 bug fires on 100% of the live notification population.** Every notification in
production is one hop into workstream 2 — notification → CTA → Review Set page → update panel — and
the panel-does-not-close defect sits on exactly that hop. It is not a polish item; it is in the path
of every learner the current announcement reaches. **This should be the first thing fixed and it is
the cheapest thing in the release.**

**2. The CTA label A2 names for removal is the real one.** The spec says remove the redundant
*"View Review Set"*; production confirms that is verbatim the `cta_label` on all 42 rows. Removing
the visible CTA therefore loses no information the card body does not already carry — the title
already says *"This Review Set has been updated."*

**3. ⚠️ A3's population is currently ZERO.** There is no CTA-less notification in production, so the
informational path is entirely speculative today. Build it for correctness — the code has an
`ANNOUNCEMENT` type and the suite already covers it (`renders an announcement row but never lets it
reach the badge`, `:82`) — but **do not let A3 shape the card design**, and do not treat its absence
from production as evidence it works.

**4. Part C must use synthetic data, not production data.** Real content is short — 32-character
titles, 70-character bodies — so production will never exercise the long-title and wrapping cases
Part C requires. **Testing the card against real notifications would silently skip the states most
likely to break.**

**5. Do NOT over-read the zero dismissals.** The entire population is one day old and 41 of 42 are
unread, so nobody has engaged with anything yet. This is not evidence that dismiss is unwanted or
undiscoverable, and A4's decision to keep it should not be revisited on this number.

**6. The announcement is mid-flight.** 41 unread of 42 means almost nobody has opened one yet — so
fixes shipped now still reach most of the intended audience, and a regression now lands on the same
population.

### B5 resolved — the rename is clear

The copy check returned **zero rows**: no notification title, body, or CTA label anywhere in
production contains *"Apply additions"*, *"upstream"*, or *"addition"*. **Nothing freezes the label
and there is no mismatch to document.** The one adjacent note: the delivered body frames the action
as *"review and apply the latest published changes"*, which stays accurate under the new
*Add N new topics* wording.

## Workstream 2 — Review Set update experience

One panel, one consumer: `collection-detail-page-client.tsx:763-807`.

**B1 — partition by meaning.** Today it is a negative filter (`:753-758`): additions, and
*everything else*. That is what files `SKIPPED_NOT_PUBLIC` — *"is no longer public and will be
skipped"* (`:645`) — under the heading **"Changed upstream — no action taken"**, which tells the
learner the section does not affect them while one of its row types decides what they receive. This
is a correctness bug in the copy, not polish. Replace with an explicit map over all seven known
types: `ADDED_NOTE`, `ADDED_SUBJECT_PLAN`, `RENAMED`, `REORDERED`, `RETIRED`, `MOVED`,
`SKIPPED_NOT_PUBLIC`, with an explicit conservative branch for anything unknown.

**B9 — aggregate the fan-out.** Three types emit one row per note, and any one alone produces the
wall:

| Type | Site | Fan-out |
|---|---|---|
| `REORDERED` | `:2358-2365` | one row per note whose position shifted — moving one note to the top of a 79-note plan shifts every note below it |
| `RETIRED` | `:2374`, `:2397` | one row per adopted note no longer in the source |
| `MOVED` | `:2374`, `:2397` | same shape, for notes that relocated |

**I deliberately do not claim which produced the owner's screenshot.** My first read said
`REORDERED`; the screenshot says *"retired upstream"*, pointing at `RETIRED`. Both have identical
fan-out shape, so aggregating generically — as B9 requires — is correct precisely *because* it does
not depend on being right about which dominates, now or next month.

**B2/B3/B13 — compact main page, two paths.** No cap is needed once the wall is aggregated and the
detail surface exists. The server confirms nothing bounds the payload today: `addChange`
(`:2624-2632`) dedupes on `type:sourcePlanId:sourceNoteId` and never caps, and
`ReviewSetUpdateResponse` carries a bare `List` with no page or cursor.

**B12 is already how the code behaves, and the release must not disturb it.** Two invariants in
`docs/features/collections.md` are load-bearing and worth restating because a UI change is exactly
what would break them:

- *"Applying acknowledges only what it applied"* — a pass re-baselines source facts only for plans
  that actually received an addition. Acknowledging every matched plan once meant a learner pressing
  the button for three notes silently accepted an unrelated rename as their new baseline,
  **unrecoverably**, because the previous value was overwritten.
- *"Which plans are examined comes from the learner's own structure, never the source's shape."*

**Nothing in this release may touch either.** The detail surface is presentation over an existing
payload.

## ⚠️ Release size, routing, and verification tier

**This is the part I have to flag rather than quietly absorb.** The repo's own rule: *"When asked to
fold more items, say what it does to the verification tier."*

The first brief was three items on two surfaces, and I sized it at **one `advisor()` call**. The
tightened spec is **two workstreams with roughly fifteen sub-items**, including a new detail surface,
a re-partitioned data model, a copy sweep, and a tap-target change across an existing 20-test suite.

`CLAUDE.md` is explicit that verification scales worse than linearly with items shipped, and that
folding is what forced the heaviest option in `v0.93.0`.

**Revised tier:**

| | First brief | Tightened spec |
|---|---|---|
| Routing | Inline for 2 of 3 items | **Codex for both workstreams** — each exceeds >100 LOC and the tiebreaker (anti-drift rules applied across files) fires |
| Pre-signoff | One `advisor()` | **One scoped cold agent, falsification-framed — minimum.** Rises to the **full three-agent test if option B is taken**, because that makes it a backend release touching adopted learner content |

**Two concrete triggers already fire for the cold agent**, independent of size: two PRs will touch
the same shared surface (the update panel's classification and its detail surface), and the release
changes what a user-facing claim *means* — which the repo has been bitten by three releases running.

**The cheapest way to hold the tier down is option A** (no backend change). That is a second,
independent reason to prefer it.

**Also required at signoff:** `docs/features/collections.md` must be re-read against final code, not
against the PR that last edited it — and **no Backlog row exists for either surface**, so the
signoff owes *new* rows rather than closures. Unlike the last four releases there is nothing stale
here to re-litigate.
