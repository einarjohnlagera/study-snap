Written 2026-11-10 by the Claude Code release session. **This is a plan for Product UX and the owner to approve, not an approval and not a recommendation to deploy.** Every threshold below is stated before the post-deploy evidence exists, on purpose (the checkpoint convention): a result read later may not move them. ## 1. What this deploy changes (verified 2026-11-10 against `origin/releases/v0.180.0` at `e93e56d3`)

- **The deploy is ONE merge: the release PR from `releases/v0.180.0` into `main`.** It touches two platforms:
  1. **Vercel production rebuilds** from the merge commit. This is the real change: 11 non-test frontend files (`git diff --name-only origin/main..origin/releases/v0.180.0 -- frontend`: the two profile routes and their two `error.tsx`, `lib/server-public-profiles.ts`, `lib/catalog-cache.ts`, `lib/public-profile-metadata.ts`, `components/public/public-profile-error-state.tsx`, the exam hub page and its unavailable component, and a comment in `app/public/library/[subject]/page.tsx`).
  2. **Render will redeploy unchanged backend code unless `[skip render]` works.** The only `backend/` change is `backend/pom.xml` (version 0.180.0): `git diff --stat origin/main..origin/releases/v0.180.0 -- backend` shows exactly that one line. **Treat a Render restart as a deploy** (section 3 and section 5 apply to it). Both earlier redeploys of unchanged code (`dep-dbpc9dgae00c73e5tisg`, `dep-dbpei55g1s2s73cb6o7g`) were followed by clean one-hour reads, but `CLAUDE.md` records that every deploy since 2026-10-25 except `v0.178.0`'s was followed by a Postgres signal-9 kill (Stage A has since passed its 72 h read), so this is not assumed safe. **A Vercel rollback does nothing about a kill caused by a Render restart.**
- **Behaviour changes (frontend only):**
  1. Creator and profile server reads leave the 300 s Next data cache for a separately bounded `profile` partition of the in-process hard-TTL cache: 120 s maximum, single flight, 15 s failure backoff, 15 s deadline, `ok` and `private` cached, `not_found` never cached, no stale value after expiry or failure, 512-key bound; both routes `force-dynamic`. **This closes the recorded privacy defect (a withdrawn note, an edited bio or a switched-to-private profile lingering up to 5 minutes).**
  2. A route-level `error.tsx` on both routes and a static `Profile temporarily unavailable | NoteLib` `noindex` head when the read fails. The HTTP status of a failed page stays 200; no crawler-visible error handling is claimed.
  3. The exam hub keeps its notes when only its review-sets request fails, and logs `EXAM_HUB_REVIEW_SETS_UNAVAILABLE reason=<error name>`.
  4. `.` and `..` usernames return not-found without a backend request.
- **Not changing:** the API, any migration, any prompt, pricing, quota or entitlement, robots or `noindex` rules, the other `revalidate: 300` fetches (listed in `RELEASES.md` "Not in this release").
- **Deploy-order statement (the API-form rule):** no API form, parameter, header or response shape changes. There is no ordering hazard between Vercel and Render in either direction, and a skipped Render deploy leaves a backend that is functionally identical.

## 4. Pre-T0 baselines, recorded now so a post-deploy number has something to be compared with

Re-read the same statements at T0 minus 1 and use deltas.

- **There is NO clean per-path baseline for creator and profile reads, and none can be built before the deploy.** Render keeps no request logs for the backend service (the log label `type` has only `app` and `build` for 2026-11-10), the `http_request_count` metric cannot filter by these paths (a wildcard path returned no data), and `PUBLIC_API_DIAGNOSTICS` groups paths as `listing`, `discovery-sections`, `facets`, `note-detail`, `collections`, `other-public`, so profile requests are not attributed. **The nearest statement is shared:** `select ue1_0.… from users ue1_0 where upper(ue1_0.username)=upper($1)` is `findByUsernameIgnoreCase`, called by the three public-profile methods (`PublicProfileService.java:74,91,109`) AND by sign-in (`AuthService.java:1222`, `:1329`). **`pg_stat_statements` shows 2,847 calls since the stats reset at 2026-11-01T20:49:16Z (about 9.7 days, so about 12 an hour on average; read 2026-11-10T13:04Z); the profile share of that is unknown.** (A different statement, a bare `select ue1_0.id … where upper(…username)=upper($1) fetch first $2 rows only`, 3 calls, is `existsByUsernameIgnoreCase` from username generation and is unrelated.) The by-id lookup (`where ue1_0.id=$1`, 5,012 calls, and the `id in ($1)` shapes) is shared with every authenticated request.
- **Backend total requests (Render `http_request_count`, one-hour buckets):** 54, 85 and 182 in the buckets starting 10:00Z, 11:00Z and 12:00Z on 2026-11-10 (bucket edges not confirmed; one hour of low traffic is not a baseline of its own).
- **Frontend:** no profile-class `CATALOG_CACHE_STATS` data exists before the deploy (the `profile` token is new), and Hobby keeps one hour of logs, so the first hour after T0 is the only frontend profile-read record.
- **Observation threshold (stated before the evidence, provisional, Product UX to confirm): a finding, not a stop, and a COARSE signal because the statement is shared with sign-in.** Take hourly deltas of the username-lookup call count at T0 minus 3, minus 2 and minus 1 hours; the **pre-deploy hourly rate is the largest of those three deltas, floored at 12 an hour** (the 9.7-day average). Report a finding if the post-deploy delta exceeds **three times that rate in each of two consecutive hours**, or if total backend requests in an hour exceed twice the busiest hour of the 24 hours before T0. Why: the per-instance cache's worst case is one read per key per instance per 120 s (30 an hour per key per instance); a burst reached 19 to 21 instances on the Preview. A crossing is consistent with, not proof of, the per-instance cache raising backend profile reads (D2 accepted that risk; this is the best available measurement, and it can be masked or inflated by sign-in traffic).

## 5. Watch plan (T0 = the Vercel production deployment of the merge commit reports READY)

Cadence: every 5 minutes for 30 minutes, every 15 minutes to +2 hours, hourly to +24 hours. All reads are read-only.

1. **Database (Render):** memory (30-second samples around any reading above 250 MB), connections, the Postgres log for `signal`, `terminated` and `recovery` (each alone), backend 5xx and 502 counts per one-minute period.
2. **Render deploy list:** whether a deploy started at the merge, its `trigger`, its commit, and when it went live. Record it either way (section 7).
3. **Frontend logs (Vercel runtime logs, within the hour):** `CATALOG_CACHE_STATS` (the `profile=[...]` token: `hit`, `miss`, `join`, `backoff`, wait buckets, `err`; read as READ-level, and the head and body each read the cache, so one cold request can show as a `miss` plus a `join`), `CATALOG_CACHE_DEADLINE class=profile`, `EXAM_HUB_REVIEW_SETS_UNAVAILABLE`, and error-level function logs.
   **Observability gap, stated now: the profile read code writes no log line on a failed read** (`lib/server-public-profiles.ts` has no logging; only the deadline path logs). A thrown read surfaces only through the framework's own error-level server log, and **its presence for a thrown render error was not read in the Preview logs (unverified).** So failure visibility rests on the `err` count in `CATALOG_CACHE_STATS` and on `CATALOG_CACHE_DEADLINE`; the error state itself cannot be seen from logs.
4. **Statement load:** the username-lookup call count per hour against the section 4 pre-deploy rate (coarse: shared with sign-in).
5. **Smoke GETs (owner's call; a smoke check, not a load test), all single requests:** see section 8.

## 6. Hard stops (any one means pause and decide; never an automatic rollback)

Database and platform, unchanged from the Stage B plan:
- Any `signal 9` kill after T0 (including one that follows the Render restart).
- Backend 5xx above 2%, read as sustained across five consecutive one-minute observation periods (Product UX, 2026-11-08), or database connections above 25 for 5 minutes. A single connection sample near 40 during the deploy overlap, as after both earlier redeploys, is not this stop.
- Database memory above 260 MB (of 268.4 MB) at two consecutive reads.

Release-specific:
- **Privacy header failure (the smoke check in section 8 step 1 is REQUIRED, so this stop is always evaluated):** a production creator or profile response whose `cache-control` lacks `no-store`, or contains `public` or `s-maxage`, or whose `x-vercel-cache` is `HIT` or `STALE`. The test is on meaning, not the exact string (the Preview showed `private, no-cache, no-store`; production may append directives such as `max-age=0, must-revalidate`). A failure would mean production's own settings differ from the Preview and the 120 s bound is not met.
- **`profile` class `err` above 20% of reads in any 15-minute window that contains at least 10 profile reads** (hit plus miss plus join), from `CATALOG_CACHE_STATS`. This is the profile analogue of Stage B's walk-error stop; below 10 reads it is reported as "not read yet".

Not stops, findings to report: a single `CATALOG_CACHE_DEADLINE class=profile` line (a read outlasted 15 s; report its count and the surrounding backend latency), any `EXAM_HUB_REVIEW_SETS_UNAVAILABLE` line, a `w10p` share above zero on the profile class, the observation threshold in section 4, the instance count (distinct `inst` values per hour), and a `profile=[...]` token with a high `backoff` share. **The Stage B walk-side stops (`CATALOG_WALK` p95, sitemap 5xx, guard breach) are not part of this release; they are not asserted here, and a breach of them would be a finding about Stage B, reported but not scored.**

**Rollback (owner's action):** Vercel's rollback to the previous production deployment (dashboard or `vercel rollback`; `vercel promote` undoes it). It reverts the frontend only, so the privacy defect returns; it does not touch Render. A `git revert` PR is the slow alternative and is itself a production deployment.

## 7. `scripts/check-deploys.sh` expectations, stated before the merge so a working skip is not read as a failed deploy

The script compares each platform's live commit with `origin/main`: Vercel by the deployment's commit SHA, Render by the newest `live` deploy's `commit.id`.

|---|---|---|---|

| Either case, Vercel | n/a | `VERCEL: <merge>, state=success` | Required; if Vercel is BEHIND the merge did not deploy, which is a failure to investigate |

## 8. Smoke checks (single requests, not a load test)

1. **Production privacy header (REQUIRED, at about T0 plus 5 minutes):** one request to a real public creator page and one to a real profile page, checking that `cache-control` includes `no-store` with no `public` and no `s-maxage`, and that `x-vercel-cache` is not `HIT` or `STALE` (the Preview showed `private, no-cache, no-store` and `MISS`). **The owner chooses a username and a profile id (Claude does not pick a real person's page) and either runs the two requests or explicitly authorizes Claude to issue exactly these two.** It is the only direct check that production's own settings match the Preview, and sections 6 and 9 depend on it.
2. Owner's call: one request to `/exam/<an exam slug>` to see the hub render with its notes.
3. Optional, owner-run, a write on the owner's own account (the hard evidence for the 120 s bound in production): edit your own bio, wait over 120 seconds, reload; the new text should appear. Claude does not run this.

## 9. Success criteria, stated before the evidence

A quiet window is not a pass for the load question: if fewer than 10 profile reads occur in the first hour, report "profile load not read" and extend with whatever database-side reads remain.
