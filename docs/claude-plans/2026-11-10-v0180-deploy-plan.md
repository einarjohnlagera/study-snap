## 1. What this deploy changes (verified 2026-11-10 against `origin/releases/v0.180.0`; code unchanged since `e93e56d3`, tip `3fcc168d` at the time of this revision)

- **The deploy is ONE merge: the release PR from `releases/v0.180.0` into `main`.** It touches two platforms:
  1. **Vercel production rebuilds** from the merge commit. This is the real change: 11 non-test frontend files (`git diff --name-only origin/main..origin/releases/v0.180.0 -- frontend`: the two profile routes and their two `error.tsx`, `lib/server-public-profiles.ts`, `lib/catalog-cache.ts`, `lib/public-profile-metadata.ts`, `components/public/public-profile-error-state.tsx`, the exam hub page and its unavailable component, and a comment in `app/public/library/[subject]/page.tsx`).
  2. **Render will redeploy unchanged backend code unless `[skip render]` works.** The only `backend/` change is `backend/pom.xml` (version 0.180.0): `git diff --stat origin/main..origin/releases/v0.180.0 -- backend` shows exactly that one line. **Treat a Render restart as a deploy** (section 3 and section 5 apply to it). Both earlier redeploys of unchanged code (`dep-dbpc9dgae00c73e5tisg`, `dep-dbpei55g1s2s73cb6o7g`) were followed by clean one-hour reads, but `CLAUDE.md` records that every deploy since 2026-10-25 except `v0.178.0`'s was followed by a Postgres signal-9 kill (Stage A has since passed its 72 h read), so this is not assumed safe. **A Vercel rollback does nothing about a kill caused by a Render restart.**
- **Behaviour changes (frontend only):**
  1. Creator and profile server reads leave the 300 s Next data cache for a separately bounded `profile` partition of the in-process hard-TTL cache: 120 s maximum, single flight, 15 s failure backoff, 15 s deadline, `ok` and `private` cached, `not_found` never cached, no stale value after expiry or failure, 512-key bound; both routes `force-dynamic`. **This closes the recorded privacy defect (a withdrawn note, an edited bio or a switched-to-private profile lingering up to 5 minutes).**
  2. A route-level `error.tsx` on both routes and a static `Profile temporarily unavailable | NoteLib` `noindex` head when the read fails. The HTTP status of a failed page stays 200; no crawler-visible error handling is claimed.
  3. The exam hub keeps its notes when only its review-sets request fails, and logs `EXAM_HUB_REVIEW_SETS_UNAVAILABLE reason=<error name>`.
  4. `.` and `..` usernames return not-found without a backend request.
- **Not changing:** the API, any migration, any prompt, pricing, quota or entitlement, robots or `noindex` rules, the other `revalidate: 300` fetches (listed in `RELEASES.md` "Not in this release").
- **Deploy-order statement (the API-form rule):** no API form, parameter, header or response shape changes. There is no ordering hazard between Vercel and Render in either direction, and a skipped Render deploy leaves a backend that is functionally identical.

## 5. Watch plan (T0 = the Vercel production deployment of the merge commit reports READY)

Cadence: every 5 minutes for 30 minutes, every 15 minutes to +2 hours, hourly to +24 hours. All reads are read-only.

1. **Database (Render):** memory (30-second samples around any reading above 250 MB), connections, the Postgres log for `signal`, `terminated` and `recovery` (each alone), backend 5xx and 502 counts per one-minute period.
2. **Render deploy list:** whether a deploy started at the merge, its `trigger`, its commit, and when it went live. Record it either way (section 7).
3. **Frontend logs (Vercel runtime logs, within the hour):** `CATALOG_CACHE_STATS` (the `profile=[...]` token: `hit`, `miss`, `join`, `backoff`, wait buckets, `err`; read as READ-level, and the head and body each read the cache, so one cold request can show as a `miss` plus a `join`), `CATALOG_CACHE_DEADLINE class=profile`, `EXAM_HUB_REVIEW_SETS_UNAVAILABLE`, and error-level function logs.
   **Validated telemetry facts (Product UX D2/D5; read from `frontend/lib/catalog-cache.ts` and from 12 live production lines, Vercel runtime logs 2026-11-10T13:19Z to 14:07Z):**
   - **Unit: READ-level, per instance, per class** (not HTTP requests, not backend loads). A page view makes at least two reads (`generateMetadata` and the page body); a hit makes no backend call; a miss makes two backend requests for a profile (the profile and its Learning Focus).
   - **`err` numerator:** the count of settled WAITS that rejected: the leader of a load (`catalog-cache.ts:265`) and each joiner (`:201`). One failed load with 3 joiners adds 4. It includes backend 5xx, the 10 s request timeout and the 15 s deadline. **It excludes `backoff`:** a read rejected inside the 15 s failure window is counted as `backoff` and never settles; it also excludes hits.
   - **Correct share:** the failures a visitor can see are `err` plus `backoff`, so the read-level failure share is `(err + backoff) / (hit + miss + join + backoff)`. The earlier draft formula, `err / (hit + miss + join)`, left out `backoff` and so under-counted. Neither is a request-level rate.
   - **Window: specific to each flush, not cumulative** (counters are cleared after each line), **but there is no timer**: a line is written only when a LATER read arrives at least 60 s after the window started. An idle instance emits nothing until its next read, the line carries the counts of the PREVIOUS window, and its log time is the flush time. Observed `windowMs` on 2026-11-10 ran from 83,501 to 1,359,289 (about 22.6 minutes).
   - **Aggregation across instances: none exists.** Each line carries `inst`; there is no global counter. In the 12 sampled lines the same `inst` appears under different `region` labels, so `region` was not used to partition instances.
   - **Reconstructing a 15-minute window is therefore approximate:** sum the lines whose log times fall in the range, across all instances that flushed. That is a count of reads seen by the instances that flushed, not a production error rate. It is possible only within the first hour after T0 (Hobby keeps one hour of runtime logs, at most 100 lines per query), i.e. at the +10, +30, +45 and +55 minute pulls.
   - **Retrievable now:** yes, 12 `CATALOG_CACHE_STATS` lines came back for the last 50 minutes (classes `rail` and `walk:page:subject`; the `profile` token does not exist until the deploy). Baseline noise on the new paths: **zero warning, error or fatal log entries and zero entries on `/public/creator/*` or `/public/profile/*` in the same 50 minutes** (a successful profile read writes no log line).

## 6. Hard stops (any one means pause and decide; never an automatic rollback)

Database and platform, unchanged from the Stage B plan:
- Any `signal 9` kill after T0 (including one that follows the Render restart).
- Backend 5xx above 2%, read as sustained across five consecutive one-minute observation periods (Product UX, 2026-11-08), or database connections above 25 for 5 minutes. A single connection sample near 40 during the deploy overlap, as after both earlier redeploys, is not this stop.
- Database memory above 260 MB (of 268.4 MB) at two consecutive reads.

Release-specific:
- **Privacy header failure (the smoke check in section 8 step 1 is REQUIRED, so this stop is always evaluated):** a production creator or profile response whose `cache-control` lacks `no-store`, or contains `public` or `s-maxage`, or whose `x-vercel-cache` is `HIT` or `STALE`. The test is on meaning, not the exact string (the Preview showed `private, no-cache, no-store`; production may append directives such as `max-age=0, must-revalidate`). A failure would mean production's own settings differ from the Preview and the 120 s bound is not met.
- **Manual investigation trigger, NOT an enforceable hard stop (Product UX D2, 2026-11-10):** the read-level failure share `(err + backoff) / (hit + miss + join + backoff)` from the `profile` class, summed across the instance lines whose log times fall in a 15-minute range, above 20% with at least 10 reads in that range. It starts an investigation (F1 to F4 and the backend signals), never a rollback by itself, and below 10 reads it is reported as "not read yet". It is approximate and first-hour-only (section 5); do not present it as a global production error rate.
- **First `CATALOG_CACHE_DEADLINE class=profile` line: pause and decide (Product UX B1: reconciled with the Stage B rule "any `CATALOG_CACHE_DEADLINE` line", not downgraded).** Reasoning from code, to be confirmed by the first real occurrence: both profile requests carry their own 10 s timeout (`CATALOG_PROFILE_REQUEST_TIMEOUT_MS`, `lib/server-public-profiles.ts:30,38`, `createRequestSignal`) and run concurrently, so a slow backend ends the read at about 10 s as an `err` with no deadline line. The 10 s timers are cleared only in the `finally` after both response bodies are read (`server-public-profiles.ts:50,70-71`, with `response.json()` inside the guarded region), so a slow body is covered too; the 15 s outer deadline (`CATALOG_PROFILE_DEADLINE_MS`) should therefore be unreachable unless a request ignored its abort. The four cases:
  1. **A correctly enforced timeout that failed closed:** about 10 s, counted in `err` and `w10p`, no deadline line, then the 15 s failure backoff. A finding, no stop, no rollback.
  2. **A deadline line:** the outer bound fired, i.e. an intended upper bound was violated. The read still failed closed (nothing stale or private is served), so it is not a privacy event. **Pause and decide:** read the surrounding backend latency, the database signals and the instance, then decide. Never an automatic rollback.
  3. **Repeated timeouts across keys:** widespread profile unavailability; the manual investigation trigger above plus the 5xx and latency reads.
  4. **A timeout associated with backend or database instability:** the existing database hard stops govern and take precedence; frontend rollback is not indicated unless the frontend is causally implicated (section 6b).

Not stops, findings to report: any `EXAM_HUB_REVIEW_SETS_UNAVAILABLE` line, a `w10p` share above zero on the profile class, the observation threshold in section 4, the instance count (distinct `inst` values per hour), and a `profile=[...]` token with a high `backoff` share. **The Stage B walk-side stops (`CATALOG_WALK` p95, sitemap 5xx, guard breach) are not part of this release; they are not asserted here, and a breach of them would be a finding about Stage B, reported but not scored.**

**Rollback (owner's action):** Vercel's rollback to the previous production deployment (dashboard or `vercel rollback`; `vercel promote` undoes it). It reverts the frontend only, so the privacy defect returns; it does not touch Render. A `git revert` PR is the slow alternative and is itself a production deployment.

### 6b. Privacy-sensitive rollback decision tree (Product UX B2, REQUIRED)

**The rollback target is `dpl_39MdpRZxjCPNoU31endwJYmei4o2`. Verify it again immediately before the deploy (it changes with every `main` merge).** It predates the `v0.180.0` fix: **rolling back restores the 300 s data cache, i.e. the recorded privacy freshness defect (a withdrawn note, an edited bio or a switched-to-private profile can show for up to 5 minutes), so it is NOT automatically a safe response to a finding.** No rollback is executed without the owner's incident authorization (or an existing emergency procedure that explicitly permits it); Claude never rolls back.

| Finding | First action | Rollback? |
|---|---|---|
| **Privacy regression** (the header stop fires, or private or withdrawn content is seen after 120 s) | **Pause immediately; assess containment first.** Establish what is exposed, to whom and for how long. If a production response is CDN-cacheable (`public`, `s-maxage` or a cache `HIT`), compare against the old behavior (a 5-minute bound): the new build may be worse than the target, in which case rollback is on the table. Containment options for the owner: a CDN cache purge of the two route families (Vercel invalidate by path or tag), a revert PR (itself a production deployment), or rollback | Owner decides, with the privacy tradeoff written into the incident note |

The Render restart is NOT reversed by a Vercel rollback | **Not indicated** if the cause is the Render restart or unrelated traffic: follow the database procedures. Considered only if the frontend is shown to be the cause, with the privacy tradeoff documented |
| **Widespread profile failure** (the manual investigation trigger confirmed by F1 and F2) | Fail-closed is the safer failure: visitors see a calm error state, not stale private data. Investigate the backend first (the cause is usually upstream) | **Not by default.** Considered if the failure is attributable to this release, persists, and the owner judges the error state worse than the 5-minute defect; document both |
| **A deadline line, repeated timeouts, wait buckets of 10 s or more** | Section 6 cases 1 to 4 | No |

After any rollback the code stays on `main`; re-deploying needs a new deploy and its own approvals. A rollback is itself a production event and moves the rollback target.


## 7. `scripts/check-deploys.sh` expectations, stated before the merge so a working skip is not read as a failed deploy

The script compares each platform's live commit with `origin/main`: Vercel by the deployment's commit SHA, Render by the newest `live` deploy's `commit.id`.

| Case | What Render shows | What the script prints | Reading |
|---|---|---|---|
| `[skip render]` works | No new deploy; the live deploy stays `dep-dbpei55g1s2s73cb6o7g` at `2cf895f6` | `RENDER: serving 2cf895f6, but origin/main is <merge> — BEHIND`, exit 1 | **Expected and acceptable.** The backend code is identical (the only difference is the `pom.xml` version string). Confirm with `list_deploys` that no deploy started after the merge, record "skip phrase works", **do not follow the script's "redeploy the lagging platform" advice** |
| `[skip render]` does not work | A new deploy with `trigger: new_commit` at the merge commit, live within about 2 minutes | After it goes live: `RENDER: <merge> live`, exit 0 | The Render restart is a deploy: sections 5 and 6 apply from its live time, and the one-hour database read is taken from that moment as well as from the Vercel T0 |
| Either case, Vercel | n/a | `VERCEL: <merge>, state=success` | Required; if Vercel is BEHIND the merge did not deploy, which is a failure to investigate |

**Verification list (Product UX D6): what is already done and what is read at deploy time:**
1. **No backend source or dependency change requires deployment:** DONE (gate table: one `pom.xml` version line). At deploy time re-run `git diff <the Render live commit>..<main> -- backend`; the only line should be the `pom.xml` version.
2. **The version bump introduces no runtime compatibility requirement:** DONE (gate table).
3. **The actual Render deployment outcome:** at deploy time, `list_deploys` (a new deploy at the merge commit, or none) and `list_events` for the service; record which case of the table above occurred and whether the skip phrase was honoured. **Do not assume it is supported until observed.**
4. **The deployed backend's health:** the service's health check path (`/api/actuator/health/liveness`), the Render deploy status and the one-hour database read, whichever case occurred.
5. **`check-deploys.sh` BEHIND solely because of the skip:** accept only if item 1's diff shows nothing but the `pom.xml` version; then record "BEHIND, expected limitation of an intentionally skipped deploy". **Do not redeploy Render merely to synchronize commit identifiers.** If the skip did NOT work and Render redeployed, the full backend and database monitoring applies from its live time.
