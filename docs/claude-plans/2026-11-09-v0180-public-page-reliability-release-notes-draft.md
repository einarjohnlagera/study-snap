## Shipped on the branch

- **Creator and profile server reads are bounded at 120 s in-process and fail closed.** `lib/server-public-profiles.ts` no longer uses `next: { revalidate: 300 }`. Both the profile and the Learning Focus request are `cache: "no-store"` and go through a separately bounded `profile` partition of `lib/catalog-cache.ts` (Product UX D2/D3/D5, 2026-11-08): 120 s hard TTL, single flight, 15 s failure backoff, 15 s whole-load deadline (`CATALOG_PROFILE_DEADLINE_MS`), 10 s per-request timeout, `ok` and `private` cached, `not_found` never cached, no stale value after expiry or a failure. Case variants of a username share one key; the request path is URL-encoded; an empty value returns `not_found` with no request.
- **The partition is separate, not a key prefix.** Entries, in-flight map, failure map, item count and eviction are per partition (`catalog`: 1,024 keys as before; `profile`: `CATALOG_PROFILE_CACHE_MAX_KEYS` = 512, sized from 447 accounts and 441 visible profiles on 2026-11-08). The partition is chosen from the key inside `getCatalogCached`. Profile churn or profile failure churn cannot evict a catalog entry or a catalog backoff record. For every non-`profile:` key behaviour is unchanged (`catalog-cache.test.ts` and `catalog-cache.static.test.ts` pass unedited). New stats and log class `profile`; a profile deadline logs `CATALOG_CACHE_DEADLINE class=profile`.
- **A calm failure state for creator and profile pages (Product UX decision A2, 2026-11-09).** New `components/public/public-profile-error-state.tsx` and a route-level `error.tsx` in each of `app/public/creator/[username]/` and `app/public/profile/[userId]/`. Heading `We couldn't load this profile`, body `Something went wrong while loading this profile. Please try again in a little while.`, action `Try again`. Try again calls `router.refresh()` and `reset()` inside a transition, because a plain `reset()` only re-renders the client boundary and would not re-fetch a failed server render. The error message and digest are never shown. **Known limitation (stated by Product UX):** this is a client-side boundary; the HTTP status stays 200 and the server-rendered HTML for a client without JavaScript contains only the site navigation. No claim is made about server-side error status or crawler-visible error handling.
- **Exam hub keeps its notes when the review-sets request fails.** Only the plans leg is contained: a rejection (including `CatalogBackoffError`) logs one `EXAM_HUB_REVIEW_SETS_UNAVAILABLE reason=<error name>` line and renders `Official review sets are temporarily unavailable` / `Your study notes are still available. Please try loading the review sets again in a little while.` (`exam-hub-official-review-sets-unavailable.tsx`; no Retry, no link). A notes failure still rejects the page; an empty plans result still renders nothing; nothing is cached.
- **Comment correction.** The `app/public/library/[subject]/page.tsx` comment states the B4 finding and the `prefetch={false}` rule instead of the disproved "no `loading.tsx` stops prefetch" claim.

## Missing-profile request-cost investigation (read-only, code-based, nothing measured, nothing changed)

1. **A confirmed 404 cannot avoid the Learning Focus request today.** `loadPublicProfile` starts both requests before awaiting either, on purpose (a visibility toggle must not land in the gap between two sequential requests). The focus request is therefore already in flight when the 404 arrives and is only aborted. Making them sequential would let a 404 skip the second request.
2. **What that saves is small.** For a nonexistent username the backend does one `findByUsernameIgnoreCase` lookup per endpoint and no note loading (`PublicProfileService.getByUsername` and `getFocusByUsername`); a blank username and a non-UUID id on the by-id route are rejected with no database query (`UuidParsingUtils.parseUuidOrThrow`). **Sequential fetching would add the focus request's duration to every valid profile's cold render (not measured) and reintroduces the toggle gap.** `V53` creates a unique index on `LOWER(username)`; whether `findByUsernameIgnoreCase` uses it was not verified, and with about 447 accounts it does not matter.
3. **A short negative cache would help only if the same missing username repeats.** Nothing measured says it does. Not proposed.
4. **Amplification:** case variants share one key (lower-cased, trimmed), so they add nothing. Arbitrary usernames are not cached and not failures, so each costs two cheap lookups and cannot grow the partition. One scenario to be aware of: if the backend itself is failing, each distinct arbitrary username becomes a failure-backoff record; the failure map is capped at 512 per partition with oldest-first eviction, so a flood of distinct names during an outage could evict real profiles' backoff records and let those keys retry upstream sooner. That is confined to the profile partition (catalog keys are unaffected) and bounded; it needs an outage and a flood together.
5. **Discoverability:** `app/sitemap.ts` has no creator or profile entries; `robots.ts` does not disallow `/public/creator` or `/public/profile` (its `/profile` entry does not match them); the pages are `robots: index false, follow true`; and no component or lib file outside the page, the path helper and the API client links to `/public/creator/...` or `/public/profile/...` (searched by literal path and by helper name). Discovery would therefore come from externally shared links, not from the app or the sitemap.
6. **The 512-key partition and the separate failure map stay bounded under invalid-key traffic** for the reasons in 4. Whether the real request volume to these routes is meaningful was **not measured** (Vercel runtime logs keep one hour; Web Analytics sees only scripted browsers). A measured count would need a read-only look at request logs or analytics.

## Independent cold falsification review of the implementation (2026-11-09, a no-context Opus agent, read-only)

It ran five single-file suites (all green) and attacked eight claims. **Not disproved:** the partition is chosen from the key and every piece of cache state is per partition; no non-profile caller can build a `profile:` key; the TTL clamp, never serving a failed load, never caching `not_found`, and listener and timer cleanup; the error boundary re-throws router errors (so `notFound()` and redirects are not masked), catches metadata errors, never renders the message or digest, uses the exact approved copy, and pairing `router.refresh()` with `reset()` is the right retry; the exam hub contains only the plans leg; the guard in `instrumentation.ts` returns before importing in a production deployment. **Disproved or partly disproved, and what was done:**

- **"Behaviour for non-`profile:` keys is identical" was too strong for logging.** One stats window is shared by all classes, so a profile read can open or flush it and the `CATALOG_CACHE_STATS` line gains a `profile=[...]` token. Cache behaviour is unchanged. Wording corrected in `public-library.md` and here; no code change.
- **Test gaps, closed:** a Learning Focus failure on its own (fails closed, nothing cached, backs off) and a hung Learning Focus request hitting its own 10 s timeout while the profile answers were unpinned. Two tests added to `server-public-profiles.test.ts`, and a static guard `server-public-profiles.static.test.ts` (no `revalidate`, no `next:` option, no `AbortSignal.any(` call, both fetches `no-store`, both routes keep an error boundary). **Mutation checks, restored by copy:** swallowing a focus failure in the `ok` branch fails both new cases; replacing the focus request's own timeout signal with the bare controller signal fails the timeout case. The two explicit focus aborts on 404 and 403 are redundant with the `finally` abort and cannot be told apart by a test; left as is.
- **Doc gaps, closed:** the stats class list now includes `profile`; the error boundary is documented in `public-library.md` and `public-profile.md`.
- **No test reaches** routing into `error.tsx` (the unit test renders the component directly; the real-browser run above covers the routing, outside the Jest suite) and the `deadlineError` `profile` branch through a real profile read (covered through the partition test's direct key).

**Risks the review raised that need a decision (not changed):**

1. **Page-level bound on Vercel (the reviewer's top item).** A cache-hit render issues no `no-store` fetch, so only a Vercel Preview run can show that no layer above the in-process cache serves the rendered page. Both routes now export `force-dynamic` (D1) and build as `ƒ`; locally every one of 258 sampled responses, including cache-hit renders, carried `cache-control: private, no-cache, no-store` and freshness held. That is local evidence; the Preview is still required.
2. **Crafted usernames reach the error state.** Observed: `/`, `\` and NUL (encoded) get a container 400 HTML page and `%` and `;` get a 401 `AUTH_REQUIRED`; each is a non-ok response, so the visitor sees the error state and a failure-backoff record is written (the old code's behaviour for a raw `/` was not observed). Over 512 such distinct names could evict real profiles' backoff records within the profile partition only. Smallest fix if wanted: treat a 400 from these two endpoints as `not_found` (never cached, never a failure). That is a behaviour change outside the approved scope, so it is not made here.
3. **Sizing:** 512 keys was sized from 441 visible profiles, but one profile can hold two keys (`profile:id:` and `profile:username:`), so the worst case is about 882; the cost of exceeding 512 is refetching, not wrong data.
4. **Case folding:** `toLowerCase` folds the Kelvin sign to `k`, so a Kelvin-sign spelling of a username is served the cached lower-case entry (public data, canonical URL correct). Low.
6. **The error state's empty `<title>` and missing `robots` meta (measured locally before the fix, then fixed under D3).** The failure came from the same metadata read as the page, so `generateMetadata` never produced the normal profile's head. Now fixed server-side and observed in a local real browser: `title: Profile temporarily unavailable | NoteLib`, `robots: noindex` on both routes. Not observed on Vercel; no crawler-handling claim is made.
5. **Per-instance cache:** more backend profile reads than the shared 300 s cache when there are many instances (already accepted in D2; unmeasured).

## Product UX decisions D1 to D3 (2026-11-09, second round) and what was done

- **D1 (approved): `export const dynamic = "force-dynamic"` added to both routes.** Guarded by `lib/server-public-profiles.static.test.ts`. **Verified:** the production build after the change lists `/public/creator/[username]`, `/public/profile/[userId]` and `/exam/[slug]` as `ƒ` (evidence run 8 and the final run). It is an explicit safeguard, not proof of the bound on Vercel.
- **D2 (conditional): the 400-to-`not_found` mapping is DEFERRED; one real gap found and fixed.**
  - *Backend contract (read):* application errors carry a code (`PublicProfileNotFoundException` is 404 `PUBLIC_PROFILE_NOT_FOUND`); a blank username and a non-UUID id are already 404 inside the service. A 400 for an encoded `/` would have to come from the servlet container or request firewall, outside that contract, so it would be a *generic* 400 with no code identifying an invalid profile identifier. Per the decision, a generic 400 is not mapped. **Observed (2026-11-09, current backend source built from a scratch copy, a throw-away Postgres container, dummy secrets, port 8089; nothing under `backend/` touched; the container, the copy and the process were removed):** controls (unknown username, its focus endpoint, a non-UUID id, an unknown UUID) all return 404 JSON with `PUBLIC_PROFILE_NOT_FOUND`. `%2F`, `%5C` and `%00` return **HTTP 400 `text/html` (Tomcat's own error page, no app code, no request id)**; `%25`, `%3B`, and the dot segments `.`, `..` and `%2e%2e` return **401 `AUTH_REQUIRED`**; `%3F`, a unicode name and a 300-character name return the normal 404. A container 400 and an auth 401 identify nothing about a profile identifier, so **no mapping is made** (decision D2). Full output: `~/notelib-verify-evidence/2026-11-09-v0180-followup/runs/11-backend-malformed-identifier-responses.txt`. The 401 for `.` and `..` confirms the dot-segment guard avoids a needless failure record.
  - *Unintended route matching (verified in Node with the WHATWG URL parser fetch uses):* `encodeURIComponent` leaves `.` and `..` unchanged and URL normalization rewrites the path (`..` to `/api/public/`; `.` to `/api/public/creator/`, with the Learning Focus request `/api/public/creator/learning-focus`, which is the profile route of a user named `learning-focus`). This pre-dates the follow-up (the old code interpolated the raw value) but is exactly the "unintended route matching" the decision asked to rule out. **Fix:** both functions return `not_found` for `.` and `..` (also trimmed) with no request and no cache entry; a longer value such as `a..b` is unaffected. Test added and mutation-checked (removing the guard fails it).
- **D3 (conditional): server-side failure metadata implemented and observed locally.**
  - *Correction to the decision's premise:* normal creator and profile pages are **already `noindex`** (`index: false, follow: true`; private and not-found `index: false, follow: false`), so the failure state was the only profile state with no robots directive, and adding `noindex` follows existing policy and cannot cause an indexing regression.
  - *Measured earlier (local real browser):* the failure state had an empty `<title>` and no robots meta.
  - *Change:* each route's `generateMetadata` catches a failed read and returns static `PUBLIC_PROFILE_UNAVAILABLE_METADATA` (title `Profile temporarily unavailable | NoteLib`, `robots: { index: false }`); no `nofollow`; no profile data; the page body still throws so `error.tsx` renders; no root layout, Suspense or `error.tsx` metadata workaround. Unit tests on both routes (including that the page body still rejects) and a mutation check (removing the `try/catch` fails the test).
  - ***Verified locally (real headless Chrome, production build, both routes):*** the failing response's `document.title` is `Profile temporarily unavailable | NoteLib` and the robots meta is `noindex` (runs 8 and the final run). **Not verified on Vercel.** Reviewer-noted limit: the head and the page body each read the reader and `not_found` is never cached, so when the head resolves before the body starts a second request pair is issued and a backend change in between can leave them out of step (an error state under a not-found head); the head is always `noindex`; every confirmed 404 can cost two request pairs.
