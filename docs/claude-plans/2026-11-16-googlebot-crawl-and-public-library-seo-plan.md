## 1. What this plan is, and what already decided part of it

**Goal:** protect the database from crawler-shaped load, keep private content out of search, make view counts honest, and improve how public notes convert, **without** blocking Googlebot and without chasing traffic for its own sake (qualified learners, no ad monetization, no mass-generated pages).

**The findings doc says no existing plan covers this. That is mostly right but two existing owner decisions bind it, and the plan must not contradict them:**
- **Product UX decisions of 2026-11-02** (`docs/claude-plans/2026-11-01-v0178-followup-listing-projection-scope.md`, section 1): #4 crawler policy (keep high-value pages indexable; arbitrary filter and sort combinations *generally `noindex`*; no blanket Googlebot or Bingbot block; no blind canonicalization to page 1) **approved in principle, nothing changed yet**; #5 AI and low-value crawler restriction **deferred to owner approval** (rule, scope, thresholds, rollback, enforcement point); #7 trade-off order (targeted limits on proven high-cost crawlers before depth limits; sign-in walls rejected). Its section 5 also says: **do not treat public-note view events as benefit.**
- **"Direct note visibility immediate"** (same decisions, #2): the public note page is `cache: "no-store"` for privacy (`frontend/lib/server-public-notes.ts:34-37`, CONFIRMED). The findings' P1 "make the note page cacheable" therefore needs an **explicit owner re-decision**, not a technical go-ahead (section 6).
- **The governing record is the later one.** Decision #4 is "approved in principle, nothing to change until the audit is acted on", and the same note's FINAL APPROVALS and anti-drift list "blocking, rate limits, robots or `noindex` changes" as not in scope (`:232`; ROADMAP `:13`, release-scoped to `v0.179.0`). Nothing here reopens that silently: **every new `noindex`, robots, rate-limit or caching rule in this plan is OWNER-gated and needs explicit approval.**
- **ROADMAP** already lists "cacheable public note page, indexed slug column, ranked-listing cache, creator-impact repeat" as code fixes deferred behind the 2026-10-29 operational gate, and carries older SEO rows (exam-hub focused; "expansion not now" until exam-hub deepening and Search Console exist). Search Console now exists, so that gate has partly cleared; whether it reopens is the owner's.
- **v0.182.0** (the interactive LLM migration, deadline-sensitive) and **`v0.181.0`** anti-drift stand. This plan must not interfere with either.

## 2. Audit result: what holds, and four corrections to the findings

**Held (CONFIRMED, `origin/main`):** the four share routes have no `noindex` anywhere (no layout, middleware, `vercel.json`, `X-Robots-Tag`; `frontend/next.config.ts` is empty) and are not in the sitemap; `robots.ts:9-16` disallows only `/dashboard`, `/study`, `/settings`, `/profile`, `/api`, `/app`; every public note page render creates a backend note-detail call and an unconditional `PUBLIC_NOTE_VIEWED` event (`NoteService.java:1163-1191`, `:1150-1160`) with no dedupe, no user agent, no IP, and no bot check anywhere; the Next server forwards no headers (`server-public-notes.ts:34-37`); the popularity score is `(views + copies*3 + likes*2) * 1/(1 + daysSinceCreated/30)` with a 0.1 floor (`PublicNotesScoringUtils.java:39-58`; SQL form `PublicLibraryRepositoryImpl.java:941-945`), where the view totals are **counted over all time** (`:98-101`, `:257-258`). **Correction from the cold review: inflation does NOT fade on its own.** The factor depends on the note's age, not on when a view happened, so bot views added today raise a note's score permanently against same-age peers and keep it POPULAR-eligible for good; the facet links and line numbers (`page.tsx:224, 377, 462`); `redirect()` (307) legacy routes and no `permanentRedirect` anywhere; no route for `/{id}/view`; no rate limiting on public endpoints (only auth, AI, OCR, invitations).

**Corrections that change the plan:**
1. **P0 as written is partly infeasible and partly self-defeating.** The four routes are `"use client"` pages, which cannot export `metadata`, and there is **no `layout.tsx` under `frontend/app` except the root**. So `noindex` needs a new server layout per route segment or an `X-Robots-Tag` entry in `next.config.ts`. And a robots **disallow plus `noindex` conflicts**: a crawler blocked by `robots.txt` cannot read the `noindex`, and a blocked URL that is linked can still be indexed URL-only. Robots rules are also **prefix matches**: a bare `/p` would block `/public/*` and `/pricing`. **The plan uses `noindex` only, no `robots.txt` line** (section 4, Track A).
2. **More view-count inflators than the findings listed.** `opengraph-image.tsx:17` calls the same note endpoint, so every OG-image fetch (Googlebot-Image, link-preview scrapers) records a view; the legacy `public/notes/[id]/page.tsx:11` records an `id`-path event and then redirects to a page that records a second one; `generateMetadata` and the page body each make the same `no-store` call (whether Next memoizes it is **unverified**; the 5-of-5 sample suggests one event per crawl). Views from server renders are **always anonymous**, so owner, admin and human views cannot be separated from bots. POPULAR eligibility is `views >= 20 OR copies >= 3` (`PublicNotesScoringUtils.java:27-28`), so **bot views alone can make a note eligible**.
3. **B7 is narrower than stated.** The heavy public-profile metrics query runs only from the full-profile endpoints `/public/profile/{id}` and `/public/creator/{username}` (`PublicProfileService.java:128,134-135`), not the summary or learning-focus endpoints; it is **not** on the note-page render path; no backend cache; the frontend cache is 120 s **per serverless instance**, so a crawler visiting every few minutes misses it every time; no `@Scheduled` job or polling client calls it. **A missed crawl route:** every authored note page links to `/public/creator/{username}` (`public-note-author-card.tsx:66-67`), and those pages are `noindex,follow` (`creator/[username]/page.tsx:51`), so Google still follows them. A plausible discovery path for B7's unexplained caller; nothing explains the 5 to 15 minute cadence.
4. **Prefetch is a missed inflator (cold review).** The repo's own measured rule (`docs/features/public-library.md:713`) says Next.js runs a route's `generateMetadata` when a `<Link>` to it is prefetched, and `generateMetadata` for a note (`[slug]/page.tsx:50`) calls the counting read. Only `[slug]/page.tsx:185` and `:422` set `prefetch={false}`; the related-note rail cards and the exam hub's note cards use the default (reported by the review at `[slug]/page.tsx:386-389`, `:431-433` and `exam/[slug]/page.tsx:90`; line-level not re-read by me). So one visitor scrolling past about seven rail cards could record about seven views and seven backend reads for pages nobody opened. Whether Googlebot's renderer triggers prefetch is unverified.
5. **The analytics endpoint is open (cold review, CONFIRMED).** `POST /analytics/events` is `permitAll` (`SecurityConfig.java:44`), the controller forwards any `eventType` and `entityId` (`AnalyticsController.java:23-42`), and `AnalyticsEventRequest` has no allowlist. Anyone can write `PUBLIC_NOTE_VIEWED` (or `PUBLIC_NOTE_SHARED`) for any note, anonymously. Those rows feed ranking, POPULAR eligibility and creator totals, and user-agent flagging cannot see this path. Also, the analytics executor has a bounded queue (`AppConfig.java:93-98`), so event writes can be dropped under load.
6. **Small attribution:** `?subject=` is not linked from `[slug]/page.tsx`; it comes from `public-note-ownership-actions.tsx:70`. Also, a just-unpublished note's title can remain on other cached surfaces: another note's rail, subject pages, exam hubs and creator/profile note lists for up to 120 s (`docs/features/public-library.md:717`; scope note `:204`), and sitemap slugs (derived from titles) for up to 1 h (`catalog-cache.ts:3`). **These are separate approved bounds on list surfaces; they do not redefine "direct note visibility immediate" for the note page itself**, so they are context for the caching decision, not a precedent for it.

**Not verifiable here:** all production data, Search Console, the Vercel firewall, the apex redirect and cache headers, any Vercel dashboard rule (the likely source of the `/{id}/view` JSON 404, since no repo code emits that body), whether Next memoizes the duplicate fetch, who caused the 2026-11-11 burst, and the 52% "Other file type" in Search Console.

### Track A: keep share links out of search (privacy; frontend only; OWNER approval for a new `noindex` rule)
- **Facts (CONFIRMED):** `/shared/notes/[id]` and `/shared/study-packs/[id]` require a verified, onboarded login (`requireVerifiedOnboardedUser`), so a crawler sees nothing; `/p/[token]` and `/quiz/[token]` render content only after browser-side fetches, so a JS-running crawler could index them; bad or private tokens render an in-page error with **HTTP 200** (a soft 404). The exposure needs an outside link; no evidence any URL is indexed (QUOTED).
- **Recommendation (PROPOSAL):** `noindex` only, **no `robots.txt` line**. Two mechanisms, pick one in the brief: (a) a new server `layout.tsx` per segment (`app/p`, `app/quiz`, `app/shared`) that exports **only** `robots: { index: false, follow: false }`. **Do not use `buildPageMetadata({ noIndex })`: it hardcodes `follow: true` and always sets a canonical, title, description and Open Graph URL from a required `path` (`site-metadata.ts:49`), so every token URL would inherit one shared canonical.** Segment scoping is safe: `app/p` contains only `[token]`, so it cannot wrap `/pricing` or `/public`. Or (b) a `headers()` entry in `next.config.ts` (`X-Robots-Tag: noindex`) with sources written as `/p/:path*`, `/quiz/:path*`, `/shared/:path*` (never a bare prefix), which also covers non-HTML responses. (b) changes nothing else; (a) matches the repo's metadata pattern. **Unverified:** whether segment-layout metadata lands in the initial `<head>` under the root `<Suspense>` and streamed metadata (`app/layout.tsx:88-96`); the acceptance test must read the rendered production HTML.
- **Go/no-go:** run Track 0.1 first. If nothing is indexed, this is defence in depth and can wait for a frontend deploy that is happening anyway.
- **Never `noindex` anything else:** a test must assert `/public/library`, subject pages with at least 6 notes, exam hubs, `/explore`, `/`, and public note pages are never `noindex` and canonicals stay on `https://www.notelib.app` (the largest risk is accidental deindexing, section 7).

### Track B: honest view counting (data integrity; PRODUCT UX decision; backend plus frontend)
**DECIDED 2026-11-16 (section 11): view attribution = Option A; crawler classification deferred (Option C for now); anonymous analytics allowlist = Option A. The text below is the pre-decision analysis.**
- **Why it matters:** bots inflate FEATURED/POPULAR ranking and creators' view counts, and every crawl costs one extra database write. **Inflation is permanent in the score (section 2), so "wait for decay" is not a plan.**
- **Options (PROPOSAL; none chosen):**
  1. **Count a view once, where a page is actually opened, smallest:** make `generateMetadata`, the OG-image route (`opengraph-image.tsx:17`) and the legacy-redirect hop non-counting, so only the page body's read records the event. That one change also removes the prefetch inflation and any `generateMetadata` duplicate, whatever Next's memoization turns out to be. Needs a non-counting read mode on the backend endpoint (ASSUMPTION: a query flag or a separate internal route) and the frontend to use it. A flag can only undercount: it must not touch the PUBLIC visibility or slug checks (cold review).
  2. **Forward the visitor user agent** from the Next server to the backend (a header) and either **skip** or **flag** (store a bot marker in the event metadata, exclude flagged events from ranking and creator counts) known crawler agents. A user agent is spoofable and forwarding it is a small privacy question (do not store the raw string: store a boolean or category).
  3. **Count views in the browser after hydration** instead of on server render, which removes non-JS crawlers entirely but not Googlebot's renderer, and changes what a "view" means.
- **Constraints:** the FEATURED/POPULAR weights are pinned; changing ranking inputs is a product decision; **history is not rewritten by Claude** (a production data write is the owner's), and past inflation therefore stays in the score unless the owner later decides on a reviewed SQL correction (a separate decision, not proposed here); owner and admin self-views are a separate, smaller question.
  4. **Close the open write path (OWNER, found by the cold review):** `POST /analytics/events` accepts any event type and entity anonymously (section 2). Options: an allowlist of event types that may arrive anonymously, or server-side-only recording for `PUBLIC_NOTE_VIEWED`. Neither is specified here; user-agent flagging does not address it.
- **Recommendation:** option 1 first (no ranking semantics change, removes the clearest inflators), then option 2 with a category flag only if Product UX wants bot exclusion. Do not start before the product decision.

### Track C: crawl waste on facets and the creator route (frontend only; OWNER approval)
**DECIDED 2026-11-16 (section 11): `nofollow` on tag, programme and subject filter links is conditionally approved; creator links are NOT to be `nofollow` at this stage. The text below is the pre-decision analysis.**
- **Facets:** 36% of Google's example URLs are `?tag=`, `?courseProgram=`, `?subject=`, `?creator=` variants, discovered through note-page links. They canonicalize to `/public/library` today and carry **no `noindex`** (`public/library/page.tsx:10-14`). The 2026-11-02 decision #4 already approved, in principle, `noindex` for arbitrary filter and sort combinations; its scope note says that needs a dynamic `generateMetadata` on `searchParams` and tests that the real surfaces are never `noindex`, and warned of accidental deindexing.
- **Recommendation (PROPOSAL):** add `rel="nofollow"` to the filter links on note pages (`[slug]/page.tsx:224, 377, 462`, `public-note-ownership-actions.tsx:70`), keeping the canonicals. It is a hint, it cannot deindex anything, and it is smaller and safer than `noindex` or a robots disallow (a disallow would hide the canonical). Treat the earlier-approved `noindex` on filter variants as a **separate, later, riskier step** with its own guard tests.
- **Creator links (corrected by the cold review):** `nofollow` on `public-note-author-card.tsx:66-67` alone does NOT remove the crawl route. Every note page has a second followable creator link (`PublicNoteAuthorLine`, `public-note-ownership-actions.tsx:80-81`), listing cards link to creators (`public-library-page-client.tsx:386`, reported by the review), and creator pages themselves emit facet links (`public-profile-page-client.tsx:619`, `:737`) and are `noindex,follow` (`creator/[username]/page.tsx:51`), so Google still follows them. Facet links also come from `exam-hub-cta.tsx:53`. The brief must **inventory every generator of facet and creator links first** (grep `buildPublicCreatorOrProfilePath`, `?tag=`, `courseProgram=`, `?creator=`, `?subject=`) and confirm the shared link component can pass `rel`. Creator pages are noindex, so little SEO value is lost; OWNER decision (creator pages are a product surface people use). Any `rel` change must keep the existing `prefetch={false}` and its static guard (`docs/features/public-library.md:713`).

## 7. Acceptance criteria and risks

- **Never deindex a real surface:** tests (real request, rendered HTML and headers) that `/`, `/public/library`, subject pages with at least 6 notes, exam hubs, `/explore` and public notes are never `noindex` and canonicals equal `https://www.notelib.app/...`. This is the largest risk; a reverted frontend deploy (Vercel instant rollback) is the rollback, with days for Search Console to settle.
- **Track A:** (rendered production HTML, not a unit test of the layout) the rendered response for each of `/p/x`, `/quiz/x`, `/shared/notes/x`, `/shared/study-packs/x` carries `noindex` in crawler-visible output (metadata or `X-Robots-Tag`), including the bad-token soft-404 case, and `robots.txt` is byte-identical.
- **Track B:** a test per counted and uncounted path, as a real request, not a direct method call: **target state** (today a normal view can record more than one, section 2): one page open records exactly one event; a prefetch (metadata only), an OG-image fetch and the legacy redirect hop record none beyond the destination's one; a flagged crawler agent is recorded as flagged and excluded from the ranking aggregate; an anonymous `POST /analytics/events` with a restricted type is rejected (if option 4 is adopted).
- **Track C:** `rel="nofollow"` on the named links; canonicals unchanged; no `noindex` change.
- **Track D:** evidence of the caller before any change; no change to the 120 s page-class cache or the sitemap 1 h cap without the owner.
- **Privacy:** no change exposes private, unpublished or unauthorized content to search engines or to caches beyond the owner-chosen bound.
- **Risks:** accidental deindexing (above); a spoofable user agent used for a privacy-adjacent decision (store a category, not the string); a bundled frontend deploy that also carries unrelated changes (keep the range check); caching that lengthens the exposure of an unpublished note (owner-bounded).

### 11.2 Refined phases and dependencies (no versions, no dates)
- **S0, owner-side and read-only, no deploy.** (a) The Track 0 checks, plus two additions: in Search Console, are `?tag=`, `?courseProgram=`, `?subject=` variants reported as alternates with the canonical, and does any rank on its own (D4's precondition)? (b) **A pre-change baseline** (SELECT only, owner or an attended Claude read; the Render connection failed this session): `analytics_events` rows with `event_type = 'PUBLIC_NOTE_VIEWED'` per day for the last 30 days, split by `metadata_json->>'pathType'` and by `user_id is null`; the top 20 POPULAR and FEATURED notes with their view counts; the top 20 creator-impact totals. Without this, S3 has nothing to compare against. **Independently authorizable now.**
- **S1a, backend, additive.** The public-note read endpoints (`NoteController` `getPublicBySeoPath`, `getPublicById`; `NoteService.java:1155`, `:1189`) accept a skip-count signal. **Absent signal = today's behaviour, so this is safe to deploy first and changes nothing until the frontend sends it.** Precedent for a frontend-to-backend allowlisted header: `X-NoteLib-Catalog-Walk` (`frontend/lib/server-public-notes.ts:158`, `PublicApiDiagnosticsAggregator.java:49`); the exact form (a header or a flag) is the brief's choice, and its name is an ASSUMPTION. The signal may only **suppress the event**: the PUBLIC visibility and slug checks must run exactly as today, an unrecognized value must count (fail toward today's behaviour), and a caller who sends it can only undercount their own views.
- **S1b, frontend, after S1a.** Send the signal from: `opengraph-image.tsx:17`; the legacy redirect (`public/notes/[id]/page.tsx:11`, which needs only the SEO path); and the prefetch case (below). **Design constraint:** the note page's `generateMetadata` and body currently make an identical `no-store` fetch that Next appears to de-duplicate within one render (unverified; the 5-of-5 sample suggests one event per crawl). **If metadata were made non-counting through a different fetch, the two calls would no longer match and the backend would do about twice the note-detail reads per render, a load regression.** So metadata and body must keep sharing **one** fetch whose signal is decided once per request (for example through React `cache()`), not two differently-headed fetches. **Prefetch discriminator is an ASSUMPTION:** a prefetch request carries a header a server component can read through `headers()` (for example `Next-Router-Prefetch`; Next 16 segment prefetching may use a different one). **It must be verified in a real browser on a Vercel Preview**, as the repo did for the existing prefetch rule (`docs/features/public-library.md:713`). **Fallback if no reliable discriminator exists:** `prefetch={false}` on the related-note rail and exam-hub note cards (the existing rule's remedy), which costs some navigation speed and so needs Product UX.
- **S2, backend, separately reviewed (D3).** Depends on nothing in S1; independent of it. See 11.4 and 11.5 for the design points. Recommended safe rollout: **shadow mode first** (log, do not reject, the events that the allowlist would reject, for an owner-chosen window), then enforce.
- **S3, measurement and validation, no deploy** (D2 and D6). After S1b has run for an owner-chosen window: compare the S0 baseline with the same read-only queries; estimate remaining crawler activity by comparing events per day with Search Console crawl counts for the same Pacific days and with Vercel logs read within the hour; check whether the Explore POPULAR and FEATURED top lists and the creator-impact totals changed in ways that reflect real learners. **The owner and Product UX define "material distortion" (for example a rank-change threshold on the top N) before the measurement, not after seeing it**, as with other preregistered gates. Output: evidence for or against a separate crawler-filtering proposal.
- **S4, frontend only, conditional (D4).** Only after S0(a) confirms the filtered variants are not meant to rank. Scope: the tag, programme and subject **query-variant** links on public-note pages (`[slug]/page.tsx:224, 377, 462`; `public-note-ownership-actions.tsx:70`). **Do not touch** the links that SHOULD be followed: the subject breadcrumb and "See all" links to the indexable `/public/library/{subject}` pages (`:185`, `:422`, which already carry `prefetch={false}`), the note-to-note rails, exam-hub pages, or the creator links. Keep every existing `prefetch={false}` and its static guard. Return with a finding, not an implementation, if the benefit looks immaterial. Independent of S1 to S3.
- **S5, a separate growth plan (D5).** Written later, when the owner wants it, from the S3 measurements and first-touch signup data.

### 11.4 Acceptance criteria and regression coverage
**S1 (view attribution), real requests, not direct method calls**
- Backend (MockMvc with `.contentType` where a body is sent, plus the PostgreSQL integration pattern): a note read **without** the signal records exactly one `PUBLIC_NOTE_VIEWED`; **with** the signal it records none and returns the same body; with the signal a PRIVATE or unknown note still answers 404 and records none; an unrecognized signal value counts; an event row count assertion, not only a return value.
- Frontend: a test that the OG image route and the legacy redirect send the signal; a test that metadata and body share one fetch (one backend call per render); the static prefetch guard for `prefetch={false}` still passes.
- **Real-browser Preview check (required, not a unit test):** hovering or scrolling past related-note cards causes **no** event; opening a note causes exactly one; fetching the OG image causes none; the legacy `/public/notes/{id}` URL causes at most the destination's one. State the result in the release notes.
- Existing tests that pin counting change or gain a case (`AnalyticsServiceTest`, `CreatorImpactServiceTest`, `PublicProfileServiceTest` and the public-library integration tests that insert `PUBLIC_NOTE_VIEWED` rows pin the aggregate, not the recorder, and should not need change; the brief greps to confirm).
- **No ranking change:** the weights, the 20-view and 3-copy thresholds and the formula files are byte-identical; a guard test already specifies them (`PublicNotesScoringUtilsTest`).

**S2 (analytics integrity)**
- Inventory first: the event enum has more than 150 types (`AnalyticsEventType`) and many frontend call sites; the allowlist is **derived from the frontend call sites on anonymous routes** (landing, public library, public notes, explore, exam hub, share-link pages, signup), not written from memory. The controller already has a per-type rule to extend: `DUE_CONCEPTS_DIGEST_LANDED` requires sign-in (`AnalyticsController.java:29-36`).
- MockMvc real requests: an anonymous `POST /analytics/events` with `PUBLIC_NOTE_VIEWED` is rejected; with an allowlisted type and a valid target it is accepted; with a non-allowlisted type it is rejected; an authenticated request keeps working. **Reject with a non-401 status:** the client tracker treats 401 as "refresh the token and retry once" (`frontend/lib/api.ts:3555-3590`), which would trigger needless refresh attempts for anonymous visitors.
- Target validation: for events that name a note, the target must be an existing PUBLIC note; use a primary-key lookup and say how its cost is bounded on the 256 MB database.
- Abuse protection and deduplication are added only where justified by what the inventory finds; no new sign-in requirement; the tracker stays best-effort (`catch {}`), so rejection must never surface to a user.
- Shadow mode logs, per event type, what enforcement would have rejected, so a missed legitimate type is found before it silently loses analytics.

**S3 (measurement)** is read-only; its acceptance is a written comparison against the S0 baseline with the preregistered materiality rule.
**S4:** a test that exactly the named links carry `rel="nofollow"` and the subject breadcrumb, rails and creator links do not; canonicals unchanged; no `noindex`, robots or redirect change.

### 11.5 Conflicts with existing production behaviour, and open design points
1. **Metadata becoming non-counting can double backend reads** unless metadata and body keep one shared fetch (S1b). This is the one place the decision could raise load.
2. **The prefetch discriminator is unverified**, and if the page body (not only metadata) renders during prefetch, only a request-level signal can separate it. The fallback (`prefetch={false}`) trades speed.
3. **"Recorded only through the authorized server-side viewing flow"** (D3) is already how views are recorded in practice (the client view functions at `frontend/lib/api.ts:6407` and `:6415` are reported unused, to be re-checked in the brief), but the endpoint still accepts the event from anyone today; S2 closes that.
4. **Analytics that feed product decisions may be lost** if the allowlist misses an anonymous event type; hence the inventory and shadow mode. Several ROADMAP checkpoints read anonymous events (for example `EXPLORE_VIEWED`).
5. **Today's popularity and creator totals keep their historical inflation** (accepted by D1, with a later reconciliation only by a separate owner-approved plan, since a production-data write is the owner's).
6. **S4's precondition is not yet met**: the filtered variants canonicalize to `/public/library` in code (`public/library/page.tsx:10-14`, CONFIRMED), but whether Google treats any as independently ranking is a Search Console read (S0a). The subject pages (`/public/library/{subject}`) **are** meant to rank and must never be `nofollow`ed.
7. **D4 forbids any redirect or `noindex` change under this approval**, so the legacy-redirect `permanentRedirect` (Track E), the share-link `noindex` (Track A) and any robots change stay owner-only and out of S1 to S4.
8. **Residual risk:** an unverified assumption that crawlers and prefetches are the dominant inflators. S3 exists to test that; if bot views remain material after S1, D2 returns it as a separate proposal.
