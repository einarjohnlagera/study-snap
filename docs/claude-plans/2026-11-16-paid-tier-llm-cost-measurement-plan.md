## 1. The question and the constraint

**Question:** what does one operation of each paid-tier benefit cost in LLM spend, and what would a paying user at their plan caps cost per month? That feeds the pricing, margin and conversion decisions the cost audit raised.
**Scale warning:** paid-tier usage is tiny (Adaptive 2 to 8 sessions a month, one companion batch in September, no paying user today; QUOTED). Production logging alone will therefore yield few observations per workflow. The plan is built to get answers from data that already exists before it adds anything.
**Anti-drift:** no pricing, quota or entitlement change; no model, route or prompt change; no model switch; no new paid service or infrastructure (so no log drain); no production-data write; no artificial production traffic or load test; independent of `v0.182.0` and Study Plan Discovery.

## 2. What the audit changed: the premise "no token logging" is wrong

The cost audit's section D says Adaptive, Board and Long Exam, teacher quizzes, Interview, critique, note-from-topic and multi-note log no tokens. **That is false (CONFIRMED).**
- **Every call through `OpenAiLlmStudyPackService.executeJsonSchemaOperation` logs one INFO line per HTTP call:** `action=llm_call operation route model tier latency_ms attempt outcome input_tokens output_tokens cached_tokens reasoning_tokens` (format at `impl/OpenAiLlmStudyPackService.java:120-129`, emitted by `logCall` at `:521-523`; `usage` read at `:482-490`). Failed and retried calls are logged too (`outcome` SUCCESS, HTTP_ERROR, TIMEOUT, SCHEMA_OR_PARSE). The line carries **no user id and no content**. **Corrected by the cold review (CONFIRMED, `LlmModelRouter.java:19-21, 52-57`):** lines on the TIERED route (Study Pack, summary regeneration, note-from-topic, Challenge generation and top-ups, templates) already carry `tier` = FREE, PAID or ADMIN (PAID does not separate Plus from Pro); lines on `INTERACTIVE_QUIZ`, `PAID_INTERACTIVE` and `CRITIQUE` all log `tier=n/a` (`:33-36`), so free and paid Adaptive cannot be told apart from the line.
- **The `operation` field is the OpenAI schema name, and several workflows share one (cold review; the field is `operation.schemaName()` at `OpenAiLlmStudyPackService.java:484`, CONFIRMED):** `note_lib_challenge_quiz` covers the initial Challenge Quiz, top-ups, multi-note quizzes and admin template seeding; `note_lib_board_exam` covers learner sessions and Board pool fills; `note_lib_long_exam` covers learner sessions and Long pool fills; `note_lib_adaptive_quiz` covers note-scope and plan-scope Adaptive; `note_lib_generated_note` covers learner note generation and curator bulk generation (reviewer-reported call sites: `ChallengeQuizService:1153`, `LongExamService:1160`, `ExamQuestionPoolService:288`, `OfficialChallengeQuizTemplateService:285`, `NoteBulkGenerationService:442`). **So the log alone cannot split cost per workflow for those**; section 4 apportions with the counters and rows, or M3 adds a finer label.
- **Mislabelled fields (cold review, CONFIRMED for the flush):** `retryInternallyInconsistentQuestion` flushes the still-pending main-batch call as `SCHEMA_OR_PARSE` (`OpenAiLlmStudyPackService.java:2928`) even though that batch's other questions were used, so the failure ratio would be overstated; `attempt` is the outer retry number, so consistency retries and verifier replacements log `attempt=1` and are findable only by their own operation names. The statement-pair verifier logs `route=CRITIQUE` hard-coded (`:2713`) while running Sol or Luna, so aggregate **by model**, not by route.
- **One exception, CONFIRMED:** `OpenAiAskCompanionLlmService` has its own request path, model `CRITIQUE`, and neither reads `usage` nor logs anything (no `usage`, `tokens` or log call in the file). Ask Companion is a paid-tier benefit (0 / 20 / 20 a month).
- **Persisted tokens exist only in two places:** `study_packs` (input, output, cached input; main response only) and `quick_review_sessions` (Challenge generation and top-ups, via `ChallengeQuizService.accumulateLlmUsage`). **Persisted counts exclude retries, consistency-retry calls, verifier calls and replacement calls**, which appear only in the log lines. So **database-based Study Pack cost estimates (including the audit's $1 to $4 a month) undercount retries**; the log lines include them. **The database sum also over-counts in places (cold review):** a remixed Study Pack copies the source's token columns (`ShareService.java:94-101`, CONFIRMED), so the same tokens are summed twice and attributed to a remixer who spent nothing; in-place regeneration overwrites the tokens and moves `updated_at`, so earlier generations vanish from the monthly series (reviewer-reported, `StudyPackService:726-728`); `estimated_cost` is always written NULL (reviewer-reported). So the database figure is neither an upper nor a lower bound.
- **The log lines live only in Render application logs, whose retention is short** (the earliest line Render returned was 2026-11-03, per `docs/claude-plans/2026-11-10-next-releases-sequence-recommendation.md:111`; the audit agent's reading). Durability, not existence, is the gap.
- **The cost alert covers less than the audit said:** `CurationCostAlertJob` (hourly, threshold $10) sums `study_packs` tokens for **ADMIN-owned packs only** (`StudyPackRepository.java:30-45`, `where u.role = 'ADMIN'`). It does not see learner packs, quizzes or any other workflow.
- **Prices:** per million tokens, `gpt-6.1-sol` $2 / $10, `gpt-6-luna` $0.10 / $0.50, `gpt-4.1` $2 / $8, `gpt-4.1-mini` $0.40 / $1.60 (`StudySnapProperties.java:605-610`). `ModelPrice.cachedInput` exists but is never configured, so every estimate is an **upper bound** that ignores the cached-input discount, which the logs and `study_packs` do record.
- **No attribution reaches OpenAI:** the request carries no `metadata`, `user` or `safety_identifier`; there is one API key for every route. An OpenAI usage export splits only by model (and by day), so by route only where models differ.
- **Other corrections to the cost audit's section D:** Challenge top-ups route by the TIERED per-user route, not `INTERACTIVE_QUIZ`; the collection companion and summary regeneration are ADMIN-only operations, not paid-tier benefits; Adaptive, Board, Long Exam and teacher quizzes all use `INTERACTIVE_QUIZ` and none uses `PAID_INTERACTIVE`, and Ask Companion calls the critique model directly with no route; the audit's "Quick Review ≈ $0" is contradicted by the study tip appearing live in production (one call per Quick Review with misses on every tier, no row or counter; reviewer-reported); the audit's Study Pack monthly dollars cannot be reproduced from the alert (admin-only); counters overcount pool-sourced Board and Long Exam sessions, which increment a counter with no LLM call, and undercount retries.

## 4. The plan, in order of cost (cheapest first)

### M0: owner-side, no deploy, no code (OWNER)
1. **OpenAI usage export** by day and model since March (and by project or key if more than one is used, including the owner's benchmark runs), plus the invoices (audit section G, item 3). This is the ground truth for total spend and the reconciliation target for everything below.
2. **Real cached-input prices** for the four models (values only), so cached tokens can be priced offline.
3. **Environment flags by screen read (values only, no secrets):** `EXAM_POOL_PREWARM_ENABLED`, `QUICK_REVIEW_STUDY_TIP_ENABLED`, the three statement-pair verifier switches, `OCR_PROVIDER`, `LLM_MODEL_FREE`, `LLM_MODEL_PREMIUM`. **Correction (cold review, CONFIRMED): the prewarm flag is not the only gate on pool spending.** It guards only `initiatePool` (`ExamQuestionPoolService.java` around `:225-235`, the `requireEagerPrewarmEnabled` branch). `refreshPool` calls the LLM whenever a Study Pack is regenerated in place (`StudyPackService.java:914-922`, also admin regeneration, reviewer-reported `AdminStudyPackTransactionHelper:80-81, :148-149`), and `initiatePoolForUsage` is documented as independent of the prewarm switch (`:71`) and runs after a learner's first non-pool Long Exam (`LongExamService:282-288`). So **regenerating curated packs regenerates every existing Long and Board pool even with the flag off**, which no counter or row records. **Already answerable from existing evidence:** the v0.182.0 sequencing doc records production `llm_call` lines for `note_lib_study_tip`, so **the study tip appears to be ON in production** (`docs/claude-plans/2026-11-10-next-releases-sequence-recommendation.md:109-113`, a read of 2026-11-11), which contradicts the audit's "Quick Review ≈ $0"; the same read found **no `PAID_INTERACTIVE` or `CRITIQUE` lines at all** in the retained window, corroborating very low Interview, companion and Ask Companion volume.

### M1: harvest the logs that already exist (read-only, no code; Prod Investigator or an attended session with the Render MCP)
- Aggregate `action=llm_call` lines from Render logs by `operation`, `route`, `model`, `outcome`: call count, input, output, cached and reasoning tokens, latency, and the retry ratio (attempt greater than 1, non-SUCCESS outcomes). Archive the result as a dated read-only findings file so the series survives Render's retention.
- **Cadence is the owner's choice and must beat Render's retention window.** The earliest line returned was 2026-11-03 in a read of 2026-11-11, so retention is probably about a week (the reviewer's inference, ASSUMPTION): **the lines counted in the 2026-11-10 sequencing doc are probably already gone, and that doc and the v0.182.0 ceilings doc are the only surviving captures.** The first read should record how far back the logs go. Each read is bounded and read-only.
- **Pricing rule (cold review):** cached tokens are a **subset** of input tokens and reasoning tokens a subset of output tokens, so price `uncached = input - cached` at the input rate, `cached` at the cached rate, and **output as logged, never adding reasoning on top**. The production cost alert already does this (`CurationCostAlertJob.java`, uncached = input minus cached); the harness's `conservativeUsd` double-counts reasoning (reviewer-reported), so use its `nonAdditiveUsd`.
- **Output:** a measured table of tokens and cost per operation per **model** (priced with the real cached prices from M0), a measured **retry and failure overhead** from the call counts, the retry operation names and the non-SUCCESS outcomes (not from `attempt` alone, and with the `SCHEMA_OR_PARSE` mislabel in mind), and the **true Study Pack cost including retries**, to compare with the database-based figures. Workflows that share an operation name are reported **together** and apportioned with the rows and counters, with the apportionment stated as an estimate.
- **Limits, stated up front:** the lines carry no user or plan, so per-plan and per-user cost cannot come from them; volumes are small; Ask Companion is absent; log content before the retention horizon is gone.

### M2: estimate monthly cost per workflow and per plan (no code)
Monthly cost of a workflow is its call count (from M1, cross-checked against the section 3 rows and counters, which are only a cross-check) times its measured cost per call. **Known spend the counters miss (cold review, reviewer-reported):** pool regeneration after a Study Pack regeneration; a Long Exam parallel path that times out at 240 s and falls back to a sequential run while the abandoned batches are still billed; multi-note source retries (`ChallengeQuizService:621`, not persisted); Ask Companion resending the full turn history on every message, so its input grows with each turn; admin template seeding and bulk note generation (tier ADMIN, shared operation names). **Per-plan worst case** is the plan cap (Free / Plus / Pro, as the pricing cards state) times the per-operation cost, per workflow, for the route the plan actually uses. **Reconcile** the summed M1 tokens per model and day against the OpenAI export (M0.1); explain any gap (Ask Companion, the benchmark key, calls outside the logged path) before trusting the table. The tolerance is set with the owner before the comparison, not after.

### M3: a small backend change, only if M1 and M2 leave a decision-relevant gap (OWNER and PRODUCT UX; separately reviewed)
1. **Ask Companion usage capture:** read `usage` and emit the same `action=llm_call` line (operation name, route `CRITIQUE`, tokens), with no content. Smallest and clearly useful, because it is a paid-tier benefit with no measurement. It must not touch routing, prompts or models.
2. **[DEFERRED by Product UX Q1, section 9: no new user identifiers or plan-tier labels in LLM logs at this stage; return with a narrowly scoped attribution proposal only if the estimates prove insufficient.]** A finer label on the `llm_call` line (a scope or caller tag, for example learner versus pool fill, Challenge versus top-up, note versus plan scope) and, only if still needed, a plan tier (**not** the user id). **This is not small (cold review, reviewer-reported):** `LlmRouting.interactiveQuiz()` and `paidInteractive()` carry a null user across about ten call sites, and `generateInterviewCritique(...)` and `AskCompanionLlmService.answer(...)` take no user at all, so a plan tier means changing signatures or the router's input, which is the surface this plan promises not to touch. **Recommendation: M3.1 alone first; decide on a finer label only after M1 and M2 show whether apportioning with counters is good enough.** Whether even a user id is acceptable beside token counts is a privacy-product decision; the default is no.
3. **Not recommended:** persisting usage rows (a database write per call on a 256 MB database, plus a migration, for volumes this small), a log drain or any new paid service (anti-drift), widening `CurationCostAlertJob` before M2 shows what it should cover.
- **Deploy shape:** M3.1 is backend only and touches one class, so a Render deploy: separate owner approval, the section-5 checklist, at least 24 hours from any other deploy, and it competes for slots with `v0.182.0` (whose three route switches are Render saves that also redeploy). It must not interfere with that release.
