# V117 curator depth backfill — pre-deploy capture, reversal, and the checkpoint read

Written 2026-08-16, before `releases/v0.82.0` merged to `main`.

`V117` writes `notes.learner_level` onto roughly 900 curator-owned notes. Merging to
`main` auto-deploys, so the migration runs once and irreversibly unless the population
is recoverable. The migration itself logs nothing about which rows it changed — recorded
as a Known Limitation in `RELEASES.md` — so this file is the recovery path.

**The captured population serves two purposes**, which is why it is worth keeping rather
than re-deriving: it is the reversal key, and it is the denominator for the
`[CHECKPOINT — due 2026-09-16]` read on whether `BOARD_TAKER` is trustworthy outside
Information Technology.

## What the pre-deploy capture established

Ran 2026-08-16 against production, before merge. The query listed every curator-owned
note with a `BOARD_TAKER` or `PROFESSIONAL` audience and no authored depth, joined to
its resolved programs (catalog rows via `note_course_program`, else the free-text
`notes.course_program`).

**Two findings, both worth keeping.**

### 1. `PROFESSIONAL` is empty — `V117` has one live mapping, not two

Every row returned `BOARD_TAKER`. Not a single `PROFESSIONAL` note exists in the
affected population, consistent with the earlier audit finding that `PROFESSIONAL` is
unused across all 945 public notes.

So `V117`'s `PROFESSIONAL → PROFESSIONAL` arm writes **nothing** in production today.

**Keep it anyway.** `notes.target_profile_type` is still a writable field with
`PROFESSIONAL` in its enum, so a note could acquire that audience tomorrow; a migration
that handled only the value that happened to exist on one afternoon would be wrong the
moment one is authored. But do not describe this release as having populated two
depths — it populated one.

### 2. The nine Information Technology notes are exactly the nine the audit found

`24a98a93`, `3b1b76be`, `4d2b6ed1`, `7f8566bd`, `8840b0e6`, `9c884c1d`, `c291ad2f`,
`c8aec353`, `fa80777f` — all present in the capture, all `BOARD_TAKER`, all resolving to
the exact catalog name `Information Technology`.

That is independent confirmation of two separate things: the audit found the **whole**
population rather than a sample, and `V117`'s exclusion is **correctly sized** — it
catches all nine and nothing else. Without it, those nine public notes would carry a
licensure-review curriculum floor for every future regeneration.

It does not make the exclusion spelling-proof. A free-text `IT` or `Info Tech` would
still slip through; the known population simply does not contain one.

### 3. A second `BOARD_TAKER` mis-tag, found the next day, outside Information Technology

An audit of academic-level program values (run 2026-08-16 to test a `STUDENT` backfill
that turned out to have zero eligible notes) found a public curator note tagged
`BOARD_TAKER` with program `High School`, whose depth **the same curator authored as
`JUNIOR_HIGH`**. There is no junior-high licensure board.

`V117` does not touch it — its depth is non-NULL — but the rule `V117` encodes would
have stamped `BOARD_EXAM_REVIEW` onto junior-high material had that depth been NULL.
**The exclusion was therefore widened before merge** from one named program to a
denylist of program values known not to be licensure programs: `Information Technology`,
`Grade School`, `Junior High`, `High School`, `Senior High …`.

That widening changes zero rows today and does **not** discharge the checkpoint below.
A denylist protects only against the non-licensure programs somebody has already
audited.

## Step 1 — capture the population, immediately before the `main` merge

**Re-run this rather than reusing the 2026-08-16 result.** Hours will have passed, and
a note authored in between would be migrated without being captured — which is the one
way the reversal can be incomplete.

```sql
-- The exact population V117 will write to. Export to
-- docs/claude-plans/v0.82.0-curator-depth-backfill-population.csv
SELECT n.id
FROM notes n
JOIN users u ON u.id = n.owner_user_id
WHERE u.role = 'ADMIN'
  AND n.learner_level IS NULL
  AND n.target_profile_type IN ('BOARD_TAKER', 'PROFESSIONAL')
ORDER BY n.id;
```

An earlier draft carried two `LEFT JOIN`s onto the program tables. They were left over
from a version that also selected the program name; with `SELECT n.id` and no program
predicate they only fanned rows out and deduplicated them again.

**RAN 2026-08-17, immediately before merge: 828 rows.** Sizing breakdown, run alongside
it:

| visibility | on the denylist | notes |
|---|---|---|
| `PUBLIC` | no — **`V117` writes these** | **819** |
| `PUBLIC` | yes — stays NULL | 9 |

**Three things this settled, none of them assumed beforehand.**

1. **Zero `PRIVATE` rows.** `V117` has no `visibility` or `status` filter, which was
   recorded as a Known Limitation with no post-deploy detector. It has **no live
   instances** — every affected note is public.
2. **The 9 excluded notes are exactly the Information Technology ones**, so the
   academic-level denylist entries exclude **zero** rows. That confirms the migration
   comment's claim, which could not be checked from the repo, and means the 6 curator
   `High School` NULL-depth notes are all `STUDENT` rather than `BOARD_TAKER`.
3. **819 written, against a ~905 estimate.** The estimate counted all curator-owned
   notes carrying any audience, including `STUDENT`, which `V117` deliberately skips.

**⚠️ One figure does not reconcile and is recorded rather than explained away.** 828
curator-owned public `BOARD_TAKER`/`PROFESSIONAL` NULL-depth notes exceeds the 823
*total* public `BOARD_TAKER` notes measured on 2026-08-16 — a subset larger than its
superset. The likely cause is notes authored in the intervening day, which is exactly
why this capture must be re-run immediately before merge rather than reused. It does not
affect the migration, whose predicate is verified independently, but **if the `905` and
`823` figures quoted through these docs are ever load-bearing again, re-measure them
rather than trusting them.**

This is a **superset** of what `V117` writes — it applies none of the denylist
exclusions, so the nine IT notes and any academic-level notes are included and stay NULL
after the migration. Keeping the capture free of the exclusions is deliberate: it stays
correct if the denylist is ever widened again.

**⚠️ But the superset must NOT be used directly as the reversal key or the checkpoint
denominator.** An earlier draft of this file claimed it was harmless for both, on the
grounds that *"the checkpoint read counts them as uncorrected."* **That was wrong in the
most damaging possible direction** — `NULL IS DISTINCT FROM 'BOARD_EXAM_REVIEW'`
evaluates to **TRUE**, so every deliberately-excluded note would have been counted as a
**correction** on day one, against a kill criterion that decides whether ~900 curriculum
floors get reversed. Step 2 exists to fix that.

**The capture was exported** to `docs/claude-plans/v0.82.0-curator-depth-backfill-population.csv`
— 828 ids, one uuid per line, no header. Verified 2026-08-17: 828 unique, all UUID-shaped,
and **all nine excluded Information Technology ids are present**, so 828 − 9 = 819
reconciles by identity rather than by count alone.

*The file was originally written as `…-population.csv.csv`. Renamed to the name this
document names, because following this document to the documented path is what a reader
does — and the doubled extension made it look missing.*

## Deploy timestamp — recorded 2026-08-17, needed by step 4 read (b)

**`2026-08-17 08:29:14 +08`** — commit time of merge `c7523652` (PR #1089) to `main`,
which is what auto-deploys. Deploy lag is not instrumented, so treat this as a lower
bound: a row edited in the first minutes after merge could fall either side. Read (b)'s
job is to *weaken* confidence in (a)'s silence, so a lower bound errs conservatively —
it over-counts touches rather than under-counting them.

Recorded now because it is cheap today and expensive to reconstruct on 2026-09-16.

## Step 2 — narrow the superset to what `V117` actually wrote, immediately after deploy

**One query, run once, as soon as the migration has run.** It converts the superset into
the exact written set, and it is what both the reversal and the checkpoint key on.

**Runnable in two forms — pick by client, they run the same queries:**

- **`v0.82.0-post-deploy-narrowing.sql`** — psql only. Uses `\copy` to load the capture
  and write the result, so it must be run **from the repo root** (`\copy` resolves paths
  client-side). Guards the load with a `DO` block that aborts if the capture is not
  exactly 828 rows.
- **`v0.82.0-post-deploy-narrowing-inline.sql`** — any client (DBeaver, TablePlus,
  pgAdmin). The 828 ids are inlined as a CTE and there are no backslash meta-commands.
  **Export query 1's grid by hand** to `…-written.csv` — and check the saved filename,
  since an export dialog appending `.csv` to a name that already had one is exactly how
  the input file became `…-population.csv.csv` and looked missing.

Both verify the 9 exclusions **by identity** rather than by count, and both carry the
`v0.83.0` `STUDENT` sizing query. Validated 2026-08-17 against a local PostgreSQL: all
five statements parse and execute, and the guard was confirmed to abort rather than
print.

```sql
-- The exact rows V117 wrote. Safe because V117 only ever touches learner_level IS NULL
-- and nothing else moves that column on its own.
SELECT id FROM notes
WHERE id IN ( /* the ids captured in step 1 */ )
  AND learner_level IS NOT NULL;
```

**Expected: 819 rows.** 828 captured minus the 9 Information Technology notes. A count
other than 819 is a finding, not a rounding difference — the `.sql` file states what each
deviation means.

**⚠️ Both CSVs must be committed.** They were untracked as of 2026-08-17; until committed
the reversal key and the checkpoint denominator exist in exactly one working tree.

**Keep both lists.** The superset is the correct *capture* (it survives a widened
denylist); the narrowed set is the correct *key* (it contains only rows the migration
touched). Choosing one over the other breaks something either way.

**Known hole, minutes wide:** a curator authoring a depth between the `main` merge and
this query would be wrongly included. Run it promptly and the window is negligible — and
it is strictly smaller than the alternative, which has a permanent ≥9-note error.

## Step 3 — the reversal, if it is ever needed

```sql
UPDATE notes
SET learner_level = NULL
WHERE id IN ( /* the NARROWED ids from step 2 — not step 1 */ )
  AND learner_level IN ('BOARD_EXAM_REVIEW', 'PROFESSIONAL');
```

**Both clauses are load-bearing.** The `id IN` restricts the reversal to notes the
migration actually wrote — using the step 1 superset here would NULL any of the nine
excluded IT notes a curator had since authored by hand, which is exactly the
human-authoring destruction this key exists to prevent. The `AND learner_level IN` skips
a note re-authored to some *other* depth, and it must list **both** values `V117` can
write: a `PROFESSIONAL`-stamped row left un-reversed would also be unreachable by the
kill criterion's re-migration, since that requires `learner_level IS NULL`.

Nothing else needs undoing. `V117` writes one column, never deletes, never touches
`target_profile_type`, and does not move `updated_at`.

## Step 4 — the checkpoint read this capture makes possible

Recorded as `[CHECKPOINT — due 2026-09-16]` in `ROADMAP.md`'s Backlog Index. Stated here
because the query belongs with the data it reads.

**The question:** `V117` encodes the rule *"`BOARD_TAKER` is trustworthy where a
licensure board exists."* That rule was validated against exactly one program —
Information Technology — and it **failed**, all nine notes mis-tagged. Every other
program's `BOARD_TAKER` notes were assumed correct and never audited.

**⚠️ Both queries key on the NARROWED set from step 2, never on the step 1 superset.**
Against the superset, (a) reports a false-positive floor of at least nine before any
curator does anything, because the excluded notes are NULL and `NULL IS DISTINCT FROM
'BOARD_EXAM_REVIEW'` is TRUE.

```sql
-- (a) How many migrated notes has a curator since corrected away from the stamped depth?
-- The narrowed set contains only rows V117 wrote, so anything no longer at its stamped
-- value -- including a row set back to NULL -- is a genuine correction.
SELECT count(*) FILTER (
           WHERE learner_level IS NULL
              OR learner_level NOT IN ('BOARD_EXAM_REVIEW', 'PROFESSIONAL')
       ) AS corrected,
       count(*) AS migrated
FROM notes
WHERE id IN ( /* the NARROWED ids from step 2 */ );

-- (b) How many has a curator touched at all since the deploy?
-- notes.updated_at is set explicitly in service code -- no @PreUpdate, no @UpdateTimestamp,
-- no trigger anywhere in the 117 migrations -- so V117 did not move it, and a migrated row
-- keeps its pre-deploy timestamp until something edits the note.
SELECT count(*)
FROM notes
WHERE id IN ( /* the NARROWED ids from step 2 */ )
  AND updated_at > timestamptz '<deploy timestamp with zone>';
```

Read (a) is the primary signal and (b) is its floor — a correction requires a touch, so
(b) materially exceeding (a) means these notes are being changed for other reasons and
(a)'s silence is weaker evidence than it looks.

**(b) is looser than "a curator looked at this note."** `updated_at` also moves on
generation lifecycle transitions — `StudyPackService.markNoteGenerated`,
`markNoteGenerationFailed`, `syncNoteTags`, `syncNoteMetadata` and
`applyGeneratedMetadataToNote` all bump it. Since (b)'s job is to *weaken* confidence in
(a)'s silence, that looseness errs in the conservative direction.

**Neither read can distinguish "correct" from "wrong but unnoticed."** Curators may
simply not have looked. So pair them with a **spot-audit of ~10 notes from Civil
Engineering** — 254 notes, the largest population, and the one carrying the most risk if
the rule is wrong. That audit is the only read that can actually falsify the assumption
rather than observe its consequences.

**Kill criterion, stated before the data:** if corrections appear at a material rate, or
the spot-audit finds mis-tagged notes the way the IT audit did, then `BOARD_TAKER` is
unreliable beyond Information Technology and the mapping needs a **per-program
allowlist** rather than a single named exclusion. In that case the reversal above is the
mechanism, and it should be run before re-migrating on the narrower rule.

## What this does NOT cover

- **Challenge bank rows stranded at the old level.** Reversing depth does not unstrand
  them, and it does not need to: `v0.81.0`'s `V115` means a level change degrades
  reachability rather than failing sessions. Recorded in `RELEASES.md` under this
  release's anti-drift rules.
- **Anything about Target Audience.** `V117` does not write it, and no later phase may
  remove it before `[CHECKPOINT — due 2026-09-13]` reports.
