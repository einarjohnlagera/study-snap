## 2. Backend versioning policy (approved prospectively from `v0.181.0`; `v0.180.0` keeps its approved approach)

- Frontend-only releases do not bump `backend/pom.xml`; backend-code releases bump it normally; environment-only changes are real deployments with their own gates; mixed releases coordinate both platforms explicitly.
- **A missing `pom.xml` bump does not by itself prove Render will skip a deployment. What was verified (2026-11-11):**
  - Render service `notelib-backend-prod`: `autoDeploy: yes`, `autoDeployTrigger: commit`, `branch: main`, `rootDir: backend`. Render's documentation says a root directory makes the service ignore changes outside it and that a skip phrase in a commit message prevents an auto-deploy; it does not say how a multi-commit push is evaluated.
  - **Evidence from the pushes to `main` after `v0.179.0` Stage A (#1551, 2026-11-03): ten measured on 2026-11-11, plus #1575 (2026-11-11, whose range contained the kickoff's `pom.xml` bump and a merge-forward commit, and which redeployed Render as expected)**, measured per commit against each commit's FIRST parent (how GitHub lists a commit's changed files): **eight pushes had zero backend changes in every commit and Render did NOT redeploy**: #1554, #1555, #1557, #1559, #1560, #1561, #1570 and **#1571 (`v0.179.0` Stage B, a real frontend-only release)**; **two pushes had backend changes in at least one commit and Render DID redeploy**: #1547 (10 commits touching `backend/`, 24 files net) and **#1573, whose net `backend/` diff was zero and for which plain `git log -- backend` shows no commit touching it, yet Render redeployed, because the push contained a merge-forward commit (`9338870e`, "Merge origin/main into releases/v0.179.0") whose diff against its first parent changes 24 backend files** (`git log` hides it by history simplification). This corrects the earlier "unconfirmed" hypothesis: all ten pushes are consistent with Render deploying when ANY commit in the push changes `backend/` against its first parent. It is inference from ten cases, not documented Render behaviour.
- **Consequence for a frontend-only release:** omitting the bump is not enough. The release must also contain no merge-forward or other commit that changes `backend/` against its first parent. Two controls, both read-only: (1) **squash-merge the release PR** (squash merging is allowed on this repository) so the pushed commit's diff is the net diff; (2) a **pre-merge range check**, for example `for c in $(git log --format=%H <main>..<release tip>); do git diff --name-only $c^1 $c -- backend; done` (and, for the squash case, `git diff --name-only <main> <release tip> -- backend`), which must print nothing.
- **Small future improvement to `scripts/check-deploys.sh` (APPROVED by Product UX 2026-11-11 as a separate small change; NOT implemented, not part of `v0.180.0`):** compute `git diff --quiet <Render live commit> <origin/main> -- backend`; when the Render live commit differs from `main` but that diff is empty, report "Render behind main but backend-equivalent" and exit 0 (an intentionally or incidentally unchanged backend), and keep exit 1 when the backend paths differ (an unexpectedly lagging backend). Also print the per-commit pre-merge prediction above so a surprise deploy or a surprise skip is visible. It needs its own small change, review and approval.
- **Kickoff checklist:** `.claude/commands/kickoff.md` and the `CLAUDE.md` checklist still say to bump `backend/pom.xml` on every release; they must be edited at the `v0.181.0` kickoff (not now: they are process files, not planning documents).

### 3.1 Infrastructure context (owner-confirmed 2026-11-11)

`notelib.app` (A) and `www.notelib.app` (CNAME) are Cloudflare **DNS only**: Cloudflare is not in the path of the website's traffic. The frontend runs on Vercel, the backend on Render (region `singapore`). Consequences: nothing in this plan relies on `CF-IPCountry` being supplied for the website; Cloudflare proxying, DNS, SSL and caching are not changed. **What the code shows about the header the backend does read:** `BillingController.java:35-40` (pricing) and `PaymentController.java:25-32` (checkout) take `CF-IPCountry` from the request; `users.country_code` has exactly one non-null writer in the Java code, `PricingService.resolvePricingContext` at `:151-153` from that header (the two other `setCountryCode` calls set it to null; no builder, native query or migration writes it beyond the V1 column and the V81 sentinel seed; `getPricing` is `@Transactional`, `PricingService.java:55`, so the write persists), and **420 of 447 users have a country code (392 PH, 8 US, 3 CA, 3 SG, 2 MY)**, so the header **has reached** the backend on browser-originated calls (historical code versions that might also have written it were not examined, and a manual data load cannot be excluded) (every `PUBLIC_API_DIAGNOSTICS` line also shows `cfConnectingIp` equal to the request total, i.e. the API host's own edge is Cloudflare-fronted). Where exactly it is added (Render's edge) was not verified, and the value of `NEXT_PUBLIC_API_BASE_URL` (the API host the browser calls) is encrypted and was not read.

### 3.2 The twelve questions (code read 2026-11-11)

1. **How is the homepage rendered?** Statically, with incremental regeneration: `app/page.tsx` is a server component (`export default async function Home()`, `:520`) that awaits `getServerPublicNoteCount()` (a 300 s fetch cache), and the production build lists it as `○ /` with a 5-minute revalidate (`5m`, expire `1y`). `/pricing` is `○` static. Reading request headers or cookies in the page would make it dynamic.
2. **Where are homepage prices defined?** Nowhere but the frontend: `SimplePricingSection` (`components/billing/pricing-plans-section.tsx:413-414,439-440`) prints `₱{pricingConfig.intro.PH.*.monthly} first 1-month pass, then ₱{pricingConfig.price.PH.*.monthly} after` from `lib/pricing-config.ts:44-77`, for every visitor, with no API call. **`/pricing` is also partly static:** its "Regional Pricing" card (`pricing-plans-section.tsx:330-350`) prints PH and international amounts from the same static table, whatever the backend says.
3. **Does `/pricing` support anonymous visitors and regional resolution?** Yes for its plan cards: `PricingPlansSection` calls `useBillingPricing`, which calls `getBillingPricing()` (`lib/api.ts:5054`) without a token when signed out; the backend resolves the region itself. The static Regional Pricing card is the exception (question 2).
4. **Is the pricing API public?** Yes: `SecurityConfig.java:48` `.requestMatchers("/billing/pricing").permitAll()`.
5. **Does Vercel give usable country information to server-side routes?** Yes, in principle: Vercel documents `x-vercel-ip-country` (ISO 3166-1 alpha-2) among "the headers sent to each Vercel deployment" (`https://vercel.com/docs/headers/request-headers`, fetched 2026-11-11). **NoteLib uses no Vercel geo header anywhere** (no `x-vercel-ip`, `geolocation` or `ipCountry` in `frontend/`). Plan or runtime limits on Hobby were not tested.
6. **Can that country be safely passed to the backend's pricing logic?** **No, not without changing the backend, and it would create a second authority.** The backend accepts only `CF-IPCountry` and decides the region itself (question 7). A call from a Vercel server to the backend arrives from the Vercel function's network address and not the visitor's, so the backend's own edge would report the data centre's country (not verified by a test, but follows from how the header is derived); a forwarded header cannot be trusted by the backend because nothing authenticates it (whether Render's edge overwrites a client-supplied `CF-IPCountry` was **not tested**, and it is an existing trust question for display and checkout alike). The two edges (Vercel's and the API host's) use independent geolocation and **are not known to agree**; the amounts must come from the one that also decides checkout.
7. **How does the backend decide PHP versus other currencies?** `PricingRegionResolver.resolveRegion` (`:15-29`): the normalized `CF-IPCountry` maps `PH`, `US`, `GB`, `AU`, `CA`, `SG`, `IN` to themselves, EU countries to `EU`, **any other country to `US`**, and **a missing or invalid country to `PH`** (`:17-19`). `PricingService.resolvePricingContext` (`:150-166`) uses the header if present, else the user's stored country, and then looks up `pricing-regions` (US, PH, GB, EU, AU, CA, SG, IN, each with its own currency, `application.yaml:336-539`). **Correction to the working assumption "non-PH visitors see USD": non-PH visitors see their own region's configured currency (GBP, EUR, AUD, CAD, SGD, INR), and USD only for the United States and unlisted countries.** The frontend's own static table knows only PH and a USD default (`lib/pricing-config.ts`, `resolvePricingDisplayRegion` returns `PH` or `DEFAULT`), which is why static prices cannot represent the real regions.
8. **Does checkout validate the region and the amount independently?** Yes. The request body carries only `planType`, `billingCycle` and `returnUrl` (`BillingCheckoutSessionRequest.java`); `PaymentService.createCheckoutSession` (`:90-107`) calls `PricingService.resolveCheckoutSelection` with the `CF-IPCountry` header of the checkout request, computes the base price from configuration and applies any auto-eligible voucher server-side, and requires an authenticated, email-verified user. The client never supplies a price or a region. **Display and charge use the same resolver and the same configuration; they can differ only if the detected country differs between the two requests** (a VPN or network change between page view and checkout, or the header being absent on one of them, in which case the stored country, then `PH`, applies).
9. **Can the homepage show region-specific prices without becoming dynamic?** Yes, if the amounts are fetched by the browser: the static page ships a reserved-height placeholder and a client component fills it after load, so `○ /` stays static. Anything server-side (reading `headers()`, a per-request route handler) makes the page dynamic and costs a function invocation per view.
10. **Can existing caching or static configuration avoid per-visitor database queries?** Prices themselves are in-memory configuration: **no query**. The only database work in `GET /billing/pricing` is the active-voucher lookup, once per active cycle (`PricingService.toCyclePricing` into `findBestEligibleVoucher` into `findByIsActiveTrue()`): about 4 queries for an anonymous call today and 2 once the Pro yearly and exam flags are off (and the vouchers are inert). There is no application cache and `BillingController` sets no cache headers (HTTP cacheability was not measured). **Static frontend configuration would remove the queries but is exactly the duplicated authority to avoid.** Measured load is negligible: 2 to 9 homepage pageviews a day (40 from 2026-11-03 to 11-10) against about 103 voucher queries a day already (999 calls since the 2026-11-01 stats reset).
11. **Pricing API failure on the homepage:** today there is none (static). With a client component the failure must be handled explicitly: no amounts, and a calm line linking to `/pricing` (section 3.5). Persistent server-side failure also breaks `/pricing` and checkout; the API can also 503 for a region with no configuration (`PricingService.java:335-347`), but all eight resolver regions are configured.
12. **Unknown regions, VPNs, crawlers, a changing country:** an unknown or absent country resolves to `PH` in the backend (consistent between display and checkout, but a PH price offered to an unlocated international visitor; a backend default change is a separate decision). A VPN or travelling visitor gets the price of the country detected on each request, so a change between page view and checkout changes the charge (existing behaviour; the payment provider's invoice shows the actual amount). Crawlers that do not run JavaScript see only the placeholder; JavaScript-running crawlers (Web Analytics already counts many) will see the region of their own address, usually US. The homepage's metadata and structured data contain no price text (checked), so SEO does not depend on the amounts; the static HTML would no longer contain `₱…` text for any visitor.

### 3.3 Options compared (smallest safe solution, from the existing code)

| | **A1** Vercel-derived region (server-side) | **A2** small client component reading the existing public API from the browser | **B** no homepage amounts, link to `/pricing` |
|---|---|---|---|
| UX clarity | Right currency, no flash | Right currency after a short load; a reserved-height placeholder avoids layout shift | Clear and honest; one extra click |
| Anonymous access | Yes | Yes (public endpoint) | Yes |
| Price consistency with checkout | **Not guaranteed**: two geolocation sources; the backend cannot be told the Vercel country safely | **Same resolver as checkout** | n/a (no amounts) |
| Checkout compatibility | Needs a backend change and a new trust boundary | None | None |
| Backend and database load | One call per view if dynamic (the page loses static rendering); same 2 to 4 voucher queries | Same call per JavaScript view: about 10 to 20 extra queries a day at today's traffic, scales with traffic | None |
| Vercel function usage | **One invocation per view** (dynamic page) | None (static page, browser calls the API) | None |
| Cache behavior | Page not cacheable | Page stays `○` with a 5-minute revalidate; API response uncached | Unchanged |
| SEO | Prices in server HTML but dynamic page | Prices client-rendered only | No price text; unchanged otherwise |
| Implementation complexity | High (backend plus frontend, new header contract) | Low to moderate (one component, loading and failure states, tests) | Lowest (remove the section's amounts, add a link) |
| Failure behavior | Wrong country is a silent wrong price | Placeholder, then a calm "see current prices" line | None |
| Operational risk | Highest (new authority, backend deploy) | Low (frontend only; extra read load) | Lowest |

**A2b, noted and not recommended now:** a backend response cache or `Cache-Control` for `GET /billing/pricing` would cut the voucher queries but is a backend change (a Render deploy) for a saving that is negligible at 2 to 9 views a day; revisit if homepage traffic grows. A per-session client cache would only save the second call in a visit.

### 3.4 Recommendation

**Smallest safe solution: A2, with B as the fallback if the owner prefers the lowest risk or if A2 proves fragile.** A2 reuses the existing public endpoint and the backend's own region and price authority, adds no frontend authority, keeps `/` static, needs no backend change and no Cloudflare or Vercel configuration, and satisfies Product UX's invariant. **The frontend must stop printing any price the backend did not provide**, which means the compatibility adjustment below (requested here for approval, not implemented).

**Recommended UX (anonymous visitors):**
- A Philippine visitor sees `₱99 / 1-month pass` (Plus) and `₱149 / 1-month pass` (Pro) after the environment change; an international visitor sees the backend's price in their region's currency; no country or currency selector (unnecessary complexity: the backend already decides, and the checkout invoice shows the exact amount).
- While loading: a placeholder of the same height (no layout shift). Do not show a temporary generic price: a wrong number that then changes is worse than a brief placeholder.
- On failure: no amounts and a calm line such as "See current prices" linking to `/pricing` (copy to follow `VOICE_AND_TONE.md`), never a static fallback number.
- Show the currency code with the amount (for example `₱99 PHP`, `US$3.99`) so the basis is visible; no extra control.
- Unknown region: the backend's existing default applies (`PH`); because the amounts come from the same resolver as checkout, what is shown is what is charged. Whether an unlocated visitor should instead default to the US price is a product decision that needs a backend change, so it is **not** part of this release.
- **The homepage shows the plain monthly price only, never an intro** (consistent with the 2026-11-04 decision for a plain price; it also removes the anonymous-eligibility exception above from the highest-traffic page). The signed-in plan cards keep showing the intro the backend reports for the signed-in user, which is correct for them; on `/pricing` an anonymous visitor can still be shown an intro they would not get until the environment save makes the vouchers inert, a bounded and pre-existing exception (the existing label does not say "new subscribers"; adding those words is a copy option). After the environment change the vouchers are inert and no intro is shown anywhere.

## 5. Board Exam "Redo Missed": investigated (code read 2026-11-11; not reproduced in production; nothing implemented)

- **Mechanism (from code reading, unreproduced).** The endpoint `POST /notes/{id}/challenge-quiz/redo-missed` reaches `startRedoMissedSession` (`ChallengeQuizService.java:1199`), which calls `resolveExistingChallengeSession(..., MODE_CHALLENGE, requireRedoMissedSource = true, ...)` (`:1204-1213`). Board Exam sessions share the `CHALLENGE` session mode (the creation helpers at `:1396-1448` and the lookup at `:2185` use `QuickReviewSessionMode.CHALLENGE`) and are told apart only by `mode = board_exam` in their state. `resolveExistingChallengeSession` (`:2175-2326`) looks up the learner's latest active session for the study pack. Board Exam sessions are stored in the same session table and carry `mode = board_exam` in their state, so `ordinary` is false for them (`:2211`). The collision prompt (`:2251-2257`) requires `ordinary`, but **two branches that handle a Redo Missed start do not check `ordinary`**: for a Board Exam in `GENERATING` (`:2280-2283`) and for a Board Exam with a quiz present (`:2290-2294`), `requireRedoMissedSource && !isRedoMissedSource(state)` calls `forfeitStaleOrdinarySession`, which marks the Board Exam forfeited and releases its claims **with no confirmation**.
- **Learner-visible failure.** A learner with a Board Exam in progress on a note who starts "Redo Missed Questions" for the SAME note (the post-session next step, `PostSessionNextStepService.java:60,207-219`, or the dashboard's Redo Missed focus) has the exam silently forfeited: the timed attempt and its answers are gone. It needs a started or generating Board Exam on the same study pack plus a Redo Missed start (`POST /notes/{id}/challenge-quiz/redo-missed`, `NoteController.java:592`); narrow, real in the code, and not confirmed in production by any read.
- **Affected states:** Board Exam sessions (`board_exam`) in `GENERATING`, or `IN_PROGRESS` with a quiz, on the pack, at the moment of a Redo Missed start. Ordinary Challenge sessions are handled (a collision prompt for a started one).
- **Independence.** It can be fixed on its own: it does not depend on the broader Board Exam timer-and-expiry work ("press Start first", the expiry sweep, the pool size) and not on the migration. The fix must give the learner a choice or a calm refusal instead of a silent forfeit, which needs a backend change (the two branches, and the collision intent label, which today can only say `redo_missed` or `challenge`, never `board_exam`) **and** frontend copy on the existing collision dialog (`app/study-packs/[id]/challenge-quiz/page.tsx`), so it is about 5 files and not a one-liner.
- **Smallest safe regression-test scope:** unit tests on `resolveExistingChallengeSession` for a started Board Exam, a generating Board Exam and an ordinary session under a Redo Missed request (the Board Exam is not forfeited; ordinary behaviour is unchanged), one real-request `MockMvc` test of `POST .../redo-missed` with a JSON content type for the collision response, and a frontend test of the new collision copy; write the failing test first to reproduce it.
- **Release risk tier:** Tier 2 in Product UX's proposed scheme (a bounded workflow change with a limited backend change, no migration, no money or privacy boundary): relevant tests, rollback readiness, owner approval, first-hour monitoring. It restarts Render because it carries backend code.
- **Product UX, 2026-11-11 (second handoff): planning the independently fixable guard defect as a Tier 2 standalone release candidate is approved; the slot after pricing and before the migration is preferred ONLY if the 2026-12-15 migration target stays safe, otherwise the migration is prioritized; no implementation is authorized.**
- **Recommendation (the owner decides):** investigate and write the failing test now (no deployment); ship as a **small independent release between the pricing environment deployment and the migration's environment saves**, because the migration benchmark and preregistration are offline and do not need a deployment slot; **if the migration schedule slips, the migration wins and the fix moves after it.** It is not inserted ahead of the deadline-sensitive migration automatically.
