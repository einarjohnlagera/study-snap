|---|---|---|---|

| `CIVIL_ENGINEERING` | Civil Engineering | **true** | :14 |
| `PROFESSIONAL_PRACTICE_AND_REGULATION` | Professional Practice & Regulation | false | :15 |
| `GENERAL_EDUCATION` | General Education | false | :16 |
| `PROFESSIONAL_EDUCATION` | Professional Education | false | :17 |
| `NURSING` | Nursing | **true** | :18 |
| `ACCOUNTANCY` | Accountancy | **true** | :19 |
| `ARCHITECTURAL_DESIGN` | Architectural Design | false | :30 |
| `ARCHITECTURAL_HISTORY_AND_THEORY` | History and Theory of Architecture | false | :31 |
| `PLANNING_AND_SITE_DEVELOPMENT` | Planning and Site Development | false | :32 |

Persisted via `@Enumerated(EnumType.STRING)`; the column is `notes.domain_context VARCHAR` with **no CHECK constraint**, so the enum is the only enforcement. `fromString` (`:42-51`) returns `null` on an unknown value rather than throwing — an unrecognised persisted string degrades silently to "unset".

### A.2 Precedence chain and the fallback gate

`StudyPackGenerationContextResolver.java`

- **Authoring domain** — `effectiveAuthoringDomain(context)` (`:186-194`): returns `context.domainContext().getLabel()` when a Domain Context is set, otherwise falls back to `context.courseProgram()`.
- **Course/Program resolution** — `resolveCourseProgram` (`:130-147`). The load-bearing gate is `:143`:
  ```java
  if (joinedPrograms.size() == 1) { return joinedPrograms.getFirst(); }
  ```
  Exactly one joined catalog program may reach the prompt as the domain. Two or more may not; the code falls through to the note's free-text `courseProgram`, then the profile's — and for a curator the profile is deliberately excluded (`:131-133`, via `CuratorAuthoringPredicate.isCurator`).
- **Multi-program gate** — `assertGenerationReady` (`:33-39`): throws `MultiProgramDomainContextRequiredException` when `domainContext == null` **and** the note has more than one joined program. Called from five sites: `StudyPackService:122`, `StudyPackService:201`, `AdminStudyPackTransactionHelper:64`, `:119`, `GeneratedQuizService:119`.
- **Curriculum level** — `effectiveCurriculumLevel` (`:196-204`): note level → profile level → `COLLEGE`. Independent axis; not part of this audit beyond noting it does not interact with Domain Context.

**The behavioural consequence, which is the spine of this audit:** a **single-program** note with no Domain Context generates perfectly happily, using the *program name* as its domain. A **multi-program** note with no Domain Context cannot generate at all. Classification is therefore forced by the gate, never by curator diligence — and production confirms the pattern exactly (§B.3).

### A.3 How Domain Context reaches the prompt

`OpenAiLlmStudyPackService.java:1566` builds the context block, emitting a single line at `:1569`:
```java
lines.add("Domain: " + promptValue(authoringDomain));
```
That is the **entire generation payload** of a Domain Context: one label string. The prompt files then instruct the model to use it — `developer.txt:28` and `note-generation-developer.txt:73`, both worded *"Use Domain to set the … subject matter, terminology, examples, and framing (for example, Engineering Mathematics, Nursing, or Accountancy)."*

This is why the "provable no-op" argument was ever coherent: if the label string a new enum value would emit is byte-identical to the program name the fallback already emits, the LLM receives the same bytes. §D.1 shows precisely which programs that holds for and which it fails for.

### A.4 The `quantitative` flag and `QUANTITATIVE_KEYWORDS`

`OpenAiLlmStudyPackService:1630-1661`:
```java
if (context != null && context.domainContext() != null && context.domainContext().isQuantitative()) {
    return true;
}
// ... otherwise fall through to the keyword scan
```
**Two mechanical facts that a reader will otherwise get wrong:**

1. **The flag is an early `true`, never an early `false`.** A `quantitative = false` value does **not** suppress computation guidance; it falls through to the untouched keyword scan. So classifying a note as `PROFESSIONAL_EDUCATION` (false) cannot strip guidance a mathematical note already earns via the scan. This is what makes `false` genuinely a no-op, exactly as `DomainContext.java:23-29` asserts.
2. **The haystack differs by call site, and the difference matters.** The scan reads `effectiveAuthoringDomain + subject + tags + conceptHints + summary` (`:1636-1652`). Most quiz/exam call sites (`:728, :758, :803, :837, :887`) pass a real `studyPackSummary`, which is long prose and will often trip a keyword by accident. But the **initial static Study Pack generation** — `buildStudyPackDeveloperPrompt:281` — passes `isQuantitativeContext(context, List.of(), null)`: **no concept hints and no summary**. The haystack there is only domain + subject + tags.

That is the precise, defensible scope of the defect: **at the one moment that is permanent per note** (Study Packs never auto-regenerate — `DomainContext.java:26-27`), the flag is decided on the thinnest possible haystack. Downstream quiz paths may recover guidance by accident via the summary; the static content cannot.

`QUANTITATIVE_KEYWORDS` (`:156-164`) is 49 English substrings. Note `"engineering"` is one of them, so **every program with "Engineering" in its name passes for free** — the `v0.85.0` name-tracking finding, still exactly true (measured in §D.2).

### A.5 Curator UI and learner-facing behaviour

`frontend/lib/domain-context.ts` holds `DOMAIN_CONTEXT_OPTIONS` — value, label, and a curator-facing `description` per value (`:3-94`). The descriptions carry substantial routing guidance added in `v0.99.0`/`v0.111.0`: each names what belongs *and* routes adjacent material away (`:82`, `:87`, `:92`). This exists because the defect that produced the unset ALE rows was a description enumerating a *narrower* value than the one it named.

`isSubjectSameAsDomainContext` (`:113-123`) is **advisory only** — never a validation error, never a save block (`:107-112`).

Domain Context is **not learner-facing**. It appears in authoring surfaces and in `NoteApplicableProgramsService:52` (which computes the effective writing domain for display). Learners never select it.

### C.3 Method

1. **Subject-first, note-second.** Group by `subject`, assign the indicated context, then hand-check the exceptions the table names (Theory of Architecture, Architectural Design, Structural Components). Do not batch-apply to those three.
2. **Apply the description's own routing sentences as the tie-breaker.** Each `v0.111.0` description ends by routing adjacent material away; that sentence is the rule, not a hint.
3. **Change `domain_context` and nothing else.** Review Set membership, Subject Plans, Sections, titles, Applicable Programs, Authored Depth, topics, ordering and placements are all preserved. The pass is a single-column update.
4. **Do not force 100%.** An honest unset is a findable backlog marker.
5. **Owner executes every write.** This audit produces the mapping; it does not run it.

### C.4 Expected residue — a number, not a mapping

**Expected honest residue: 0–3 rows, and most plausibly 0.**

Every one of the 88 maps onto an existing context without strain. That is not a convenient result — **it is the audit's primary evidence against adding `ARCHITECTURE`** (§D.3). The only rows I would not assign sight-unseen are the 11 Theory of Architecture notes, and those are a *split between two existing values*, not a gap.

If a curator working the pass finds a row that genuinely fits nothing, **that row is the only real argument for a twelfth value** and should be recorded verbatim rather than forced.

### C.5 A measurable side effect worth stating

Of the 88, **73 currently receive no computation guidance at static generation** (§D.2 method). Most of those are the Building Utilities and Building Technology notes, which route to `ENGINEERING_SCIENCES` (`quantitative = true`). So the pass materially changes how ~73 notes would be authored — this is `v0.99.0`'s diagnosis, still measurable.

**This does NOT retro-fix existing Study Packs** — they never auto-regenerate. The benefit accrues to notes generated after classification. Do not mass-regenerate.

## D. Multidisciplinary taxonomy proposal

### D.1 The fallback table — why "provable no-op" holds for some programs and fails for others

This is the computation the old audit did not perform. For an **unset single-program** note, the LLM receives `Domain: <program name>`. Compare that to what the nearest enum value would emit:

| Program | Fallback string sent today | Nearest enum label | Identical? | `quantitative` delta if classified |
|---|---|---|---|---|
| Nursing | `Nursing` | `NURSING` → "Nursing" | **YES** | **false → true** (flag is the only change) |
| Accountancy | `Accountancy` | `ACCOUNTANCY` → "Accountancy" | **YES** | **false → true** (flag is the only change) |
| Civil Engineering | `Civil Engineering` | `CIVIL_ENGINEERING` → "Civil Engineering" | **YES** | none (scan already passes on "engineering") |
| Education | `Education` | `GENERAL_EDUCATION` / `PROFESSIONAL_EDUCATION` | **NO** | none (both false) |
| Architecture | `Architecture` | three `v0.111.0` values | **NO** | varies |
| Information Technology | `Information Technology` | **no enum exists** | **NO** | n/a |

**Reading:** the no-op argument is *literally true* for Nursing, Accountancy and Civil Engineering — the domain string is byte-identical. For those, classification buys **only the `quantitative` flag**. It is *false* for Education, Architecture and IT, where the model receives a domain string the taxonomy never sanctioned.

This is exactly the shape the repo has already mis-derived once (the Architecture no-op verdict). Computed per program, it stops being arguable.

|---|---|---|---|---|---|

| Nursing | 130 | 24 | **106** | **true** | **106** |

**Findings:**
- **~239 curator notes (Nursing 106 + Architecture 73 + Accountancy 60) would gain computation guidance AT STATIC STUDY PACK GENERATION from classification alone, with no enum change whatsoever.** ⚠️ **Scope this precisely:** the simulation uses the `:281` haystack (domain + subject + tags), which is the *static* generation path — the one that is permanent per note. Downstream quiz/exam call sites (`:728/:758/:803/:837/:887`) pass a real summary and will often trip a keyword independently, so an unknown fraction of these notes already receive guidance in their *quizzes*. The claim is about static content, where it cannot be recovered. That is the single highest-leverage action available and it needs no release.
- **`v0.85.0`'s Accountancy fix is inert for 60 notes** — "accountancy" does not contain "accounting", and the flag that was supposed to rescue them is never reached because they are unset. (Scoped precisely: 94 of 154 *do* pass via subject/tags such as "Financial Analysis" or "Interest"; the claim is 60 notes, not all 154.)
- **Civil Engineering is the control case** — 62/62 pass without classification purely because "engineering" is in the program name. The `v0.85.0` name-tracking diagnosis is confirmed, unchanged.
- **Education is the honest null result** — classification changes nothing mechanically. It should still be done for correctness of the domain string (§D.1), but nobody should expect a generation improvement.

### D.4 New contexts proposed — **ONE**, and conditionally

I propose **exactly one** new value, and I hold it at **medium** confidence pending the proof table in §E.

#### `COMPUTING_AND_INFORMATION_SYSTEMS` — label "Computing and Information Systems", `quantitative = false`

- **Treatment difference:** computing material is authored around *systems, models, protocols and correctness* — schemas and normalisation, layered network models, threat models, program semantics. Its worked examples are code, queries, packet traces and schema diagrams, not free-body diagrams or closed-form formulae. Nothing in the engineering bundle produces that register.
- **Programs served:** Information Technology (80), Computer Science (8), Software Engineering (8), and — partially — Computer Engineering (97) and Electronics Engineering (97), whose hardware material stays in `ENGINEERING_SCIENCES`. That split is exactly the one-program-to-several-contexts shape a healthy taxonomy shows.
- **Why every existing context fails:** `ENGINEERING_SCIENCES` is described as "Strength of Materials, Engineering Mechanics, Hydraulics, Thermodynamics, Engineering Materials … building services". A curator classifying *Database Normalization* under that description is being asked to lie. `ENGINEERING_MATHEMATICS` covers algorithms-as-mathematics but not databases, networking or security.
- **`quantitative = false`** — deliberately. Algorithms and complexity are mathematical, but `"algorithm"`, `"algorithms"`, `"computation"`, `"compute"` and `"numerical"` are **already in `QUANTITATIVE_KEYWORDS`**, so genuinely computational computing notes trip the scan on their own. Setting `true` would force calculation framing onto *Database Systems* and *Computer Networking*, and `true` is permanent per note. This follows the `v0.111.0` precedent exactly.
- **Confidence: MEDIUM.** The expressive gap is real and readable in the subject list. What is **missing** is a multi-program forcing case (§E.2) — and by the `ADR-001` bar as this repo has applied it, that matters.

```

```
