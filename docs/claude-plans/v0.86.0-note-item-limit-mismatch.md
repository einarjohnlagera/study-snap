# Topic note generation rejects formula bullets on an unpublished word limit

**Status:** scoped into `v0.86.0` as planned-scope item 4, ordered last. Not implemented.
**Found:** 2026-08-18, from an owner report of repeated bulk-generation failures on Engineering Economics topics.
**Reproduced live** against the real OpenAI API (not stubbed), with the owner's exact authoring metadata.

## Symptom

Bulk Generate fails for certain topics with a generation error. Reported topics: `Compound Interest`, `Present Worth`, `Future Worth`. Authoring metadata: Subject `Engineering Economics`, Domain Context `Engineering Mathematics`, Authored Depth `College`, 13 applicable engineering programs.

**The reported topic list understates it.** A live run over five topics rejected bullets on **all five**, including `Annuities` and `Simple Interest` — which the owner had not reported. It is not a fixed set of cursed topics: it is a probability that rises with formula density, and `retryOnceOnInvalidOutput` gives each topic two chances, so a lightly-quantitative topic sometimes squeaks through. `Simple Interest` passed on one run and failed on the next.

## Root cause

`buildGeneratedNoteContent` validates each `coreDetails` / `whyItMatters` bullet with `normalizeGeneratedNoteItems`, which enforces **`MAX_GENERATED_NOTE_ITEM_WORDS = 28`** (`OpenAiLlmStudyPackService:2504-2512`, via `normalizeGeneratedNoteText`).

**That limit is published nowhere.** What the model is actually told, and what the API strictly enforces, is a *character* budget:

| Contract | Value | Where |
|---|---|---|
| Prompt instruction | **240 characters** | `note-generation-developer.txt:46` |
| JSON schema `maxLength` (strict) | **240 characters** | `buildGeneratedNoteArraySchema:1161` |
| Java validation | **28 words** | `OpenAiLlmStudyPackService:2506` |

The prompt line is not incidental — it was written for exactly this case:

> "Keep each bullet at or under {MAX_ITEM_CHARS} characters, **counting the formula and any variable definitions together**"

So the model obeys the contract it was given and the validator rejects it on one it never saw. A formula bullet with variable definitions is **word-dense and character-light** — many short tokens (`$P$`, `is`, `the`, `interest`, `rate`, `per`, `period`) — so it clears 240 characters while blowing past 28 words. That is why the failure tracks *quantitative* topics specifically.

Rejected samples from the live run (all within the 240-char contract):

```
words=35 chars=191  The future value (FV) with compound interest is calculated by $FV = P(1 + r)^n$,
                    where $P$ is the principal, $r$ is the interest rate per period, and $n$ is
                    the number of compounding periods.

words=43 chars=240  The formula for compound interest is $A = P \left(1 + \frac{r}{n}\right)^{nt}$, ...
                    ^ exactly at the schema's maxLength — the model hit its stated budget precisely
                      and was still rejected

words=37 chars=195  The present value of an ordinary annuity is calculated as
                    $PV = P \times \frac{1 - (1 + i)^{-n}}{i}$, where ...
```

### ⚠️ CORRECTION — this is not an oversight, and the fix reverses a deliberate decision

An earlier draft of this document called the mismatch an internal inconsistency nobody had noticed. **That was wrong.** The identical bug class was found and fixed for `quickRecall` after the "Weirs" failure (Civil Engineering, logged 2026-08-03), and `coreDetails` / `whyItMatters` were **knowingly** left on the word ceiling. The reason is recorded in the test that guards it, `OpenAiLlmStudyPackServiceTest:1038-1039`:

> `void generateNoteFromTopic_stillRejectsAnOverlongCoreDetailsItem()`
> *"coreDetails and whyItMatters are prose and deliberately keep the 28-word ceiling."*

Consistent with that, the prompt's 240-char rule at `note-generation-developer.txt:46` sits **under the `quickRecall` heading only**. `coreDetails`'s own rules say *"Key events, facts, mechanisms, stages, or categories / One fact per bullet — no storytelling, no multi-clause sentences"*, and `quickRecall` is the section that says *"Must include: dates, names, key terms, formulas, or precise definitions."*

So the design intent was: **formulas live in `quickRecall`; `coreDetails` is prose.** The defect is that for a quantitative topic the *mechanism* is the formula, so the model files it under `coreDetails` — which is what that section asks for — and is then judged by a ceiling built for prose.

**Any fix here is a reversal of a recorded decision and must say so.** The prior fix treated one field and the same root cause resurfaced on the neighbouring one, at the same sampled failure rate (4 of 5 then, 4 of 5 now).

**8 OK / 2 failed, and every failure was the same mode — no second failure type surfaced.** An earlier draft of this document predicted that Nursing dosage strings and Accountancy statutory citations would fail the same way. **They did not**, and that prediction is withdrawn rather than left standing. Even formula-heavy topics elsewhere (Beam Deflection, Dosage Calculation) passed.

What makes Engineering Economics uniquely fatal is variable density: interest formulas carry four or five symbols, each needing *"where P is the principal, i is the interest rate per period, n is the number of periods"* — the most word-dense, character-light shape in the catalog.

**⚠️ Open, and deliberately not claimed:** the owner reports that topics in other subject areas also fail. Those topic names were not captured, and guessed substitutes did not reproduce it. Whether they share this cause or represent a second defect is **unknown**. Capture the actual failing topic and its error message the next time it happens; if the message is anything other than *"invalid core details"*, it is a different bug.

## Why it matters beyond the error message

Topic generation is how the curator builds the public catalog — `NoteBulkGenerationService:283` and the single-note `POST` at `NoteController:141` are its only callers. So the surface that systematically fails is the one that authors curriculum at scale, and it fails hardest on computational subjects. That compounds `v0.85.0`, which established that quantitative notes are the underserved half of the catalog: the release made the *prompt* signal quantitative content correctly, while this defect makes quantitative notes disproportionately **hard to create at all**.

Quota is consumed either way — `noteGenerationUsageProtectionService.recordUsage` runs only after a successful return (`NoteGenerationService:63`), so a failed topic costs no quota, but it does cost two billed OpenAI calls per attempt.

## Proposed fix

Validate `coreDetails` and `whyItMatters` **by characters**, matching the schema, the prompt, and the sibling `quickRecall` path. The per-item word cap has no published counterpart and should not exist; the whole-note bound (`MAX_GENERATED_NOTE_WORDS = 700`, checked at `:2418`) already limits total length.

Smallest correct change: `normalizeGeneratedNoteItems` uses `normalizeGeneratedNoteChars` with `MAX_GENERATED_NOTE_ITEM_CHARS`, exactly as `normalizeQuickRecallItems` does, keeping its `minItems` check.

**The justification is the principle, not the volume.** The 28-word cap is the **only** bound in this path the model is never told about — the 240-char item limit is in both the prompt and the schema, the 700-word note limit is in the prompt, and `minItems`/`maxItems` are in the schema. A bound that exists only in Java fails unpredictably on whatever content shape nobody anticipated, and the sweep shows it bites precisely where content is word-dense. Fixing the principle costs the same as fixing the symptom, so there is no reason to take the narrower option — but the claim is *"the only unpublished bound in the path"*, **not** *"many subjects are silently failing."*

Pair the validation change with **stating the 240-char bound in the `coreDetails` and `whyItMatters` prompt sections**. That applies the "Weirs" fix's own recorded lesson, preserved in `OpenAiLlmStudyPackServiceTest`: *"The 4-of-5 sampled-failure rate came from the model never being told the bound it was judged against."* Changing the validator without publishing the bound repeats the original mistake in the opposite direction.

`MAX_GENERATED_NOTE_ITEM_WORDS` has no other use (`grep` confirms `:71` declares it and `:2506` is its sole reader), so it is removed rather than left dangling.

**Do NOT fix this by raising `MAX_GENERATED_NOTE_ITEM_WORDS`.** That keeps two limits for one contract and re-opens the same gap the moment a bullet is word-dense enough — it is the same shape as `v0.85.0`'s rejected "just add more keywords" fix.

**Routing:** isolated bug fix, one method plus a prompt edit → Claude Code implements directly per the `CLAUDE.md` routing table, on its own branch and PR. Ordered **after** `v0.86.0` items 1-3 so it does not disturb the pool-first sequence. Needs a regression test using a real formula bullet (>28 words, <240 chars) asserting it is **accepted**.

**⚠️ `OpenAiLlmStudyPackServiceTest:1038` currently asserts the opposite** and will fail. It must be *updated to the new contract*, not deleted — rewrite it to assert the **character** ceiling still bites on `coreDetails` (mirroring `generateNoteFromTopic_rejectsAQuickRecallItemOverTheCharacterCeiling`), so the bound is still guarded after the word cap goes. A deleted test would leave `coreDetails` unbounded on the backend side, which is exactly what the `quickRecall` fix was careful to avoid.

## Second, independent defect found in the same run — LaTeX escape corruption

Two rejected bullets came back reading `$I = P imes r imes t$`. The `\times` lost its backslash: the model emitted a raw `\t` inside a JSON string, `\t` is a valid JSON escape, so Jackson parsed it as a TAB and whitespace normalisation collapsed it into a space. `\frac`, `\b`, `\f`, `\r`, `\n` are all exposed the same way; `\frac` survived elsewhere in the run only because the model happened to escape it correctly there.

**This is a content-corruption bug, not a validation bug** — a bullet mangled this way is *shorter*, so it passes both checks and is persisted into the note. Any note containing `imes`, `rac`, or similar is evidence. It has a different fix (a prompt rule requiring escaped backslashes, in the spirit of `note-generation-developer.txt:71`'s existing Unicode sub/superscript rule, and/or a post-parse repair), and it should be scoped separately rather than folded into the length fix.

**Not yet sized against production.** A read for affected stored notes is owed before deciding whether existing content needs repair.

## Reproduction

A `@SpringBootTest` calling `LlmStudyPackService.generateNoteFromTopic` for the topics above, with
`new StudyPackGenerationContext(COLLEGE, null, "Engineering Economics", List.of(), ENGINEERING_MATHEMATICS, COLLEGE)`.

**⚠️ `src/test/resources/application.yaml` shadows the main `application.yaml`, so the entire `studysnap.*` tree is absent under test** and the LLM key resolves empty no matter what the environment holds. A live test must re-supply `studysnap.llm.api.*` and `studysnap.settings.*` via `@DynamicPropertySource`. This cost a full debugging cycle and is worth knowing before anyone writes the next live-API test.
