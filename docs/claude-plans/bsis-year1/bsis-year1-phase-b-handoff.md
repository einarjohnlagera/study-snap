## 3. Corrected metadata SQL handoff and safe execution

Three scripts. **Scripts 1 and 2 are independent of each other and can be run in either order; script 3 requires the corrected wording to be in place (script 2, or an in-app edit).**

| # | Script | What it does | Runs when |
|---|---|---|---|

| 3 | `bsis-year1-is-applicability-global-citizenship-held.sql` | Adds Information Systems to the sixth Note (1 row) | **Refuses to run until the corrected wording is in the Note** (a content check, not a hash: it works after script 2 or after the same edit made in the application editor) |

**What changed from the first draft (the Strategist's review), all FACT in the files:**
- **A. One connection.** The earlier instructions ran the file and then a separate `psql -c "COMMIT;"`. Two `psql` invocations are two connections, so that was unsafe. Now `BEGIN`, preconditions, write, verification and `COMMIT` or `ROLLBACK` happen in **one `psql` run**, chosen by a psql variable. `\set ON_ERROR_STOP on` is set inside the script, so an error stops the run even if the owner forgets the flag, and the open transaction rolls back when psql exits.
- **B. Hard preconditions, not informational SELECTs** (`RAISE EXCEPTION`): the target Note exists; title matches; Domain Context is `GENERAL_EDUCATION`; level is `COLLEGE` and visibility `PUBLIC`; current programs equal the expected snapshot; the Information Systems catalog row exists, is unique, and has the expected id; no target already has the association; the held Note is not a target and not already tagged. For the correction script: id, title, Domain Context, exact body md5 and length, exact `updated_at`, the phrase occurs exactly once and `2012` exactly once, the Study Pack is the expected one.
- **C. Exact audit and rollback.** `INSERT … RETURNING` captures and prints the exact inserted association ids, and the script prints an **id-exact rollback statement** (a `DELETE` by primary key, note and program). `created_at = now()` is no longer used to identify rows; the global Information Systems association count must rise by exactly 5 (or 1), and each target's programs must equal the snapshot plus Information Systems. There is no broad `DELETE`.
- **D. No automatic commit.** Three modes: `dry` (default, ends in `ROLLBACK`), `hold` (interactive only; leaves the transaction open for the owner to type `COMMIT;` or `ROLLBACK;` on the same connection), and `commit`, which needs **both** `-v mode=commit` and `-v confirm=owner-approved`. Any other value is refused with a non-zero exit. The final decision to commit is itself gated on both variables.

**Owner instructions (the same for each script):**
1. **Dry run** (default): `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f <script> | tee <name>-dryrun.log`. Everything executes, the exact ids and the rollback statement print, then it rolls back.
2. **Inspect** the log. If any precondition fails the run stops with the reason and nothing is written.
3. **Apply** (explicit owner action): add `-v mode=commit -v confirm=owner-approved`. The preconditions run again inside the apply transaction.
4. **Keep** the apply log and the printed rollback statement. Run the read-only verification at the foot of each script.
5. psql 10 or later (the scripts use `\if`).

**TESTED (FACT), and the limits of that testing.** Each script was run against a **throwaway local PostgreSQL 16.2** (a scratch server, never production) seeded with a minimal copy of the relevant tables and the production values read today. For the five-Note script: dry run (nothing kept), hold via `-f` (rolled back on exit), commit, a second apply after commit (stopped by the already-associated precondition, count unchanged), the id-exact rollback statement (DELETE 5, back to baseline), and **fifteen deliberate failures** (missing Note, changed title, wrong Domain Context, wrong level, not public, programs differing, pre-existing association, duplicated catalog row, missing catalog row, wrong catalog id, the held Note already tagged, the held Note in the target list, a bad mode, commit without confirmation, commit with a wrong confirmation), plus one commit-without-confirmation run **without** the `ON_ERROR_STOP` flag: every one stopped with nothing written. **Testing caught one real bug in the first version** (an array type error in a post-insert assertion), fixed before this handoff. For the correction script: dry, commit, re-run after commit, changed body, changed `updated_at`, changed title, changed Domain Context, a second occurrence, a changed Study Pack (two ways), already corrected, bad mode, commit without confirmation, and a rollback that restored md5 `834de9de…` exactly. For the held script: refused on the uncorrected body and when both years were present; then dry, commit, re-run and rollback after the correction; and **it accepted a body corrected by a CRLF-normalizing in-editor edit** whose md5 differs from the SQL path's (a hash gate would have refused it). **Limits:** the local schema had only the columns the scripts read, so a production-only trigger, constraint or replication detail was not exercised; the scripts' own post-insert checks (global count, body and `updated_at` unchanged) are the guard for that, and the owner's dry run against production is the real test. Production was only read.
