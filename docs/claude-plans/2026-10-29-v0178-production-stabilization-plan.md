## 1. Confirmed request architecture and protection gaps

**V. The browser calls the Render backend directly.** The production JavaScript bundle served at `https://notelib.app/explore` contains `https://notelib-backend-prod.onrender.com/api` (fetched and searched 2026-10-29), and the browser helpers build URLs from `NEXT_PUBLIC_API_BASE_URL` with no proxy (`frontend/lib/api.ts:2521-2525,6118-6121`; `frontend/next.config.ts:1-7` has no rewrites). Server-rendered pages also call the same host (`frontend/lib/server-public-notes.ts:4,28-35`). Render's ip allow-list is `0.0.0.0/0`. **So the Vercel firewall protects page requests only; every `/api/notes/public`, `/api/subjects`, `/api/tags` and `/api/course-programs` call made by a browser, a script or a scraper reaches Render without passing Vercel.** The project has no Vercel firewall configuration at all today.

```
Visitor browser ──page request──────────────► Vercel (Next.js SSR, firewall = none configured)
      │                                              │ server fetches (listing/SEO/creator)
      │                                              ▼
      └──── client JS API calls (direct) ────► Render backend  /api/...   ◄── scripts/scrapers (direct)
                                                     │  no rate limit on the public library controller
                                                     ▼
                                              PostgreSQL basic_256mb (0.1 CPU, 268 MB)
```

**V. Per-visit backend calls** (signed-out, default, counted from code, before framework caching): `/public/library` = **6** (listing `GET /notes/public?page=0`, subjects, course programs, learner levels, tags, discovery sections; `public-library-page-client.tsx:607-683`); **every filter or tag change repeats the five-call batch**; "load more" adds one. `/explore` = **8** (the same 6, plus `/collections/public` from a Review Sets panel that is **rendered while hidden** and an `/analytics/events` POST; `explore-page-client.tsx:70-72,114-130`). A populated note page = 4 to 7 server fetches, the note detail itself `cache: "no-store"`. Subject pages and the sitemap walk the whole public catalog in 50-note pages (`server-public-notes.ts:100-120`; `sitemap.ts:17-96`).

**V. The backend has no rate limit or bot filter on the public library**; limiters exist for auth, AI, OCR and invitations only (`SecurityConfig.java:42,67`; `NoteController.java:824`). CORS limits browser origins, not direct clients (`WebConfig.java:14,21`).

**V. Render deploys only when something under `backend/` changes** (`rootDir: backend`, auto-deploy on commit; per [Render's docs](https://render.com/docs/monorepo-support) pushes that change nothing under that directory do not trigger an auto-deploy). So a change confined to `frontend/` does not restart the backend or overlap its pool. **But it is NOT free for the database, because Vercel's own production build calls the production API** (see section 2, candidate 3): `NEXT_PUBLIC_API_BASE_URL` is set for the production target only (previews have none and fall back to localhost, so **preview builds never touch the production backend**, verified from the Vercel project's variable targets, values not read), and `generateStaticParams` on `/public/library/[subject]` prerenders every public subject at build (`frontend/app/public/library/[subject]/page.tsx:132`). **UNKNOWN: whether a backend-only push also triggers a Vercel production build** (the project's root-directory and ignored-build-step settings were not read; the owner can check in the Vercel dashboard).

**V. Why each call is expensive.** A plain `EXPLAIN` (no `ANALYZE`) of the tag-filtered ranked statement with a sample tag shows planner **cost estimates**: a full scan of `notes` to aggregate copies (about 37%), an index scan over 60,922 view events grouped by note (about 40%), the notes filter with the tag test (about 21%), likes (about 1%). **Those are estimates, and the local measurements below corrected them:** on a production-shaped dataset the same statement measured (full CPU, execution time) about **52% in the three metric aggregates** (almost all of it the views aggregate; the copies aggregate was about 1 ms, 5%, not 37%) and about **45% in the tag clause**, which the estimate had under-weighted. The tag clause is `exists (select 1 from unnest(n.tags) ... where <regexp slug normalisation> in (:tag))` evaluated for every public note (`PublicLibraryRepositoryImpl.java:493-508`): about 10,000 regexp evaluations per call whatever the tag, which is why even a **nonexistent** tag costs about 10 ms locally. Tables are small (2,032 public notes; `analytics_events` 131,304 rows, 84,400 of them `PUBLIC_NOTE_VIEWED`; 44 MB), so this is repeated CPU work on 0.1 CPU, not I/O. The production mix of copies versus views cost may differ from the local one (production data is colder and the `notes` heap is read from disk when evicted); the local result is evidence for the mechanism, not a prediction of the production percentage.

## 4. Step 0 and Release 1: design, local evidence, remaining risk

### 4.1 Step 0 (Vercel only, no Render deploy): stop the build-time catalog walks

**Design (three small edits, `frontend/` only):** `generateStaticParams` on `/public/library/[subject]` (`page.tsx:132`) returns `[]`; `generateStaticParams` on `/exam/[slug]` (`page.tsx:171`, five hub slugs, revalidate 300) returns `[]`; `frontend/app/sitemap.ts` gets `export const dynamic = "force-dynamic"`. Pages then render on first request and are cached by the existing `revalidate: 300` fetch cache (`server-public-notes.ts`). The code already tolerates an unreachable backend at build with `[]` ("ISR will populate on first live request"), so this is the existing fallback made unconditional.

**Measured locally** (scratch copies of `frontend/` at Next 16.1.6, a counting mock backend serving 212 subjects, 2,032 notes and the real per-program counts; the `node_modules` are the project's):

| Build | Backend requests during `next build` | Breakdown |
|---|---:|---|
| A: today | **393** | 1 subjects + 212 subject listings + 125 exam-program pages + 41 catalog pages + 12 collections + 1 exam goals |
| B: subject pages and sitemap changed | 139 | the exam hubs still prerender |
| C: B plus exam hubs (the full design) | **1** | the landing page's note count |

**Parity A versus C (8 URLs: `/`, `/public/library`, two subject pages, an unknown subject, three exam hubs):** identical status, title, canonical, robots and h1; the sitemap URL set is identical (2,274 URLs). **Runtime behaviour in C:** a subject page costs 1 backend call on the first request and 0 on the second; `/exam/ale` 10 then 0; a crawler burst over 209 cold subject pages costs 209 calls once and a repeat adds 0; the sitemap within 300 s costs 0 calls. **Expiry (item 4 of the brief's verification list), measured:** after more than 300 s the next request to a subject page, an exam hub and the sitemap each returned 200 and triggered the stale-while-revalidate refresh, **53 backend calls in total** (41 of them the sitemap's catalog walk, 9 the exam hub's program pages), and the next round added **0**. So Step 0 **removes the build walk** (393 requests at every deploy). The steady-state refresh is **not** a new cost: today's fetches carry the same `revalidate: 300`, so build A very likely refreshes on the same cadence on top of its build walk; I measured the 300 s refresh only on build C, not on A.

**What this does not prove, stated so it is not over-read:** (1) the sitemap's response header locally is `Cache-Control: public, max-age=0, must-revalidate`; whether Vercel's CDN additionally caches it can only be seen post-deploy (`x-vercel-cache`); the backend calls are bounded by the fetch cache either way. (2) The first crawler after a deploy or cache expiry waits on the walk synchronously (about 41 calls for the sitemap); that is slower for that one request, not heavier overall. (3) A Vercel-only production deploy is an **observation, not a controlled experiment**: the Vercel build still runs once, and a kill that follows or does not follow cannot be attributed to a single cause on one sample. (4) **A backend-only push does trigger Vercel builds** (verified for previews on 2026-10-28; the production-target behaviour and the project's root-directory or ignored-build-step settings were not readable, so the owner checks them in the dashboard). That is why **Step 0 should ship before Release 1**: otherwise Release 1's own deploy is accompanied by a 393-request build walk against the same database.

### 4.2 Release 1: the ranked listing

**What was benchmarked.** A throwaway PostgreSQL 18 (Docker) with all 156 real Flyway migrations applied and a synthetic seed matched to production counts: 17,264 notes (2,032 public; 14,987 copy rows from 1,483 sources), 84,597 view events over 2,032 notes, 3 likes, 444 users, 60,960 `note_course_program` rows, 212 subjects. It differs from production in three ways that matter: distinct public tags are 3,985 (production 6,037), the **tag distribution is far heavier than production's** (maximum 503 notes per tag and a 472-id "common" tag, against a production maximum of 74 and a median of 1), and the cache is warm. Study Packs (1,442, about 70% of public notes) were added only for the parity run, so **the timings below were taken without them and use RECOMMENDED**; FEATURED timing was not measured. The SQL under test is **built by the repository's own private builders through reflection** (`buildFilter`, `rankedFrom`, `rankedEligibility`, `rankedOrderBy`, with the real join constants), so it is the shipping statement, not a re-typed copy. Variants: **current**; **array metrics** (the three aggregating joins replaced by `unnest(?::uuid[], ?::bigint[])` under the same aliases `rank_copies`, `rank_likes`, `rank_views`); **array metrics plus tag ids** (additionally the tag clause replaced by `n.id = any(?::uuid[])`, the ids coming from a snapshot of normalized tag to public-note ids built with the repository's own `normalizedSlugSql`). Constrained runs use Docker's cgroup CPU quota of 0.1 CPU, which approximates but is not Render's CPU limit.

**Parity: 108 of 108 comparisons identical.** Each compares three variants (current, array metrics, array metrics plus tag ids) for six sorts (RECOMMENDED, FEATURED, POPULAR, COPIED, VIEWS, MOST_COPIED) times nine tag shapes (none, common, medium, rare and nonexistent tags; **two-tag and three-tag OR unions**, matching the `in (...)` semantics of `appendTagFilter`; the 74-id tag), for both statements: the **full ordered id list with no limit** (up to 2,032 rows, so positions and ties past the first page are covered) and the **ranked count** composed exactly as `countPublicLibraryRankedMatches` does (plain count when a sort has no eligibility rule, otherwise `rankedFrom(sort, eligibilityMetrics(sort))` plus the eligibility predicate; POPULAR and COPIED counts of 1,810 against 2,032 unfiltered show the eligibility path is exercised). **FEATURED is not vacuous**: 1,442 Study Packs were seeded late, so it returned 1,151 rows unfiltered and 256 for the common tag. **Disclosure:** my first parity pass compared only the first 20 ids (the harness appended `limit 20`) and never compared counts; I replaced it with the run above after review, and the 60-comparison claim in an earlier draft of this paragraph is withdrawn. Remaining scope limits: single backend instance semantics only, the seed's tie structure is synthetic, and the engagement-score arrays were taken from the same database moments before each comparison (so parity says nothing about snapshot **age**, which test plan item 4 covers).

**Planner cost versus measured time.** The planner put 77% of the cost in the two aggregates; measured execution put about 52% there and 45% in the tag clause (section 2). Planning time is 0.1 to 0.3 ms in every variant, so none of this is planning overhead. Full-CPU execution time (RECOMMENDED sort, median of 15 `EXPLAIN ANALYZE` runs):

| Tag case | Current | Array metrics | Array metrics + tag ids |
|---|---:|---:|---:|
| unfiltered | 10.4 ms | 2.5 ms | n/a |
| common tag (472 ids) | 20.1 ms | 9.5 ms | 1.4 ms |
| medium tag | 20.9 ms | 11.0 ms | 0.7 ms |
| rare tag | 22.4 ms | 10.6 ms | 0.6 ms |
| nonexistent tag | 9.7 ms | 9.8 ms | 0.0 ms |

Swapping only one aggregate (full CPU, RECOMMENDED, common tag): views only 11.3 ms against 11.2 ms for all three, so **the views aggregate is essentially the whole metric saving**; copies only 16.8 ms against 17.6 ms current. A **partial index on copies** (`notes(copied_from_note_id) where copied_from_public ...`) changed nothing measurable (it would also need a migration, which is the owner's), so it is dismissed. Snapshot refresh cost: the three aggregate queries took 32 to 66 ms at full CPU (an **extrapolation** to about 0.3 to 0.7 s at 0.1 CPU, not measured) once per 300 s; the tag-index query was not timed separately (I expect it to cost about one tag-clause scan, 10 ms at full CPU).

**Throughput at 0.1 CPU, the production-like constraint** (custom plans, common tag, RECOMMENDED sort, 20-second runs):

| Variant | 1 caller: queries/s, median, p95 | 8 concurrent callers: queries/s, median, p95 |
|---|---|---|
| Current | 1.8/s, 598 ms, 797 ms | 1.3/s, 6,902 ms, 11,798 ms |
| Array metrics | 3.1/s, 303 ms, 499 ms | 2.3/s, 3,496 ms, 6,099 ms |
| Array metrics + tag ids | **10.9/s, 99 ms, 192 ms** | **7.0/s, 1,002 ms, 2,599 ms** |

**What this says about production (V for the measurement, H for the inference).** The constrained single-caller median of about 600 ms and the 8-caller median of 7 s are the same order as production's observed mean of 1.37 s and maximum of 60 s, which supports the explanation that these queries are **CPU-bound on a 0.1 CPU limit and queue behind each other**: capacity for the current statement is under 2 calls a second in total, so any sustained burst above that saturates the database, holds connections and memory, and is consistent with the kills (H; a kill's trigger is still not observed). The array metrics alone roughly double that capacity; with tag ids it is about five to six times. Single 20-second runs on a laptop-hosted container are noisy (repeat runs of the same variant differed by 20 to 30%); read these as orders of magnitude.

**One hazard found by measurement, and it is the reason the tag-id variant is not a drop-in.** With the JDBC driver's default (`prepareThreshold` 5, which the application uses: `application.yaml` sets none), PostgreSQL switches the statement to a **generic plan** after five executions. For the tag-id variant that plan measured **8 to 10 ms wall** for tags of 66 to 74 ids (production's largest tag has 74 notes) against **about 1 ms** execution with a custom plan, and 1.2 s median in one constrained run before I switched to custom plans (99 ms after). The array-metrics variant did not flip. **So the implementation must pin a custom plan for the tag-id statement, and the acceptance test is wall time within 2x of `EXPLAIN ANALYZE` execution time at the default `prepareThreshold` with a 74-id tag.** Candidate ways, for the implementing session to benchmark rather than assume: inline the ids as UUID literals (typed, bounded by the tag's note count, no injection surface, but a distinct SQL text per tag); `set_config('plan_cache_mode', 'force_custom_plan', true)` inside the transaction; `prepareThreshold=0` for the whole datasource (not recommended: it touches every query).

**Design (recommended, Option B).** A single in-process snapshot (single backend instance today), rebuilt at most every 300 s with single-flight (reuse the `PublicLibraryDiscoveryRankingCache` pattern, `:36,147`), holding: the three metric maps (about 2,000 entries) and the **tag index** (normalized tag slug to ids of **public** notes, about 10,000 entries; computed by the database with the repository's own `normalizedSlugSql`, never re-implemented in Java). The ranked id page and its paired count both read the **same snapshot generation**, so `hasMore` and totals cannot disagree. `visibility = 'PUBLIC'` and every other filter stay **live in SQL**, so a snapshot can never expose a note that is no longer public. Facets, projections and creator-impact are untouched.

**Option A (fallback if Option B's staleness is not acceptable):** the three metric maps only, the tag clause untouched. No new staleness class; about 2x at 0.1 CPU. Recommended only if the owner will not accept R1 below.

**Decision R1 (owner): accept a tag-membership lag of up to 5 minutes?** A note that is newly published, or whose tags are edited, can be missing from a tag-filtered ranked listing, or still listed under an old tag, for up to 5 minutes. It is **not** a publication-status or privacy staleness (visibility is evaluated live and a note unpublished a second ago is still excluded), and the unfiltered listing, note pages and search are unaffected. Because there is one backend instance, publish, unpublish and tag-edit paths can additionally invalidate the snapshot in process; **I recommend the brief asks for that if it is a small, well-covered change, and accepts the 5-minute bound otherwise.** The brief's allowance was "five minutes of engagement-score staleness"; this is a second, different staleness and is therefore asked for explicitly.

**Failure behaviour (hard requirements, each needs a test).**
- *Single-flight:* one refresh in flight; concurrent callers wait on it or use the current snapshot, never start a second load.
- *Failures are not cached and not published:* a failed or timed-out refresh leaves the previous snapshot in place and is retried on the next request after a short backoff (for example 30 s), never a hot retry loop.
- *Last-known-good with a hard ceiling:* serve the previous snapshot up to **15 minutes** old (3x the TTL, a number for the implementing session to confirm); beyond that, use the current heavy SQL **behind a bulkhead (at most 2 concurrent)**, with excess requests answered by a fast, calm error rather than queued. **This is the guard against a fallback storm**: if the snapshot is unavailable exactly when the database is struggling, falling back unbounded would recreate the load being removed.
- *Empty-snapshot safety:* a snapshot that contains no public notes while the previous one did, or while a cheap live `count(*)` of public notes is positive, is treated as a failure, never published. A tag absent from a **healthy** snapshot returns an empty listing (correct); an unhealthy or missing snapshot never does.
- *Bounded memory:* a hard cap (for example 100,000 notes or 1,000,000 tag entries; today's footprint is well under 1 MB); beyond it the snapshot refuses to build and the fallback applies. Footprint is logged at refresh.
- *No stale-forever:* a snapshot older than the ceiling is never served, whatever the failure.

**Remaining risk after Release 1 (honest).** (a) The tag-filtered count is covered because it shares the predicate; the **listing projections (17% of DB time), the program and tag facets (7%) and creator-impact (6%) remain**, so total DB time falls by an estimated third (the tag-filtered ranked page and its count are 42% of the quiet-period mix, and the benchmark removes most of their cost; H, not measured on production). The projection cost has a likely cause (a grouped program-name subquery over all public notes in `NOTE_LIST_ITEMS_FROM`, `:121`) that I did not benchmark and that is **deliberately out of Release 1** (its SQL is pinned by golden files from #1498); it is the next candidate. (b) The optimization does not stop deploy-time overlap, so a kill after the deploy remains possible. (c) A bypassing caller can still make the other endpoints expensive; the limiter is Release 2. (d) The benchmark cannot show the production-only effects of a colder cache and `shared_buffers` of 64 MB.

## 5. Deployment checklist (mandatory for every deploy in this plan) and diagnostic-logging controls

**Stated plainly: any Render deploy overlaps two connection pools on a database that peaked at 258.7 MB (96% of its limit) at the last one.** Do not assume that a signal 9 on the backend means the database restarted: a kill of a database backend makes the postmaster terminate the other backends and run crash recovery while the postmaster itself survives (`pg_postmaster_start_time` still reads 2026-06-11); read the Render event log and the database's own log to see which it was.

**Before (owner, with the owner's go-ahead for the specific deploy):**
1. **Verified backup.** Confirm in the Render dashboard what recovery this instance has (per Render's documentation paid databases have point-in-time recovery with a window that depends on the workspace plan, and logical exports are kept for 7 days; **I could not verify either for `basic_256mb` or this workspace**). Take a fresh logical export and check that it completes.
2. **Restore rehearsal into an isolated database.** Restore that export into a separate, empty database (a new instance or, if free of charge, a local PostgreSQL 18; this is the owner's run, with no production credentials given to me) and run `select count(*) from notes` and one public listing query against it. A backup that has never been restored is not a backup.
3. **Off-peak timing.** The quietest hour by the Render request metrics (about 150 backend requests an hour before the 10-28 burst); never during or within 30 minutes after a burst.
4. **Current health, read just before:** database memory (must be under 200 MB at rest; investigate if above), CPU, active connections (about 20 at rest), and the kill log for the previous 24 hours. If any non-deploy kill occurred in the last 24 hours, **do not deploy**.
5. **Pool overlap, stated:** old and new instance each hold up to 20 connections (`maximum-pool-size` 20, `minimum-idle` unset so 20 idle) for about 3 minutes, so the database sees up to 40. **No HikariCP change in Release 1.** `DataSourcePoolContractTest` bounds the pool at 45.
6. **Vercel build coincidence:** state whether a Vercel production build will run at the same time. With Step 0 live it makes one request; without it, 393. Deploy Step 0 first and let it settle (24 hours).
7. **Rollback is not instant, and it overlaps too.** Reverting the Render deployment, or changing an environment variable such as the snapshot TTL, **triggers another deploy and its own 3-minute pool overlap**; an environment-variable save is not a kill switch. So the new behaviour must be **bounded and self-limiting** (the fallback ceiling and bulkhead above) rather than something to switch off in an emergency. Never use the Render MCP's environment update.

**During (30 minutes minimum):** watch database memory and active connections each minute, the kill log (`text: signal 9`), backend 5xx, and Vercel's runtime error summary. **Stop conditions:** memory above 250 MB, a kill, 5xx above 2% for 5 minutes, or connections that do not return to about 20 within 5 minutes after the new instance is live. On a stop condition the owner decides on rollback with the cost above in view; do not roll back reflexively and create a second overlap.

**After:** 24 hours of the kill log; the gate C criteria in section 7.

**Recovery (owner actions):** if the database was restarted, wait for crash recovery and confirm the application's pool reconnected (a health read and one public listing); if data is suspect, use the verified backup per the rehearsal; if a second kill follows within 24 hours, that is an upgrade trigger (section 8).

### Diagnostic logging (Release 1, minimal and temporary)

**Goal:** identify who calls the public API directly and which tags and parameters they send, because no request log exists and Vercel Hobby keeps runtime logs for 1 hour.
- **Content, per aggregated minute rather than per request:** request count, count of distinct clients, the **names** of the query parameters seen (never their values, except the tag slug in an aggregate top-N, which is public catalog vocabulary), top user agents by count (**capped string, not a hash**: the user agent is what separates a named crawler from a headless fleet), and the status-code histogram. Plus **sampled** per-request lines only while the rate exceeds a threshold, hard-capped (for example 20 lines a minute) so a burst cannot flood the log or the 0.1 CPU.
- **The client address.** Truncating to a /24 (or a /48 for IPv6) **does not make it anonymous**: it can still identify a small network and counts as personal data in many regimes, and hashing it would not change that for a small address space. Log it only inside the sampled lines, truncated, and treat the log as personal data. **Which header carries the real client address behind Render's proxy is UNVERIFIED** (community reports say the proxy appends to `X-Forwarded-For` and does not strip a caller-supplied value, which would make the leftmost entry forgeable). The first diagnostic output must therefore log the raw count of `X-Forwarded-For` entries and the presence of `True-Client-IP`, no values, so the right header is chosen from evidence before any limiter keys on it.
- **Retention:** Render's service-log retention (7, 14 or 30 days by workspace plan; the plan is not read) is the retention; nothing is copied elsewhere. **Access:** Render workspace members and the Render MCP read tools only. **Off-switch:** a property that defaults to on until a fixed review date; **turning it off needs a redeploy** (the brief says so), so the logger is bounded by design (aggregation, caps) rather than relying on being switched off. It is removed in the release after its question is answered.
- **Privacy review:** no cookies, no tokens, no request bodies, no values of free-text parameters (search text).

## 7. Operational gates

The three states are different and each must pass: **(a) a quiet database** (proves nothing), **(b) healthy under representative real traffic**, **(c) healthy through a deploy.** The gate is a **HOLD evaluated against fixed criteria, not reset by every new kill**: a non-deploy kill restarts gate B's 72-hour clock; a deploy-adjacent kill is evidence for gate C, not a reason to restart B. **No artificial production traffic and no load test against production will be used to satisfy any gate**; B must be met by organic traffic, and if organic traffic is too low to exercise it, the gate says so and the call is the owner's.

**Hard safety requirements (a failure blocks, regardless of any target):**
- Ranked-listing results equal the previous implementation's on the parity suite (ordered ids and counts).
- No private, unpublished or deleted note is ever listed.
- Snapshot failures are never cached, and fallback is bounded (no storm).
- A verified backup and a completed restore rehearsal exist before each deploy.
- The owner approves each deploy separately; no deploy during a burst or within 24 hours of a non-deploy kill.
- SEO parity: sitemap URL set, canonicals and robots unchanged.

**Gate A, optimization success (before any production claim):**
- *Hard:* the parity suite passes on real PostgreSQL; the tag-filtered ranked call at 0.1 CPU is faster than current at the benchmark's median and p95 for every sort tested, with no regression for the untagged or nonexistent-tag case (equal within noise in the benchmark).
- *Provisional target:* at least **3x** the throughput of the current statement at 0.1 CPU with 8 callers (measured 5.4x for Option B and 1.8x for Option A, so Option A would miss it); plan-stability test within 2x. **There is no fixed "share of SQL time" as the sole measure**, because the share shrinks when other things change; after deployment the report gives the ranked listing's calls, mean, p95 and total DB time per hour, with the quiet-period baseline (33% share, mean 1.37 s) as context.

**Gate B, production stability:** *Hard:* **zero signal-9 kills in 72 hours** of organic operation after Release 1 is live (a kill within a deploy's first hour is attributed to gate C). *Provisional targets:* database memory maximum at or below 250 MB and p95 at or below 235 MB; CPU maximum at or below 0.08; connections at or below 25 outside deploys; zero new "Could not load public note" or "fetch failed" groups on `/signup` and the public pages in Vercel's runtime error summary. If organic traffic never exceeds the quiet level (about 150 backend requests an hour) during the 72 hours, report that the window was quiet and extend it rather than declaring success.

**Gate C, deployment safety:** *Hard:* **one separately approved controlled deploy** completed under the section 5 checklist, followed by **24 hours with no kill**. *Provisional targets:* peak memory at or below 250 MB, connections peaking at no more than 40 and back to about 20 within 5 minutes.

**Crawlers and discovery (monitor, not a gate):** the sitemap and `robots.txt` fetch; human page views on public pages (Vercel Web Analytics) and referrals do not fall materially against the week before. View-event counts are not a valid measure (they include bots and have no dedupe).

When A, B and C pass, `v0.176.0` and `v0.177.0` may be merged, each with its own deploy approval.
