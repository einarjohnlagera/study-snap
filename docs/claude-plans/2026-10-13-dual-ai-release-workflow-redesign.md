Planning-question answers are tagged inline as **(PQ1)** … **(PQ10)** so coverage can be checked by scanning.

**Premise in one paragraph.** Claude Pro runs out before the weekly reset and Codex Plus is underused. The fact sheet points to three cost drivers. ## 1. Recommended operating model

**Release Implementor stays the end-to-end Release Manager.** Its relationship to Codex follows the handoff-and-stop pattern that Feature Planner and Prod Investigator already use:

Release Implementor writes the brief and judges the evidence. It does not do bulk exploration, bulk implementation, or first-pass review. Codex does that work through `codex exec` (implementation, exploration) and `codex review` (first-pass review), both verified in installed `codex-cli 0.158.0`.

**Smallest practical boundary (PQ1).** Each role owns one kind of artifact:
- Feature Planner owns the **contract**.
- Note Strategist owns the **curriculum plan**.
- Prod Investigator owns the **finding**.
- Codex owns the **diff and its tests**.
- Release Implementor owns the **release state and the acceptance verdict**.

A role may read another role's artifact. It never edits it. Change requests go back to the artifact's owner.

**Where defect correction goes (D7, provisionally adopted; this reverses the first draft).** The model has three parts:
- **Codex fixes every confirmed implementation defect.** That covers defects found while a feature is being built (failing tests, audit-diff findings) **and** defects found at signoff or in the pre-signoff pressure test.
- **The independent reviewer or falsification agent stays strictly read-only, always.** That means both the Opus cold agent and any Codex read-only leg. It finds and reports, and never fixes anything itself. A Codex fix runs as a **separate** `workspace-write` invocation with its own brief, and never inside the review leg.
- **Release Implementor's job is to verify the correction.** First it confirms the finding in code. After Codex applies the fix, it re-checks that the specific defect is actually gone. Codex saying so is not enough. Only then is the finding counted as resolved.

**The tiny inline exception is unchanged.** It follows the existing Tier-S routing thresholds: a one-line, obviously correct fix can still be made inline by whoever is already in the loop, same as today.

**✅ Re-confirmed directly by the owner, 2026-10-14 — no longer open.** D7 reversed a decision recorded in the owner's long-term memory (`feedback_pressure_test_opus_and_codex.md`: "Claude, never Codex, implements fixes from pressure-test findings"). All nine D-decisions in this plan arrived the same way — through a relayed Product-UX note — so the relay itself wasn't what made D7 different. What made D7 different is that it was the only one that **overrides a specific, previously recorded instruction** rather than confirming or extending the plan's own first-draft recommendation. That direct re-confirmation has now happened, and the memory file has been updated to match.

## 5. Context-reset and handoff protocol

**State that survives `/clear` (PQ5).** No new document type. Release state already has a home:
- **Release progress:** the current version's `RELEASES.md` section. Each scope bullet carries `[queued | with-Codex | in-audit | merged-to-release | blocked: <reason>]`. Release Implementor updates the marker when it changes, in its own small commit decoupled from any feature PR (below). Markers ride along with the next such commit and are never a separate "commit?" ask.
- **In-flight work detail:** the contract's own `docs/claude-plans/*.md` file and its `Status:` header.
- **Codex runs:** the per-item worktree path and the feature branch name, recorded in the scope bullet, never a transcript. Since Codex runs directly inside that worktree (no patch-transfer step, §4), the worktree path IS the handoff — nothing else needs to survive `/clear` for this purpose.

**`RELEASES.md` has exactly one writer: Release Implementor — and it edits the file directly in the shared tree, which is exactly what today's workflow already does.**

This is the structural fix, not just a naming convention, but it's narrower than an earlier draft of this revision made it: that draft gave Release Implementor a *separate* worktree for release-management work, which would have broken `CLAUDE.md`'s auto-injection for every session (§4's "Isolation" explains why, with the `git reflog` evidence). The real hazard Product UX named isn't "Release Implementor edits a file in the shared tree" — every role already does that for its own artifacts without incident. It's specifically **feature-branch checkouts** happening in that shared directory, which move every other session's view along with them. That risk is removed by taking feature work out of the shared tree entirely (§4's per-item worktrees), not by moving `RELEASES.md` out of it.

So the actual design is:
- **The shared tree** stays checked out on `releases/vX.Y.Z` for the whole release, same as today (confirmed via `git reflog`, §4). Release Implementor edits `RELEASES.md` and makes the kickoff/signoff commits there, directly.
- **A separate per-item worktree per Codex task** (§4 step 4), on its own new branch off the shared tree's current tip. This is where Codex works, where Release Implementor reviews, and where the commit for that item happens — never in the shared tree.
- **Feature PRs never touch `RELEASES.md`.** Codex's final message states the scope-bullet text for the item; Release Implementor writes the actual `RELEASES.md` update itself, as its own small commit directly in the shared tree (an existing `CLAUDE.md` exception already covers small doc-only commits straight to the release branch). This is a deliberate change from today's per-PR-bullet habit, made specifically so that pulling a merged feature branch into the shared tree can never collide with an uncommitted or differently-shaped `RELEASES.md` edit — there is nothing in the feature branch's diff to collide with.

**On the session's own working directory:** the memory system keys off the directory a session is **launched** from, not a directory it `cd`s into mid-session — a Bash `cd` doesn't move it, and this harness resets the shell's cwd after every tool call anyway (observed directly in this session's own sandbox tests). Release Implementor's conversational session launches from the repo root (the shared tree), same as today and same as every other role; git operations against a per-item worktree use `git -C <path> <command>` or an ordinary `cd` inside a single Bash call — either is fine, since neither persists past that call.

With this design, there is exactly one writer of `RELEASES.md`, and the one new rule that actually prevents a collision is "no feature PR touches this file" — not a separate worktree. The only residual shared-tree risk is a broad `git add` sweeping in unrelated uncommitted edits — already covered by the existing `git add <specific-file>` discipline (`dd9b5329`).

**Codex is a second potential writer, and it has no built-in guardrail against it.** Confirmed by grep (§3): `AGENTS.md`'s first mention of `RELEASES.md` sits at character 186,438, past the ~32,278-character window Codex auto-loads. So every Codex brief (§4 step 3) must explicitly instruct: *"Do not edit `RELEASES.md`. Report your scope-bullet status text in your final message instead."* Because Codex only ever works inside its own per-item worktree, never the shared tree where `RELEASES.md` lives, a violation of this instruction would show up as a visible diff against `RELEASES.md` in that worktree during the evidence check (§4 step 7), before anything is committed, and the "PR carries code, tests and the feature-doc update only — never `RELEASES.md`" rule above means it could never land even if missed there.

- Other roles signal status through their own plan file's existing `Status:` header convention (e.g. `Status: ready for release`), never by touching `RELEASES.md`.
- Release Implementor polls those plan-file headers at scope-lock time (§4 step 2) and whenever it sequences the next brief. It is the only party that then writes the matching `RELEASES.md` bullet or marker, directly in the shared tree.

**✅ Owner decision, 2026-10-14: `ROADMAP.md`'s Backlog Index gets the identical single-writer fix, for the identical reason.** The D3 cross-role consistency review (§7 M3) surfaced that `ROADMAP.md` had **four** uncoordinated writers — Feature Planner (a row "in the same pass" that finalizes a plan), Note Strategist (a row per working set), Prod Investigator (a row per finding), and Release Implementor (version sections, `Last reviewed` bumps, CHECKPOINT rows) — the same shared-tree hazard `RELEASES.md` was just fixed for (`dd9b5329`: one session's uncommitted edit swept into another's commit). **Release Implementor is now the sole writer of `ROADMAP.md`'s Backlog Index, directly in the shared tree.** Other roles signal a new or updated Backlog item through their own plan/finding file's `Status:` header, exactly as they already do for `RELEASES.md` — never by touching `ROADMAP.md` directly. Release Implementor polls those headers at scope-lock time and at kickoff step 8's existing unindexed-file scan, and writes the matching Backlog row itself. **This reverses Feature Planner's previously-stated "same pass" habit** (its own charter said it writes a Backlog row "in the same pass that finalizes" a plan) — that charter, and Note Strategist's and Prod Investigator's, need updating to match.

**Fresh-session bootstrap (PQ6).** The recommended default is decided by D2 and gated by the dry run in D5.

- **Default now (zero new risk):** every role session starts with one fixed opener:
  > `You are <Role>. Read docs/agents/claude/<role>.md, then the current RELEASES.md section, then report the release status and your next action in ≤10 lines.`

  The charter ends with a "how to use in a fresh session" block copied in shape from `docs/agents/gpt/NoteLib Product UX.md`.

  `claude --name "<Role>" --agent <role>`. The `.claude/agents/<role>.md` file is a thin pointer to the charter, and the persona persists across `--resume`.

  Add a `hooks.SessionStart` hook in `.claude/settings.json` on matchers `startup|resume|clear|compact`. This needs `--agent` (or `--name`) at launch, because `agent_type` and `session_title` are empty otherwise. That is why the launch command matters.

  The background form `claude --bg --name … --agent …` is documented. **The interactive equivalent is unconfirmed**, and **whether settings or commands reload on `/clear` is unverified.** The dry run tests both.

**Cold-spawn hygiene (if D2 = `--agent`).** Every `.claude/agents/*.md` file becomes a spawnable `subagent_type` in every session. That means another role could one-shot-spawn a fake "release-implementor". Mitigations:

- Each pointer file's `description` should read "Persona for the named interactive session only — do not delegate to this agent."

No per-file "persona only" flag was found, so this is hygiene, not enforcement.

**Cutting duplicated investigation (PQ2).**
- Contracts carry **file-path anchors** from the planner. Codex explores; Claude doesn't.
- Codex feasibility output is summarised into the contract or brief once, and never re-derived.
- Claude roles read `AGENTS.md` **by targeted section** (grep the heading), not whole. At ~214k chars a whole read is the single most expensive read. Codex auto-loads only the first ~32k characters of it (confirmed, see §3) — not the whole file — so Claude still needs to read and excerpt the relevant rule into the brief; it is not safe to assume Codex already has it. The gated D9 restructure (front-loaded core rules, plus `docs/archive/AGENTS_ARCHIVE.md`) shrinks both costs once executed.
- Delegations to cold agents carry a fact sheet. This document is an example.
- The `CLAUDE.md` trim (D4, gated on the M5 pilot measurement plus safety verification) is the per-turn saving.

## 6. Risk-based audit policy

This **extends the existing 3-tier `/audit-diff` structure**. It adds a Codex first-pass layer underneath and makes the pressure-test choice explicit. No new invention.

| Tier | Applies when | Codex does | Claude does | Artifact |
|---|---|---|---|---|
| **S — Small** | Copy, CSS, a prop, a single-method fix in 1–3 files with a clear root cause. No migration, endpoint, auth, money or quota change. | Nothing, if Claude implemented it inline (D1). Otherwise `codex review`. | Inline checklist only, plus "did a test move beside the behaviour change?" | **None.** One `RELEASES.md` bullet. |
| **N — Normal** | New endpoint, service logic, migration without data mutation, multi-file feature | Implementation, tests, `codex review` | `/audit-diff` inline checklist **plus one `advisor()` on the diff**. **When Codex review alone is enough vs. when Claude review is mandatory (PQ4).**
- `codex review` alone is enough for **nothing that merges**. Claude's acceptance audit is always the gate, but for Tier S/N it is the cheap inline checklist, which is where the saving comes from.
- Deeper Claude review (cold agent) is mandatory at Tier H. This is not optional just because Codex built the code: historically every blocking finding traced to the **implementer's own unverified claim**. Codex inherits a flawed brief's premises exactly as Claude does, so fresh-context review keeps its value.
- Every Codex review finding is **verified in code before it is acted on**, because past reports contained overstatements and mix-ups.

**Worked example — `v0.170.0` signoff (real, already executed).** The release added a data-mutating migration and touched 5+ areas. Two rule checks decided the tier:
1. `git diff --name-only` across the two PRs showed **no shared Java method**.
2. The touched surface (goal/content exclusivity) was a **profile-preference rule, not an access-control boundary**: no cross-user read, no money or quota change.

So the full-test trigger did not fire, and Release Implementor ran **one Opus cold falsification agent against 7 named claims**. That is Tier H, scoped variant. It is the template: name the checks, record why the full test did not trigger, list the claims.

**Directory for the optional Codex falsification leg.** This runs against the release's finished code, not any one item's per-item worktree, and it must not depend on whatever the shared tree happens to be checked out on at that moment. Release Implementor creates a disposable **detached** worktree of the release branch's current tip for the duration of the leg: `git worktree add --detach <tmp-path> releases/vX.Y.Z`, then `codex exec -C <tmp-path> --sandbox read-only "<falsification brief>"`. Verified directly: a detached checkout of a branch does not conflict with that same branch already being checked out elsewhere (unlike a second *branch* checkout, which git refuses) — so this works regardless of what the shared tree or any per-item worktree is doing at the time. Remove the detached worktree once the leg finishes.

**Honest gap: as written, this plan does not reduce the single largest known cost line.** `v0.93.0`'s full pressure test ran ~490k tokens across three Claude agents, and the owner's standing correction keeps the Tier-H cold agent on **Opus**, mandatory, with a Codex pass only as an **optional extra** leg. ## Recommended approach

Keep Release Implementor as Release Manager and change **what it spends tokens on**, not what it owns. These go to Codex through a standard brief (`codex exec` / `codex review`): exploration, implementation, tests, first-pass review, and **every confirmed defect fix, including signoff and pressure-test findings** (D7). Release Implementor writes the brief, judges the evidence with the existing `/audit-diff` (extended to Tiers S/N/H), and **verifies each correction** Codex applies. Review and falsification legs stay strictly read-only. Small contained fixes stay inline per your 2026-08-14 preference (D1).

Codex works directly inside a fresh **per-item git worktree** that Release Implementor creates for each task, off the shared tree's own current tip — never in the shared tree itself. There is no patch, no transfer step, and no `codex apply`: review and commit happen in the exact worktree Codex worked in. This topology was verified with real `git worktree add` commands in a throwaway sandbox repo: a branch cannot be checked out in two worktrees at once (confirmed it fails cleanly, which is why the per-item worktree uses its own new branch, not the release branch), and a per-item worktree on its own branch works with no conflict even while the shared tree has the release branch checked out. Release Implementor commits only on the owner's "commit" and opens the usual PR into the release branch — that PR carries code, tests and the feature-doc update, never a `RELEASES.md` change.

Release state lives in status markers on the `RELEASES.md` scope bullets, and **Release Implementor is the only role that ever edits `RELEASES.md`, directly in the shared tree.** This is exactly what today's single-session workflow already does (confirmed via `git reflog`: the shared tree already sits on the release branch for the release's duration), so the design doesn't move that file out of the shared tree — it instead takes feature-branch work *out* into per-item worktrees, since that was the part actually unsafe with four persistent sessions. Codex is a second potential writer with no built-in protection for that file (confirmed: `AGENTS.md`'s first mention of it sits past Codex's auto-load window) — every brief forbids it explicitly, Codex never has access to the shared tree, and the "PR carries code, tests and the feature-doc update only" rule means a violation couldn't merge even if missed. No `docs/workflow/` files. Fix the existing two-copy ritual drift instead, keeping the one deliberate exception, the archive check.
