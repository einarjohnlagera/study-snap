# v0.100.0 — Domain Context A–F implementation audit

**Run 2026-09-01, against real code on `releases/v0.100.0`.** Owed by the 13 ratified Stage 2 decisions
before any implementation; recorded as unrun in `RELEASES.md`, `ROADMAP.md` and `CLAUDE.md`.

**Method:** every claim below was read out of the source, not inherited from the Stage 1/Stage 2 audit.
Enforcement points were enumerated mechanically (`grep` on the exception type *and* on the assert helper)
rather than trusted from the decision text, because the anti-drift rule for item 3 requires exactly that.

---

## ⚠️ Headline: two of the enforcement points are already where Decision 6 wants them — and the path that matters most has none

The kickoff records *"four write paths, hard-blocked at save."* **The count is not the finding, and it is
worth being precise rather than dramatic about it:** there are **five call sites** but **four write paths**
across four files, because `NoteService` create and update share one helper. By either count the load-bearing
discovery is the same, and it is not arithmetic:

**Two of the enforcement points are ALREADY at generation time**, which is exactly where Decision 6 wants
them — so only **three save-time sites** actually move. And **the primary generation path validates
nothing.**

| # | Site | When | Under Decision 6 |
|---|---|---|---|
| 1 | `NoteService:181` (create), via `assertMultiProgramHasDomainContext:1470` | **save** | moves |
| 2 | `NoteService:231` (update), same helper | **save** | moves |
| 3 | `NoteApplicableProgramsService:75` (replace programs) | **save** | moves |
| 4 | `NoteGenerationService:75` (topic generation, curator branch) | **already generation** | stays |
| 5 | `NoteBulkGenerationService:466` (bulk batch normalization) | **already generation** | stays |

**⚠️ THE FINDING THAT CHANGES THE WORK: `StudyPackService.startAsyncGenerationFromNote` — the primary
note → Study Pack path, and the one every learner and most curator notes actually use — VALIDATES NOTHING.**
It calls `generationContextResolver.resolve(...)` at `:207` and proceeds. Today that is safe *only because
the save-time block guarantees the state cannot exist.* **Move the block without adding a gate here and
Decision 6 does not relocate the invariant — it deletes it for the path that matters most.**

**The failure is silent, which is what makes it serious.** With no Domain Context and 2+ joined programs,
`resolveCourseProgram:131` fails the `size() == 1` test and falls to `firstNonBlank(note.getCourseProgram(),
profileCourseProgram)`. For a curator note `note.getCourseProgram()` is **already null** (`NoteService:182`
nulls it by design), so it resolves to **the curator's own profile program** — and if that too is blank,
`effectiveAuthoringDomain` returns null and `OpenAiLlmStudyPackService:1577-1581` **omits the `Domain:` line
and `DOMAIN_CONSTRAINT` entirely, with no error and no log.**

**⚠️ So Decisions 4 and 6 are coupled too, not just 1 and 4.** Decision 4 exists to stop the curator's
profile program reaching the prompt. Decision 6, implemented naively, **re-opens that exact defect through a
new door** — and widens it, because the state becomes legal going forward rather than being confined to
pre-invariant rows.

**Recommendation:** item 3 is not "move three checks." It is **"add generation-readiness enforcement to
`startAsyncGenerationFromNote`, then remove the three save-time blocks"** — in that order, so the invariant
is never unprotected between commits.

## A. Resolver boundary

**A1. The profile fallback has THREE entry points, not one.** Decision 4 is usually discussed as though it
were a single line:

- `resolveCourseProgram:134` — `firstNonBlank(note.getCourseProgram(), profileCourseProgram)`, the note path
- `resolveBulkCourseProgram:149` — same shape, the bulk/topic path
- `buildFromStudyPackFallback:159` — `user.getCourseProgram()` **unconditionally**, when a Study Pack has no
  reachable source note

**⚠️ A3 is the one that will be missed.** It is reached via `resolveForStudyPack` when `findSourceNote`
returns empty — a Study Pack whose note was deleted, or is not owned by the caller. It takes the profile
program with no note involvement at all, so a fix scoped to `resolveCourseProgram` leaves it live.

**A2. Conflict 3 of the Stage 2 audit is HALF right, and the wrong half is load-bearing.** It says the
curator boundary "already exists, no brittle role check needs inventing." The *predicate* exists. It is
**not reachable from the resolver**, because all four copies are private or inlined:

| Class | Form |
|---|---|
| `NoteService:1524` | `private boolean isTeacherSelectableOwner` |
| `NoteGenerationService:116` | `private boolean isCurator` |
| `NoteBulkGenerationService:411` | `private boolean isCurator` |
| `NoteApplicableProgramsService:122` | **inlined, not even a named method** |

All four are `onboardingCompletedAt != null && (ADMIN || TEACHER)`. `NoteApplicableProgramsService`'s own
comment calls itself *"the FOURTH curator predicate"* and notes it was created without the onboarding guard
in the very release that added the guard to the third.

**⚠️ Decision 4 needs a FIFTH call site — in the resolver — and adding a fifth copy is the wrong move.**
Extract the predicate to one shared component and have all five use it. This is the cheapest moment: the
release already touches three of the four classes.

**A3. The resolver already has the data it needs.** `resolve(ownerUserId, note)` loads the `UserEntity`
(`:37`). Only the predicate is missing, not a repository or a parameter.

**⚠️ A4. THE IDENTITY PASSED TO THE RESOLVER IS NOT CONSISTENT, AND CHECKING IT FOUND A LIVE SECOND LEAK.**
All 18 call sites were enumerated (`grep` on `generationContextResolver.`). `AdminStudyPackTransactionHelper:147`
passes `note.getOwnerUserId()`; **every other site passes the CALLER** (`ownerUserId` / `userId`).

That difference is live, not latent, on the twelve `resolveForStudyPack(callerId, studyPack)` sites that
drive quiz, exam, interview and adaptive-practice generation. `resolveForStudyPack:57` calls
`findSourceNote`, which is `findByIdAndOwnerUserId` — so **when a learner practises a curator's public Study
Pack, the source-note lookup returns empty**, falls through to `buildFromStudyPackFallback:159`, and the
authoring domain becomes **that learner's own profile course program.**

**⚠️ This is Decision 4's invariant broken on the READER axis rather than the author axis:** two learners
generating a quiz from the *same canonical pack* get **different authoring-domain instructions** because
their personal profiles differ. Decision 4's stated invariant names two curators; the same argument applies
here verbatim, and this path is far more heavily trafficked.

**Recorded, and explicitly NOT auto-scoped into this release** — it is adjacent to Decision 4 rather than
named by it, and folding it in without an owner call would widen a release that is already re-shaped.
**It should be an explicit owner decision, because it is the larger of the two leaks by volume.**

## B. Effective-domain exposure

**B1. Decision 2's value is ALREADY COMPUTED, backend-side, as a public static.**
`StudyPackGenerationContextResolver.effectiveAuthoringDomain(context)` (`:167`) returns the Domain Context
label when set, else the resolved course program. **This is precisely the "effective writing domain"
Decision 2 asks for, and it is the same function the prompt builder uses** — so reusing it satisfies
Decision 2's "never a frontend re-implementation" constraint *by construction* rather than by discipline.

**B2. It has ZERO production callers outside the prompt builder** — three sites in
`OpenAiLlmStudyPackService` (`:1577`, `:1625`, `:1648`) and nothing else. **It appears in no DTO and no
controller.** So Decision 2 needs a new *read path*, but **no new logic**.

**B3. `Writing domain needs attention` maps exactly to `effectiveAuthoringDomain(...) == null`** — the same
condition under which the prompt silently drops its `Domain:` line. That is a clean, honest mapping and it
means the UI state and the generation behaviour cannot drift apart.

**⚠️ B4. The resolver is a `@Service` with four repository dependencies and `resolve` performs a
`findByNoteId` query.** Exposing the effective domain on a note-detail read adds a query per note. Fine for
a detail view; **do not put it on a list endpoint** without batching.

## C. Generation readiness

Covered in the headline. Three further points:

**C1. Decision 6 falsifies a deliberate, recently-argued fix.** `NoteService:218-231` carries a long comment
explaining that the learner branch computes `effectiveProgramCount` from **stored rows** because *"a learner
could clear domainContext on a copied multi-program note and the client was the only thing preventing it."*
Decision 6 makes that legal again at save. **That is the ruling working as intended, not a regression** —
but the comment must be rewritten, not deleted, or the next reader will restore the block.

**C2. The two already-generation-time checks are curator-only.** `NoteGenerationService:75` sits inside
`if (isCurator(user))`; `NoteBulkGenerationService:466` guards `courseProgramIds`, which is `Set.of()` for a
non-curator. **So no learner path has generation-time enforcement anywhere today.** After C1 removes the
learner save-time block, the learner multi-program case is unguarded end to end unless the new
`startAsyncGenerationFromNote` gate covers both authors.

**C3. `MultiProgramDomainContextRequiredException` extends `AppException`** and is a real error contract with
a code and message. Moving enforcement must keep it — the generation path should fail with the same
exception, so the frontend's existing handling keeps working and no new error vocabulary appears.

## D. Exact copy

**D1. `Automatic — based on the program` has THREE sites:**
`bulk-generation-page-client.tsx:627`, `private-note-detail-page-client.tsx:2457`, `note-editor-form.tsx:490`.

**⚠️ D2. THE FIND-AND-REPLACE TRAP: each of those files has a SIBLING string three lines later —
`Automatic — based on the reader` (`:656`, `:2487`, `:518`) — which is AUTHORED DEPTH, not Domain Context.**
Decision 1 governs the domain label only. A careless sweep changes both and silently rewrites a second
axis's copy. **`based on the reader` is also accurate** for depth, since `effectiveCurriculumLevel:177` does
fall back to the profile level.

**D3. Decision 3 has no existing string to edit — the copy must be written new.** There is no per-note
helper text explaining what Applicable Programs do. The only nearby prose is the admin page header
(`app/admin/course-programs/page.tsx:29-32`, *"which programs a note is discoverable under"*), which is
page-level and does not state the boundary Decision 3 asks for.

**D4. `ENGINEERING_MATHEMATICS`'s description is the carried item and it is still unfixed**
(`lib/domain-context.ts:7`). It enumerates subjects (*Algebra … Engineering Economics*) and never states the
selection rule: a note belongs here when it **teaches** the computational method, not when it **uses** one.
**⚠️ Opposite failure mode from Decision 13's rubric** — that one asks whether a description makes a broad
value look *narrower*; this makes a narrow value look *broader*.

**D5. Decision 13's sweep has a clear target list — counted, not estimated.** **THREE** descriptions were
revised in `v0.99.0` and carry explanatory comments (`ENGINEERING_SCIENCES`, `CIVIL_ENGINEERING`,
`PROFESSIONAL_PRACTICE_AND_REGULATION`). **FIVE have never been reviewed** and are bare one-liners:
`ENGINEERING_MATHEMATICS` (which is D4 above), `GENERAL_EDUCATION`, `PROFESSIONAL_EDUCATION`, `NURSING`,
`ACCOUNTANCY`. **⚠️ Three of those five are the zero-usage values
`[CHECKPOINT — due 2026-09-28]` reads** — so revising them is legitimate copy work but **changes the very
input the checkpoint measures.** Record the deploy-split caveat with the checkpoint, or the September read
cannot separate "curators finally understood the value" from "the description changed."

## E. Observability

**E1. Confirmed: Domain Context authoring emits nothing.** No `DOMAIN_*` value exists in
`AnalyticsEventType` (146 lines, read directly).

**E2. `NOTE_CREATED` is the natural host and needs no new event.** It fires at `NoteService:203` with
`buildMetadata("subject", …, "visibility", …)` into a `jsonb` `metadata_json` column
(`AnalyticsEventEntity:39`), so **adding keys is free** — no migration, no enum change, no new endpoint.
This is the *smallest honest addition* Decision 9 asks for.

**⚠️ E3. Ordering is already correct, and it is load-bearing.** `NOTE_CREATED` fires at `:203`, **after**
`noteCourseProgramRepository.replace(...)` at `:201`. So the join rows exist and the Automatic-resolved
value is computable at that point. **Firing it earlier would make the resolved value wrong** for exactly the
multi-program notes this release is about.

**E4. Decision 11 needs a PAIR, and only the pair answers it:** what `Automatic` would have resolved, and
what was persisted. Equal → accepted; different → overridden; persisted-null → declined. One key each.

**⚠️ E5. `update` has no `NOTE_UPDATED` event, so overrides applied AFTER creation are invisible.** The
authoring surfaces that edit Domain Context are the note editor and note detail — both `update` paths.
**Instrumenting only `create` measures first-authoring choice, not override behaviour**, which is what
Decision 11 actually asks about. This gap must be closed or the September read will systematically
under-count overrides.

## F. Tests

**⚠️ F1. `StudyPackGenerationContextResolverTest:146` asserts the behaviour Decision 4 removes.**
`resolve_multiProgramNoteWithoutDomainContextFallsBackToASingleValueNotAList` asserts
`context.courseProgram()` equals the user's profile program `"Software Engineering"`. Its comment says *"The
invariant forbids this state going forward … but pre-invariant rows exist."* **Decision 6 makes the state
legal going forward, so that comment becomes false.**

**⚠️ The subtle part: this test will KEEP PASSING under a correctly curator-scoped Decision 4 fix**, because
its `UserEntity` has no role and no profile type and therefore reads as a learner — where profile fallback
legitimately survives. **A green test here is not evidence the fix works.** It needs a curator-owner twin
asserting the profile program is *not* inherited, or Decision 4 ships unverified.

**⚠️ F2. `NoteServiceTest:858` is directly falsified by Decision 6.**
`update_byLearnerOwner_rejectsClearingDomainContextOnAMultiProgramNote` pins the save-time rejection the
ruling removes. **It must be consciously rewritten to assert the new contract — cleared at save, rejected at
generation — never simply deleted**, or the release silently loses the only coverage of that transition.

**F3. Every resolver test is Mockito-mocked.** `NoteCourseProgramShadowing.isShadowed`,
`assertMultiProgramHasDomainContext` and the resolver fallbacks have **zero real-row coverage** — the
recurring gap `CLAUDE.md` records as this repo's most expensive test-quality failure.

**F4. Required, per the release's own anti-drift rule:** any predicate deciding whether a note may generate,
or which domain reaches the LLM, needs a real-row test with the killing test named. Minimum set:
a curator multi-program note with null Domain Context **saves**; the same note **fails generation** with
`MultiProgramDomainContextRequiredException`; a curator single-program note resolves to the **joined program
name**, not the profile; a learner note still resolves to the **profile** program.

## Consequences for the release as kicked off

1. **Item 3 is re-shaped, not re-sized.** Add the generation gate to `startAsyncGenerationFromNote` first,
   then remove three save-time blocks. Two of the five sites are already correct and must be left alone.
2. **Item 1 grows by one fallback site** (`buildFromStudyPackFallback:159`) and by a predicate extraction.
3. **Item 2 shrinks** — the value already exists as a public static; only exposure is missing.
4. **⚠️ ITEM 4 AS KICKED OFF IS INSUFFICIENT FOR THE READ IT EXISTS TO SERVE, and this is the finding most
   likely to be compressed away.** Item 4 says *"one authoring event."* But `NOTE_UPDATED` **does not
   exist** (confirmed absent from the 146-line enum), and **both surfaces that let a curator change Domain
   Context — the note editor and note detail — are `update` paths.** Instrumenting `create` alone measures
   *first-authoring choice*, not *override behaviour*, and override behaviour is the entire question
   Decision 11 asks. **Ship `create`-only and the September read comes back empty for the one thing it was
   built to answer.** Item 4 must cover the update path.
5. **Item 5 acquires a checkpoint interaction** — three of the four unreviewed descriptions are the
   zero-usage values `2026-09-28` reads.

**⚠️ Verification tier: the literal escalation trigger fired — *"escalate if item 3's four write paths turn
out not to be four."* They are five. But the trigger's SPIRIT did not fire**, and the distinction matters:
the count moved because two sites were already where the ruling wants them, and the newly-found risk
(`startAsyncGenerationFromNote`) is a **gap to close inside one method**, not a widening of blast radius.
**Recommendation: hold at one scoped cold agent, and hand it this document plus the specific claim to
falsify — that after implementation, no path can generate a Study Pack for a multi-program note with no
Domain Context, and no curator's profile program can reach a prompt.** Escalate only if the predicate
extraction turns out to change behaviour at any of the four existing call sites.
