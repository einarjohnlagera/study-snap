## §0. Correction to the brief's premise

The brief's *"Premise verified against current code, 2026-10-06"* line states: *"nothing in the persisted model already represents either concept below."* That is true only at the grain the brief checked (`NoteEntity`, `NoteCollectionEntity` — §9's own audit). It is **false at the profile grain**, and the gap matters because it changes what §11 is actually asking:

- **`UserEntity.studyGoal`** (`backend/src/main/java/com/studysnap/backend/entity/UserEntity.java:60`, `text`, nullable) is a persisted, single-valued **Learner Goal** in every sense the brief uses the term. It holds either free text (a subject name) or one of four validated licensure-exam slugs. It already drives real product behavior: `ProgressReportService.buildGoalSummary`/`buildGoalNudge` (`ProgressReportService.java:83-97, 353-448`) filter which generated Study Packs "qualify" for the goal and choose `GOAL_TYPE_EXAM` vs `GOAL_TYPE_SUBJECT` framing; the dashboard goal card, goal-prompt banner, and goal-nudge card all read it.
- **`course_programs.exam_goal_slug`** (`V106__course_program_catalog.sql:12,15-16`, `CHECK (... IN ('ale','pnle','let','cpale'))`) is a persisted, catalog-grain **Target Credential** taxonomy, already four licensure exams deep, backing `ExamGoalConfig.java` (short name, full name, fallback course-program list per exam). It is not hypothetical — it is live, constrained by a DB `CHECK`, and seeded at `V106:24-45`.
- **`UserEntity.examDate`** (`UserEntity.java:98`) is a second single-valued, profile-grain field in the same conceptual family.

None of this contradicts §9's narrower claim (no `goal`/`purpose`/`intent` field on `NoteEntity` or `NoteCollectionEntity` — still true, re-confirmed below). But §11 cannot be answered as "what grain should we invent this at" when a crude version of Learner Goal and Target Credential already exists, is wired into shipped behavior, and has a known shape with known gaps (single-valued; free-text-or-slug conflation; four-exam-only coverage with a documented asymmetry — see §10 below). The right frame for every question below is **"does the existing mechanism already solve this, partially solve it, or solve it wrongly"** — not "design from zero."

## §11 Questions, in order

### Q1. What concrete user/product problem are we solving?

**Owner decision — not resolved here.** The evidence below supports at least three different candidate problems, of different sizes, and the brief's own §1 warns against assuming they're the same problem. Presenting evidence for each rather than picking one:

- **Candidate A (narrowest, fully evidenced, but NOT necessarily cheap — see cost note below and Q11/Q12):** official Study Journeys that are licensure-exam-flavored (Review Sets for ALE/PNLE/LET/CPALE) are presented to a learner using the **learner's own `ProfileType`**, not the Journey's actual nature — a genuine gap in what the model can express, demonstrated in Q2, independent of any future taxonomy. **Cost caveat, found on review: this is not a cheap fix even if it needs zero new persistence, though its reach is narrower than first drafted.** The terminology half (`getCollectionLabels`) differs by `ProfileType` on every plan tier. The terminal-mode half (`resolvePlanPremiumExamMode`) only diverges by profile for `PRO`-plan accounts — every other plan collapses to `"challenge"` regardless of profile (`exam-mode-visibility.ts:75-77`) — so the mode question is a `PRO`-only presentation question, not an all-accounts one. Where it does apply, `resolvePlanPremiumExamMode` currently implements `docs/product/EXAM_MODES.md:26-30`'s own **locked** audience-by-profile mapping correctly; re-keying the terminal mode to the Journey's nature instead means amending a locked contract document, and runs directly against the brief's own §7 caution not to assume Journey Purpose changes quiz-mode behavior. "Zero new persistence" is not the same claim as "low cost" — the cost here is a product/contract decision, not an engineering one.
- **Candidate B (medium, partially evidenced):** `studyGoal`'s single-valuedness and free-text/slug conflation under-serves the existing BOARD_EXAM goal-nudge/progress-filter feature itself — a learner pursuing two licensure tracks, or using free text for a goal that happens to collide with nothing in `ExamGoalConfig`, gets degraded nudging. This is a quality problem with a shipped feature, not a new concept.
- **Candidate C (broadest, the brief's original framing):** canonical Notes should serve degree study, licensure prep, certification prep, interview prep, and professional upskilling without duplication or re-tagged Domain Context — the Computing BST example. This needs new representation only where Q11 shows membership insufficient, which for the *reuse* half of this candidate it is not (§2's own argument, confirmed by Q11) — the open part is purely in distinguishing journeys whose *audience experience* might legitimately differ (Q2's gap, generalized beyond licensure).

These are not mutually exclusive — A is a strict subset of C's gap surface, narrowed to the part that's already fully reproducible from code with no new data. **Recommend the owner pick a scope (A alone; A+B; or C in full) before Q12's minimum model is finalized**, since the minimum model differs materially by scope (see Q12).

### Q2. What behavior is impossible or incorrect with today's Study Journey identity, structure, membership, `ProfileType`, and learner state?

Reproducible from code, no production read needed — but the framing requires care, corrected below after an advisor pass caught an overclaim in the first draft:

- **Journey terminology is keyed to the viewer, not the Journey.** `getCollectionLabels(profileType)` (`frontend/lib/collection-labels.ts:98-100`) returns the Collection's display name purely from `ProfileType`: `STUDENT` → "Study Plan", `BOARD_EXAM` → "Review Set", `TEACHER` → "Lesson Plan". The Collection entity itself (`NoteCollectionEntity.java`) carries no field this reads instead. Confirmed this is the only use of the viewer's profile on the Explore catalog page too: `explore-page-client.tsx:33-34` derives `collectionProfileType` from the viewer and feeds it straight into `getCollectionLabels` — labeling only, not filtering.
- **The terminal exam-mode CTA is keyed the same way, but only for `PRO`-plan accounts.** `resolvePlanPremiumExamMode(profileType, planType)` (`frontend/lib/exam-mode-visibility.ts:71-91`) gates on plan first: any non-`PRO` plan returns `"challenge"` for every profile except `TEACHER`/unauthenticated (`:75-77`), so profile only changes the *terminal mode* for `PRO` accounts. Only there does `STUDENT` → `"long_exam"`, `BOARD_EXAM` → `"board_exam"`, `"PROFESSIONAL"` → `"interview"` diverge by profile, regardless of which Collection is open. **This narrows the mode half of the gap considerably — it is a `PRO`-only presentation question, not an all-plans one** — and this is NOT a bug. `docs/product/EXAM_MODES.md:26-30` is an explicitly **locked contract** whose own Mode Hierarchy table specifies audience by profile: Long Exam is "Student profile (primary), Board Taker (secondary)"; Board Exam is "Board Taker profile"; Interview Practice (sub-mode table) is "Professional profile." **`resolvePlanPremiumExamMode` implements this locked mapping correctly.** The real Q2 finding is narrower and more honest: *journey purpose is not an input to mode or terminology selection anywhere in the current model, and the locked contract keys modes on viewer audience by design* — a thing the current Study Journey model genuinely cannot express, not a defect in what's shipped. This also means the brief's own §7 caution ("do not assume Journey Purpose automatically changes... quiz behavior") already argues against changing this wiring lightly.
- **Catalog discovery and adoption are not restricted by `ProfileType` — verified directly, not inferred from an absence of hits.** `NoteCollectionController.listPublic(courseProgram)` (`NoteCollectionController.java:82`) is the backend endpoint behind official-catalog browsing; its only filter parameter is `courseProgram`. There is no `profileType` parameter on this endpoint, and nothing in `NoteCollectionService`'s adoption path (`adopt`/`adoptSource`, `NoteCollectionService.java:1078-1144`) reads the caller's profile either. **This means the cross-profile scenario is genuinely reachable, not merely un-forbidden, for any authenticated account**: any `ProfileType` can filter the public catalog by `courseProgram="Nursing"` and adopt whatever official Collections exist there, including a PNLE-flavored one, regardless of their own profile. (`explore-page-client.tsx:33`'s `authUser === null` fallback governs anonymous **browsing/labeling** only — `adopt`/`adoptSource` require a `userId`, so an unauthenticated visitor can see the catalog but not adopt from it.)

**So the accurate Q2 finding is: a learner can reach — through ordinary, unrestricted catalog browsing — an adopted Journey whose terminology and terminal exam mode are determined solely by their own `ProfileType`, with no way for the Journey's own nature to override that presentation, because no such journey-level signal exists or is consulted anywhere in presentation logic.** Whether that composition counts as "wrong" for a specific learner is itself a product judgment (e.g., whether a `STUDENT` who deliberately sought out licensure-prep content "should" see Board Exam mode is a product decision, not a fact this codebase can settle) — label it that way rather than as an established defect. What is established as fact, not judgment: no existing signal lets a Journey's own nature participate in that decision at all.

Separately, consistent with the brief's own §9: `ConceptHealth` (`ConceptHealthEntity.java`) is keyed on `(userId, studyPackId, concept)` with no purpose/goal dimension — learner state genuinely carries no purpose signal today, confirming that half of the premise.

### Q3. Is the missing concept Study Journey Purpose, Learner Goal, a target credential, a target professional role, some other concept, or no new persisted concept at all?

Given §0: **a crude Target Credential and a crude Learner Goal already exist** (`exam_goal_slug`, `studyGoal`). The open question is narrower than the brief frames it — not "do these concepts need inventing" but **"does Journey Purpose need to exist as its own thing, separate from the credential signal that already lives on `course_programs`."** Q2 shows the Journey's own nature currently has no path into presentation logic at all; whether making it one requires something beyond `courseProgram` is Q11's open empirical question, not yet settled — so it's not yet established that something journey-grained beyond the existing field is implicated, only that it might be, pending that read. Whether that something needs its own name/enum (`Study Journey Purpose`) or is better expressed by **strengthening the existing credential link at the journey grain** (e.g., a Review Set's own `courseProgram` resolving to `exam_goal_slug` being read by presentation logic, instead of `ProfileType`) is a Q11/Q12 question, not answerable here in isolation. **Target professional role has zero existing representation of any kind** — no field, no config, no precedent — consistent with the brief's caution (§6) not to infer it's needed from the hypothetical Software Engineer example alone.

### Q4. At what grain does each demonstrated behavior belong?

- The **Q2 gap** (terminology/terminal mode driven solely by viewer, never by the Journey) belongs at the **Study Journey grain** — it is a property of which Collection is open, not of who is viewing it or which Note is inside it. `NoteCollectionEntity` already has the grain for this (it has `id`, `courseProgram`); the question is which field presentation should read.
- **Learner Goal**, where it already exists (`studyGoal`), is at the **learner-profile grain**, not per-adoption. Q6 shows this is a real limitation, not neutral.
- A **per-learner adoption of a specific Journey** is also already a distinct, existing grain: `NoteCollectionEntity.sourcePlanId` (`:65`) plus the adopted copy's own `id` is precisely "this learner's instance of this Journey," separate from both the learner profile and the official source. If a concept needs to vary per-adoption (e.g., "I personally adopted the official PNLE Review Set for CPD refresher, not licensure prep" — the brief's own distinction in §1), **this grain already exists and holds data; it does not need to be created.** Confirming whether it's the *right* grain for Learner Goal, versus the profile grain `studyGoal` already uses, is Q5/Q6's job.

### Q5. Can one Study Journey legitimately serve learners with different personal goals?

Yes, and nothing in the current architecture prevents it structurally — the question is whether anything *expresses* it. Today: no. A Journey's adopters are tracked only as independent copies (`sourcePlanId` lineage); nothing records why a given adopter adopted it, and `studyGoal` lives on the adopter's profile, entirely decoupled from which Journeys they've adopted or why. The brief's own BST example argues this should be legitimate; the codebase does not contradict it, but also does not yet let a learner *say* their personal reason differs from the Journey's apparent purpose.

### Q6. Can one learner simultaneously pursue journeys with different purposes?

**Structurally yes, but the existing Learner Goal mechanism (`studyGoal`) cannot express it, and this is a real, named limitation of what's already shipped — not a future hypothetical.** A user can adopt arbitrarily many Collections with different `courseProgram` values (no constraint stops this). But `UserEntity.studyGoal` is a single `text` column — one learner, one goal, full stop. A learner adopting both a CPALE Review Set and a Civil Engineering refresher Journey simultaneously can set `studyGoal` to represent only one of them; `ProgressReportService.filterGoalStudyPacks` (`ProgressReportService.java:427-452`) then simply excludes any Study Pack whose course program isn't in the stored goal's set — read directly, this is a clean filter, not a misattribution, but it means the second, unrepresented goal's packs never appear in the goal summary or nudge at all. **This is evidence against solving "Learner Goal" by extending `studyGoal` as-is**, and evidence for the brief's own caution (§1) that purpose may need to live closer to the adoption than to the profile.

### Q7. Does any purpose need first-class discovery/filtering?

Partially — and partially already shipped. `studyGoal` already drives **post-hoc filtering of generated content** (which Study Packs "qualify" toward a goal, in `ProgressReportService`), but this is a dashboard/progress feature, not catalog discovery. At the **catalog/adoption** layer — browsing official Study Journeys to adopt one — there is **no purpose-based filter of any kind** today (confirmed by the same `NoteCollectionService` grep in Q2). Whether catalog discovery needs it is unevidenced either way; no finding here says it does or doesn't, only that it doesn't exist yet.

### Q8. Does any purpose actually alter learning behavior, or only discovery/presentation?

Confirms the brief's own strong prior (§7): everything found that's keyed to anything goal/purpose-adjacent today is presentation (`collection-labels.ts`, `exam-mode-visibility.ts`) or a progress-dashboard filter (`ProgressReportService`). Nothing touches `ConceptHealth`, quiz question generation, readiness computation, or Study Pack content. No counter-evidence found.

### Q9. Does purpose ever need to reach generation?

No counter-evidence found to the brief's strong prior (§8/§9 open question). Recommend holding the line as stated.

### Q10. Are specific credentials or roles genuinely required as entities/taxonomies?

**Credentials: partially yes, already.** `exam_goal_slug` is a first-class, DB-enforced, 4-value credential taxonomy (`ale`, `pnle`, `let`, `cpale`) — it is not a neutral, generically-extensible "credential" concept, it is four specific Philippine licensure exams hardcoded into a `CHECK` constraint and a Java `Map.of(...)`, which is itself the shape of risk §10 asks the future workstream to watch for (an exam-specific assumption standing in for universal architecture). **Civil Engineering** (`course_programs` row `20000000-0000-0000-0000-000000000005`, `V106__course_program_catalog.sql:33`) has `exam_goal_slug IS NULL`, confirmed in the seed migration — **unmodeled, and the reason is unrecorded in anything read this pass** (no comment, commit, or ROADMAP row explains why Architecture got a slug at `V106` and Civil Engineering, which also has a genuine PH board exam, did not). This is noted as a candidate Backlog item in its own right, not folded into this discovery's scope — **widening the `CHECK` constraint needs a migration, which this pass's own anti-drift forbids**, so it is the owner's to schedule, not something this pass can recommend doing "regardless." Computing has **no `course_programs` row carrying a slug at all**, correctly, since no generalist board exam exists for it. **Before inventing a new, separate Target Credential concept, the future workstream should at least consider whether widening this existing mechanism solves the credential half of the problem**, rather than building a parallel taxonomy next to one that already does this job for 4 of the 5 licensure-bearing programs in the §10 table. **Professional roles: zero existing representation, and no finding here argues one is needed** — consistent with the brief's §6 caution against inferring need from a hypothetical.

### Q11. Can existing Study Journey membership solve the use case without new metadata?

**The answer bifurcates, and the split matters for Q12:**

- **For canonical-knowledge reuse** (the originating BST problem — the same Note serving BSCS, interview prep, and a professional refresher): **yes, membership already solves it**, exactly as brief §2 argues, and nothing found contradicts this. No new metadata needed for this half.
- **For the Q2-demonstrated presentation gap:** **courseProgram alone is necessary but likely not sufficient**, and this is an open empirical question the future workstream must verify before concluding either way. Reasoning: `course_programs.exam_goal_slug` can tell you a *program* is licensure-bearing, but official Journeys of genuinely different purpose can plausibly share the same `courseProgram` value — e.g., an official "BS Nursing — Year 2" academic Study Plan and an official "PNLE Comprehensive Review" Review Set both plausibly carry `courseProgram = "Nursing"`, and nothing in `NoteCollectionEntity` distinguishes them from each other once you're not relying on the viewer's `ProfileType`. **One candidate existing field was checked and ruled out:** `termLabel`/`termOrder` (`NoteCollectionEntity.java:94-98`) looked promising but is a term/semester placement field for a Journey's *children* (copied source→child on every adoption/sync path in `NoteCollectionService.java:710-711, 891-892, 1347-1348, 2211-2212, 2739-2740`) — it organizes a degree Journey's own internal structure (Year 1/Year 2, semester order), not whether the root Journey itself is academic vs. licensure-prep. **It does not resolve this ambiguity**, so the code-only check this pass could cheaply run came back inconclusive, not positive. **This was not verified against production data** — the verifying query (`SELECT title, course_program, learner_level, visibility FROM note_collections WHERE published_at IS NOT NULL ORDER BY course_program`) is a plain `SELECT`, permitted under `CLAUDE.md`'s read-only rule, but **Render MCP connection timed out this session** (noted at session start, unresolved — see the companion checkpoint-gate updates made to `ROADMAP.md` this session for the unrelated signoff checkpoints, same blocker). **This is the single most important unresolved empirical question this pass leaves behind**: if published Journeys sharing a `courseProgram` are already distinguishable by some existing field (a naming/title convention, root-vs-child position, or simply because Review Sets and Study Plans never actually share a `courseProgram` value in practice), then Q11's answer for the presentation gap is also "yes, membership/existing fields solve it" and Q12's minimum model needs zero new persistence — modulo the Q2 cost caveat about `EXAM_MODES.md` regardless. If they are not distinguishable today, some new journey-grain signal is required — but even then, it may be as small as deriving presentation from `courseProgram` **plus** which catalog root the Journey descends from, not a new column.

### Q12. What is the minimum model that solves demonstrated cross-domain use cases?

**Contingent on Q1's owner pick, and on the Q11 production read being run. Not a final recommendation — a conditional one:**

- **If scope is Candidate A alone** (fix the demonstrated viewer-vs-Journey presentation gap): the minimum *persistence* model is very likely **zero new columns** — re-pointing `getCollectionLabels` to consult the open Collection's own `courseProgram` → `exam_goal_slug` (already-existing data, already-existing join), with `ProfileType` as the fallback for Journeys whose program carries no slug (Computing, professional-refresher, interview-prep), contingent on the Q11 empirical read confirming `courseProgram` is sufficient to disambiguate published Journeys. **But per the Q2 cost caveat, `resolvePlanPremiumExamMode`'s terminal-mode mapping is a different matter**: it is not just unwired, it correctly implements a locked contract (`EXAM_MODES.md`), so changing it is a contract amendment and a product decision about whether Journey nature should ever override viewer audience for mode selection — not a data-availability question. Candidate A's labeling half may be cheap; its mode-selection half is not, regardless of what the Q11 production read shows.
- **If scope extends to Candidate B** (fix `studyGoal`'s single-valuedness/conflation): minimum model is evolving `studyGoal` from a single free-text-or-slug column toward something that can hold more than one concurrent goal, and/or separating "which licensure exam" from "which subject" rather than overloading one field — this is a refinement of an existing feature, not new architecture.
- **If scope extends to Candidate C in full** (the Computing interview-prep/professional-refresher case, which has **no** existing data signal of any kind, not even a crude one): some new journey-grain concept is likely genuinely needed, because unlike the licensure case there is no existing field to derive it from. Even here, the brief's own §5/§6 caution against a single speculative enum holds — the future workstream should scope it to the specific purposes it can demonstrate a presentation or discovery need for (per Q7/Q8), not pre-populate a taxonomy for roles/credentials it hasn't evidenced (per Q10).

**In all three cases: no finding here calls for a new field on `NoteEntity`. The candidate surface for any new persistence, if one turns out to be needed at all, is `NoteCollectionEntity` (the Journey) or a refinement of `UserEntity.studyGoal`/adoption lineage (the Learner Goal/adoption grain) — never the canonical Note.** This matches brief §3's prior and no evidence here contradicts it.
