## 3. The facts the prompt encodes — do not re-derive these, and do not let them drift

These were established by reading code and by read-only production queries during the session that wrote
the prompt. Each one changed the design.

**❌ The brief's performance premise is FALSE.** Impact was **never** part of the Public Profile payload.
`GET /creator-impact/me` is a separate endpoint fetched client-side behind an `isOwner` gate
(`public-profile-page-client.tsx:216-232`). **Moving the page saves Public Profile nothing.** Do not write
a test asserting an improvement that cannot occur — that test would pass against `main`.

**⚠️ The live defect is the headline, and it is independent of the IA move.**
`frontend/app/settings/page.tsx:276-296` calls `getCreatorImpact()` on every Settings load and uses the
whole payload for **one boolean** (`setHasPublicNotes`) — **1,587 note records** on the owner's account,
through three `IN (:noteIds)` grouped queries, on the 20-connection pool that has **already failed twice
from unbounded reads** (2026-09-04, 2026-09-05). Fix this first; item 3 consumes the bounded query.

**⚠️ NEVER add a `userId` parameter.** Its **absence** is the privacy control — `CreatorImpactController`
takes identity from `@AuthenticationPrincipal` and has no user input at all. `/impact?userId=…` must stay
**unrepresentable, not merely blocked**. The test asserts the **absence of the input**, never a 403: a test
that passes a param and expects rejection would pass against a build that added the param and then
rejected it.

**⚠️ The tie-break is `noteId ASC` ALONE, never `copyCount DESC`.** `copyCount` is not in the ranking query
(separate grouped query over the page), and it promotes a *distribution* metric into *semantic* ranking.
`noteId` is immutable and unique — the only tie-break that makes pagination stable.

**⚠️ Views are "page views".** `PUBLIC_NOTE_VIEWED` has **25,262 rows and ZERO with a `user_id`** — all
anonymous. Views can never be deduplicated per person; the label is a correctness matter, not taste.

**❌ No "Awaiting first study · 1,526" counter.** It turns a contribution surface into a deficit
scoreboard, and 1,526 would be the largest number on the page. Collapse the zero-impact set; show the
impacted count only.

**❌ `/impact?note=<id>` is deferred, not optional.** No shipped consumer needs it.

**✅ What is already correct and must survive the diff:** the 5-query, N+1-free access path (the problem is
**cardinality**, not access path — bound it, do not restructure it); no new index needed; the
headline-dedup explanatory copy, verified accurate against the queries; the self-copy exclusion
(`NoteService.copyNote:392-397`); the `impactRequestIdRef` out-of-order-response guard; and
**`public-profile-page-client.test.tsx:277`**, which asserts a visitor issues no impact request.

## 5. Verification tier, and why

**At least one scoped cold agent, framed as falsification** — hand it a tight file list and the specific
claims the implementing session made, and ask it to **disprove each**. `model: "sonnet"` is enough for
claim-checking.

Three independent reasons, any one of which fires the gate:

1. **Seven items** in one release. Verification scales worse than linearly with items shipped.
2. **The owner overrode the audit's own split recommendation** — the release is deliberately larger than
   its author advised.
3. **The precedent is measured, not hypothetical.** `v0.133.0` was tiered at a single `advisor()` call,
   gained a write endpoint mid-release, ran one cold agent, and had **three of seven named claims
   refuted**. `v0.135.0` ran one and had a claim refuted that changed the shipped query (the self-copy
   exclusion in `NoteCollectionRepository`).

**And the cheapest check is still the one with the best yield:** before any deeper tier, ask whether a test
actually **executes** the path the change touched. It is free and visible in `git diff --stat`. `v0.116.0`
and `v0.117.0` each shipped a silent no-op that compiled, passed the whole suite, and was written up as
shipped — both found only by a cold agent, and in both cases the tell was that the diff changed behaviour
while touching no test that runs it.

## 6. Standing constraints that outlive this release

- **⚠️ PRODUCTION DATABASE IS READ-ONLY FOR CLAUDE, ALWAYS.** Every route — Render MCP, `psql`, JDBC, a
  one-off endpoint, an admin surface acting on Claude's behalf. **Owner approval of a plan containing a
  write is not approval to execute it.** When a write is needed: write the exact statement to a
  `docs/claude-plans/*.sql` file with expected row count and how to verify, hand it over, and **stop**.
  This happened once already this cycle (`v0.133.0-owner-profile-string-update.sql`) and worked correctly.
- **`main` is protected by ruleset `17016892`** (`require_extra_approval_for_unattributed_changes: true`,
  `required_approving_review_count: 0`). `--admin` is an **owner** action. A blocked merge is reported,
  never forced.
- **Index a planning artifact in the commit that writes it.** Kickoff step 8 runs at kickoff; plans arrive
  mid-release. This document is indexed in the same commit that creates it, for exactly that reason.
- **Do not switch branches while a cold agent is running** — it reads files underneath itself and will
  report the change as a finding. This cost a confused exchange earlier in the cycle.
