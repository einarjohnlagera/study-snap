## 3. Whole-arm re-review of the proposed arms (pre-registered, owner, 2026-10-28)

The rubric (section 2, rule 5) already requires that if a cold reviewer finds even one confirmed critical defect that the primary scorer missed in a **proposed-prompt arm (B2 or B3)**, **that entire arm** is independently re-reviewed by a fresh cold reviewer, with a separate adjudication, before its gates are interpreted. `v0.176.0` Amendment 4b then staged that re-review by cost and skipped it for Luna because Sol's result had already decided HOLD, which left Luna's proposed arm uninterpreted.

For `v0.177.0`:
1. **Amendment 4b's skip is withdrawn.** The whole-arm re-review of **each** proposed arm is run whenever the rubric's trigger fires for that arm, **whatever the other model's result is.** A model's arm is never left uninterpreted to save cost.
2. **Scope and mechanism:** all about 300 items of the arm, one fresh reviewer identity for the whole arm, the same scratch-directory isolation, self-report and receipt checks as `v0.176.0` Amendment 3, with new disagreements adjudicated by fresh adjudicators and the harness's own validator accepting every row.
3. **Cost, stated before the run:** up to about 300 items per proposed arm, so up to about 600 items if both triggers fire (about 6 reviewer passes of about 100). That is reviewer usage on the owner's Claude and Codex plans, not OpenAI API spend, and it is not part of the $4 cap.
4. **If the owner wants the re-review run unconditionally rather than on trigger, that is a different pre-registration and has not been chosen.** This section is the on-trigger reading of "pre-register the re-review"; the owner may rule otherwise before the freeze.

## 6. Amendment 1: void and re-run starts that failed with no HTTP response (2026-10-28, after the first paid commands, before any output was scored or read)

This is a dated amendment to a frozen pre-registration. Per its own rule it is a recorded deviation, never a silent fix. Nothing above is edited.

**What happened.** On 2026-10-28 the owner ran the five `quality-full-*` commands (runs 2 to 20) of the frozen run sheet. The five `quality-smoke-*` commands (run 1) were **not run**, so note 1 has no start in any arm, and the smoke-pass prompt-hash check did not run before the bulk spend (it was run afterwards by reading the result rows: A1, A2 and A3 carry `5bf4a8e9…`, B2 and B3 carry `019c5bdf…`, models as mapped). Between about 23:25 and 23:26 the owner's machine lost DNS or network: **A3** has 3 successful starts (notes 2 to 4) and 16 failures (15 `UnknownHostException`, 1 `SocketException`); **B3** has 0 successes and 19 failures (all `UnknownHostException`). Those 35 failures carried **no tokens and no spend** (verified). A1 has 4 `SCHEMA_OR_PARSE` failures (notes 2, 4, 15 and 20: model output rejected by validation), A2 and B2 are complete (19 of 19). Metered spend at that point: $0.5148. The v0.176.0 data is untouched (the `diff -rq` guard against the backup printed nothing).

**Why this needs an amendment.** Under the frozen rules a failed start is a missing side of a pair, never re-run, and the missingness trigger "the proposed arm has at least 2 more failed starts than the same-model current arm" (here B3 19 against A3 16) would make Sol INCONCLUSIVE, so the release would be HOLD for a reason that has nothing to do with the prompt.

**Decision (owner, 2026-10-28, "go with option B"; recommended by the Release Implementor).** Product UX has not reviewed this amendment text; the owner chose it. Rules:
1. **Void class (mechanical, fixed now, before any output is viewed):** a start whose row has `success=false`, `failureClass=HTTP_ERROR` and `errorMessage` equal to `UnknownHostException` or `SocketException`. All 35 such rows are listed in the addendum by input id with the fingerprints of the untouched originals. Parse and validation failures (A1) are **not** void and stand.
2. **Symmetric:** the rule applies to every arm. Only A3 and B3 contain void rows today.
3. **At most two attempts per start in total** (the original and one re-run). A void-class failure on the re-run stands as a missing side, with no third attempt.
4. **Re-runs go into fresh folders** (`quality-rerun-A3`: notes 5 to 20; `quality-rerun-B3`: notes 2 to 20). The original folders are never edited or deleted. Because the export and the descriptors reject a duplicate arm and note, the analysis reads **effective folders** built by a data-only script from the non-void original rows plus the re-run rows (`quality-effective-A3`, `quality-effective-B3`); the script is in the addendum and aborts on any duplicate.
5. **The pre-registered smoke commands for note 1 (all five arms) are run as frozen**, since they were never run.
6. **No code changes.** The pinned benchmark tree and `backend/` tree are untouched; the script and commands live in `docs/claude-plans/2026-10-28-v0177-run-sheet-addendum-1.md`.
7. **Budget:** the $4.00 ceiling is unchanged and now covers all spend so far: $0.5148 metered, plus the smoke stops ($0.33), a 16-note A3 re-run stop ($1.20) and a 19-note B3 re-run stop ($1.40) is $3.4448 of stops, about $3.76 with one call of overshoot per command, expected about $3.07.

**Disclosed limitations.** The run order and time of day differ from the frozen sheet (the original Sol starts, the re-runs and note 1 are separated in time), which can affect the latency comparison in G6; note 1 is generated after notes 2 to 20; the A3 arm mixes starts from two sittings.
