# Stage 1 Audit — Official Study Plan / Review Set adoption and UPDATE semantics

**Status:** Stage 1 analysis only. No implementation, no migration, no build was run.
**Date:** 2026-09-05
**Auditor scope:** Sections J, K, L, M, N, and the adoption slice of O (§28, §35), plus Parts XV/XVI.
**Method:** every load-bearing claim below was verified by opening source and is cited `file:line`.
Production figures are read-only `SELECT`s against `dpg-d6tvb8fkijhs73fda4m0-a`.

> **Governing idea.** Official curricula can improve over time without forcing early adopters to
> choose between losing their progress and remaining permanently stuck on an obsolete curriculum.
>
> **Learner promise.** *Your plan stays yours. When the Official plan improves, you can add the
> updates without losing your progress or changes.*

---

## 0. Headline findings

1. **The no-op is real and it is EARLIER than the repo's own note claims.** Re-adoption bails in
   `adopt()` before any copy work runs — not inside `persistAdoptedPlan`. The copy pass never
   executes. (§J.3, §Doc-discrepancies.)
2. **The update mechanism is ~80% already built and nobody calls it.** `copyNote` is idempotent per
   `(owner_user_id, copied_from_note_id)`, so re-running the existing copy pass over an existing
   adoption is *already* non-destructive and additive: existing notes resolve to the learner's own
   copy (preserving `ConceptHealth`, sessions, history) and only genuinely new source notes mint
   rows. What is missing is the **decision to call it**, plus removal and rename semantics.
   This is the single most consequential finding in the audit. (§J.6, §O.)
3. **Placement identity is reconstructable TODAY with zero new columns.** 4,374 of 4,374 adopted
   items (100%) carry `notes.copied_from_note_id`. (§L.)
4. **The stranded population is measured, not hypothetical: 364 source placements added after
   adoption have never reached 28 learners**, and **68 whole Subject Plans are missing from 34
   adopted Goals**. (§L.)
5. **Learner removals are currently a ZERO population** — every absent placement is explained by
   post-adoption source growth. A removal record can therefore be added *prospectively* with no
   backfill and no reconstruction risk. (§L.4, §O.28.)
6. **The repo already contains the right staleness pattern and it is not a revision integer.**
   `companion_structure_snapshot` + `companionMayBeOutdated` is a structural-snapshot comparison
   surfaced as an *advisory flag to a curator*, never auto-applied. That is the model to reuse.
   (§N, §XV/XVI.)
7. **Progress% and readiness% dilute in lockstep** — all 4,374 adopted items are `GENERATED` with a
   copied Study Pack, so there is no divergence to exploit. The fix for the 80%→43.6% problem is
   **semantic, not arithmetic**. (§M.)

## J. Review Set adoption architecture — full trace

### J.1 The shape

```
Official Goal (note_collections, visibility=PUBLIC, parent_collection_id=NULL)
  └── Official Subject Plan (note_collections, parent_collection_id = Goal.id, sibling_position)
        └── note_collection_items  (collection_id, note_id, label, position)
              └── Official Note (notes, visibility=PUBLIC, owner = ADMIN curator)
                    └── StudyPackEntity (study_packs.note_id)
```

Two levels of collection only. `NoteCollectionEntity`
(`backend/src/main/java/com/studysnap/backend/entity/NoteCollectionEntity.java:68`) carries
`parent_collection_id`; there is no third level, and **Sections are NOT a level** — see J.4.

### J.2 What adoption produces

`adopt()` (`NoteCollectionService.java:823`) and `adoptGoal()` (`:857`) mirror the source shape into
learner-owned rows:

| Source | Learner artifact | Provenance retained |
|---|---|---|
| Official Goal | new `note_collections` row, `visibility=PRIVATE` | `source_plan_id` = Official Goal id |
| Official Subject Plan | new `note_collections` row, reparented under learner Goal | `source_plan_id` = Official Subject Plan id |
| Section (item `label`) | copied verbatim onto the learner item | **string only — no identity** |
| `note_collection_items` placement | new row via `buildAdoptedItems` | **NONE on the row itself** |
| Official Note | learner note copy via `noteService.copyNote(..., true)` | `copied_from_note_id`, `copied_from_user_id`, `copied_from_title`, `copied_from_public`, `copied_at`, `source_note_id` |
| Study Pack | copied via `copySourceStudyPack` | none (new row, `note_id` = learner copy) |

Fields deliberately copied at plan level (`persistAdoptedPlan:1449-1500`): `title`, `description`,
`courseProgram`, `learnerLevel`, `estimatedStudyHours`, and Companion *conditionally*
(`shouldCopyCompanion`). Deliberately **not** copied: `targetCompletionDate` (commented in place —
"a curator's or previous owner's target date means nothing to the new owner").

`V76__collection_visibility_and_plan_source.sql:4-11` adds `source_plan_id` plus a partial unique
index on `(owner_user_id, source_plan_id) WHERE source_plan_id IS NOT NULL`. **That index is the
whole idempotency substrate** and it is what makes "one adoption per learner per source" a database
guarantee rather than a convention.

### J.3 The duplicate / no-op logic — the key claim, VERIFIED and CORRECTED

The prior repo finding said re-adoption is a hard no-op because `persistAdoptedPlan` returns early.
**Directionally true, mislocated, and the true behaviour is stronger.**

`NoteCollectionService.adopt(UUID, UUID, boolean)`:

```java
// Fast idempotency path: an existing personal plan for this source is returned as-is.
Optional<NoteCollectionEntity> alreadyAdopted =
        collectionRepository.findByOwnerUserIdAndSourcePlanId(userId, sourceCollectionId);
if (alreadyAdopted.isPresent()) {
    return alreadyAdoptedResponse(userId, sourceCollectionId, alreadyAdopted.get());
}
```
— `NoteCollectionService.java:830-835`

The bail happens **before `copySourceItems` is ever called** (`:840`). The `...ForUpdate` re-check
inside `persistAdoptedPlan` (`:1456-1460`) is a *second* guard that only fires on a lost race, and
`adopt()` additionally catches `DataIntegrityViolationException` from the unique index (`:847-853`).
So there are three layers of idempotency, and the copy pass is short-circuited by the outermost.

`adoptGoal` does the same at Goal level (`:864-868` → `alreadyAdoptedGoalResponse`).

**Consequence, stated plainly: an adopted plan is a PERMANENT SNAPSHOT in practice.** No code path
in the repository adds a source note to an existing adoption. Confirmed by exhaustive search:
`copySourceItems` has exactly one caller, `adopt()` at `:840`.

`alreadyAdoptedResponse` (`:1536-1545`) still fires `STUDY_PLAN_ADOPTED` with
`alreadyAdopted=true` — which is why we have production evidence of learners trying (§L.5).

### J.4 Sections are derived, and must stay derived

Sections exist **only** as `note_collection_items.label`
(`NoteCollectionItemEntity.java:28-29`, `varchar(120)`), grouped client-side:

- Learner surface: `getCollectionItemSections` in
  `frontend/app/collections/[id]/collection-detail-page-client.tsx:155-198` — groups by
  `normalizeSectionName(item.label)`, folding blank/reserved into a synthetic
  `UNGROUPED_SECTION_NAME` bucket (`frontend/lib/collection-labels.ts:134`, `"Not in a section"`).
- Builder surface: `buildLeafSections` in
  `frontend/app/collections/[id]/builder/study-plan-builder-page-client.tsx:147`.
- Section readiness: `aggregateSectionReadiness` (`collection-detail-page-client.tsx:216-236`) —
  **sums** `masteredConceptCount` / `totalConceptCount` / `dueConceptCount` across the section's
  notes. It makes no concept-identity claim; it is pure summation.

Adoption carries the label through: `copySourceItems` captures `sourceItem.getLabel()` into
`CopiedPlanItem` (`:1432`) and `buildAdoptedItems` writes it onto the learner item. So sections
*start* identical to source and then drift silently.

**Anti-drift honoured:** nothing in this audit's recommendations turns Sections into a collection
level. The minimal provenance in §O attaches to the *placement row*, not to a new Section entity.

### J.5 Ordering

`position` on `note_collection_items` is the leaf order; `sibling_position` on `note_collections` is
the Subject-Plan order within a Goal (`setChildrenOrder:783-805`). Both are learner-mutable.
`setOrder` (`:1115-1140`) **mutates existing item rows in place** — `item.setPosition(index)` and
`item.setLabel(...)` — and `validateSubmittedSetMatchesCurrent` forbids membership change. So
**item UUIDs survive both reorder and relabel**; they do not survive remove-and-re-add
(`removeItem` hard-deletes, below). This is load-bearing for the key choice in §O.35.

### J.6 The idempotent copy — the mechanism that makes updates cheap

`NoteService.copyNote(String, UUID, boolean)`:

```java
Optional<NoteEntity> existingCopy = noteRepository
        .findFirstByOwnerUserIdAndCopiedFromNoteId(ownerUserId, source.getId());
if (existingCopy.isPresent()) { ... return mapToResponse(existing, existingStudyPack); }
```
— `NoteService.java:333-350`

For a non-owner copy this returns the learner's **existing** note, and even back-fills a Study Pack
if the learner's copy lacked one. It does not touch the learner's title, content, tags, or any
session/`ConceptHealth` history hanging off that note id.

**Therefore: re-running `copySourceItems` against an existing adoption is already safe and already
additive.** Every source note the learner already has resolves to their own copy; only new source
notes create rows. The destructive-overwrite risk this audit was asked to guard against **does not
exist on this path** — `copyNote` never writes back into an existing copy's content.

Two caveats, both verified:
- `copyNote` calls `onboardingGuardService.assertProfileComplete(ownerUserId)` (`:323`) — an update
  path must tolerate/consider that gate.
- `copySourceItems` (`:1422-1445`) swallows **every** `RuntimeException` per item and increments
  `skippedCount`, logging `study_plan_adopt_item_skipped`. Silent partial failure is by design
  ("a single failed copy is isolated and never rolls back the whole adopt", `:837-838`), but it is
  also why *absence of a placement is ambiguous* — see §K.

### J.7 The one existing partial-merge path (in-repo precedent)

`adoptGoal` (`:857-935`) is **not** a pure no-op when the Goal itself is new. For each source child
it calls `adopt(sourceChild.getId(), userId, false)`; if the learner already adopted that Subject
Plan standalone, `adopt` returns already-adopted, and then:

```java
if (child.getParentCollectionId() == null) {
    child.setParentCollectionId(persistedGoal.collection().getId());
    child.setSiblingPosition(index);
    child.setTargetCompletionDate(null);
    child.setCompanion(null);
    child.setCompanionStructureSnapshot(null);
    ...
}
```
— `:1899-1911` region (`NoteCollectionService.java:899-911`)

So the repo **already ships a re-run that picks up pre-existing learner state and reparents it**
rather than duplicating or refusing it. That is the shape an update flow should extend, and it is a
precedent to cite rather than a pattern to invent.

⚠️ **But state its cost precisely rather than calling it lossless:** the same branch NULLs
`targetCompletionDate`, `companion` and `companionStructureSnapshot`. A learner who adopted a
Subject Plan standalone and set **their own target completion date** silently loses it when they
later adopt the parent Goal. The invariant being enforced (those three are top-level-Goal-only, the
same rule `updateParent:697` applies) is correct; the *learner-visible loss* is unacknowledged. An
update flow reusing this branch inherits that defect and should preserve or re-prompt for the date.

### J.8 Primary plan and progress linkage

`assignAdoptedCollectionAsPrimaryWhenMissing` + `reassertPrimaryInvariant` set
`users.primary_collection_id` on first adoption. `setPrimary` requires `parentCollectionId == null`
(`:708-710`). Nothing in the update question disturbs this.

## K. Update feasibility matrix

### K.1 Can the schema distinguish the three learner-plan states?

| State | Distinguishable today? | How / why not |
|---|---|---|
| **learner-added** | **YES** | `notes.copied_from_note_id IS NULL`, or non-null but never placed in this `source_plan_id`. Verified: 0 no-lineage items and 430 lineage-elsewhere items in production. |
| **unchanged from source** | **PARTIAL** | Membership and note identity: yes, via `copied_from_note_id`. **Label/section and position: NO** — nothing records the value *as of adoption*, so a mismatch cannot be attributed. |
| **learner-modified** | **PARTIAL** | Note *content* edits are inferable by comparing `notes.title`/`content` against the source row (32 such rows in production) — but only while the source row is unchanged, so it degrades the moment the curator edits upstream. Label/position edits: **not distinguishable at all.** |
| **learner-removed a source item** | **NO** | `removeItem` (`NoteCollectionService.java`, `removeItem`) **hard-deletes** the `note_collection_items` row and rewrites positions. No tombstone. Indistinguishable from `copySourceItems` having skipped it. |

**This is the sharpest schema gap and it is the core of §O.**

### K.2 The matrix

Ground rules used: "safely auto-mergeable now" means the current schema can perform it without
guessing and without touching learner state.

| Source change | Classification | Reasoning (grounded in code) |
|---|---|---|
| **Add Note to a Subject Plan** | **Safely auto-mergeable now** | `copyNote` idempotency (`NoteService.java:333-350`) makes it purely additive; append at `max(position)+1` as `addItems` already does. Zero risk to existing rows. Still recommended to be *learner-approved* on policy grounds, not technical ones. |
| **Add Subject Plan to a Goal** | **Safely auto-mergeable now** | Same shape one level up: `adopt(child, userId, false)` + reparent, which `adoptGoal:899-911` already does. |
| **Remove Note from source** | **Should only be SURFACED, never applied** | Learner may have practiced it (`ConceptHealth`, sessions keyed on their note id). Anti-drift: prefer *"no longer in the current Official plan"* + optional learner cleanup. Production: 206 such placements already exist. |
| **Remove Subject Plan from source** | **Should only be SURFACED, never applied** | Same, at higher blast radius. |
| **Rename Subject Plan** | **Mergeable with additional provenance** | Needs a "title as-of-last-sync" marker to tell *learner renamed* from *source renamed*; without it, following source silently overwrites a learner rename. Title matching is forbidden by anti-drift and unnecessary — `source_plan_id` is the identity. |
| **Reorder Subject Plans** | **Mergeable with additional provenance** | `sibling_position` is learner-mutable (`setChildrenOrder`). Following source blindly destroys a learner reorder. Needs an as-of-last-sync position, or: only apply ordering to *newly added* children. |
| **Add Section** | **Safely auto-mergeable now** (as a side effect) | A Section exists iff an item carries the label. New items arriving with a new label create the Section for free. No Section entity is needed and none must be created. |
| **Rename Section** | **Mergeable with additional provenance** | Requires label-as-of-last-sync per placement. Otherwise indistinguishable from a learner rename — and `handleRenameLeafSection` in the Builder mass-relabels every matching item, so a wrong guess is a bulk overwrite. |
| **Reorder Sections** | **Should only be SURFACED** | Section order *is* item `position` order; there is no section order field. Reapplying it rewrites every position and destroys any learner arrangement. Low value, high blast radius. |
| **Move Note between Sections in source** | **Mergeable with additional provenance** | Same label problem. Production shows 224 notes already moved between source plans. |
| **Rename canonical Note** | **Should only be SURFACED, not auto-applied** | `notes.title` on the learner copy is learner-editable. `copied_from_title` (`NoteService.java:376`) preserves the title *at copy time*, so a three-way comparison (`copied_from_title` vs source title vs learner title) is **already possible today** — a genuine free win. |
| **Update canonical Note content** | **NEVER overwrite** | Explicit anti-drift. `copyNote` already never writes into an existing copy. Surface only. Production: 266 learner copies whose source has been updated since `copied_at`. |
| **Update Companion guidance** | **Should only be SURFACED** | See §N. Companion is a plan-level JSONB blob with no per-field provenance; replacing it wholesale would discard nothing learner-authored (learners cannot author Companion) but would silently change guidance mid-journey. |

### K.3 Desired merge semantics vs. what the schema supports

| Learner state | Official change | Desired | Supported today? |
|---|---|---|---|
| unchanged | source adds item | safe update candidate | **YES** — fully |
| unchanged | source renames/reorders | may follow source | **NO** — cannot prove "unchanged" |
| unchanged | source removes item | preserve history, no destructive delete | **YES** (do nothing is trivially correct) |
| learner-modified | source changes same thing | learner wins | **NO** for labels/positions; **YES** for note content (never overwritten anyway) |
| learner-added | anything | never overwrite | **YES** — `copied_from_note_id IS NULL` is decisive |
| learner removed a source item | source retains it | do not auto-resurrect | **NO** — no removal record exists |

Two rows are unsupported, and they are exactly the two the minimal provenance in §O addresses.

## M. Progress / readiness impact

### M.1 The actual formulas, read from code

**Plan progress** — `NoteCollectionService.toProgressResponse:2038-2046`:

```java
int notesWithStudyPack = (int) items.stream()
        .filter(item -> STUDY_PACK_READY.equals(item.studyPackStatus())).count();
int notesPracticed = (int) items.stream()
        .filter(item -> item.lastSessionCompletedAt() != null).count();
return new NoteCollectionProgressResponse(items.size(), notesWithStudyPack, notesPracticed);
```

The denominator is **`items.size()` — the live membership count**. It dilutes the instant new items
land. `notesPracticed` counts items with any completed session (`lastSessionCompletedAt`, populated
by `loadLastSessionCompletedAt` at `:2157`).

**Section readiness pill** — `frontend/app/collections/[id]/collection-detail-page-client.tsx:295-299`:

```
{Math.round((sectionReadiness.mastered / sectionReadiness.total) * 100)}% · {sectionReadiness.due} due
```

built from `aggregateSectionReadiness` (`:216-236`), which **sums concept counts** across notes and
**skips any note with no entry in `countsByNoteId`**.

**Plan readiness** — `toPlanReadinessResponse:2059+` builds from `studyPacks` and
`progressReportService.buildSubjectProgressEntries`, i.e. concept totals across the plan's packs.

### M.2 Do progress% and readiness% dilute together? — RESOLVED against production

They do. **All 4,374 adopted items are `status = GENERATED` and all 4,374 have a `study_packs`
row.** `copySourceItems` calls `copyNote(..., includeStudyPack = true)` (`:1431`), which sets
`NoteStatus.GENERATED` when the source has a pack (`NoteService.java:383-385`) and copies it via
`copySourceStudyPack`. `NoteStudyPackStatusResolver.resolve` maps `GENERATED → STUDY_PACK_READY`
unconditionally.

**Consequence:** newly added Official notes arrive *already* carrying a Study Pack and concepts, so
they immediately enter **both** the progress denominator (`items.size()`) **and** the readiness
denominator (`sectionReadiness.total`, plan concept totals). There is no divergence to lean on, and
**no arithmetic dodge is available.** 240/300 = 80% genuinely becomes 240/550 = 43.6%, and the
readiness pill drops in lockstep.

### M.3 What breaks, precisely

| Surface | Effect of a 300 → 550 expansion |
|---|---|
| Plan progress denominator | 300 → 550 immediately; 80% → 43.6% |
| Section readiness pill (`N% · M due`) | mastered/total both change; % drops; `due` count jumps |
| "Next topic" / `getContinuePlanAction` | picks by position; **new items may appear before practiced ones** if inserted mid-order |
| `getLatestPracticedCollectionItem` | unaffected — reduces over `lastSessionCompletedAt`, ignores new items |
| Previously completed topics | **unaffected** — sessions key on the learner's note id, which `copyNote` idempotency preserves |
| `ConceptHealth` | **unaffected** — keyed `(user_id, study_pack_id, concept)`; new packs add new rows, old rows untouched |
| Exams / Long Exam / Board Exam | source pool **widens**; plan-sourced sampling draws from more packs. `LongExamPlanSourceSampler` already bounds this (`MAX_PLAN_SOURCE_PACKS`), so no unbounded fan-out |
| Recent Sessions | **unaffected** — historical session rows |

**The single most important fact for the product framing: nothing the learner actually earned is
lost.** Every completed session, every `ConceptHealth` row, every mastered concept survives an
expansion untouched. Only the *ratio* moves, because its denominator legitimately grew.

### M.4 Recommendation — least misleading semantics

Do **not** freeze the denominator, and do **not** preserve 80% artificially. Readiness against the
current curriculum is a genuine and useful number; falsifying it would make Board Exam readiness
lie, which is the one place this product must not lie.

Instead, **separate the two claims that a single percentage currently conflates**:

1. **An absolute, monotonic achievement count that can never go down:**
   *"You've completed 240 topics."* Derived from existing data (`notesPracticed`-style count over the
   learner's own history), it is unaffected by curriculum growth by construction.
2. **A relative, honest coverage figure against the current curriculum:**
   *"43.6% of your current Review Set is practiced."*

And at the moment of update, an explicit, non-defensive message:

> **250 new topics were added to your Review Set.**
> Your 240 completed topics and all your study history were preserved. Your Review Set now covers
> more of the exam, so your coverage percentage has been recalculated against the larger curriculum.

Three supporting recommendations:

- **Show the delta, not just the new state.** "240 completed (unchanged) · 550 topics (was 300)"
  reads as growth. "43.6%" alone reads as loss.
- **Never animate the percentage downward** and never fire a "progress dropped" style signal.
- **"Next topic" must prefer unpracticed items in the learner's existing order before newly added
  ones**, or the first thing a learner sees after an update is unfamiliar material displacing the
  topic they were mid-way through. This is a real regression risk in
  `getContinuePlanAction`/position ordering and is worth pinning with a test.

**Confidence: HIGH** on the mechanics (formulas read directly, production-verified). **MEDIUM** on
the copy specifics, which are an owner/UX call.

## N. Companion implications

### N.1 How Companion actually works

- Stored as JSONB on `note_collections.companion` (`NoteCollectionEntity.java:59-61`), typed
  `CompanionContent`.
- **Curator-authored, ADMIN-only.** `setCompanion` / `clearCompanion` / `generateCompanion` all call
  `assertAdmin(user)` (`:733`, `:755`, `:773`). Learners cannot author or edit Companion.
- **Top-level-Goal-only.** `validateCompanionTarget` restricts it; `updateParent` (`:697`) and
  `adoptGoal` (`:909`) both NULL it when a collection becomes a child.
- **Copied at adoption, conditionally** — `shouldCopyCompanion(source, userId)` inside
  `persistAdoptedPlan` (`:1471-1473`) and `persistAdoptedGoal`. The predicate is
  `source.getParentCollectionId() == null && !source.getOwnerUserId().equals(userId)` — i.e. copy
  Companion only when adopting a **top-level Goal** that someone **else** owns. A self-copy never
  inherits it, and a Subject Plan never carries one.

So Companion is **copied, not referenced**. An adopted Goal carries a frozen snapshot of the
curator's guidance and there is no path by which an improved Official Companion reaches it.

### N.2 The staleness precedent — this is the important find

`NoteCollectionEntity.companion_structure_snapshot` (`:62-63`) holds a
`CompanionStructureSnapshot(int memberCount, List<UUID> memberIds)`.

```java
private boolean companionMayBeOutdated(NoteCollectionEntity collection,
        List<NoteCollectionEntity> children, UUID userId) {
    if (collection.getCompanion() == null || collection.getCompanionStructureSnapshot() == null) return false;
    UserEntity user = getUserOrThrow(userId);
    if (user.getRole() != UserRole.ADMIN) return false;
    CompanionStructureSnapshot currentSnapshot = computeCompanionStructureSnapshot(collection, children);
    return !currentSnapshot.equals(collection.getCompanionStructureSnapshot());
}
```
— `NoteCollectionService.java:1184-1198`, with `computeCompanionStructureSnapshot` at `:1200-1214`

This is **exactly the pattern the update feature needs**, already shipped and already trusted:

- a **structural snapshot** (member count + sorted member ids) captured when guidance was authored;
- compared against the live structure to produce a **boolean "may be outdated"**;
- surfaced as an **advisory flag to the person who can act**, never auto-applied;
- **no revision integer, no version string, no event log.**

⚠️ **One inversion to note before anyone reuses it verbatim:** `companionMayBeOutdated` returns
`false` for any non-ADMIN caller (`:1190-1192`). It is a **curator** flag; the update feature's
consumer is a **learner**. The structural-snapshot *idiom* transfers; the role gate does not.
Reusing the method as-is would report "never stale" for every learner. This is a one-line
distinction, and it reinforces the recommendation rather than weakening it — the pattern is proven,
only its audience changes.

### N.3 Recommendation for Companion updates

1. **Do not auto-replace an adopted Companion.** Guidance describes a curriculum shape; replacing it
   mid-journey changes the learner's stated plan without their say.
2. **Reuse the snapshot idiom, don't invent a parallel one.** An adopted Goal can carry a snapshot
   of the *source* structure as of last sync; comparing it to the source's current structure answers
   "is my adopted curriculum behind the Official source?" for free.
3. **Bundle Companion refresh into the same learner-approved update action**, described in outcome
   terms ("your study guidance was refreshed to match the updated plan"), never as a separate
   technical step.
4. **Avoid duplicating stale guidance:** if `shouldCopyCompanion` declined to copy at adoption, the
   update must not opportunistically introduce one.

**Confidence: HIGH** on mechanics. The `companionMayBeOutdated` precedent is the strongest argument
in this audit against building a revision system.

## O. Minimum durable provenance (adoption slice)

### O.35 — Does durable source identity exist at every level?

| Level | Durable identity today | Verdict |
|---|---|---|
| Adopted Goal ↔ Official Goal | `note_collections.source_plan_id` (`V76:4`) | **EXISTS** ✓ |
| Adopted Subject Plan ↔ Official Subject Plan | `note_collections.source_plan_id` | **EXISTS** ✓ |
| Section ↔ source Section | `note_collection_items.label` string only | **MISSING** — and title/label matching is forbidden by anti-drift |
| Placement ↔ source placement | none on the row; **derivable** via `notes.copied_from_note_id` → source `note_collection_items.note_id` | **DERIVABLE** (100% coverage in production) |
| Learner Note ↔ canonical Note | `notes.copied_from_note_id` (+ `copied_from_title`, `copied_from_public`, `copied_at`) | **EXISTS** ✓ |

Two provenance fields exist on `notes` and they are **not** interchangeable — verified at
`NoteService.java:367-380`:

- `source_note_id` — set on **all** copies, *including self-copies* (`copy.setSourceNoteId(source.getId())` at `:366`, outside the owner branch).
- `copied_from_note_id` — set **only on non-owner copies** (`:373`); explicitly NULLed for self-copies (`:368`).

**Key placement identity on `copied_from_note_id`, not `source_note_id`.** Reason: adoption is
always a non-owner copy, `copied_from_note_id` is what `copyNote`'s own idempotency lookup keys on
(`findFirstByOwnerUserIdAndCopiedFromNoteId`), and using the same key as the dedup keeps one
definition rather than two. (`source_note_id` and general copy provenance are a sibling agent's
question; this audit does not touch them.)

⚠️ **Uniqueness caveat, verified and then diagnosed:** `(owner_user_id, copied_from_note_id)` is
**NOT** unique — the repository method is `findFirst...` and there is exactly one index touching
`copied_from_note_id`. Production contains **1 such pair, materialising as 3 rows**: three copies of
*"APGAR Scoring and Newborn Assessment"* by one user, all stamped `2026-06-07T04:04:57` within
**30 milliseconds** — a concurrent double-submit race in `copyNote`, whose dedup read is unlocked.

**It is benign for this audit:** all three rows have **0 placements and 0 sessions**. They are
orphaned notes that never entered a collection, so **placement reconstruction is unaffected and is
effectively 1:1 in practice.** An update pass should still tie-break deterministically (prefer the
copy actually placed in this plan, else oldest `copied_at`) rather than assume a single row — but
this is defensive, not a live obstacle.

### O — The smallest addition that makes updates safe

Deliberately **adoption-scoped**. This is not an inheritance framework and must not be generalized.

**1. Placement source + label-as-of-last-sync (the one genuinely missing fact).**
On `note_collection_items`, for adopted plans only:
- `source_note_id` — the canonical note this placement came from. *Optional*: fully derivable via
  `copied_from_note_id` today, so this is a denormalization for query cost and duplicate-safety,
  not a new fact.
- `source_label_at_sync` — **the one fact that does not exist and cannot be reconstructed.** Without
  it, a label mismatch cannot be attributed to the learner or the source, and every Section merge
  is a guess. Cheap now (74 labelled adopted items); expensive after the reshape.
- `source_position_at_sync` — same argument, lower value. Optional.

**2. A removal record (§28).**
A small `(collection_id, source_note_id, removed_at)` record written by `removeItem` **when the
collection has a `source_plan_id` and the item had source lineage**. Not a general tombstone, not a
soft-delete of the placement row — the existing hard delete stays, since "Remove never means
canonical note deletion" is standing doctrine and the learner's note survives regardless.

Why a record and not something smaller: absence is currently **ambiguous by construction** — an
item can be absent because the learner removed it *or* because `copySourceItems` silently swallowed
a `RuntimeException` for it (`:1436-1444`). Only an explicit record separates the two. Production
confirms the population is **currently zero**, so this ships prospectively with an empty backfill
and zero reconstruction risk.

**Anti-drift honoured:** this does **not** detach the plan from updates. The record suppresses
re-adding one topic; the plan keeps receiving everything else.

**3. A last-sync marker on the adopted collection.**
`source_synced_at` (and optionally a `CompanionStructureSnapshot`-shaped structural snapshot of the
source as of that sync). This answers *"is my adopted curriculum behind the Official source?"* and
*"what changed since I adopted?"* by direct comparison — **reusing the `companionMayBeOutdated`
idiom rather than inventing a second one.**

**What is explicitly NOT needed:**
- No Section entity or third collection level.
- No `source_item_id` FK. Per §J.5, item UUIDs survive reorder and relabel (in-place UPDATEs) but
  **not** remove-and-re-add (`removeItem` hard-deletes). The pair
  `(source_collection_id, source_note_id)` is the more robust key and is already reconstructable.
- No event log, no diff/merge storage, no per-field provenance on note content.
- No backfill of historical labels or positions — they are unrecoverable and must be reported as
  such, not guessed. Existing adoptions simply start their sync history at the migration.

## XV / XVI. Are explicit revisions needed?

**Recommendation: NO version numbers, NO event sourcing. A structural snapshot + timestamp is
sufficient, and the repo already proves the pattern works.**

The two questions that must be answerable are narrow:

| Question | Answerable by |
|---|---|
| *Is my adopted curriculum behind the Official source?* | compare source structure now vs `source_synced_at` snapshot — exactly `companionMayBeOutdated`'s shape (`:1184-1198`) |
| *What changed since I adopted?* | set difference over source placements: `copied_from_note_id` join gives additions, removals and moves directly. **This already works today** — every figure in §L.3 and §L.6 was produced by exactly such a query, with no schema change. |

A `revision` integer on the Official plan would be **cheap and mildly useful** for display ("Official
CE Review Set, updated 3 Sept") and for a stable "you're on the version from X" phrase. It is
**not required** for correctness and should not be mistaken for the mechanism. Semantic versions
(`v1.2.0`) are unjustified — nothing consumes the semantics.

Content revision on individual notes is **not needed**: `notes.updated_at` vs `copied_at` already
identifies drifted copies (266 in production), and content is never overwritten anyway.

**Confidence: HIGH.** The falsifying evidence would be a requirement to reconstruct *historical*
curriculum states ("show me the plan as it was in June"), which nothing in the brief asks for.

## Update POLICY

**Endorsed: hybrid, leaning user-controlled** — detect and summarize automatically, apply on the
learner's say-so. The repo supports this rather than contradicting it, and three things reinforce it:

1. `companionMayBeOutdated` is already exactly this shape — detect automatically, surface as an
   advisory flag, let a human act.
2. The additive half is technically safe to automate (`copyNote` idempotency), but the
   **restructuring half is not** — labels and positions cannot be merged without guessing until the
   provenance in §O lands.
3. `adoptGoal`'s reparenting path (§J.7) is the in-repo precedent for "a re-run picks up existing
   state without destroying it."

**Suggested shape (no learner-facing merge/diff/branch vocabulary):**

> **Your Review Set has updates.**
> 250 new topics were added, and 12 topics are no longer part of the Official plan.
> *[Add the new topics]*  ·  *[See what changed]*

Applying performs only: (a) copy new source notes the learner lacks, skipping any with a removal
record; (b) append their placements; (c) refresh the sync snapshot. Retired topics are **labelled,
never deleted**. Renames and reorders are surfaced only, until §O's provenance exists.

**One challenge to the stated preference, offered rather than assumed:** *purely additive* updates
(new notes only, no restructuring) are safe enough to auto-apply and would be invisible in the good
case. I still recommend against it — a learner opening their plan to find 250 unfamiliar topics they
did not ask for is a worse first impression than a dismissible prompt, and it silently moves the
progress percentage they last saw. **Notify always; apply on consent.**

## Stage 2 feasibility constraint — the cost profile of an update pass

Stated at scoping rather than discovered mid-implementation.

`copySourceItems` is deliberately **one transaction per note** — `adopt()` is non-transactional so
"a single failed copy is isolated and never rolls back the whole adopt"
(`NoteCollectionService.java:837-838`). Each iteration performs a note insert, a
`noteRepository.flush()`, `noteCourseProgramRepository.replace`, and `copySourceStudyPack`
(`NoteService.java:389-399`).

At reshape scale that is **~250 sequential copy transactions for one learner pressing one button**,
and the CE Review Set is planned to go from ~300 to ~550 notes.

This intersects the open release directly. `v0.112.0` shipped on **HikariCP pool exhaustion** and
`v0.114.0 — Connection Evidence` is currently *measuring* connection-hold behaviour. An update pass
with this shape is exactly the class of workload under measurement. It is not a defect in the
adoption design — the per-note isolation is a deliberate and good property — but Stage 2 must decide
its execution model rather than inherit `adopt()`'s synchronous loop by default. Options worth
pricing: run it on the existing async generation executor with a status the UI polls (the Study Pack
pipeline precedent), batch the copies, or bound the per-invocation item count.

**Do not resolve this here** — it is a Stage 2 decision and it may be informed by `v0.114.0`'s
evidence. It is recorded so the update pass is not scoped as a synchronous request.

## Final Questions 7–18

**Q7 — Is an adopted plan a permanent snapshot in practice?**
**Yes, completely.** `adopt()` bails at `:830-835` before `copySourceItems` runs, and that method has
exactly one caller. No code path adds a source note to an existing adoption. Production confirms the
consequence: 364 source placements and 68 whole Subject Plans have never reached their adopters.
*(§J.3, §L.3 — HIGH)*

**Q8 — Can `sourcePlanId` support safe updates?**
**Yes, and it is already sufficient at the collection level.** `(owner_user_id, source_plan_id)`
carries a partial unique index (`V76:10-11`), giving a database-guaranteed one-adoption-per-source
mapping at both Goal and Subject-Plan level. It is the right anchor; nothing about it needs changing.
*(§J.2, §O.35 — HIGH)*

**Q9 — What additional source identity is minimally required?**
Three small, adoption-scoped things: (1) **`source_label_at_sync`** on the placement — the only fact
that genuinely does not exist and cannot be reconstructed, without which every Section merge is a
guess; (2) a **removal record** for source-lineage items; (3) a **`source_synced_at` + structural
snapshot** on the adopted collection. Placement→source-note identity needs **no new column** — it is
100% derivable via `copied_from_note_id`. *(§O — HIGH)*

**Q10 — How does new material reach early adopters?**
By **re-running the existing copy pass**, which is already safe: `copyNote`'s dedup on
`(owner_user_id, copied_from_note_id)` (`NoteService.java:333-350`) resolves every already-owned note
to the learner's own copy — preserving sessions, `ConceptHealth` and edits — and mints rows only for
genuinely new source notes. The mechanism is built; only the decision to call it is missing.
*(§J.6 — HIGH)*

**Q11 — How is learner customization preserved?**
Structurally, by construction on the parts that matter: note content is **never** written back into
an existing copy, and learner-added notes are identifiable. But **label and position customization
cannot be preserved across a merge today**, because nothing records their value as of adoption — so
until `source_label_at_sync` exists, renames and reorders must be **surfaced only, never applied**.
*(§K.1, §K.3 — HIGH)*

**Q12 — How are learner-removed topics respected?**
**They cannot be today.** `removeItem` hard-deletes the placement row with no tombstone, and absence
is ambiguous anyway because `copySourceItems` silently swallows per-item failures (`:1436-1444`).
The fix is a small removal record. The population is **currently zero** — 0 of 364 absences are
learner removals — so it ships prospectively with an empty backfill and no reconstruction risk.
*(§L.4, §O.28 — HIGH)*

**Q13 — How should retired topics behave?**
**Labelled, never deleted.** The learner may have practiced one, and their sessions and
`ConceptHealth` key on their own note id. Mark as *"no longer included in the current Official
plan"* with optional learner cleanup. 206 such placements already exist, and zero source notes were
deleted or unpublished, so nothing forces a destructive path. *(§K.2, §L.6 — HIGH)*

**Q14 — How are canonical note content updates surfaced without overwriting?**
`copyNote` already never writes into an existing copy, so overwrite is structurally impossible on
this path. Drift is detectable today with no schema change: `source.updated_at > copy.copied_at`
(266 rows in production), and `copied_from_title` enables a three-way title comparison
(source vs at-copy vs learner). Surface as *"the Official version of this note was updated"* with an
optional learner-initiated refresh. *(§K.2, §L.6 — HIGH)*

**Q15 — What happens to completion percentages on expansion?**
They genuinely fall. The progress denominator is `items.size()` (`:2038-2046`), and readiness dilutes
in lockstep because **all 4,374 adopted items arrive `GENERATED` with a copied Study Pack** — so new
notes enter both denominators at once. 240/300 = 80% really does become 240/550 = 43.6%.
*(§M.1–M.2 — HIGH)*

**Q16 — How is that explained?**
Do not freeze the denominator and do not fake 80% — readiness against the current curriculum must
stay honest. **Split the two claims the single percentage conflates:** an absolute, monotonic
*"You've completed 240 topics"* that can never fall, beside an honest *"43.6% of your current Review
Set is practiced."* Show the delta, never animate the number downward, and prefer the learner's
existing unpracticed items in "next topic" over newly inserted ones. **Nothing the learner earned is
lost** — every session and `ConceptHealth` row survives untouched, and the message should say so.
*(§M.3–M.4 — HIGH on mechanics, MEDIUM on copy)*

**Q17 — Are explicit revisions needed?**
**No.** A structural snapshot plus `source_synced_at` answers both required questions, and the repo
already proves the pattern in `companionMayBeOutdated` / `companion_structure_snapshot`
(`:1184-1214`). *"What changed since I adopted?"* is answerable **today** with zero schema change —
every figure in §L was produced by exactly such a query. A display-only `revision` integer is cheap
and mildly useful; semantic versions and event sourcing are unjustified. *(§XV/XVI — MEDIUM-HIGH)*

**Q18 — Automatic, user-approved, or hybrid?**
**Hybrid, leaning user-controlled** — detect and summarize automatically, apply on consent. The
additive half is technically safe to automate, but the restructuring half is not until §O's
provenance exists, and `companionMayBeOutdated` is already the in-repo precedent for
detect-and-flag-without-applying. Four learners have already pressed Adopt on an
already-adopted Goal ten times and received nothing, so the intent exists in the wild. I considered
auto-applying purely additive updates and **recommend against it**: 250 unfamiliar topics appearing
unannounced is a worse first impression than a dismissible prompt, and it silently moves the
percentage the learner last saw. *(§Update POLICY, §L.5 — MEDIUM-HIGH)*
