# RELEASES.md - NoteLib

## v0.71.0 - Applicable Programs

**Status: In Progress**

Theme: a canonical note stops belonging to one program. `note_course_program` makes applicability a many-to-many fact, so an Algebra note authored once for Engineering Mathematics can surface under every engineering program that needs it — which is the payoff Release A built the foundations for.

This is **Release B of `docs/architecture/ADR-001-canonical-knowledge-architecture.md`**. Release A closed with `v0.70.0`.

**Read ADR-001's own warnings before scoping anything here.** Release B is materially riskier than Release A, and the ADR says so in its own Consequences section:

- **It is not reversible** once filters and badges read the join; rollback would require a migration. This knowingly fails clause 2 of the ROADMAP bootstrap test and is accepted as a multi-release commitment.
- **Filter and search paths move to join/`EXISTS` semantics on a hot paginated path** that already required a dedicated performance release (`v0.51.0`).
- **Facet counts will sum above the note total**, because a note appears under every applicable program. That is correct behavior needing a UI affordance, not a bug to fix.
- **Program Families are an authoring shortcut only** — selecting a family expands to explicit `note_course_program` rows at save time. Applicability is never inferred from a family at read time.

### Planned Scope

Cut into **three slices along the irreversibility boundary**, not by layer — full reasoning in `docs/claude-prompt/canonical-knowledge-architecture-out/18-release-b-slice-sequence.md`. Release A split by layer because all of it was reversible; Release B is not.

**Slice 3's former gate is cleared.** The opening framing of this section read "blocked on the applicability question," which is a broader reading than ADR-001's own gate: the ADR required curator verification *"before **family-expansion defaults** are set"* — not before the join table, the backfill, or a curator adding programs to a note by hand. The 2026-08-05 owner rulings narrowed family expansion to an unconditional authoring shortcut, removing the curriculum question from the implementation.

- **Slice 1 — `note_course_program`, 1:1 backfill, admin write surface (backend + migration + frontend).** Additive, reversible, gated on nothing. Backfills exactly one row per note from the existing string resolved against the `v0.70.0` catalog; a note whose value the catalog deliberately excluded gets **no** join row and keeps its string. Nothing reads the join. **This is the slice that delivers what the whole ADR exists for** — one canonical note applicable to many programs, no duplication.
- **Slice 2 — filters, facets, badges, and search move to join/`EXISTS` (backend).** The irreversible commitment, and a hot paginated path that already needed a dedicated performance release (`v0.51.0`). **Must run while every note still has exactly one program row**, because that is what makes it testable: facet counts are `count(*)` grouped on `notes` today, so the join version returns identical counts and the regression test is "same filter, same counts, before and after" rather than a judgment call. Once notes carry several programs, facet counts sum above the note total — correct per ADR-001, needing a UI affordance rather than a fix.
- **Slice 3 — Program Family expansion (frontend).** Gate cleared. The shared Applicable Programs control adds every catalog member of a family to the explicit selection, which the author can trim before the existing save path persists it; no backend or catalog change is involved.
- **Slice 4 — Single Program Axis: remove "Primary Course / Program" (backend + frontend).** One `Course / Program(s)` picker replaces the two-field model across Note Editor, Note Detail inline edit, Create-from-topic, and Bulk Generate. Learners use one free-text personal program stored in `notes.course_program`; Teacher/Admin curation uses one-or-many catalog ids stored in `note_course_program`. Domain Context is required above one program on both save endpoints, and program lists never reach the LLM. Copies inherit both representations; no migration or catalog seed is needed.
- **Slice 5 — Onboarding Intent Router (frontend + backend). Added 2026-08-06 after the pre-signoff pressure test, by owner ruling.** The pressure test found onboarding to be the flow most severely affected by this architecture change, including **B0 — an activation-blocking regression this release introduced**: `resolveRequestedCourseProgram` gained a `throw` where `main` returned null, and onboarding creates its first note without sending a program, so every new user on the create-note path receives *"Choose at least one course or program."* on a screen with no such field and cannot finish onboarding. Scoped in `docs/claude-plans/onboarding-activation-and-intent-router.md`. Five parts, in order: **(1)** the B0 repair, independent and landing first so signoff is never blocked behind the redesign; **(2)** an owner-run production audit of Official Review Set program vocabulary (`onboarding-review-set-vocabulary-audit.sql`); **(3)** activation repair — persist Profile Type at Step 1 and learning context at Step 2 through a new narrow `PUT /users/profile/learning-context`, replacing a fire-and-forget write that can silently lose a user's learner level and program; **(4)** a program-resolution layer shaped by the audit; **(5)** the Intent Router itself — a first-intent step whose supporting copy resolves against the learner's own program *before* selection, practice-first opened beyond `BOARD_EXAM`, and an honest availability state for unsupported programs. **Governing philosophy, owner-ratified:** onboarding is no longer profile collection — it is an intelligent router that helps every learner reach the fastest successful study experience available to them. **Deliberately scoped in rather than deferred:** onboarding is a one-time flow, so unlike slice 4 there is no re-learning cost to deferring — the owner's reason is that shipping a first impression that models the wrong product is worse than the added scope.

**The gate on slice 3 — CLEARED 2026-08-05 by owner ruling.** It read: *applicability groupings are unverified against current PRC board syllabi; `[EFFORT]`, not `[EVIDENCE]` — no query answers whether `Engineering Sciences` spans 8 or 11 engineering programs.* It was cleared by narrowing the question rather than answering it as posed: the catalog holds **3** engineering programs and one family, not 11 (the figure came from an early doc reasoning about Philippine engineering education generally), and the rulings make expansion **unconditional**, so no subject→program mapping is needed and the syllabus question stops gating anything. **R4 still did not settle applicability** — that caveat stands, it is simply no longer load-bearing.

Four rulings, none of which slice 3 may re-litigate. Full text in ADR-001 and `docs/product/ROADMAP.md`:

1. **The catalog represents *valid applicability*, not curriculum coverage** — "who can legitimately study this note?" Review Sets communicate completeness. **The catalog still follows curriculum, but a program no longer needs a complete Review Set to earn an entry** — it earns one once legitimate canonical notes are applicable to it. **Pre-seeding every PRC engineering program is rejected as premature**; growth is incremental and demand-driven by authoring. **So slice 3 ships no catalog seed migration** — the 21 seeded programs stand until authoring demands more. Refines rather than reverses the `v0.70.0` follow-not-lead posture; the `Computer Science` / `Software Engineering` rulings stand.
2. **Program Families stay intentionally dumb** — an authoring shortcut, never a curriculum engine.
3. **Expansion fills in all family members** — no curated subsets; the author trims.
4. **Expansion is never subject-conditioned** — explicitly rejected, because it would re-couple Subject knowledge to applicability rules.

**Binding principle, now in ADR-001:** Program Families are a **productivity feature, not a curriculum feature**, deliberately allowed to over-select because the Note's explicit Applicable Programs are always the source of truth.

**Slice 2's stated safety property was falsified after slice 1 shipped, and its semantics changed — owner ruling, 2026-08-05.** The scope above says the join returns identical facet counts at one row per note. It does not: `V107` deliberately creates no join row for a catalog-*excluded* value, so a pure-join rewrite changes **result sets**, not counts — an excluded value's facet disappears, its filter returns 0 notes instead of N, and its public shareable slug URL stops resolving. **Slice 2 therefore reads the join with a legacy-string fallback** (`EXISTS(join rows) OR (no join rows AND legacy string matches)`), which is identical to today's behavior at 1:1 and correct once a note carries several programs. Accepted cost: `notes.course_program` stays load-bearing on read paths, making slice 2 a smaller irreversible step than originally scoped — the join becomes the primary read, not the only one. Retiring the fallback is a separate, unscheduled decision. Production impact sizing: `19-slice-2-facet-equivalence-impact.sql`, query A. Full correction: `18-release-b-slice-sequence.md`.

### Carried forward

- **The two `v0.70.0` Known Limitations**, both documented rather than fixed: the Challenge bank orphaning on a learner-level correction (including the write path whose duplicate-key failure surfaces at commit, outside its own catch, contradicting `docs/features/challenge-quiz.md`'s best-effort claim), and the null-by-null pool/bank cohort (40 pools, 15 bank rows). Each now has a ROADMAP Backlog Index row.

### Pre-signoff pressure test — run 2026-08-06, findings OPEN

The full pressure test required by `CLAUDE.md` ran against the whole release (112 files, 17 non-merge commits).
**Full findings: `docs/claude-findings/v0.71.0-pre-signoff-pressure-test.md`.** Nothing below is fixed yet; per
`CLAUDE.md` every finding must be fixed or explicitly recorded here as a Known Limitation before signoff.

Five blockers, ranked:

- **B0 — onboarding is a dead end for every new user.** Release-introduced. **FIXED — see the Shipped section below.** The remaining slice 5 scope (early persistence, the Intent Router) is independent of the repair.
- **B1 — `copyNote` throws a foreign-key violation**, proven empirically with a probe test: `NoteService.java:339-340` calls `save()` then a raw-JDBC child insert with no `flush()` between, unlike create (`:191-194`) and update (`:231-234`) which both flush. Measured: 18 of 40 public notes locally (45%) carry join rows, so "Copy to my library" 500s on them, and study-plan adoption silently yields an empty plan. **Do not fix in isolation** — the `flush()` makes copy succeed, which then propagates B2's stale rows into every copy.
- **B2 — V107's unfiltered backfill froze the Course / Program of every learner note it touched.** Found independently by three agents. A learner's edit is permanently inert on both discovery and generation. **Open decision** — owner ruled 2026-08-06 to keep learner-owned join rows and validate against stored rows, which resolves C1 but leaves B2 open; see "Open decision A" in the onboarding plan.
- **B3 — curated notes are invisible to the non-paginated public path**, so the dashboard "community notes for your program" widget disappears for exactly the content it promotes. Same class at `public/library/[subject]/[slug]/page.tsx:102-105`, which kills the exam-hub callout and the "More {program} notes" rail.
- **B4 — the test suite cannot catch any of the above.** Shape B (join rows + NULL legacy string), the shape slice 4 made canonical, appears in **no** test; the join repository is `@MockBean` in all five integration tests; every `@BeforeEach` deletes join rows before notes, designing out cascade coverage; and V107's backfill sits inside its `DO $$` block, which the repo's own migration-test helper strips. Two blockers are additionally *locked in* by tests asserting the broken behaviour.

Also found: 9 High (including a falsified `RELEASES.md` LaTeX claim — ~10 quiz surfaces still render raw, and the shared answer-review **explanation** is raw across 5 call sites), 16 Medium, 12 Low. **Four claims in the handoff brief were disproven**, including a "removed compatibility constructor" that never existed in any commit and an H2/V107 schema divergence that does not exist. ADR-001's founding constraint was verified to genuinely hold: both resolver guards are strict `size() == 1`, so a multi-program note can never send a list to a prompt.

### Shipped

- **C1 fixed — the multi-program invariant is enforced on the server, not just the client (backend).** `NoteService.update` validated the *request's* program set, but a learner's request carries no programs at all, so the count was always 0 and the rule was unenforceable on the only author who can reach it: a learner could copy a curated multi-program note and clear its Domain Context, producing exactly the state slice 4 forbids, with the client as the sole guard. Validation now reads the set that will be in effect *after* the update — the request for curators, whose request is the new set, and the stored join rows for learners, whose rows survive the update untouched. **The one-line fix recorded in the findings doc would have broken curators**, checking the pre-update set against the post-update domain: it blocks a legal reduction from several programs to one and lets an illegal one-to-many expansion through. Both directions are now covered by tests. `create` is unchanged and needs no stored-row lookup — the note does not exist yet. **No gate is owed.** A pre-existing violating population would have locked its owner out of every later save, since Domain Context is curator-only — but it cannot exist: production has not received `note_course_program` at all, slices 1–4 deploy as one unit, V107 creates at most one row per note, and both the slice 4 invariant and this fix ship in that same deploy. `docs/claude-plans/c1-multi-program-null-domain-sizing.sql` is retained as a **post-deploy** check, where a non-zero result would mean a write path regressed rather than legacy data.
- **B0 fixed — new users can complete onboarding again (frontend).** Onboarding collected a Course / Program at Step 2 but sent it on neither of its Step 3 note calls, while the profile value it would have fallen back to is not persisted until Step 5. Every new user on the create-note path was stopped by *"Choose at least one course or program."* on a screen that has no such field, and could not reach the dashboard. Both calls now send it — `courseProgramText` on `createNote`, and the program argument on `generateNoteFromTopic` — which unblocks the generate path at *Generate* and both paths at *Generate Study Pack*. Regression coverage added on both sides: the onboarding test asserts both call payloads exactly, and two backend tests cover the shape where the request supplies the program and the profile has none, which no existing course/program test did. Rule recorded in `docs/features/onboarding.md`. **Known limitation, unchanged:** a hand-provisioned ADMIN account still takes the curator branch and cannot complete the create-note path; ADMIN accounts do not sign up through onboarding.
- **LaTeX now renders in quiz questions, options, and explanations (frontend).** A generated Algebra question read literally as `simplify \(\frac{x^3 - 4x^2 + 5x}{x - 2}\)?` in Quick Review. KaTeX and a text-plus-math renderer already existed in this repo, but had only ever been wired to *working solutions*. **Unrelated to Applicable Programs** — found while reviewing this release, fixed here. The first pass covered only the components it happened to open; the result and preview surfaces (`practice-quiz-card`, `generated-quiz-preview-page-client`, `quiz-matching-group`) render question text directly and were still broken, and **explanations were raw on every surface**, including session pages whose question text was already correct. `renderMathText` returns the raw string untouched when text contains no math delimiters, so the DOM is unchanged for the overwhelming majority of questions — wrapping every string had silently moved `break-words` off the elements callers style. Rule recorded in `docs/features/quiz.md`: any surface showing a question, option, or explanation routes through `renderMathText`, and a raw `{item.question}` is the bug.
- **Note authoring UX pass (frontend).** Four fixes from real use of the slice 4 editor. **Course / Program(s) keeps its original position in the main metadata grid for curators** — slice 4 had moved only the curator control into the gated "Generation & discovery" fieldset, which misfiled a discovery field as generation metadata and contradicted its own helper text. **A curator's programs pre-fill from their profile again** on a new note; slice 4 seeded only the learner free-text draft, so curators saw "No course programs selected" while the footer read "Tailored for: Accountancy". The pre-fill is guarded three ways — never in edit mode, never after the author touches the selection, and silently skipped when the profile value has no catalog match. **Subject is surfaced through the always-visible sticky bar** (`Tailored for: Accountancy · Algebra`, or `· no subject yet`) rather than by moving it up the form, so authors learn it exists and is editable while "Add details" stays collapsed and capture-first is preserved; no AI call is added to the editor, so subject suggestions remain post-generation. **The collapsed "Add details" summary reflects state instead of restating rules** — it previously read "Course / Program is required", which after the pre-fill usually described something already done. Field order stays Title → Subject → Course / Program(s), the sequence students actually author in.
- **Single Course / Program(s) axis (slice 4).** Removed derived-primary synchronization and the `NoteApplicableProgramsMaintenanceService`; curator saves reconcile catalog joins atomically while learner authoring continues to write its single free-text personal program. The resolver uses Domain Context, then exactly one joined catalog name, then the personal note string, then the profile string. Private and public note detail now say `Applicable to N programs` and expose the program list. **Two authoring modes on one gating line, ratified in `ADR-001`:** curators (Teacher/Admin) get catalog-only programs and one-or-many; learners get free text and exactly one. This is a product distinction — multi-program authoring is a curation act — not a permission tier, and `notes.course_program` is the **personal-notes program field** rather than a legacy column. Domain Context becomes required above one program, enforced on both save endpoints, because the prompt's domain constraint is unsatisfiable given several disciplines.
- **Product vision ratified (docs).** NoteLib is **a learning system built on top of a knowledge library** — the library is the foundation, the learning journey is the product. Three layers earned strictly in order: Trust (comprehensive Official Review Sets) → Habit (Study Packs, Companion, Progress, Review Sets) → Community (user-created knowledge). **Community content is no longer the primary acquisition strategy**; the community vision is not abandoned, it is being earned in the correct order. Recorded in `docs/product/SPEC.md` → Product Philosophy and as a governing block in the ROADMAP's prioritization lens, because it changes what outranks what when scoping.

- **Applicable Programs UX polish (pre-signoff pass).** Cards now state reach as a summary instead of a list — one program is named, several render as `Applies to N programs` — and the identity row above the title is the Subject badge alone. Listing names there made them read as a second identity, left adjacent names with no delimiter (`Accountancy Architecture` scanned as one value), and mostly repeated what a program-filtered learner had already asked for. On Note Detail the header collapses both program facts to one muted line — `Accountancy · Applies to 6 programs` — with the count suppressed at a single applicable program, since the seeded default is exactly one. A first attempt rendered the full set as pills in a bordered block; that cost roughly a quarter of the mobile viewport and pushed `Start Quick Review` and the whole content tab bar below the fold, and it boxed a single line for plain student owners who never see Applicable Programs at all. Names now appear only where they can be acted on — the Edit details panel and the admin table — which makes one rule across every surface: **names where you author, counts where you read.** Authoring keeps both fields but explains why the first seeds the second, which is the point authors reliably misread as duplication. Domain Context and Note Learner Level empty options move off implementation vocabulary — "Use … fallback" becomes "Automatic — based on the program / reader" — and the fieldset is now "Generation & discovery". Copy and presentation only; no resolution, persistence, or query behavior changed.
- **Slice 3 — Program Family authoring shortcut.** The shared Applicable Programs control on Note Editor, Note Detail, and the Admin Dashboard now derives Program Families from the existing catalog and can add every currently-unselected member in one action. Expansion unions into the explicit selection, shows removable chips immediately for trimming, and is unconditional across Subject, Domain Context, and learner level; it adds no network call or persisted family state, never expands at read time, and ships with no backend, schema, endpoint, or catalog change.
- **Slice 2 — Applicable Programs discovery reads.** Private Library course/program filters and facets and Public Library slug filters and search now read `note_course_program` first, while notes with no join rows retain their legacy `notes.course_program` filter, facet, search, and shareable-URL behavior. Paginated list projections aggregate joined catalog names in the list query so cards can render program information without an N+1 request (the card's own presentation was then reworked by the UX polish bullet above); facets use the mutually-exclusive join/legacy `UNION ALL`, so multi-program counts may correctly exceed the note total and both filter panels explain why. `GET /course-programs` keeps its existing path and `List<String>` contract but now includes join-only program names, intentionally widening both discovery and the legacy authoring suggestions that consume the same endpoint. Program Families remain unexpanded and Applicable Programs remain prompt-free.
- **Slice 1 — Applicable Programs storage and write surfaces.** V107 adds the unmapped JDBC-only `note_course_program` join with uniqueness, lookup indexes, note-delete cascade, and a one-row-per-resolvable-note backfill driven from the live `notes.course_program` string (exact match plus the sole `Bsed` → `Education` alias); excluded strings remain unchanged and receive no row. Authenticated catalog and owner-safe note APIs now support full-set reconciliation for Teacher/Admin authors, note create/update keeps an untouched *derived* set aligned with the legacy string — including the empty set, so a note that gains a catalog-resolvable course/program after creation gains its join row — while preserving curated sets, and the Note Editor, Note Detail, and a paginated Admin Dashboard table expose one shared catalog-backed multi-select. This slice remains additive: filters, facets, badges, search, and URLs still read only the legacy string and nothing learner-facing reads the join.

## v0.70.0 - Canonical Knowledge Completion

**Status: Released**

Theme: finish what `v0.69.0` started — make the canonical authoring axes correctable after generation, give programs a real catalog, and stop question pools being invalidated by whoever happens to be reading.

### Planned Scope

- **Authoring metadata editable on `STUDY_PACK_READY` notes (frontend).** The note editor closes once a Study Pack exists, so Domain Context and Note Learner Level cannot be corrected after generation from any surface the UI offers. Content stays locked (that lock exists to keep the note consistent with its pack); these two fields do not touch the existing pack and only shape *future* generation. **This is first because it blocks R4 step 1**, which asks for an existing note with a generated pack to be re-set and regenerated. Implementation found the gate is entirely client-side and that this item and the one below are the same change — see Shipped.
- **Note detail page's inline "Edit details" panel exposes both axes (frontend).** That panel duplicates Subject, Course/Program, Audience and Tags but omits the two axes `v0.69.0` shipped, so it reads as a complete authoring surface while silently missing them. It cost two people real time in the first hour of production use.
- **`course_programs` catalog + `program_families` (backend, data).** Deferred from `v0.69.0`. Two production reads now done: `15-vocabulary-and-impact-results.md` Parts 1 and 3. **32 values, zero character-level collisions across all three sources** — the second read (`16-program-vocabulary-seed-followup.sql`) added `note_collections.course_program` (`V76`), which `11` never covered, and confirmed collections contribute no values of their own. Resolves to **21 seeded programs, 11 excluded**, plus one `program_families` row. Nullable FK on `notes` and `users` **alongside** the existing string columns; nothing reads the FK. Retires `ExamGoalConfig`/`exam-hub-config.ts`'s hand-synced name lists.
- **Question pool / bank learner-level re-keying (backend).** Deferred from `v0.69.0`; production read now done. `exam_question_pool.learner_level` and `challenge_quiz_question_bank.learner_level` move off the **reader's** level onto the **note's**, so a College note's pool is no longer discarded the moment a Grade School user touches it. **No pre-stamping migration** — measured at 57 of 1,244 READY pools (4.6%) and 5 of 6,235 bank rows, a lazy regeneration spread across normal traffic. `PostSessionNextStepService` must be threaded in the **same** PR as the five `ChallengeQuizService` write sites.
- **`10-high-school-classification.sql` cleanup (docs).** It still says V104 where V105 applied, "expected 11 rows" where one was deleted as a duplicate, and describes clearing `course_program` — a step ADR-001's second corollary deferred out of the release entirely.

Anti-drift — what this release explicitly does **NOT** change:

- **No Domain Context backfill onto pool/bank rows (PR 6b).** Gated on R4: a changed value set would invalidate it. Only the *learner level* re-keying ships here.
- **No `note_course_program` and no Applicable Programs.** Still Release B. **`notes.course_program_id` and `users.course_program_id` are written and read by nothing** — no filter, facet, badge, search predicate, or URL changes. The one sanctioned read of the new tables is the Exam Hub name lookup described under Resolved decisions: it reads the `course_programs` **table by name**, never either FK, and must be behavior-preserving. Anything beyond that is Release B.
- **No authoring-by-inference implementation.** ADR-001 records it as a direction, explicitly gated behind R4. Pre-filling from a Review Set is *not* in this release.
- **The note-level learner depth axis is not removed, narrowed, or renamed before R4 runs** — owner constraint, 2026-08-04.
- **Note content stays locked after `STUDY_PACK_READY`.** Only the two authoring axes become editable; this is not a reopening of the content lock.
- **`docs/product/EXAM_MODES.md` is untouched** — locked contract, exactly 5 modes.

### Resolved decisions — PR 5 is scopeable

Four owner rulings, none of which PR 5 may re-litigate. The full 32-row seed table and the 21/11 split live in `15-vocabulary-and-impact-results.md` Part 3.

**1. Computer Science / Information Technology / Software Engineering — ruled by the owner 2026-08-04.** `08` ruled all three survive as distinct programs; the production read disagreed — IT has 74 notes across 11 subjects, Software Engineering has 4 notes whose only subject is *Computer Science*, and Computer Science has **0 notes** against 3 user profiles.

**Ruling: seed `Information Technology` as a catalog program. `Computer Science` and `Software Engineering` stay user-side values with a NULL catalog FK**, pending a curator ruling if either grows real curriculum. Nothing is deleted — the 4 Software Engineering notes and the 3 Computer Science profiles keep their existing strings, exactly as the catalog's other unmappable values do. This reverses part of `08` on evidence `08` did not have; it is ratified rather than assumed.

**2. The three `Senior High – …` strands are seeded — ruled by the owner 2026-08-04.** Closes the call `11`'s Query D deferred to PR 5. STEM (4 notes), ABM (4), and HUMSS (3) are curriculum *tracks*, not bare levels: `V105` deliberately left their `domain_context` NULL so the strand keeps reaching the prompt as the effective authoring domain, and excluding them would leave the value that actually reaches generation sitting outside the catalog. `Grade School`, `Junior High`, and `High School` stay excluded as bare levels now fully described by `learner_level` + `domain_context`. Excluding a value never means clearing it — ADR-001's second corollary still defers that out of the release entirely.

**3. `Medical – Surgical Nursing` is dropped from PNLE — ruled by the owner 2026-08-04.** The second production read found it matches **0 notes, 0 users, and 0 collections**: it exists only in `ExamGoalConfig:15` and `frontend/lib/exam-hub-config.ts:26`, under a comment in both files asserting that course/program values "must match production DB values exactly." It never has. It is also a PNLE board *subject area* rather than a degree program, failing the catalog's classification rule on the same grounds as `Biology`. **PNLE maps to `Nursing` only.** Behavior-preserving in effect — the dropped value matched nothing — but it must be proven by test rather than asserted. The Exam Hub's multi-program dedupe path stays; PNLE simply stops exercising it. `RELEASES.md:253`'s worked example of that dedupe is left as the historical record it is.

**4. `Bsed` → `Education` is the only non-exact FK mapping.** An enumerated single-row alias sanctioned by `11`'s settled judgment calls, written as a literal exception and never generalised into a normalization rule. The stored string stays `Bsed`.

### Known Limitations

- **Correcting a note's learner level orphans that note's existing Challenge bank rows, and the bank's duplicate-key hazard is not actually best-effort.** Found by the pool/bank re-keying audit as an interaction between two items in *this* release, which no per-PR review could see: the re-keying makes bank claims key on the note's effective curriculum level, and the editable-authoring-axes item makes that level correctable after generation. Every post-generation level correction therefore leaves that note's whole bank stranded at the old level — unclaimable, never re-stamped, and refilled by fresh LLM generation. Rows are preserved rather than deleted (ADR-001 rule 2 holds) and the measured population today is 5 of 6,235, but it is no longer bounded by that figure once authoring corrections become routine. **The sharper edge is the write path.** `uq_challenge_quiz_question_bank_user_pack_key` covers `(user_id, study_pack_id, question_key)` and **not** `learner_level`, so a stranded row's key is absent from `disallowedQuestionKeys` (only *claimed* rows are passed to the model) and the LLM can regenerate it — a duplicate insert. `ChallengeQuizQuestionBankService.persistGeneratedQuestions:118` batches a `saveAll` under a broad `catch (RuntimeException)`, but with an assigned UUID `@Id` and no `@Version` the INSERT flushes at commit, **outside** that catch and inside `startChallengeQuiz`'s `@Transactional` — so `docs/features/challenge-quiz.md`'s "bank persistence is best-effort and never blocks a Challenge session" is already false for constraint violations. This is pre-existing (a row claimed by another live session is likewise excluded from `findClaimableForUpdate` today) and was deliberately **not** fixed here rather than widening a re-keying PR into the bank's write path. The fix when it is scoped is `copyTemplateQuestions`'s existing shape: per-row saves with a `DataIntegrityViolationException` catch, which is itself the evidence that this collision class is real and was already known at one of the two bank write sites.
- **Unstamped pools and bank rows owned by a null-profile-level user change behavior, and were outside the impact read.** `sameLearnerLevel` previously received the raw nullable reader level, so a `NULL` pool level matched a `NULL` user level and sampled without refreshing; `effectiveCurriculumLevel` never returns null, so that pairing now mismatches and takes the lazy refresh path. `findClaimableForUpdate`'s `(:learnerLevel is null and question.learnerLevel is null)` branch is dead for the same reason. Pools self-heal — one refresh stamps them `COLLEGE` and they match thereafter — but bank rows do not, so a null-level user's null-stamped rows are permanently unclaimable. `12-pool-bank-relevel-impact.sql` compared note level against reader level and never covered the null-by-null cell, so this cohort is **not** inside the 57 / 5 figures above. Learner level is required from onboarding onward but remains nullable in storage for pre-existing accounts (`AGENTS.md:952`), and the cohort is **not** empty: measured 2026-08-04, **40 READY pools and 15 bank rows**. The 40 pools cost one extra lazy regeneration each and then match permanently; the 15 bank rows are the lasting item, and they are the same orphan class as the bullet above. Neither is destructive and neither was judged worth a pre-stamping migration this release, but the figure belongs on the record rather than inside a query nobody re-runs.

## v0.69.0 - Canonical Knowledge Foundation

**Status: Released**

Theme: stop the library from being forced to duplicate shared knowledge. One canonical note can now be authored for a body of knowledge that many programs share — an Algebra note authored once for Engineering Mathematics, rather than eleven near-identical copies, one per engineering program.

This is **Release A of `docs/architecture/ADR-001-canonical-knowledge-architecture.md`** (ratified 2026-08-03). Full planning: `docs/claude-prompt/canonical-knowledge-architecture-out/` — `01` (critique, code audit, 14-item migration inventory), `05` (production vocabulary audit + baselines), `06`/`08` (the Domain Context taxonomy and its Query K validation).

**Why now.** Authoring of the Civil Engineering Review Set's Engineering Mathematics subject plan was deliberately stopped: creating those Algebra topic notes under a one-program-per-note model would have committed the library to duplicating them for ten further engineering programs, along with their Study Packs, question pools, flashcards, memorization decks, and all future maintenance. The duplication has already begun at n=2 — `Strength of Materials` carries "Stress and Strain in Strength of Materials" (Civil Engineering) and "Stress, Strain, and Material Strength" (Mechanical Engineering), the same knowledge as two notes.

**Success metric** (ratified wording): *eliminates duplication of shared knowledge as NoteLib expands to more programs.* Comprehensive Review Sets, faster curriculum expansion, and lower maintenance are downstream benefits, not the architectural guarantee — this release removes the *multiplier* on every program after the first; it does not reduce the ~60% of any program's content that is program-specific, and it does not change assembly.

### Planned Scope

- **`notes.domain_context` (backend + prompts + admin frontend).** New nullable column carrying a curated, closed 8-value set: `Engineering Mathematics`, `Engineering Sciences`, `Civil Engineering`, `Professional Practice & Regulation`, `General Education`, `Professional Education`, `Nursing`, `Accountancy`. - **Note editor no longer writes the editor's profile course/program onto an existing note.** `profileCourseProgram` was populated unconditionally while the `isEditMode` guard covered only the draft pre-fill, so editing a note whose `course_program` was null rendered an empty Course / Program field and silently submitted the editing author's own profile value on save — with no toast and no validation stop. Board Exam Mode's ordering is unaffected.
- **Session-entry hardening and Redo Missed Questions (backend + frontend).** Expired in-progress Challenge Quiz and Board Exam sessions are now forfeited rather than resumed into an immediate timeout; server-side expiry cleanup also releases Challenge Quiz bank claims. A live session found through the mode-selection entry now offers Resume or Start Fresh, and the same-route Redo Missed Questions handoff reliably starts a redo session after completion. The fewer-than-three-missed case now returns to a clean prestart with the backend's ready user-facing message. **Refined during pre-signoff pressure test:** (1) `generateMoreQuestions` ("+5 Questions") now checks session expiry itself and rejects/forfeits instead of extending `timeLimitSeconds` on an already-expired session, which previously could revive it past its real deadline; (2) the frontend's redo-missed retrigger guard (`redoMissedStartRequestedRef`) now resets on every start outcome (success or error), not only the "not enough missed questions" branch, so a second Redo Missed Questions request in the same page session actually fires; (3) the Resume/Start Fresh prompt is now forced onto the mode-selection step whenever a live session is found, even for the TEACHER profile (which otherwise skips mode-selection entirely and was landing directly on Challenge Quiz Setup with the resume candidate silently unshown).

**Known limitations (logged, not fixed this release):**
- **`generateMoreQuestions`'s failure-path claim release can itself be rolled back.** On a generation failure mid-batch, the catch block calls `challengeQuizQuestionBankService.releaseClaims(...)` and then re-throws. Because the method runs under the class-level `@Transactional` on `ChallengeQuizService`, that re-throw rolls back the entire transaction — including the release call meant to undo the claim. The affected bank rows can be left stuck in a claimed state until they naturally expire, rather than being freed immediately. A real fix needs the release to run in its own transaction (e.g. `REQUIRES_NEW`) or as a post-rollback step outside the method's transactional boundary; deferred as narrow (only hit on a genuine mid-batch generation failure) and out of scope for a patch release.
- **An expiry-triggered session start can race a concurrent completion.** `resolveExistingChallengeSession`'s lookup (used when starting/resuming) reads the session without a pessimistic lock, unlike `completeSession`'s read. If a completion request and an expiry-driven forfeit land close enough together, the forfeit's write can commit after the completion's and overwrite `COMPLETED` back to `FORFEITED`, hiding a genuine finished attempt from Recent Sessions. Requires near-simultaneous requests against the same session (e.g. two tabs, or a reload right at the expiry boundary) to occur. A real fix needs `resolveExistingChallengeSession`'s query to take the same `PESSIMISTIC_WRITE` lock `findByIdAndUserIdAndSessionModeForUpdate` already uses, which needs care to avoid new lock-ordering/deadlock risk between the two paths — deferred as narrow and out of scope for a patch release.
- **The Resume/Start Fresh prompt only fires from the note detail page's Challenge Quiz card, not every "start this exam" entry point.** The prompt is scoped to the `?entry=mode-selection` query param, appended today only via `buildChallengeQuizHref`. The collection/Review Set premium-exam launch (`collection-detail-page-client.tsx`'s `openCollectionPremiumExam`) navigates to the same page without that param, so it silently auto-resumes a live non-expired session with no choice offered — same underlying gap as the TEACHER fix above, but via a different entry point rather than a different profile. Dashboard's Continue widget and a plain page refresh also skip the prompt, but that's intentional "continue where you left off" behavior, not this gap. Discovered while verifying the TEACHER fix's scope, after this release's Shipped bullets above were already written; not fixed here — the smallest correct change is likely appending `entry=mode-selection` to that one navigation call, but it wasn't verified end-to-end in time for this release.

- **Usage-driven exam-pool activation and Challenge question bank (backend).** The eager `examPoolPrewarmEnabled` kill switch still keeps ordinary Study Pack generation from prewarming pools, but actual Board Exam and Long Exam usage can now seed and reuse the learner's own pool after first use. **Known limitations (logged, not fixed this release):**
- **Copies don't inherit the source's bank or pool.** `NoteService.copySourceStudyPack()` gives every copy a brand-new `studyPackId` with no lineage back to the source, and both the Challenge Quiz bank and `ExamQuestionPoolService` key strictly on `studyPackId`. A learner who copies a popular note (including adopting an Official Review Set, which is a copy under the hood) starts with an empty bank/pool and independently regenerates everything via the LLM, even though the content is identical to the source's. This is the gap Phase 3's cross-user pool (`resolvePoolKey`, gated on adoption-concurrency evidence) is meant to close later — not attempted here by design.
- **No variety or outcome-awareness in repeat claims for the normal (non-redo) claim path.** The bank's ordinary claim query (`findClaimableForUpdate`, used by regular session-start and "give me more") returns eligible rows oldest-generated-first with no shuffling and no preference for previously-`INCORRECT`/`UNANSWERED` over `CORRECT` — unaffected by the new dedicated `findIncorrectClaimableForUpdate` query the Redo Missed Questions surface uses. A learner who never uses "give me more" or the redo-missed entry point will see the same initial batch, in the same order, on every subsequent Challenge Quiz session for that Study Pack, until their bank grows or their learner level changes. Deprioritized this release on the reasoning that repeat same-note Challenge Quiz visits are likely uncommon, and Adaptive Practice already targets missed concepts fresh.
- **`+5 Questions` is not quota-exempt-aware, so the redo-missed session's "zero LLM cost" guarantee covers only the start, not a later add-more request.** `ChallengeQuizService.generateMoreQuestions()` has no awareness of `quotaExempt`/redo-missed context and always falls through to normal LLM generation for any shortfall, exactly as it does for a regular Challenge session (this path has always been unmetered — this is not a new cost leak, only a naming/expectation mismatch for the new redo-missed entry point specifically). Whether `+5 Questions` should be disabled on redo-missed sessions to preserve a strict zero-cost guarantee, or left as-is, is an open product question deferred to a future release.
- **`resolveExistingChallengeSession` matches only on the `sessionMode` enum, not the JSONB sub-mode string, so a redo-missed request can silently resume an unrelated in-progress session.** This single-active-session check predates this release, but Redo Missed Questions is a newly reachable path into it: a user with an in-progress ordinary Challenge or Board Exam session (same `QuickReviewSessionMode.CHALLENGE` enum value, distinguished only by the `sessionState` mode string) who hits the redo-missed entry point is silently resumed into that unrelated session instead, with no signal that the redo-missed flow didn't actually start. Low probability (requires a stale in-progress session at the moment of the request) and no data corruption, but confusing if hit. Not fixed this release.
- **`DashboardService`'s independent duplicate of the "Challenge Quiz used this month" formula was not updated to subtract `quotaExemptSessions` like `ChallengeQuizService`'s copy was.** This release widened a pre-existing duplication into a divergence: `ChallengeQuizService.countChallengeQuizUsedThisMonth()` now nets out quota-exempt sessions, but `DashboardService`'s own copy of the same count does not. Currently a no-op in practice — an earlier `existsByUserIdAndSessionMode` guard in `DashboardService` short-circuits before the divergent line is reached for any user who could have a quota-exempt session — but the two copies must be kept in sync if that guard ever changes. Consider consolidating both call sites onto one shared method in a future release.
